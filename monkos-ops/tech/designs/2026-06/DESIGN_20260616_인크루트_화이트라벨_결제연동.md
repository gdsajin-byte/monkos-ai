## 0. 한 장 요약

- **인크루트 회신의 핵심 = "결제는 인크루트가 받는다."** 대안 A(웹훅)·B(쿠폰) 둘 다 결제 수령 주체는 인크루트. 우리는 결제 신호를 받아 권한만 부여. → 처음부터 말한 "스토어 입점 + CPA 매출 쉐어" 모델 그대로.
- **권고: 대안 A(실시간 웹훅) 채택.** 우리 코드에 이미 **Lemon Squeezy 웹훅 패턴(HMAC 서명검증 + 멱등성 + 크레딧부여 트랜잭션)** 이 구현돼 있어 거의 그대로 복제 가능. 신규 ~400~500줄.
- **아키텍처: 작가님 구상(별도 서버 `incruit.monkos.ai` + idphoto-kr 백엔드 공유) = 정답.** 기존 Cloud Run 이미지 재사용 + 환경변수 분기로 1~2주.
- **결제 신뢰**: 웹훅만 믿지 않고 **역검증(서버-to-서버 조회) + 우리 호출 카운트 = 정산 베이스**로 설계하면 토스 수준 이상 신뢰 가능. 단 인크루트로부터 **결제 스펙 5종**을 받아야 방식 확정.
- **브랜딩 = 코브랜딩.** `Incruit with MONKOS AI` — 우리 브랜드 적극 노출(브랜드 자산 확보). 화이트라벨(브랜드 숨김) 아님.
- **독점 = 마케팅 확장 의무 대가.** 단순 입점이면 독점 거절. 인크루트(언더독)가 "MONKOS 합류"를 경쟁사 대비 마케팅 포인트로 **전면 노출·공동 집행**할 때만 카테고리 한정·한시 독점.
- **서비스 경계.** 인크루트 전용 = **채용/이력서 증명사진 SKU 한정.** 비자대행·여권사진 등은 본진 서버 완전 분리, 인크루트 미노출.

## 1. 결제 로직 — 우리 현황 (코드 실측)

### 1-1. 우리 토스 연동 구조 (KR, 완전 구현)
| 단계 | 위치 | 내용 |
|------|------|------|
| 클라이언트 결제요청 | `idphoto-kr/public/charge.html`, `config.js:29` | 토스 위젯(라이브키 `live_gck_...`)으로 paymentKey/orderId/amount 발급 |
| 서버 승인(confirm) | `portal/lib/payments.js:173~292` `handleTossConfirm` | `POST /api/payments/toss/confirm` → 토스 confirm API 호출(시크릿키 Basic 인증) |
| 멱등성 | `payments.js:184~201` | orderId 중복 시 재지급 차단(200 반환) |
| 권한부여 | `payments.js:244~256` | Firestore 트랜잭션으로 `users.credits += N` |

→ **결제 완료 = 크레딧 충전 모델.** 1장 완성 = 80c(생성 10 + 다운로드 70). 상품: single_70(₩9,900)~package_500(₩49,900).

### 1-2. 이미 존재하는 자산 (인크루트 연동에 재사용)
- ✅ **웹훅 수신 + HMAC 서명검증**: `payments.js:74~170` (Lemon Squeezy, `x-signature` HMAC-SHA256 검증). **인크루트 웹훅의 본보기.**
- ✅ **크레딧 부여/회수 트랜잭션**: `payments.js:244~256`(지급), `136~161`(환불 회수). 원자성 보장.
- ✅ **원장 기록**: `config.js:240~257` `logTransaction()` — `provider:'incruit'`만 추가하면 됨.
- ✅ **파트너 API 키 인증**: `cms/admin-auth.js:20~89` — `AGENT_API_KEYS` env + `timingSafeEqual`. 인크루트 키 추가로 확장.

### 1-3. 없는 것 (신규 개발)
- ❌ 인크루트 전용 웹훅 엔드포인트(`POST /api/webhooks/incruit`)
- ❌ 인크루트 결제 → 엔타이틀먼트 변환 매핑
- ❌ 외부 파트너 거래 컬렉션(`externalPayments`: partner/externalOrderId/userId/status)
- ❌ 인크루트 회원 ↔ MONKOS 계정 매칭(SSO 또는 webhook payload lookup)
- ⚠️ 토스 자체에도 웹훅 부재(현재 client confirm만) — 별개 보완 권장

## 2. 인크루트 두 대안 — 평가

| | **대안 A — 실시간 웹훅 (인크루트 권장)** | **대안 B — 쿠폰 난수 발행** |
|---|---|---|
| 흐름 | 인크루트 결제완료 → 웹훅 → 우리가 유저 권한 부여 | 우리가 난수쿠폰 발행 → 인크루트 위탁판매 → 유저가 등록 |
| 재사용 | **높음** — Lemon Squeezy 웹훅 패턴 복제 | 낮음 — 쿠폰 발행/검증 전부 신규 |
| 신규 개발 | ~400~500줄 (웹훅+매핑+거래기록) | 대량 쿠폰 발행·검증 시스템 + **인크루트 CS용 어드민 페이지** |
| 결제 신뢰 | 서명검증+역검증 설계 필요 | 거의 없음(돈 흐름 인크루트 내 완결) |
| 정산 검증 | **우리 호출 카운트 = 정산 베이스(투명)** | 쿠폰 사용량 집계 |
| 권고 | ✅ **채택** | 백업/대체안 |

### 결제 신뢰 보장 — 인크루트에 요청할 스펙 5종 (대안 A)
1. **웹훅 서명 검증 방식** — HMAC 시크릿 / mTLS / 공개키 (위·변조 결제신호 차단)
2. **멱등키 체계** — transactionId / orderNo (중복 지급 방지)
3. **역검증 API** — 웹훅 수신 후 우리가 인크루트에 "이 결제 진짜냐" 되묻는 조회 엔드포인트 (웹훅만 신뢰하지 않는 표준)
4. **회원 식별/SSO** — "이력서 작성 중 이동 없이"를 구현할 토큰/식별값 전달 방식
5. **환불·취소 신호** — 권한 회수 트리거

> ⚠️ 인크루트는 "MONKOS 측 API 명세 선공유 가능?"이라 물었으나, **대안 A에서 신호 발신자는 인크루트** → 그쪽 결제 스펙이 먼저 와야 우리 수신부를 확정 가능. 답신에 이 점을 명확히 담는다.
> ⚠️ 시크릿(웹훅 secret 등)은 인크루트/작가님이 제공. 생성·추측 금지(헌법 4조 1항).

## 3. 아키텍처 — 작가님 구상 확정

```
[유저] ──이력서 작성중── [인크루트 페이지]
                              │ (① 인크루트 PG로 결제 = 인크루트가 수령)
                              ▼
                     [인크루트 결제 시스템]
                              │ ② 웹훅(서명) + 회원식별 토큰
                              ▼
        incruit.monkos.ai (신규 Cloud Run, 코브랜딩 프론트 "Incruit with MONKOS AI")
                              │ ③ 엔타이틀먼트 부여(역검증 후)
                              ▼
        idphoto-kr 백엔드 공유 (생성/다운로드 — 코드 동일)
                              │ ④ 우리 API 호출 카운트 → 정산 근거
```

- **신규**: `monkos-idphoto-kr-incruit` Cloud Run 서비스 = 기존 `monkos-idphoto-kr` **이미지 재사용** + `BRANDING=incruit` 환경변수. 도메인 매핑 `incruit.monkos.ai`.
- **백엔드 공유(윈윈)**: 생성(Imagen I2I)·다운로드·GCS·코칭 100% 재사용(`idphoto-kr/server.js`). 우리는 백엔드 품질로 기여, 인크루트는 트래픽·결제·마케팅으로 기여.
- **결제만 분기**: charge.html(토스 위젯) 대신 **엔타이틀먼트 체크**로 대체.
- **정산 무기**: 우리 호출 카운트가 정산 베이스 → 인크루트 결제 데이터 들여다볼 필요 없음(06-15 §4와 일치).
- **브랜딩 = 코브랜딩**: 프론트에 MONKOS 노출(`Incruit with MONKOS AI`). 화이트라벨 아님.
- **헌법 정합**: 외부 노출 "MONKOS"는 **적극** 사용(1조 1항 외부 브랜드 통일과 정합), 엔진명(Gemini/Imagen)만 비노출(4조 3항). 원본 정체성 보존(1조 3항).

### 3-1. 서비스 경계 — 채용 SKU 한정 (작가님 확정)
| 서비스 | 노출 위치 | 비고 |
|--------|----------|------|
| **채용/이력서 증명사진** | `incruit.monkos.ai` (인크루트 코브랜딩) | 인크루트 전용 SKU |

## 5. 결제 퍼널 (Checkout Funnel) 설계

### 현행 (직판)
`촬영 → 생성(result) → charge.html(토스 결제) → 다운로드` — 결제 주체 = 유저↔우리

### 인크루트 (결제 주체 = 인크루트) — 2모델
| | **(가) 선결제형 — 권장** | (나) 후결제형 |
|---|---|---|
| 흐름 | 인크루트 스토어에서 이용권 구매 → 웹훅 → 진입 시 이미 엔타이틀먼트 보유 → **charge 단계 스킵** → 생성·다운로드 | 무료 체험 생성 → 다운로드 직전 인크루트 결제 호출 |
| 인크루트 의도 | "스토어 입점"과 정합 ◎ | 전환율↑이나 플로우 통합 복잡 |
| 우리 변경 | charge.html 우회 + 엔타이틀먼트 게이트 | 다운로드 직전 인크루트 결제 API 연동(왕복) |
| 권고 | ✅ | 차기 |

- **선결제형 핵심 변경**: `incruit` 모드에서 `charge.html`(토스 위젯) **비활성화**, 다운로드 게이트를 "크레딧 잔액 체크"(`credits.js`)로 유지. 인크루트 웹훅이 해당 유저에 엔타이틀먼트를 선충전.
- **엔타이틀먼트 단위**: 인크루트 상품 1건 = N컷 다운로드권(예: 5컷). 기존 크레딧 시스템에 매핑(80c=1컷 기준) 또는 별도 "다운로드권" 카운터.
- **환불**: 인크루트 환불 웹훅 → `payments.js:136` 회수 패턴 재사용.

## 6. 서비스 카드 — 브랜드 파트너십 설계

### 현황 (코드)
- 포털 `monkos.ai` 서비스 카드 = `portal/public/index.html:307` **하드코딩** `svc-grid`(LIVE 증명사진 / FREE 크롭앱). **파트너 배지 슬롯 없음.**
- 매거진 카드는 Firestore 동적(`cms/home.js`) — 데이터 외부화 선례 있음.

### 설계 — 코브랜딩 ("Incruit with MONKOS AI", 작가님 방침)
**핵심: 화이트라벨(브랜드 숨김)이 아니라 듀얼 브랜드 노출.** 우리 브랜드를 인크루트 트래픽에 적극 태워 브랜드 자산을 키운다.

1. **인크루트 스토어/서비스 카드 → 코브랜딩 노출**: 인크루트 측 카드에 `Incruit with MONKOS AI` 듀얼 브랜드(인크루트 로고 + MONKOS 로고 병기). "AI 증명사진은 MONKOS가 함께합니다" 식 소구. → 인크루트(언더독)의 **경쟁사 대비 차별화 마케팅 포인트**이자 우리 브랜드 노출(윈윈).
2. **우리 포털 → 파트너 카드**: `svc-grid`에 "인크루트 채용사진" 카드 + **파트너 배지**(`.svc-bdg.partner` "인크루트 공식 제휴"). 클릭 → `incruit.monkos.ai`(utm source=incruit).
3. **카드 데이터 외부화**: 하드코딩 → `config`/Firestore `service_cards` 컬렉션. 필드: `title/desc/thumb/link/badge/partner/cobrand/source(utm)`. → 파트너 확장(잡코리아·사람인) 시 카드만 추가, 코드 불변.
4. **추적**: GA4 `source=incruit` 이벤트(촬영→생성→결제 퍼널). 정산 호출 카운트와 교차검증.
5. **브랜드 가드**: 코브랜딩 노출은 "MONKOS"만(공인 브랜드, 1조 1항). 엔진명(Gemini/Imagen)·내부 호칭 비노출(4조 3항). 채용 SKU 외 서비스(여권·비자) 카드는 인크루트에 미노출(§3-1).

> 카드 데이터 외부화는 **멀티 파트너 확장 비용 0**에 기여(06-15 §5 "독점 줄 기술적 이유 없음"의 프론트 측 근거).

## 8. 답신에 담을 핵심 (인크루트 → 우리)

1. **계약 기간**: 파일럿 생략·**1년 본계약 직행 동의**(작가님 방침). 성과 미달 시 조기 해지 조항 수용.
2. **독점 = 마케팅 확장 의무 대가 (작가님 방침)**: "스토어 한켠 입점" 수준 독점은 거절. 인크루트(언더독)가 **"MONKOS 합류"를 경쟁사(잡코리아·사람인) 대비 마케팅 포인트로 전면 노출·공동 집행**할 때만 채용플랫폼 카테고리 한정·한시 독점 검토. 대가 패키지: ① 스토어 전면/우선 노출 ② 인크루트 회원 대상 공동 프로모션·메일/푸시 ③ 최소보장(MG). 범위는 "채용플랫폼 카테고리 내"로 한정(직판·타업종 제휴 보호).
3. **브랜딩 = 코브랜딩**: 단순 공급사가 아니라 **`Incruit with MONKOS AI` 듀얼 브랜드 노출**을 입점 조건으로. 우리 브랜드 노출이 협상 자산(윈윈).
4. **서비스 범위**: 인크루트 제공은 **채용/이력서 증명사진 한정**. 여권·비자대행 등은 본진 직판 유지(별도 채널).
5. **기술 연동**: **대안 A(실시간 웹훅) 대응 가능** + 우리 명세 선공유 가능. 단 **인크루트 결제 스펙 5종(서명·멱등·역검증·SSO·환불)** 회신 요청. 대안 B는 백업.
6. **정산**: 도매단가 기반 + 우리 호출 카운트 검증 + MAP(최소판매가) 조항(06-15 §4·R1).
7. **미팅**: 위 방향성 합의되면 수수료율·정산 프로세스 확정 미팅 신속 제안.
