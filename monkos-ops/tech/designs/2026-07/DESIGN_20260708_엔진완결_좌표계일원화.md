## 0. 문제 정의 (오늘 3연쇄의 본질)

현행: 클라이언트가 원본(EXIF 포함)을 3회 왕복 전송, 각 단계가 **제각기** 이미지를 해석.

| 단계 | 좌표계 | 회전 | 결과 |
|------|--------|------|------|
| precheck (Gemini) | Gemini 자체 해석 (표시?) | 불명 | faceBox 좌표계 불확정 |
| fit (sharp+FaceMesh) | 00429~ 회전 적용 | ✅ | 수치 정합 |
| generate/matte | **미회전 원본** | ❌ | 90° 누운 출고 |

→ "재는 곳"과 "자르는 곳"이 서로 다른 좌표계. 패치할수록 경계가 늘어남.

## 1. 설계 원칙

**입구에서 1회, 이후 전원 동일 버퍼.**

```
클라이언트 원본 (EXIF 포함)
        │
        ▼
  ┌─────────────────┐
  │ normalize(image) │  ← 서버 진입점 1곳
  │ sharp: rotate()  │     EXIF 회전 적용 + 스트립
  │       + resize   │     긴 변 2048px (FaceMesh 정밀도 충분)
  │       + jpeg(90) │     단일 포맷
  └────────┬────────┘
           │ normalizedBuf (W, H = 표시 좌표계)
           ▼
  ┌────┬────┬─────────┬───────┐
  │ PC │ Fit│Generate │ Matte │  ← 전부 normalizedBuf 사용
  └────┴────┴─────────┴───────┘
```

- `normalizedBuf`는 요청 스코프 내 1회 생성, 전 단계에 전달
- W, H = 표시(정립) 좌표계 — Gemini faceBox, FaceMesh, fitFrame, matteFrame 전부 동일 기준
- 원본 보존: GCS에 원본 저장(현행 유지), 처리는 normalizedBuf로

## 2. 구현 — 4개 변경점

### 2-1. normalize 함수 (server.js 최상위)

```javascript
async function normalizeImage(rawBase64) {
  const raw = Buffer.from(stripDataUri(rawBase64), 'base64');
  const buf = await sharp(raw)
    .rotate()                                      // EXIF 회전 적용 + 메타 스트립
    .resize(2048, 2048, { fit: 'inside', withoutEnlargement: true })
    .jpeg({ quality: 90 })
    .toBuffer();
  const { width, height } = await sharp(buf).metadata();
  return { buf, width, height, rawBase64 };        // rawBase64는 GCS 원본 저장용
}
```

- precheck: `normalizedBuf`를 Gemini에 전송 → OOM 방지 + faceBox 좌표 확정
- fit: `normalizedBuf`에서 FaceMesh 실행 → EXIF 회전 문제 해소
- generate/matte: `normalizedBuf` 기반 재단 → 누운 출고 소멸

### 2-2. 해부학 검증 잣대 교체 (fit 엔드포인트)

**현행** (Gemini faceBox 기준):
```
eyeOk = eye >= fbPx.y + fbPx.h * 0.08 && eye <= fbPx.y + fbPx.h * 0.72
chinOk = chin >= fbPx.y + fbPx.h * 0.55 && chin <= fbPx.y + fbPx.h * 1.45
```
→ Gemini 박스가 2px 흔들리면 정상 사진 차단

**변경** (FaceMesh 내부 정합 기준):
```
1. 홍채 랜드마크 존재 확인 (468~477 양쪽) — 감지 자체의 신뢰
2. 눈-턱 기하 비율: (chinY - eyeY) / faceBoxH ∈ [0.35, 0.70] — 해부학적 합리성
3. 좌우 대칭: |leftEyeX - centerX| vs |rightEyeX - centerX| 편차 < 25% — 정면 판정
```
→ 검증 대상(FaceMesh)이 자기 정합성을 스스로 증명. Gemini faceBox는 러프 크롭 창 산정에만 사용, 합불 판정에서 제외.

### 2-3. 최종 출고 게이트 (generate 엔드포인트 말단)

생성 완료 후, 출고 직전 Gemini 비전 1회:

```
프롬프트: 이 증명사진의 출고 적합성을 판단하세요.
- 얼굴이 정립(직립)인가? (90°/180° 회전 = 즉시 FAIL)
- 1인인가?
- 눈이 떠져 있는가?
- 얼굴 윤곽이 자연스러운가? (합성 아티팩트 = WARN)
JSON: { "passable": bool, "reason": "string" }
```

- FAIL → 자동 재처리 1회. 재실패 → 차감 환불 + "다시 시도해주세요"
- 차감→생성→실패 시 환불 누락(OOM 사고)의 구조적 해결: **결제 전에 최종본 생성 완료** (기준서 §3-S5)가 근본이나, 엔진 완결 단계에서는 출고 게이트 + 환불 방어로 중간 보호.

### 2-4. 동일인 게이트 (generate 엔드포인트, 출고 게이트 직전)

```
프롬프트: 두 사진이 동일인인지 판단하세요.
- 입력: [원본 얼굴 크롭] vs [생성 결과물]
- 판정: 동일인이면 PASS, 아니면 FAIL + 어디가 다른지
JSON: { "same_person": bool, "confidence": 0~1, "diff": "string or null" }
```

- 헌법 1조 3항(정체성 보존) 자동 시행
- 보정 강도와 무관 — "고쳐도 나여야 한다"

## 4. 테스트 매트릭스

| 케이스 | 입력 | 기대 결과 |
|--------|------|----------|
| 아이폰 세로 (EXIF=6) | 카우치 사진 | precheck 통과 → fit 정상 측정 → 정립 출고 |
| 데스크톱 (EXIF 없음) | 스톡 이미지 | 현행과 동일 동작 |
| 상반신 와이드 | 밤 야외 전신 | precheck 통과 → fit 측정 → 정립 출고 |
| 측면 사진 | 옆모습 | precheck 또는 fit에서 차단 |
| 대용량 (10MB) | 아이폰 원본 | normalize에서 2048px 축소 → OOM 없음 |

## 5. 순서

1. `normalizeImage()` 함수 작성 + precheck 적용 → 배포 + 테스트
2. fit 적용 + 해부학 검증 교체 → 배포 + 테스트
3. generate/matte 적용 + 출고 게이트 → 배포 + 테스트
4. 동일인 게이트 → 배포 + 테스트

단계별 배포·단계별 검증. 한 번에 넣지 않는다.
