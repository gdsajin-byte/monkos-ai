# DESIGN — 발급보장 증빙 체계

**[2026-07-04 18:43 KST]** iMac/민아 → 작가님

> 근거: 작가님 승인 2026-07-04 18:43 — "B안(재작업+환불) 승인. 다만 증빙이 필요하다."
> 상위 문서: [PROPOSAL_발급보장규정초안](../../ops/proposals/PROPOSAL_20260704_민아_발급보장규정초안.md) §3을 운영 가능한 체계로 구체화한다.
> 원칙: **증빙 없으면 보상 없다.** 단, 증빙 요구가 정당한 고객의 장벽이 되지 않는 수준으로 설계한다.

## 1. 증빙물 정의 — 무엇을 인정하는가

**필수 2요소**: ① 반려 **사유** ② 반려 **일자** 가 한 증빙 안에서 확인될 것. 기관 식별 요소(로고·서식·발신번호 등)가 함께 보이면 가산.

| 인정 증빙 (KR) | 예시 |
|----------------|------|
| 온라인 민원 반려 화면 | 정부24·여권민원 신청 내역의 "반려" 상태 + 사유 화면 캡처 |
| 기관 통지 문자/알림톡 | 반려 사유가 포함된 통지 캡처 (발신번호 포함) |
| 서면 접수증 | 반려 표기·사유 기재된 접수증 촬영본 |
| 담당자 안내 | 창구 재촬영 안내 메모 등 — 단독으론 약함, 보조 증빙 |

**불인정**: 사유·일자 없는 단순 주장, 본인 작성 메모 단독, 촬영 불명 이미지, 제출 이력과 무관한 타인 명의 건.

## 2. 접수·판정 파이프라인

```
고객 신청 (주문번호 + 증빙 이미지)
   │  Phase 1: info@monkos.ai / Phase 2: 마이페이지 폼
   ▼
[자동 대조] 주문번호 → Firestore 결제 이력
   ├─ T2 산출물인가? (T1·무결제 건 즉시 안내 종결)
   ├─ 결제일로부터 90일 이내인가?
   └─ 동일 주문의 기존 보상 이력은? (환불은 주문당 1회)
   ▼
[사유 판정] 반려 사유 = 규격 사유(규정 §1.2)인가?
   ├─ Phase 1: 운영자(작가님/민아) 수동 판정
   └─ Phase 2: AI 1차 분류(규격/비규격/판독불가) + 운영자 확정 — AI 단독 거절 금지
   ▼
[처리] 규격 사유 → 재작업 안내 (무상 재코칭+재생성)
        재작업 후 재반려 (신규 증빙 필수) → 전액 환불
        비규격 사유 → 보장 제외 안내 (규정 §1.3 조항 인용)
   ▼
[기록] 감사 로그 어펜드 (§4)
```

- **처리 기한 고지**: 접수 후 영업일 2일 내 1차 회신 (초기 볼륨 기준, 카피·약관에 명시).
- **재작업 트랙**: 반려 사유를 재코칭 프롬프트에 반영해 같은 원본 또는 재촬영으로 재생성. 재작업은 횟수 명기 없이 운영 재량(카피 보수 버전 유지), 환불 판정만 "재작업 이후 + 신규 증빙" 이중 게이트.

## 3. 부정 사용 방지 — 초기 볼륨에 맞는 최소 장치

| 장치 | 구현 | 비고 |
|------|------|------|
| 주문-증빙 대조 | 주문번호로 결제·다운로드 이력 확인 (자동) | 이력 없으면 진행 불가 |
| 증빙 재사용 차단 | 증빙 이미지 해시 저장 → 동일 해시 재신청 탐지 | Phase 1은 수동 육안, Phase 2에 해시 자동화 |
| 보상 한도 | 환불 = 주문당 1회. 계정당 월 보상 건수 임계 초과 시 수동 심사 플래그 | |
| 위조 감별 | **정밀 감별 시스템 과투자 금지** — 초기엔 육안+상식 수준, 로그 축적 후 패턴 탐지 | 볼륨 낮은 단계의 현실적 판단. 악용 패턴 확인 시 격상 |

## 4. 기록 — 기존 감사 체계 준용 (ch4 10조 패턴)

- **이중 기록**: Firestore `guarantee_claims` 컬렉션 + `monkos-ops/ops/audit/GUARANTEE_AUDIT_LOG.md` (append only, 수정·삭제 금지) — CREDIT_AUDIT_LOG와 동일 패턴.
- 기록 항목: 일시 · 주문번호 · 신청 채널 · 판정(재작업/환불/제외) · 판정 사유 요약 · 처리자. **증빙 이미지 자체는 로그에 미포함** (§5 보관 규칙).
- 환불 실행은 PG(토스/레몬) 대시보드 경유 — 크레딧 보정이 필요한 경우 `scripts/credits.sh` 경유(직접 접근 금지).

## 5. 개인정보 — 수집·보관·파기

| 단계 | 규칙 |
|------|------|
| 수집 | 주문번호 + 증빙 이미지만. 신청서 전체·주민번호·여권번호 수집 금지. 마스킹 제출 안내 문구 필수 |
| 저장 | 고객사진 버킷과 분리된 전용 경로(`monk-customer-photos/guarantee-claims/` 또는 별도 버킷). 접근 권한 운영 SA 한정 |
| 파기 | **GCS 수명주기 규칙으로 90일 자동 삭제 기술 강제** (수동 파기 의존 금지). 처리 기록(§4 텍스트 로그)만 영구 잔존 |
| 목적 제한 | 보상 판정 전용. 마케팅·학습 활용 금지 |

## 6. 단계별 구현

| Phase | 범위 | 시점 |
|-------|------|------|
| **P1 수동** | 이메일 접수 + 운영자 판정 + 수기 감사 로그 + GCS 수동 업로드. **코드 작업 거의 없음 — 규정 승인 즉시 가동 가능** | T2 카피 반영과 동시 |
