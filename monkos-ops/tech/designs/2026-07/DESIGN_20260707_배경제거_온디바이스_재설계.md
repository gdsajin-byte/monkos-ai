## 1. 문제 — 왜 재설계인가

7/6~7/7 실사고 연대기가 현행 구조의 한계를 실증했다:

1. **AI 재생성물 위에서 감지·크롭** — Gemini가 배경+프레이밍을 임의 재구성한 이미지를 대상으로 FaceMesh를 돌리니, 같은 원본도 생성 변형에 따라 감지가 간헐 실패(7/7 새벽 us-visa). 실패 시 커버 폴백이 무규격 결과물을 조용히 출고.
2. **재구성 = 원본 픽셀 소실** — Gemini 출력은 "다시 그린 인물"이라 정체성 보존 제1원칙과 구조적 긴장. 무보정 트랙의 약속("사진 그대로")과 어긋남.
3. **건당 과금** — 생성마다 Gemini 비용. 퍼널 구경꾼 트래픽까지 서버 비용화.
4. IDPASS(애플앱)는 같은 크롭 수학으로 **실패 없이** 작동 — 차이는 성능이 아니라 **순서**: 원본에서 감지→크롭, 배경은 재생성이 아닌 마스크 합성.

작가님 방향 확정(7/7): **"코드는 우리가 가지되 연산은 각자 디바이스에서"** — 온디바이스 지향.

## 3. 재설계 원칙

1. **IDPASS 순서 이식**: 감지·크롭은 **사용자 원본(실사)**에서 — 비결정성 원천 제거. 배경은 재생성이 아닌 **매팅+색 합성** — 원본 픽셀 보존.
2. **온디바이스 우선**: 결제 전 전 과정(감지·precheck·크롭 미리보기·매팅 프리뷰)은 손님 디바이스 연산. 서버 비용은 결제 건에만.
3. **무음 폴백 금지**: 감지 실패는 결제 전 차단(재촬영 안내). 결제 후 실패는 재시도→경보→환불. "그럴듯한" 결과물을 조용히 출고하지 않는다.
4. **Gemini 재배치**: 무보정 트랙에서 퇴역 → 보정 트랙(헤드샷 등)·비상 폴백 전용.

## 4. 아키텍처 — 연산 3층

```
[L1 손님 디바이스 — 무료·즉시]
  FaceMesh 감지(3MB, crop.js 기성) → precheck(각도·크기, 결제 전 차단)
  → 크롭 미리보기 → (옵션) 경량 매팅 프리뷰(RMBG-1.4/MODNet, transformers.js — 크롭앱 devlog Tier2 구상)
    ↓ 결제 (토스/레몬/크레딧 — 기존 체계 그대로)
[L2 우리 서버 — 정본 처리]
  원본 재감지(신뢰 검증) → 크롭 수학 v3(정수리 앵커, 규격 DB 426국) 재단
  → BiRefNet 매팅 → 배경색 합성(#FFF or 규격색 — 유색 16국 개방)
  → 300dpi 규격 출력 + GCS 증빙 저장(발급보장 근거)
[L3 폴백]
  L2 장애 시: Gemini 경로(현행 코드 유지) + 텔레그램 경보
```

**서빙 위치 로드맵**: 4060(집, Tailscale/터널) 초기 → 트래픽 검증 후 Cloud Run GPU(L4, scale-to-zero, 장당 <₩1) 승격. 홈서버 SLA 부재는 L3 폴백으로 흡수 — "4060이 꺼져도 서비스는 산다".

## 6. 리스크·미결 (정직 항목)

1. **조명 문제**: 매팅은 배경만 바꾼다 — 어두운 셀카는 어두운 채로 나온다. Gemini는 조명을 스튜디오화해줬음(부산물). 무보정 포지셔닝엔 부합하나 체감 품질 차이 가능 → **결정 필요**: 라이트 필터(결정론적 노출·화이트밸런스 정규화, sharp 레벨) 추가 여부. precheck에 "조명 부족" 차단 항목도 대안.
2. **4060 가용성**: 홈서버 정전·재부팅 = L3 폴백 의존. 초기 한정 운용으로 감수, 매출 검증 시 클라우드 승격.
3. **그림자/복잡 배경**: BiRefNet 실측은 통과했으나 극단 케이스(모자·안경 반사 등) 전수 검증은 Phase 1에서 실사고 수집으로.
4. **idphoto-kr/jp 적용 시점**: 본 기안은 specs 우선. idphoto(80c 프리미엄 트랙)는 발급보장 T2 설계와 묶어 후속.
