## 0. 설계 원칙 (상위 문서 승계 + 확장)

1. **개인 데이터는 휘발, 스타일 메타는 자산** (쌍아 7/10 §0) — 버킷·스키마·로그 전 층위에 적용.
2. **specs 전속 구현 금지** (작가님 7/10) — 독립 모듈. idpass가 첫 소비자일 뿐, 헤드샷·스타일러가 같은 파일을 import.
3. **텍스트형 v1 = 병목 제거** (작가님 7/12) — 상품컷 이미지 없이도 오늘 배선 가능한 형태로 먼저. 이미지·VTON은 같은 스키마 위에 증축.
4. **스키마가 곧 상품** — 피커 데이터는 UI 옵션 목록이 아니라 커머스 카탈로그의 씨앗. 벤더 필드 선탑재(attire commerce vision 07-10).

## 1. 전체 아키텍처

```
[attire-presets.json]  ←  정본 (git 버저닝, schema_version)
        │
        ├─→ AttirePicker (공유 컴포넌트, 의존성 0)
        │     ├─ idpass: specs T1 결제 시트에 마운트 (v1 — 이번 구현)
        │     ├─ headshot: 스타일 선택에 동일 마운트 (후속)
        │     └─ styler: 레퍼런스 이미지 피커로 확장 (PF_STYLER v2)
        │
        ├─→ 서버: body.attireDesc → buildT1Prompt [OUTFIT] 주입 (배선 기존재)
        │         (v2: attireId → GCS 상품컷 로드 → 나노2 2이미지 i2i)
        │
        ├─→ Firestore attire_presets/ 미러 (성장 임계 도달 시 — §6)
        └─→ CITADEL: 복장 가이드 콘텐츠·광고 소재·구조화 데이터 (§8)
```

**v1 데이터 흐름**: 피커 선택 → `getSelection().attire_desc`(영문 프롬프트) → generate body `attireDesc` → 서버 `buildT1Prompt()` → 나노2. 서버 수정 **0줄** — 클라이언트가 스키마의 attire_desc를 뽑아 기존 파라미터에 실어 보낸다.

## 4. 컴포넌트 API (attire-picker.js)

```js
const picker = AttirePicker.mount(el, {
  service: 'idpass',                    // 프리셋 필터 프로파일
  useCase: ['passport','visa','resume'],// 명시 시 service 프로파일 오버라이드
  gender: 'all',                        // 'm'|'f'|'all' — 탭 분기
  lang: 'ko',                           // ko|ja|en — 스키마 labels 소비
  presetsUrl: '/components/attire-picker/attire-presets.json',
  onChange(sel){ /* {id, attire_desc, labels, tags} */ }
});
picker.getSelection();                  // 현재 선택 (기본 = default_option)
picker.getAttireDesc();                 // attire_desc | null — generate body 직결용
```

**UI 구조** (PROPOSAL 7/10 §4 승계):
- 1행: 성별 세그먼트(남/여) — 전 서비스 공통 첫 분기
- 2행: 카테고리 칩 탭 (스키마 categories, use_case 필터 후 빈 카테고리 자동 숨김)
- 3행: 아이템 행 — **모바일 = 가로 스크롤 칩** / **데스크톱(≥720px) = 그리드**. 칩 = 스와치 2톤 원 + 라벨. `thumbnail` 존재 시 스와치 대신 이미지 자동 전환 (v1.5가 데이터 교체만으로 켜짐)
- 0번 고정: "지금 옷 그대로" 기본 선택 — 다수 고객 0단 통과 (퍼널 무증가 원칙)
- 업로드 슬롯: v1은 자리만 (disabled + "곧 열려요") — 쌍아 §4-4 정책 확정 후 활성화
- 접근성: role=radiogroup, 키보드 좌우 이동, 선택 상태 aria-checked

**의존성 0 / 프레임워크 0** — ch2 기술 스택(순수 JS) 준수. CSS는 `--atp-*` 자체 변수로 격리하되 specs v2 토큰 존재 시 상속.

## 6. DB 성장 경로

**현 단계 = JSON 정본** (git 버저닝·리뷰 가능·배포 원자성·특성상 읽기 전용 트래픽). **Firestore `attire_presets/{id}` 미러 전환 임계**: ①벤더 입점 1호(계약 필드 필요) ②아이템 50+ ③비개발자 운영 편집 필요 — 셋 중 하나 도달 시.

- 마이그레이션: JSON→Firestore 시딩 스크립트 1개 (문서 id = item id, 스키마 그대로). JSON은 폴백 캐시로 강등.
- 선택 로그 (자산 축): GA4 `attire_select {attire_id, category, service}` + 기존 `generations` 문서 `attire{source, presetId}` (쌍아 §2-2 기반영) — 개인 사진 데이터와 결합 금지 원칙 유지.
- 이 로그가 커머스 협상 자료가 된다: "차콜 정장이 월 N회 선택" = 벤더 입점 영업 수치.

## 7. 커머셜 성장 (벤더 슬롯)

- **공개/비공개 분리**: attire-presets.json은 public 서빙 → 표시 필드만 (`vendor: {name, product_url, badge}`). **커미션·계약·SKU·단가는 Firestore 비공개 컬렉션** (`attire_vendors/{id}`) — 공개 JSON에 수수료율이 실리는 사고 차단.
- 단계: affiliate(쿠팡 파트너스류 소프트 링크 "이 옷 보러가기 →") → direct(벤더 상품컷 납품 = image_gcs 교체만) → vendor 크레딧 구독.
- **"연출 이미지" 고지 1행 필수** (쌍아 §4-2) — 벤더 링크 노출 화면에 상시.
- 스키마는 이미 준비됨 — 입점은 데이터 추가지 개발이 아니다.

## 8. CITADEL 연계 (광고·SEO/AEO 홍보 방안)

1. **복장 가이드 콘텐츠 블록** (AEO 타깃): 규격 데이터(국가별 배경색·복장 규정)와 피커 카테고리를 결합한 "여권사진 복장" "증명사진 옷" 섹션을 specs 페이지에 증설 — 검색어 공백(CITADEL 본령: 정부 사이트가 못 하는 실무 답변) 공략. 프리셋 12종이 콘텐츠의 실물 근거.
2. **광고 소재 파이프라인**: 12종 상품컷 그리드 + before/after 카드 → `ads/attire/` 적재 → GBP 게시물·네이버 소식·인스타(꾸 7채널). "AI가 입혀주는 취업 정장 12종" — 블로그 원본 소재로 꾸 트랙 제공.
3. **구조화 데이터 성장선**: v1.5에 프리셋 섹션 ItemList 마크업 → 커머스 단계에 Product+Offer (벤더 상품 연동 시 쇼핑 그래프 노출).
4. **OG/썸네일 재활용**: 상품컷은 specs OG 이미지·T1 카드 비주얼로 재사용 — 자산 1회 제작, 노출면 4곳.
