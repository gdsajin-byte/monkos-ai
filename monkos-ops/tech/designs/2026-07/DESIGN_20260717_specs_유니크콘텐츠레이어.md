## 1. 문제 정의 (2026-07-17 실측)

틀은 완성됐다: 428 슬러그 × 4언어(ko/en/ja/es) 전면 전개, 섹션 컴퍼넌트화(components/), officialSource 402/428 보유. 그러나 콘텐츠는 아직 템플릿이다.

| 실측 항목 | 수치 | 판정 |
|-----------|------|------|
| rejectionReasons 고유 세트 | **8종 / 428페이지** | 사실상 전면 복제 |
| details 고유 세트 | 49종 / 428 | 국가명 치환 템플릿 위주 |
| faqs | 명목상 428종 (국가명·수치 치환) | 실질 동형 |
| uniqueContent | **0건** | 부재 |
| detailSections (구조화 상세) | 1건 (kr-passport 파일럿) | 선례만 존재 |

**리스크**: ① 구글 scaled content abuse(2024.3 정책)·thin content — 1,712 URL 대부분이 실질 유사 문서로 색인 억제 가능 ② GEO(AI 검색) 관점에서 인용할 고유 문장이 없음 ③ es 확장분 품질 결함 실측(vn-visa es 페이지): 영문 누출("less than 2MB", "White"), **리서치 주석 혼입**("(not further quantified in months on this page)"), 기계번역 문법 파손("Los anteojos sin están permitidos", "a frente-mirando imagen"), 미번역 h2.

## 2. 목표

각 페이지를 "그 나라·그 문서·그 언어에서만 성립하는 문서"로 만든다.

- **SEO**: 실질 중복 해소 → 색인률·비브랜드 클릭 상승 (PF_SPECS KPI 승계)
- **GEO**: 섹션마다 AI가 그대로 인용 가능한 정답문 선두 배치 (GEO보강표준 §2-1 이행)
- **전환**: 공식 출처 링크 + 실무 디테일 = 신뢰 → 무료 도구 사용 전환

## 3. 콘텐츠 아키텍처

### 3-1. 스키마 — `uniqueContent` (specs-data.json 슬러그별 신규 필드)

```json
"uniqueContent": {
  "sections": [
    {
      "id": "visa-types",
      "ko": { "title": "미국 비자 종류와 사진 규격", "geoAnswer": "미국 비자 사진 규격은 51×51mm(2×2인치)로, B1/B2·F-1·H-1B 등 비자 종류와 무관하게 동일하다.", "body": ["...", "..."] },
      "en": { "title": "...", "geoAnswer": "...", "body": ["..."] },
      "sources": [{ "name": "U.S. Department of State", "url": "https://travel.state.gov/...", "grade": "A" }],
      "confidence": "high"
    }
  ],
  "verifiedAt": "2026-07-17",
  "pipeline": "specs-unique-pilot"
}
```

- 렌더는 기존 `detailSections` 선례(render-specs.js:535)와 동일 패턴의 **컴포넌트 1개 추가**(components/unique-content.js), 언어 폴백은 `locField()` 체계 준수.
- ja/es 미작성 슬러그는 해당 언어에서 섹션 자체를 미노출 (기계번역 채움 금지 — §5 가드).

### 3-2. 콘텐츠 유형 카탈로그 (문서유형별 표준 앵글, 근거 있는 유형만 채택)

| id | 앵글 | 예시 |
|----|------|------|
| `visa-types` | 문서(비자) 종류별 사진 요건 관계 | 미국: 전 종류 51×51 동일 + DS-160 업로드 규격 |
| `channels` | 신청 채널별 규격 차이 | 베트남: e-Visa/도착비자 40×60 vs 재외공관 35×45 수용례 |
| `digital` | 온라인 신청 디지털 스펙 (px/KB/포맷) | 미국 DV로터리 600×600 정확, 싱가포르 400×514·60KB |
| `rejections-local` | 그 나라 고유 **현행** 반려 리스크 (필터링 사각 우선) | 한국 컬러렌즈·서클렌즈+앞머리(귀 노출은 폐지 — 교정 콘텐츠), 미국 안경 금지(2016~), 캐나다 AI편집 금지 |
| `children` | 아동·영유아 특별 규정 | 호주 3세 미만 입 벌림 허용, 미국 영유아 눈 감김 일부 허용 |
| `changes` | 최근 규격 변경 이력 | 인도 여권 2025.09 51×51→35×45, 독일 2025.05 종이사진 폐지 |

### 3-3. GEO 원칙 (GEO보강표준 승계)

- 섹션 첫 문장 = `geoAnswer` 완결 정답문 (표·설명보다 먼저)
- 모든 수치 주장에 공식 출처 링크 병기 (grade A 우선) — 자연 백링크 유도(PF_SPECS 전략 3) + AI 인용 파이프라인 신뢰 신호

### 3-4. 품질 기준 — "규격 나열 금지" 조항 (작가님 확정, 07-17) ⭐

> "뻔한 규격 논리만 나열해선 품질이 낮음. 직접 공식 채널 문서들을 정독하고 요약하여 제대로 된 정보를 한눈에 보기 좋게 납품하는 것이 우리 같은 서비스의 과제."

1. **규격 수치의 단순 재진술 실격** — 치수·배경·머리높이는 페이지 상단 규격 섹션이 이미 담당. uniqueContent는 **공식 원문을 정독해야만 쓸 수 있는 정보**만 담는다.
2. **실반려 리스크 중심 편집** — "실제로 반려당하는 이유", 특히 자동 필터링 사각지대(예: 한국 컬러렌즈·서클렌즈)를 우선한다.
3. **낡은 통념 교정 = 최고 가치 콘텐츠** — 폐지·변경된 규정을 명시적으로 교정한다(변경 시점·근거 문서 병기). 검색 수요가 낡은 규정에 몰려 있어 SEO 가치도 최대.
4. **실증 사례 (한국 여권)**: 귀 노출 규정 폐지 → 현행 리스크는 눈썹·이마 노출(앞머리 가림)과 컬러렌즈·서클렌즈 반려. 철창이 DB(05-20)조차 "귀 노출=최다 반려"로 노후 — 내부 DB 앵커 자체를 신뢰하지 말 것.
5. **정독의 범위** — officialSource 랜딩 페이지가 아니라 상세 규정 문서(고시·PDF·하위 페이지)까지. 랜딩만 읽은 드래프트는 반려.

### 3-5. 실무 캘리브레이션 원칙 (작가님 확정, 07-17 2차) ⭐

규정 원문과 접수 실무는 다른 층이다. 두 층을 분리해 쓰되, 어느 쪽으로도 과장하지 않는다.

1. **규정층**: 명문 그대로 (예: "AI를 활용한 편집·가공·합성" 불허 — 한·미 등 다수국). 출처 grade A.
2. **실무층**: 실제 반려를 부르는 것의 빈도 서열 — ① 얼굴 사이즈·규격 자체 이탈 ② 눈썹·이마 가림 ③ 컬러/서클렌즈 ④ 흰색 의상(흰 배경 융합). "편집 금지" 조항으로 반려되는 건 심사관 육안 대조에서 **과한** 경우이며 빈도 자체는 낮다 — 실무에서 보정 안 하는 사진관은 없다.
3. **쌍둥이 가드**: 과경고 금지(고객이 서비스 사용을 겁내게 만드는 서술 실격) + 과보장 금지("무조건 통과" 류, 헌법 4조 4항). 조항의 취지(신원 왜곡 방지)를 설명하고, 우리 파이프라인의 정체성 보존 원칙(헌법 1조 3항)과 연결하되, 공식 근거 없는 안심 문구는 쓰지 않는다.
4. **물리 이력 요건국**: 캐나다(사진관 인장/공식 사인) 같은 채널 요건은 사실 그대로 안내 — 단 공포 프레임이 아니라 "이 나라는 이런 절차" 프레임.
5. **grade P(practice) 신설**: 작가님 사진관 실무 지식 = 국내 처리·주한 대사관 케이스 기반. ko 페이지(주한 신청자 관점)에 실무 가중치를 싣는 근거로 사용하고, en/ja/es는 규정+보편 실무 중심으로 공관별 편차 명시. **지리 경계 명시 의무** — 해외 현지 접수처 실무는 미확인 영역. grade P 단독으로 수치·정책 단정 금지 (B급과 동급 취급, 단 "빈도 가중치" 배분에는 최우선).
6. 파일럿 4국 드래프트는 병합 전 이 원칙으로 **톤 캘리브레이션 패스** 1회 실시 (특히 편집 금지 서술 3건: kr·us·ca).

## 4. 언어·시장 차별화 원칙

번역이 아니라 **관점 차별화** — hreflang 정당성의 실질 근거를 만든다.

| 언어 | 관점 | 예시 (us-visa) |
|------|------|----------------|
| ko | 한국인 신청자 맥락 | 주한미국대사관 인터뷰·DS-160 업로드 실패 대처 |
| en | 글로벌 표준 + 미국 내 신청자 | State Dept 원문 기준 정밀 수치 |
| ja | 일본인 신청자 맥락 | 재일미국대사관, 일본 사진관 관행과의 차이 |
| es | 중남미 신청자 맥락 (미국비자 최대 수요권) | 멕시코·콜롬비아 CAS/대사관 맥락 |

- **단계화 가드** (GEO보강표준 §3 준용): ko+en 선행 → 패턴 검증 → ja/es 확대. 4언어 일괄 기계 생성 금지 (scaled content abuse 직격 패턴).

## 6. 실행 파이프라인 — Workflow 선택

작가님이 열어준 두 경로(지시서/워크플로우) 중 **Workflow** 채택. 근거: 대량 병렬 리서치 + 슬러그별 독립 작업 + **적대 검증 게이트 내장**(드래프터와 별도 에이전트가 출처 재조회로 주장 단위 판정) — 오정보가 헌법 4조 4항 직결이라 검증 구조가 본질.

```
[Draft] 슬러그별 리서처: 정본 확인 → 공식 소스 정독 → 철창이 브리핑 종합 → ko+en 드래프트
  ↓ (pipeline, 슬러그별 독립 진행)
[Verify] 적대 검증자: 인용 URL 전수 재조회 → 주장별 confirmed/plausible/unverified/wrong → wrong·unverified 잔존 시 pass=false
  ↓
[민아] 취합·품질 게이트 → 드래프트 파일 (PF_SPECS/drafts/) → 작가님 검수
  ↓ (승인 후)
[반영] specs-data.json 병합 + 렌더 컴포넌트 → dev 검증 → prod
```
