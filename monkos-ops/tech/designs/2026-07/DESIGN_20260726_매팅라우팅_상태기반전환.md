> **선행 분석**: iMac/민아 07-25 세션 로그(20:46~21:30 구간). 본 문서는 그 분석을 **소실 방지를 위해 정본 문서로 승격**한 것이며, 처방 설계의 원안은 민아·작가님 공동이다.

## §1 사실 확정 — 작가님 판정은 코드로 성립한다

### 1-1. 예열은 무조건부다 (`lib/matte.js:142~159`)

```js
export function warmupMatteEngine() {
  const now = Date.now();
  if (now - lastWarmupAt < 60 * 1000) return;   // 60s 쿨다운뿐
  lastWarmupAt = now;
  for (const url of MATTE_API_URLS) {           // ← 전 엔드포인트 순회
    if (isRunpod(url)) {
      fetch(`${url}/run`, { ... })              // ← RunPod엔 실잡 투입 (과금)
      continue;
    }
    fetch(`${url}/health`, { ... })             // ← 4060엔 헬스핑 (무과금)
  }
}
```

- **4060의 건강·활성 여부를 판정하는 조건이 존재하지 않는다.** 4060이 100% 정상 처리해도 RunPod `/run` 워밍 잡은 매번 나간다.
- 호출 지점 3곳: `server.js:367`(`/api/matte/warmup`) · `:640`(precheck 측정성 통과) · `:774`(생성 직전, 60s 쿨다운으로 대개 스킵).

### 1-2. 과금 구조 — 절감분이 반올림 오차다

| 항목 | 값 | 출처 |
|---|---|---|
| RunPod 워커 `idleTimeout` | **90초** | 민아 07-25 실측 |
| `workersMin` | **0** | 민아 07-25 실측 |
| 예열 1회 과금 | 워커 기동 + 워밍잡 ~0.7s + **유휴 90초** | `matte.js` 주석 + 실측 |
| 실사용 추론 시간 | **0.41초** | 민아 07-25 실측 |

> **∴ 4060이 성공해서 아끼는 것은 `/runsync` 0.41초분이고, 90초 유휴는 이미 지불된 뒤다.**
> **매팅 실사용이 RunPod 과금에서 차지하는 비중 1% 미만.** **작가님 판정 「비용절감 0」은 정확하다.**

### 1-3. 🔴 더 나아가 — **지연 이점마저 없다**

민아 07-25 동일 조건 실측:

| 엔드포인트 | 실측 응답 |
|---|---|
| **RunPod (예열됨)** | 0.346 · 0.41 · 0.48 · 1.116초 |
| **4060** | 0.356 · 0.563 · 0.589 · 0.631 · 0.909초 |

- **예열된 RunPod이 4060과 동급이거나 오히려 빠르다.**
- ⚠️ **작가님 판정을 한 단계 더 밀면**: 4060 1순위의 근거는 *"비용"*도 *"속도"*도 아니다. **남는 것은 이중화·통제권·GPU 자원배분 학습가치뿐**이며, 이는 인정되는 가치이되 **1순위 배치의 근거로는 약하다.**
- 참고: 07-25 당일 4060은 **장애 원인 측**이었다(낮 스래싱 · 밤 외부 점유). `INCIDENT_20260725`.

## §3 🔴 부수 결함 — dev가 prod 잔액을 태운다

`portal/deploy.sh:77`의 `MATTE_API_URLS`는 **환경 분기(84행~) 바깥에 정의**되어 있다. 즉 `dev`·`prod`가 **동일 엔드포인트 + 동일 `MATTE_API_KEY`**를 공유한다.

- **`portal-dev`의 precheck도 RunPod을 예열한다.** dev 테스트가 prod RunPod 잔액을 소모한다.
- 실증: 07-25 막내2 CDP 반복 주행(15:37~15:50)은 4060 GPU만 잠식한 것이 아니라 **RunPod 과금도 발생시켰다** (낮 인시던트의 미집계 비용 항목, 민아 적발).

## §4 처방 — 상태 기반 라우팅 (민아·작가님 원안 채택)

### 4-1. 현행 → 목표

| 단계 | 현행 | 목표 |
|---|---|---|
| precheck | `/health` 핑(**응답 버림**) + **RunPod 무조건 예열** | `/health` **읽음** → 건강하면 **예열 생략**, 위험하면 예열 |
| generate | 4060 고정 1순위 → 실패 시 RunPod | **precheck 판정 상태로 라우팅 결정** |

### 4-2. 판정 입력 — 이미 존재한다

07-25 막내3이 신설한 `/health` 확장 필드를 그대로 사용: `inflight` · `oldest_inflight_sec` · `recent_matte_ms` · `rejected_503_total`.
민아가 *"폴백용이 아니라 탐지용으로 유지하라"*고 남긴 필드가 **두 번째 용도(예열 게이팅)**를 얻는다. **신규 계측 개발 불요.**

### 4-3. ⭐ 이 설계가 A/B 양자택일을 해소한다

민아가 20:46에 A(예열 조건부화=절감) / B(RunPod 1순위=안정)를 양자택일로 제시했으나, 상태 기반 라우팅은 **상태에 따른 자동 전환**으로 둘을 통합한다.

| 4060 상태 | 동작 | 얻는 것 |
|---|---|---|
| 건강 | 예열 생략 → 4060 처리 | **RunPod 과금 0** (A안 절감) |
| 위험(포화·외부점유·지연악화) | 예열 발사 → **RunPod 직행** | **25초 낭비 없이 즉시 폴백** (B안 안정성) |
| — | 위험 시 4060에 아예 안 보냄 | **유령 잡 미발생** (중단 잡 미취소 문제 소멸) |
