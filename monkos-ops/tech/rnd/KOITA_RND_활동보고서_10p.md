## 2. 연구 1 — 인물 정체성 보존 프롬프팅 연구

### 2.1 연구 배경

AI 증명사진 서비스의 핵심은 "원본 인물과 동일한 사람으로 인식되는 결과물"이다. 그러나 상용 생성형 AI 모델(Google Gemini, Imagen 등)에는 안전 장치(Safety Guard)가 작동하여, 인물 이미지 생성 시 원본 특징이 의도적으로 변형되거나 요청 자체가 거부되는 문제가 발생한다.

**연구 과제**: 오픈소스(Stable Diffusion 등) 대신 상용 모델의 품질을 활용하면서, 안전 장치를 정당하게 통과하는 프롬프팅 전략을 개발할 수 있는가?

### 2.2 연구 과정

**1단계 — 문제 관찰 (2025.12)**

초기 실험에서 "이 인물과 100% 동일하게 재현하라"는 지시를 사용했다. 결과는 두 가지로 나뉘었다:
- 안전 장치 발동으로 요청 자체가 거부됨
- 생성은 되었으나 얼굴 특징이 왜곡되어 본인 인식 불가

100% 동일을 요구할수록 오히려 모델이 "딥페이크 시도"로 분류하여 결과가 나빠지는 역설을 발견하였다.

**2단계 — 프롬프트 구조 실험 (2026.01)**

접근 방식을 전환하였다. "동일하게 만들어라"가 아니라 "이 인물의 특징을 보존하되, 스타일 적용의 자유도를 부여한다"는 프레임으로 프롬프트를 재설계하였다.

```
CRITICAL INSTRUCTION: Maintain the exact facial features,
body proportions, skin tone, facial structure, eye shape,
nose, lips, and overall model identity. Preserve identity
with artistic freedom for style adaptation.
```

핵심 발견은 **정체성 보존 영역과 스타일 자유도 영역을 명시적으로 분리**하는 것이었다. 모델에게 "어디까지가 변경 불가이고, 어디가 변경 가능한지"를 구분하여 지시하면 안전 장치를 회피하는 것이 아니라 정당하게 통과하게 된다.

**3단계 — 변수 분리 코딩 (2026.01~02)**

프롬프트 전략을 코드로 체계화하였다. 변경 불가 영역(얼굴 형태, 피부톤, 체형)과 변경 가능 영역(의상, 헤어스타일, 배경, 조명)을 프로그래밍적으로 분리하여, 용도별 프롬프트를 자동 생성하는 파이프라인을 구축하였다.

```javascript
// 정체성 보존 vs 스타일 적용 분리 구조
const identityLock = {  // 변경 불가
  face: "exact facial features, facial structure",
  body: "body proportions, skin tone",
  identity: "overall model identity"
};
const styleAdapt = {    // 변경 가능
  outfit: "professional attire, formal wear",
  hair: "neat styling, natural look",
  background: "studio backdrop, solid color"
};
```

### 2.3 성과 및 시사점

- **연령/성별 불문** 정체성 보존 달성: 영유아, 청소년, 성인 모두에서 "본인 인식 가능" 수준 확인
- **`gemini-3-pro-image-preview`** 모델에서 I2I(Image-to-Image) 파이프라인 안정화
- **안전 설정 최적화**: 정체성 유지를 위한 최소 안전 수준 조합 실증
- 이 전략은 **연구 3(Image Pro)**의 기술적 기반이 됨

## 3. 연구 2 — K-뷰티 스키마 설계 및 데이터 테이블링 연구

### 3.1 연구 배경

범용 AI 모델에게 "예쁜 헤어스타일"이라고 지시하면, AI는 서양 기준의 일반적 스타일을 생성한다. 그러나 K-뷰티 시장에서 요구하는 "허쉬컷", "에어리 룩", "청담톤 발레아쥬"와 같은 정밀한 스타일 재현은 범용 프롬프트로는 불가능하다.

**연구 과제**: K-뷰티 도메인의 전문 용어를 AI가 이해할 수 있는 구조화된 데이터 스키마로 변환하고, 이를 프롬프트 자동 생성에 활용할 수 있는가?

### 3.2 연구 과정

**1단계 — BWYA 코퍼스 분석 (2025.12~2026.01)**

자체 구축한 BWYA(Become Who You Are) 6대 학문 체계의 문서 48개(206,131자, 2,347문단)를 분석하여 프롬프트 태그 53개를 추출하였다. 6대 학문은 사진학, 패션학, 헤어조형학(자체 창설), 신체구조학/포즈론, AI 디렉팅학, 언어의 철학으로 구성된다.

**2단계 — 레이어드 아키텍팅 (2026.01)**

핵심 발견은 **레이어드(Layered) 접근법**이다. 패션을 예로 들면:

```
[Layer 0] 이너웨어 — 실루엣의 기초
[Layer 1] 캐미솔 — 소재와 비침의 은유
[Layer 2] 블라우스 — 의도적 레이어링
[Layer 3] 아우터 — 구조감과 브랜드 코드
```

"예쁜 옷을 입은 모델"이라는 단일 지시 대신, 레이어별로 소재·실루엣·브랜드 코드를 지정하면 비즈니스 수준의 패션 이미지가 생성된다. 같은 논리를 헤어에도 적용하여 [Base → Structure → Volume → Texture → Color] 5계층 구조를 설계하였다.

**3단계 — 데이터베이스 스키마 구현 (2026.01~02)**

추출된 태그 체계를 Firestore/D1 데이터베이스 스키마로 구현하였다.

| 테이블 | 용도 | 태깅 항목 |
|--------|------|----------|
| Face Tags | 헤어/메이크업 | style, length, texture, volume, color, tone |
| Body Tags | 패션/포즈 | silhouette, layer, material, occasion, pose |
| Prompt Dictionary | 프롬프트 사전 | 53개+ 태그, 7개 카테고리 |

### 3.3 성과 및 시사점

- K-뷰티 전문 용어 → AI 프롬프트 태그 변환 체계 확립
- **한송이 연구원의 도메인 전문성**이 태그 정밀도의 핵심: 미용학 학술 배경 + 현장 실무 경험이 결합되어 AI가 이해 가능한 수준으로 용어를 정의
- 이 스키마는 **연구 4(생성→큐레이팅→RLHF 순환)**의 데이터 구조 기반이 됨

## 4. 연구 3 — 이미지 생성 모델 비교 검증 및 MONKOS Image Pro 구축

### 4.1 연구 배경

정체성 보존 프롬프팅(연구 1)과 K-뷰티 스키마(연구 2)를 실현할 **기반 모델**을 선정해야 했다. "벤치마크 숫자를 믿지 않는다"는 원칙 하에, 후보 모델을 직접 테스트하여 실무 도입 여부를 판단하였다.

### 4.2 연구 과정

**1단계 — 모델 대조 실험 (2025.12~2026.01)**

5개 모델군을 동일 조건(동일 인물 사진, 동일 프롬프트)으로 테스트하였다. 검증 기준은 정체성 유지율, 아티팩팅(사시/6손 등 결함) 수준, I2I 재생성 품질이다.

| 모델군 | 정체성 유지 | 아티팩팅 | I2I 품질 | 판정 |
|--------|-----------|---------|---------|------|
| SD 1.5 | 불가 | 심각 | 불가 | 낙제 |
| SDXL (Juggernaut/HappyWorld) | 조건부 | 간헐적 | 조건부 | 보류 |
| FLUX.1 (Dev/Schnell) | 양호 | 적음 | 양호 | 유망 (하드웨어 제약) |
| Imagen 3 (T2I) | 우수 | 극소 | 우수 | 채택 — Text-to-Image |
| Gemini 3 Pro (I2I) | 우수 | 극소 | 우수 | 채택 — Image-to-Image |

**핵심 발견**: 오픈소스 모델(SD/FLUX)은 파인튜닝 자유도가 높지만, 정체성 보존에서 상용 모델(Imagen/Gemini)에 미치지 못했다. 특히 증명사진처럼 "본인임을 증명해야 하는" 용도에서 이 차이는 결정적이었다.

**2단계 — MONKOS Image Pro 엔진 구축 (2026.01)**

Gemini 3 Pro 기반의 I2I 파이프라인을 서비스화하였다.

- **인증 아키텍처**: Vertex AI ADC(실시간 코칭/QC) + Google AI Studio API Key(Imagen I2I 생성)를 하이브리드로 결합. 이는 Google의 모델별 인증 정책 차이를 연구하여 도출한 구조이다.
- **Image Pro 엔진**: Standard(고속) / Premium(고품질) 2단계 생성 모드
- **배포**: Google Cloud Run (us-central1) — 서버리스 무중단 운영

**3단계 — 실시간 코칭 + QC 파이프라인 (2026.02)**

이미지 생성 전후에 AI가 개입하는 시스템을 구축하였다.

- **촬영 코칭**: Gemini 2.0 Flash Live API + WebSocket 기반 실시간 포즈/표정/조명 피드백 (0.5fps)
- **QC(품질 검수)**: 생성 결과물을 AI가 자동 검수 — 성별/연령 일치, 과보정 감지, 아티팩팅 판별
- **파이프라인**: 코칭(촬영 보조) → 캡처(512px JPEG) → 생성(I2I) → QC(자동 검수) → 다운로드

### 4.3 성과 및 시사점

- 4개 서비스 상용 배포 완료: monkos.ai(포털), idphoto-kr(한국), idphoto-jp(일본), image.monkos.ai(Image Pro)
- **RTX 4060 한계 실증**: 8GB VRAM으로는 FLUX 추론 불가, 7B 이상 파인튜닝 불가 → 5090(32GB) 도입 근거 확보
- 상용 모델 활용의 한계(API 비용, 정책 종속)도 확인 → **연구 4(자체 지능 진화)**의 동기 부여

## 5. 연구 4 — 생성-큐레이팅-RLHF-코퍼스 진화 로직 연구

### 5.1 연구 배경

연구 1~3을 통해 "이미지를 생성하는 기술"은 확보했다. 그러나 한 가지 문제가 남았다: **AI가 생성한 이미지의 품질을 누가, 어떤 기준으로 판단하는가?** 그리고 그 판단이 **시스템에 축적되어 다음 생성의 품질을 자동으로 높이는 구조**를 만들 수 있는가?

### 5.2 연구 과정

**1단계 — 생성 → 큐레이팅 루프 (2026.01)**

초기에는 생성된 이미지를 연구소장이 직접 검수하였다. 이너웨어 모델 T2I 100컷 생성 시 71컷 성공(29컷 탈락)이라는 결과가 나왔으나, 탈락 기준이 주관적이고 기록이 남지 않는 문제가 있었다.

**2단계 — RLHF 도입: 한송이 연구원 (2026.01)**

K-뷰티 도메인 전문가인 한송이 연구원을 RLHF(Reinforcement Learning from Human Feedback) 검수자로 영입하였다.

```
[생성] AI가 이미지 생성
    ↓
[큐레이팅] 한송이 연구원 검수
    • 헤어: 볼륨/레이어/텍스처 정밀 판정
    • 메이크업: 트렌드 부합 여부
    • 패션: 레이어드 구성 적정성
    • 전체: K-뷰티 시장 적합성
    ↓
[피드백] 태깅 + 점수 + 사유 기록
    ↓
[코퍼스 갱신] 프롬프트 사전 보강
    ↓
[다음 생성] 개선된 프롬프트로 재생성
```

핵심은 한송이 연구원의 **"미용교육학 석사 + 현장 실무"라는 이중 전문성**이다. 학술적 용어와 현장 트렌드를 동시에 이해하는 검수자만이 AI 프롬프트 수준의 정밀한 피드백을 제공할 수 있다.

**3단계 — 코퍼스 자동 진화 설계 (2026.02)**

수동 피드백 루프를 자동화하는 구조를 설계하였다.

```
┌─────────────────────────────────────────┐
│                                         │
▼                                         │
[생성] → [QC 자동검수] → [RLHF 전문가 검수]│
                              ↓           │
                     [태깅/피드백 기록]     │
                              ↓           │
                     [코퍼스 갱신]          │
                              ↓           │
                     [프롬프트 사전 진화]───┘
                              ↓
                     [다음 생성 품질 ↑]
```

한 바퀴 순환할 때마다:
- 프롬프트 정밀도 향상 (태그가 추가/보정됨)
- 스타일 재현 정확도 향상 (실패 사례가 코퍼스에 반영됨)
- 도메인 지식 누적 (K-뷰티 트렌드 변화가 반영됨)

### 5.3 성과 및 시사점

- 학문(BWYA) → 실무(생성) → 큐레이팅(RLHF) → 교육(Academy) **순환 시스템** 설계 완료
- 코퍼스 현황: BWYA 문서 206,131자, 프롬프트 태그 53개+, 세션 로그 450KB+
- **자동 진화의 핵심 통찰**: "AI 모델 자체를 바꾸는 것이 아니라, AI에게 주는 지시(프롬프트+코퍼스)를 진화시키는 것" — 모델 교체 없이도 결과물 품질이 지속 향상되는 구조

---

## 6. 연구 5 — 도메인 특화 지능형 챗봇 서비스 연구

### 6.1 연구 배경

증명사진 촬영 전 "어떤 의상이 적합한가", "머리 스타일은 어떻게 해야 하는가" 등 사전 준비에 대한 사용자 질문이 빈번하다. 범용 AI(ChatGPT, Gemini 등)는 일반적인 답변만 가능하고, 우리 서비스의 구체적 규격·옵션·가격·촬영 팁을 알지 못한다.

**연구 과제**: "나보다 나의 가게를 잘 아는 챗봇" — 서비스 운영자보다 세부 사항을 정확히 알고, 고객에게 전문적 안내를 제공하는 챗봇을 구축할 수 있는가?

### 6.2 연구 과정

**1단계 — 범용 챗봇 한계 확인 (2026.01)**

Gemini 2.0 Flash 기반의 일반 챗봇을 monkos.ai 포털에 배치하였다. 시스템 프롬프트에 서비스 개요를 넣었으나, 미출시 기능을 안내하거나 가격을 잘못 말하는 등 **환각(Hallucination) 문제**가 빈번하였다.

**2단계 — RAG(Retrieval-Augmented Generation) 도입 (2026.02)**

Firestore에 `cs_knowledge` 컬렉션을 구축하고, 키워드 스코어링 기반의 검색 시스템을 개발하였다. 사용자 질문에서 키워드를 추출하여 관련 지식 문서를 검색하고, 이를 컨텍스트로 제공하여 응답하는 구조이다.

```javascript
// 통합 챗봇 아키텍처
chatWithMonkos(channel, chatId, message)
├── channel: "web" | "telegram" | "prep"
├── RAG: Firestore cs_knowledge 검색
├── 채널별 시스템 프롬프트 분리
└── 대화 이력 관리 (채널별 maxHistory)
```

**3단계 — 3채널 통합 + 준비실 코칭 (2026.02)**

하나의 통합 함수 `chatWithMonkos()`로 3개 채널을 서비스화하였다:

| 채널 | 용도 | 특징 |
|------|------|------|
| web | 포털 일반 문의 | 3개국어(KR/JP/EN) 자동 분기 |
| telegram | 텔레그램 봇 CS | 실시간 알림 연동 |
| prep | 촬영 준비실 코치 | 복장/헤어/메이크업 전문 안내 |

준비실 코치(prep)에는 5건의 시드 코퍼스(여권사진/이력서/학생증/아기/컬러가이드)를 투입하여, 용도별 맞춤 안내가 가능하도록 하였다.

### 6.3 성과 및 시사점

- **환각 제거**: "되는 것만 응답" 원칙 — RAG 검색 결과에 없는 내용은 "확인 후 안내드리겠습니다"로 응답
- 2개 함수(chatWithGemini + chatWithGeminiCS) → 1개 통합 함수(chatWithMonkos)로 아키텍처 단순화
- **코퍼스 확장 = 챗봇 진화**: 지식 문서를 추가할수록 챗봇 응답 범위와 정밀도가 자동 향상 — 연구 4의 코퍼스 자동 진화 로직과 동일 원리
- 향후: 로컬 LLM(DeepSeek 7B / Llama 4급) 파인튜닝으로 대체 가능성 검토 중 — Google API 정책 종속 탈피 목적

## 7. 연구 6 — 멀티 에이전트 오케스트레이션 체계 구축 연구

### 7.1 연구 배경

1인 개발 체제에서 설계·코딩·배포·문서화·마케팅을 동시에 수행하기 위해 LLM 기반 AI 에이전트를 활용하기 시작하였다. 초기에는 단일 에이전트(Claude Opus)와 대화하며 작업했으나, 작업량이 증가하면서 **여러 에이전트를 동시에 운용하고, 이들의 작업이 충돌하지 않도록 관리하는 체계**가 필요해졌다.

### 7.2 연구 과정

**1단계 — 단일 에이전트 → 멀티 에이전트 (2025.12~2026.01)**

초기에는 하나의 Claude Opus 세션에서 모든 작업을 수행했다. 작업 전환 시 컨텍스트가 끊기고, 긴 코딩 작업 중 전략 논의가 불가능한 문제가 있었다.

해결: 에이전트를 역할별로 분리하였다.

| 에이전트 | 역할 | 모델 | 디바이스 |
|---------|------|------|---------|
| 쌍아 | 전략 설계 + 지시서 작성 | Claude Opus | iMac (워크스테이션) |
| 막내 (복수) | 자율 코딩 실행 | Claude Opus | iMac / 맥미니 |
| 소넷이 | 모니터링 데몬 | Claude Sonnet | 4060 WSL |
| 철창이 | 전략/리서치 | Claude Opus | 상황별 |

**2단계 — 거버넌스 체계 수립 (2026.01~02)**

복수의 에이전트가 동시에 코드를 수정하면서 **병렬 작업 충돌** 문제가 발생하였다. 같은 파일을 두 에이전트가 동시에 수정하여 Git 충돌이 발생하거나, 한 에이전트의 변경이 다른 에이전트의 작업을 무효화하는 사례가 있었다.

이를 해결하기 위해 **헌법-법률-규정 3계층 거버넌스 체계**를 설계하였다:

```
[헌법] 11개 조항 — 불변 원칙 (작가님만 개정)
  ↓
[법률] 8개 장 34개 조 — 운용 규칙 (승인 하 개정)
  ↓
[규정] MEMORY.md 등 — 기술 상세 (에이전트 자율)
```

- 파괴적 명령(rm -rf, force push 등) 절대 금지
- 에이전트별 역할 체계 명문화
- 지시서 기반 작업 위임: 설계(쌍아) → 승인(작가님) → 실행(막내) → 보고
- 병렬 투입 시 수정 파일 충돌 체크 의무화

**3단계 — P2P 인프라 구축 (2026.02)**

Tailscale VPN 기반 P2P 메시 네트워크를 구축하여, 물리적으로 분산된 디바이스들이 하나의 개발 환경으로 기능하도록 하였다.

| 디바이스 | 역할 | 연결 |
|---------|------|------|
| iMac (M1) | 메인 워크스테이션 | Tailscale P2P |
| 맥미니 (M2) | 보조 연산 + 팀원 허브 | Tailscale P2P |
| RTX 4060 (Windows) | GPU 연산 + WSL 데몬 | Tailscale P2P + SSH |

### 7.3 성과 및 시사점

- **6~7기 에이전트 동시 가동** 체제 안정화 (Opus 3~4기 + Sonnet 2~3기)
- 거버넌스 체계로 병렬 작업 충돌 방지 — 세션 로그 기반 비동기 통신
- **비즈니스 확장 비전**: 동일 오케스트레이션 구조를 무인 촬영 부스 100+ 대 통제에 적용 가능
- **로컬 LLM 전환 로드맵**: 현재 클라우드 LLM(Claude Max) 의존 → 자체 파인튜닝 모델(7B~70B)로 전환 시 API 비용 $0 달성 가능 — 5090(32GB VRAM) 도입이 전제 조건

## 8. 연구 인프라 및 향후 계획

### 8.1 현재 인프라 현황

| 항목 | 내용 |

| LLM | Claude Max (Opus/Sonnet) + Gemini 2.0 Flash |
| 데이터 | Firestore + GCS + D1 (Cloudflare) |
| 네트워크 | Tailscale P2P 메시 (4개 디바이스) |

### 8.2 5090 GPU 도입 필요성

현재 RTX 4060(8GB VRAM)의 한계가 실증되었다:
- FLUX 추론: OOM(Out of Memory)으로 불가
- 7B 이상 모델 파인튜닝: 불가
- SDXL 풀 파인튜닝: 불가

RTX 5090(32GB VRAM) 도입 시:
- 7B~35B 모델 파인튜닝 가능 → K-뷰티 특화 소형 지능 개발
- FLUX 전체 튜닝 가능 → 오픈소스 이미지 모델 자체 학습
- 로컬 서빙으로 API 비용 $0 → 프랜차이즈 납품 가능 조건 달성

**전략적 의미**: 현재는 빅테크(Google, Anthropic)의 API에 의존하고 있으나, 자체 파인튜닝 모델 확보 시 **정책 변경·가격 인상 면역** + **비즈니스 독립성** 확보
