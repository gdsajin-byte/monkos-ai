## 1. 목표 상태

Routine 컨테이너가 **단독으로** 데일리 E2E 전체를 수행한다:
수집(GA4·GSC·프로브·뉴스) → 판단(해석·이상감지) → 보고(브리핑 커밋) → 알림(텔레그램).
GH Actions는 백업 트리거로 강등하거나 폐지 가능한 상태.

## 2. 실측 근거 — 현행 파이프라인이 실제 요구하는 자격

## 3. 인증 설계 (보안 관점)

### 3-1. 전용 읽기 SA 신설 — 핵심 권고

Routine은 **권한 프롬프트 없이 무인 자율 실행**된다. 이 환경에 editor SA를 투입하면
프롬프트 인젝션·오동작 시 파괴 반경이 GCP 프로젝트 전체가 된다. 따라서:

- **신설**: `minah-web-routine@{프로젝트}.iam.gserviceaccount.com` (이름은 쌍아 확정)
- **IAM 역할 단 1개**: `roles/secretmanager.secretAccessor` (그것도 필요 시크릿에 조건부 바인딩 권장)
- **GA4**: IAM이 아닌 **속성 레벨**에서 SA 이메일을 뷰어로 추가
- **GSC**: **사이트 레벨**에서 제한된 사용자로 추가
- 프로젝트 수준 editor/viewer **불부여** — GA4·GSC는 제품 레벨 권한으로 충분

### 3-2. 부트스트랩 1키 원칙

환경 변수에 들어가는 시크릿은 **SA 키 1개뿐**. 나머지(텔레그램 토큰 등)는 세션이
런타임에 GCP Secret Manager에서 취득한다.

- 6/03 확립된 하이브리드 표준(GCP SM = 정본, 시크릿 24종 기등록)을 그대로 재사용 — 웹 환경은 GH Secrets에 이은 **제3 소비자**일 뿐, 새 정본을 만들지 않는다 (헌법 3조 4항 정본 단일 원칙의 시크릿 판)
- 토큰 로테이션 시 GCP SM 한 곳만 갱신하면 웹 루틴은 자동 추종 — GH Secrets처럼 사본 동기화 부담이 없다

### 3-3. 절대 미투입 목록 (영구 원칙)

웹/루틴 환경에는 다음을 **어떤 형태로도 넣지 않는다**:
배포 자격(Cloud Run·CF), Firestore 쓰기 SA, `scripts/credits.sh` 관련 자격, OAuth client secret 류.
쓰기 작업(배포·고객데이터)은 로컬 막내 + deploy.sh 경유로 영구 유지 (헌법 4조 2항, ch5).

## 6. 작업효율 설계

1. **드롭인 재사용**: 변수명을 Actions와 동일하게 유지하면 루틴이
   `pip install -r .github/scripts/requirements.txt && python .github/scripts/daily_briefing.py`
   를 그대로 실행 — 코드 수정 없이 실행 주체만 교체. `GITHUB_OUTPUT` 의존부는 부재 시 자동 무시됨(코드 확인).
2. **환경 setup script**에 pip install 등록 → 매 실행 초기화 ~30초로 고정.
3. **루틴은 수집+판단 통합**: 스크립트가 만든 원시 브리핑을 같은 세션에서 즉시 해석·이상감지·전일 세션 연결까지 수행 — Actions 시절의 "숫자만 나열" 한계 해소.
4. **이행 단계**:
   - **Phase A (현행)**: AUTOPILOT 수집 유지, 루틴은 판단층만 (시범 가동 체계)
   - **Phase B (자립)**: 본 설계 적용, 루틴이 수집~알림까지 단독 수행. AUTOPILOT cron은 2주 병행 후 백업 강등/폐지 판단
5. **비용**: Actions 무료쿼터 소모 0으로 전환, 대신 루틴 일일 실행 캡 1회 소모 (플랜 한도 확인 필요).
