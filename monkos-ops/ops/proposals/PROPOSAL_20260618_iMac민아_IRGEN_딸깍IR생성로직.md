# 제안서 — 「딸깍 IR」 생성 로직 프레임워크 (IRGEN)

> **[2026-06-18 12:20 KST]** iMac/민아 → 작가님 (→ 쌍아 프레임워크화 인계)
> **한 줄**: 아이디어 한 줄을 넣으면, VC·심사자·클라이언트에게 **오독 없이 한눈에 읽히는 IR**이 생성되는 로직을 창안한다.

---

## 0. Executive Summary

- **무엇을**: 단순 아이디어 → 근거 기반 IR(투자제안서)/사업계획서가 "딸깍" 생성되는 로직(엔진)을 정의한다. 일회성 템플릿이 아니라 **재사용 생성 파이프라인**.
- **왜 지금**: 매 서비스마다 기획을 처음부터 다시 짠다(대충 만들다 멈춤). 표준 부재. 그리고 **과거 디딤돌 R&D 탈락**이라는 값비싼 교훈 자산이 그대로 남아있다.
- **제1원리**: 탈락의 원인은 "내용 부족"이 아니라 **"심사자의 오독"**. 따라서 IR 설계의 제1원리는 화려함이 아니라 **오독 불가능성(unmisreadable)** = 작가님이 말한 *"한눈에 읽히는"* 의 공학적 정의.
- **3파트 구조**: ① Evidence DB(근거 데이터) ② 생성 로직(9섹션 조립) ③ 출력 포맷(변주).
- **위상**: 이 로직을 돌리는 주체 = **CSO/임원 에이전트의 첫 역량**. 어제(6/17) 부서제·임원화 논의의 첫걸음. PROFILES가 이 엔진의 **첫 출력물(검증 케이스)**.

## 1. 문제 정의 — 탈락은 "내용"이 아니라 "전달"에서 났다

디딤돌 창업성장기술개발사업(RS-2026-25508252) 서면평가 8개 지적을 전수 분석한 결과, **단 하나도 "내용이 없다"가 아니었다. 전부 심사자가 잘못 읽은 것.**

| 지적 | 표면 | 실제 정체 (오독 유형) |
|---|---|---|
| ① 발색 정확성 미흡 | 내용 부족? | 제안서에 '발색' **0회** — 'K-뷰티'를 화장품 발색으로 **개념 오독** |
| ②③⑥ GPU 모순 | 전략 부실? | Serving(API) vs Training(GPU) **구조 미구분** |
| ④ 차별성 미흡 | 차별점 없음? | 자가진화 엔진을 "AI면 다 있는 것"으로 **가치 오해** |
| ⑥ 빅테크 경쟁력 | 경쟁 열위? | Adobe·Runway·Stitch Fix와 **범주 오류** 비교 |
| ⑦ 비용 모순 | 수익성 의심? | 원가 $0.04 vs 판매가 $10(마진 99.6%)를 **모순으로 오인** |
| ⑧ 사업화 미흡 | traction 부족? | 라이브 6개 서비스 가동 중인데 **실적 미인지** |

> **결론**: IR의 적은 경쟁자가 아니라 **"5분 만에 훑는 심사자·VC의 오독"**이다. 로직의 목표는 그 오독 확률을 0에 수렴시키는 것.

## 2. 설계 원리 — 탈락 8교훈을 「오독방어 게이트」로 자산화

실패를 품질 게이트로 전환한다. IR 출력 전 6종 게이트를 통과해야 한다:

| # | 게이트 | 규칙 | 출처 교훈 |
|---|---|---|---|
| G1 | **모호어 금지** | 컨셉어(K-뷰티 등)는 반드시 1줄 정의 동반 | ① |
| G2 | **헷갈림은 대조표로** | 혼동 가능 개념(Serving/Training 등)은 표로 분리 | ②③ |
| G3 | **차별점은 "우리만"** | "AI 기본기"는 차별점 불가. 경쟁이 못 하는 것만 | ④ |
| G4 | **경쟁은 정확 카테고리** | 시장·고객·가치제안 일치하는 대상만 비교 | ⑥ |
| G5 | **단위경제 숫자 못박기** | 원가·판매가·마진을 수치로 명시 | ⑦ |
| G6 | **Traction 전면 배치** | "할 것"이 아니라 "이미 한 것"을 정량으로 | ⑧ |

## Part 1. Evidence DB (근거 데이터 레이어) ★ 본 제안의 핵심

> 작가님 지적: *"근거를 댈 DB를 무엇으로 채울 것이냐가 템플릿화되어야. GA4/GSC만으로는 내부 과거 기록일 뿐 시장 설계 데이터가 아니다. VC 수준 DB 검색·스키마 자체가 한 파트급."* — 전적 수용.

### 1-1. 데이터 4계층 위계 (Tier)

내부 측정(GSC/GA4)을 시장 근거로 쓰는 것은 **눈가리고 아웅**. 신뢰 위계를 못박는다:

| Tier | 성격 | 소스 | IR 역할 |
|---|---|---|---|
| **T1 공신력** | 기관 통계·시장리포트 | 통계청/KOSIS, 한국콘텐츠진흥원, NIPA, Statista, Grand View Research | §1 시장규모(TAM/SAM/SOM) **정본** |
| **T2 업계인텔** | 앱·웹 트래픽·매출 | Sensor Tower, Similarweb, Appfigures(=Remini $93M 출처) | §2 경쟁 · §7 시장매출 |
| **T3 자체측정** | 우리 실측 | GSC · GA4 · Vertex 원가 | **traction 증거(§8)** · 단위경제(§7) ← *시장설계 아님* |
| **T4 정성신호** | 트렌드·여론 | **네이버 · 카카오 · 인스타 · 커뮤니티** | §3 타겟 · §4 수요 · 경쟁사 약점 |

→ GSC/GA4는 **T3로 강등**(traction 증명용). 시장 설계는 **T1·T2가 견인**, 한국 수요는 **T4가 1급**.

### 1-2. 소스 카탈로그 (국내 × 글로벌 × 5도메인)

| 도메인 | 글로벌 | 국내 (★ 빠졌던 핵심) |
|---|---|---|
| **시장규모** | Statista, Grand View, Precedence | 통계청/KOSIS, 한국콘텐츠진흥원, NIPA |
| **수요/검색** | Google Trends, 키워드플래너 | **네이버 데이터랩 + 검색광고 키워드도구(월간검색량)** |
| **경쟁 인텔** | Sensor Tower, Similarweb, Appfigures | 직접 수집(2/27 전수조사 방식), 앱스토어 랭킹 |
| **바이럴/트렌드** | TikTok 해시태그 볼륨 | **인스타 해시태그, 카카오/다음 트렌드** |
| **고객/JTBD** | Reddit, LinkedIn | **더쿠·디시·블라인드·네이버카페** |

### 1-3. 스키마 — `evidence_record` (레코드 1건 = IR 주장 1개의 근거)

```yaml
evidence_record:
  claim: "한국 커리어 프로필 시장 검색수요 월 ○○만"   # IR이 쓸 문장
  ir_section: §4 수요              # 어느 섹션을 받치나
  tier: T1 | T2 | T3 | T4          # 신뢰 위계
  source: "네이버 검색광고 키워드도구"
  metric: "월간검색량 PC+모바일"
  value: 00000
  freshness: 2026-06               # 갱신시점 (추정 금지 — 헌법 3조)
  acquisition: WebSearch | 네이버API | 수동리서치
  confidence: 상 | 중 | 하
  misread_guard: "G5 숫자못박기"     # 적용 게이트
```

> **구조적 효과**: IR의 모든 주장은 `evidence_record`에 연결되어야 한다. 근거 없는 주장은 **스키마상 입력 불가** = 허위·오독을 구조로 차단.

### 1-4. 획득 파이프라인 + 실제 보유 인벤토리 (2026-06-18 실측 정정)

> ⚠️ 초안의 "키 발급 필요"는 과장. SECRET_INVENTORY 실측 결과 네이버·소셜 자산이 이미 상당수 보유됨.

| Tier·소스 | 보유 상태 | 비고 |
|---|---|---|
| T1 기관통계(KOSIS·콘진원·NIPA·Statista) | ✅ WebSearch/WebFetch | 키 불필요 |
| T2 Sensor Tower·Similarweb | ⚠️ 미보유 | WebSearch 2차 인용 대체 |
| T3 GSC·GA4 | ✅ MCP 연동 | traction |
| **T3 네이버 서치어드바이저** | ✅ **개설·연동** | monkos.ai 등록 + portal 블로그 CMS Naver API 주입(rev00279, 6/11). monk.kr 2월 등록. *우리 사이트 네이버 색인/노출.* MCP 없음 → 직접 호출 |
| **T4 네이버 데이터랩 트렌드** | 🟡 **키 보유** | `NAVER_CLIENT_ID/SECRET`로 검색어트렌드 API 호출 가능. 앱 권한설정+연동만 필요 (상대 트렌드 지수) |
| T4 네이버 검색광고(월간검색량) | ⚠️ 신규 | 절대 검색량 정본. 광고계정 API키(customer_id/signature) 별도 발급 — **유일한 실(實) 갭** |
| T4 X(트위터) | 🟡 키 보유 | `X_*` 4종. 소셜 리스닝(무료티어 제한) |
| T4 카카오 | 🟡 키 보유 | `KAKAO_REST_API_KEY`. 검색트렌드 공개API 빈약 |
| T4 인스타/틱톡 해시태그 | ⚠️ | 공식 API 제한 → WebSearch/수동 |

→ **실제 신규 확보 과제는 「네이버 검색광고 API」 1건**. 나머지는 보유 키의 연동·권한설정 작업. 이 목록이 "Evidence DB 구축" 파트의 백로그가 된다.

> **개념 구분(중요)**: 서치어드바이저(T3, *우리 사이트* 노출) ≠ 데이터랩·검색광고(T4, *시장 전체* 수요). 둘 다 네이버지만 IR에서의 역할은 정반대.

## 5. 실행 인계 (다음 단계)

작가님 결정 반영: **Evidence DB 1차 = 스키마 + 카탈로그 (설계우선)**. 실데이터 수집은 차기.

1. **본 제안 승인** → 쌍아가 재사용 프레임워크로 구성 (템플릿 `TEMPLATE_BIZ_PLAN.md` + 생성 절차 스킬화)
2. **막내 도구화** — Evidence DB 스키마 파일 + 소스 카탈로그 + (가용) 수집 스크립트
3. **첫 적용 = PROFILES IR** — 오늘 확보한 자산(Remini $93M, 취업키워드 1.2위, 정체성보존 무기, 나노바나나)을 스키마에 수동 1회 채워 엔진 검증
4. **갭 해소** — T4 한국수요: 데이터랩 **연동**(키 보유) + 검색광고 API **신규 발급**(절대 검색량). 서치어드바이저(T3)는 이미 연동됨
