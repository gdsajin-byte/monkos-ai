## 3. 흐름

```
손님 [주문하기] ─ multipart(사진+주문서) ─▶ /api/studio-order
   │                                      ├ 검증: 장수·용량·형식·필수칸·봇 함정
   │                                      ├ 사진 묶음 나누기(메일 1통 ≤ 10MB 원본)
   │                                      └ Resend 발송: To 꾸(smuse73@naver.com), Reply-To 손님
   ◀─ 성공: 주문번호 화면 ─────────────────┘   (서버 디스크·DB·버킷 저장 0)
   ◀─ 실패: 오류 화면 + 톡톡·전화 안내 (선택한 사진·입력값은 화면에 그대로)
```

- **주문번호**: `MS-YYMMDD-XXXX`(서버 생성). 메일 제목 `[인화주문] MS-… 홍길동 · 증명 2종 8매 · 매장수령`.
- **`[결제완료]` 제목 표기 (10-03 12:10 꾸 동의 — 결제 방식 결정 후 적용, 조건부)**: 결제가 끝난 주문만 제목 앞에 `[결제완료]`를 붙인다(예: `[결제완료][인화주문] MS-… 홍길동 · 증명 2종 8매 · 매장수령`). 꾸는 제목만 보고 바로 인화한다. **작가님 결제 방식 3안 중 (나) monk.kr 토스 연동에서만 성립**한다(서버가 결제 확인을 알아야 함). (가) 스마트스토어 결제 링크·(다) 현장 결제면 결제 확인은 꾸가 스토어·현장에서 하고 제목은 `[인화주문]` 그대로 둔다.
- **메일 나누기**: 원본 합계가 10MB를 넘으면 `(1/3)` 식으로 여러 통으로 나눈다. 네이버 메일 수신 용량 한도에 걸리지 않게 하기 위해서다(**실측 필요** — §7 T5). 메일 본문에는 주문서 전체를 매번 반복한다.
- **원본 그대로**: 리사이즈·재압축 금지. 인화 화질이 기준이다. HEIC도 그대로 첨부하고 꾸 PC에서 변환한다.

## 5. 개인정보

- **수집**: 이름·연락처·(우편 시)주소·사진·용도. 화면에 수집 항목·목적·보관 기간·삭제 방법을 적고 **동의 체크 필수**(체크 없으면 버튼 비활성).
- **저장 위치**: 서버 0. 전달 경로는 Resend → 꾸 메일함 → 꾸 PC 한 곳이다.
- **Resend 쪽 보관**: Resend가 보낸 메일 내용을 일정 기간 보관하는지 확인이 필요하다(**실측 필요**). 보관한다면 고지문에 "발송 대행사 경유"를 한 줄 넣는다.
- **보관·삭제(D4)**: 꾸가 수령 완료 후 14일 안에 메일과 PC 원본을 삭제한다. 꾸 할 일 목록(TODO_꾸)에 주 1회 정리 항목으로 올린다. 자동 삭제가 아니므로 사람 손에 달린 리스크를 §8에 적는다.
- **로그**: Function 로그에는 주문번호·장수·용량·결과만 남긴다. 이름·연락처·파일명은 남기지 않는다.

## 7. 실패 시 손님 화면 (무음 실패 금지)

| 상황 | 화면 |
|---|---|
| 용량·장수·형식 위반 | 해당 사진 칸에 빨간 표시 + "이 사진은 20MB를 넘어요" 식 이유. 전송 전 화면에서 1차 차단 |
| 서버 거부·메일 발송 실패·네트워크 끊김 | "주문이 접수되지 않았어요. 다시 누르시거나 톡톡·전화로 주문해 주세요" + 톡톡 버튼·전화번호. **고른 사진·입력값은 그대로 유지** |
| 나누기 발송 중 일부만 실패 | 실패로 처리하고 같은 문구. 꾸 메일함에는 `(일부 실패)` 표시 메일 1통을 보낸다 |
| 성공 | 주문번호 + "확인 후 연락드릴게요" + 수령 방법 요약. 성공은 Resend가 메시지 id를 돌려준 경우에만 |
