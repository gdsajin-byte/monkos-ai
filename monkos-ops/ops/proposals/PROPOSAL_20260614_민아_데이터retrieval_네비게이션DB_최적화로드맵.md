## 1. 문제 정의 — 위험의 본질은 "관계 차수"

### 1-1. 실측 (2026-06-14)
- 전체 `.md` **3,088개** / 최근 30일 신규 **437** / 최근 7일 **195**(일평균 28 = 30일 평균의 2배, **가속 중**).
- 활성 PF **21개** (전체 27). orders 936·reports 429·sessions 381.

### 1-2. 진단
- 문서 1개 추가 = 절대량 +1(**선형 O(n)**), 그러나 맺을 수 있는 관계 = +n(**조합 O(n²)**).
- PF 21개 → 쌍관계만 ≈210, 문서가 PF에 매달리며 맥락이 곱셈. **절대량이 작아도(50M) 견디기 빠듯한 이유 = 관계 차수.**
- 작가님이 "절대량보다 속도를 우려"한 게 정확 — 속도의 진짜 비용은 문서 수가 아니라 *관계 차수 증가율*.
- **트리거 신호**: 다음 라운드의 트리거는 용량 임계가 아니라 *관계 차수가 1인(작가님) 인지 추적 한계를 넘는 순간*. 활성 PF 21개 = 그 임계 근처.

## 2. 축 A — 관계 retrieval (네비게이션 DB) 《본체》

### 2-1. 개념 (3계층)
- **L1 Hot (자동로딩)** — CLAUDE.md·MEMORY.md·rules. 현행 유지, 토큰예산 큐레이션.
- **L2 Index (신설, on-demand retrieval)** — cold 전체를 검색·관계 추적 가능하게. **원본 무변경, 포인터 인덱스만 별도 생성.** MCP로 노출 → 전 디바이스가 막힐 때 자연어로 cold 호출.
- **L3 Cold (보존)** — git 레포 그대로. 불가침. 인덱스는 L3를 가리키기만.

### 2-2. 왜 그래프인가 (관계 폭증의 해법)
- 검색("어디 있나")은 노드를 찾고, 그래프("무엇과 엮이나")는 관계를 푼다. PF 충돌 시 단서 추적 = 후자.
- 그래프가 폭증을 견디는 2원리: ① 답 탐색 시 전체가 아닌 **선 몇 개만 순회**(탐색비용 비폭증) ② 관계는 균일이 아닌 **클러스터링**(주제축으로 뭉침) → 엣지는 O(n²)이나 의미 패턴(community)은 훨씬 느리게 증가 → "PF가 낱개 점이 아니라 몇 개 패턴으로 함께 호출"(서브그래프 검색).
- "SQL급으로 가자"던 과거 직관의 진화형 — 문제가 관계 차수로 바뀌어 답이 관계형 SQL → **그래프 쿼리**(선언적: 원하는 패턴만 명시, 순회 공정은 엔진)로 진화.

### 2-3. 우리만 가능한 이유 — 스키마 선견 (자산 회수)
- **생성 시점 구조화(structure-at-write)**: 작가님이 기초부터 수발신 헤더·PF 귀속·파일 네이밍·세션로그를 *작성 순간에* 박음 = 데이터 엔지니어링에서 가장 비싼 부분을 **선지불**. 남들은 무구조로 쌓고 사후 파싱(ETL 지옥) → 추론 부정확·고비용. 우리는 당사자가 작성시 100% 정확히 박음.
- **실측 — 잠재 그래프 엣지 밀도** (orders+reports+proposals 1,423건): `from:` 84% · `to:` 83% · `date:` 96% · `portfolio:` 22%.
  - from/to = 방향 엣지, date = 시간축이 **이미 데이터에 잠재**. 네비게이션의 "도로망"이 80% 깔린 상태.
  - 🟡 `portfolio:` 22% = 노드 클러스터링 축의 구멍. **Phase 0 보강 1순위.**
- **PF/세션로그 2계층**: PF=현재상태(view), 세션로그=원본 이벤트로그(raw, append-only) = event sourcing. 둘 다 있어야 감사+재구성 가능. 작가님의 "중복 기록" 집착 = 본능적 event sourcing 구현.

### 2-4. 로드맵
| Phase | 내용 | 산출 | 공수 | 비고 |
|-------|------|------|------|------|
| **P0 스키마 정돈** | `portfolio:` 소급 보강, frontmatter 정규화(엣지 어휘 완성) | 스키마 점검 스크립트 | 소 | 단어장 채우기. 선언 질의의 전제 |
| **P1 관계 인덱스 MVP** | frontmatter→그래프 엣지 materialize + BM25 + 메타필터. 임베딩 없이 즉시 가치 | 로컬 인덱스(sqlite-vec/LanceDB) | 중 | type/PF/날짜/수발신으로 호출 |
| **P2 의미검색** | 임베딩 + 하이브리드(BM25+vector, RRF) + Contextual Retrieval(Anthropic) | 벡터 인덱스 | 중 | self-host 임베딩(주권) |
| **P3 agentic** | MCP 서버 노출 → 쿼리 재작성·다단계 순회 | mcp__monk-memory | 중 | 전 디바이스 공통 접근 |

- 증분 자동 인덱싱: git post-commit 훅 → **생성 자동화에 정리 자동화를 같은 트리거로** (사람/Opus 세션 0 소진 — 세션소진 교훈 준수).
- 주권: 임베딩·벡터스토어 self-host 우선(LanceDB/sqlite-vec + bge/nomic). 코퍼스를 벤더 API에 통째 위임 안 함 (MONK OS 주권 원칙). 정확도 부족 시 부분 교체 옵션.

## 3. 축 B — 스토리지 tiering (git 위생) 《독립 트랙》

### 3-1. 실측
- `.git` **1.2G** (size-pack 251M). 워킹트리: **apps 3.8G · monkos_AI 1.2G** · monkos-ops 673M.
- **문서(.md) 전체 ~50M** — git 비대와 무관. **범인 = 코드·이미지·빌드 산출물·PoC.**

### 3-2. 조치 (문서 제외, 바이너리만)
- 빌드 산출물·`node_modules`·캐시 `.gitignore` 점검 (히스토리 유입 차단).
- 무거운 이미지·모델 파일 **git-lfs** 이관 검토.
- 죽은 PoC(apps 내) **아카이브 레포 분리** 또는 cold 보관 — 단 삭제 아닌 이관(보존).
- 효과: clone/pull 경량화, 신규 디바이스 셋업·멀티디바이스 동기화 비용↓.
- ⚠️ 히스토리 재작성(filter-repo 등)은 파괴적 — 별도 승인·백업 전제. 본 제안은 **증분 차단 + 이관**까지만 권고, 과거 히스토리 청소는 별건.

## 4. 효과 (3관점 통합)

1. **회수(검색)**: 죽은 문서가 단서로 호출됨. PF 관계·사고 유사도 추적. grep 더듬기 → 선언 질의.
2. **용량(git)**: 축 B로 1.2G 경량화. 문서는 무관(보존).
3. **1인 인지부하**: 관계 추적을 머리→시스템 위임. 관리 부담을 데이터 양과 **디커플**. 레포·PF 증가에도 관리 인플레 선형 유지 = 1인 운영의 지속가능성.

## 5. 비범위 (안 하는 것)

- 회수율 낮다고 폐기하는 접근 **철회**(민아 1차 제안 자기 철회). 측정 결과는 폐기 트리거가 아니라 인덱스 설계 입력.
- git 히스토리 파괴적 재작성 — 본 제안 범위 밖(별도 승인).
