## 1. 정합 판독 — 철창이 방향 vs 어제 킷

결론부터: **척추는 이미 일치한다.** 철창이가 제시한 "측정 → 증명 → 시스템 납품" 구조는 킷에 대부분 선반영돼 있다. 갭은 4개이며, 전부 보강 가능한 층위다.

### 일치 (킷에 이미 있음)

| 철창이 제안 | 킷 반영 위치 |
|------------|-------------|
| 역지사지 진단(미끼) — 계약 전 상대 도메인 실측 | KIT A §2 "계약 전 무료 미니 감사" 6항목 |

### 갭 (철창이가 맞고, 킷에 없는 것)

1. **살아있는 대시보드 납품이 없다.** KIT B 산출물이 "PDF+스프레드시트"로 명시돼 있다. 철창이 지적대로 이건 "리포트를 파는" 형태다. 클라이언트 도메인 위에서 계속 돌아가는 측정기가 우리의 실제 무기인데 산출물 규정이 그걸 못 담았다.
2. **측정기가 제품이 아니라 계측이다.** 현 측정 스택(GA4+GSC+Ads+데이터랩)은 몽크스 퍼널 전용으로 계측된 물건. 도메인만 갈아끼우면 재조준되는 config 기반 멀티테넌트 추상화가 없으면 "납품"이 아니라 매번 수공업이다.
3. **해석 엔진이 사람 머릿속에만 있다.** 7/19 방향설정 제안서가 해석 엔진의 실물 샘플(실측→판단 3개→방향→4주 게이트)인데, 이건 일회성 문서지 반복 가능한 스키마가 아니다. "관측은 상품화됐고 해석은 렌트 불가"가 경쟁 지형의 결론이라면, 우리 해석을 자산으로 쌓는 구조가 있어야 한다.
4. **경쟁 지형 인텔이 내부 문서에 없다.** Semrush/Ahrefs(전통+AI 레이어), Profound(GEO 전용 리더) 등 철창이가 가져온 지도 — 킷 포지셔닝의 전제인데 어디에도 적립 안 됨. 단, 철창이 수치(시리즈C 규모·기업가치 등)는 **본문 인용 전 재검증 필수** (README "미확정 정직 표기" 원칙 준용).

## 2. 핵심 인사이트 — 경쟁 지형이 확정해주는 우리 자리

철창이 조사의 전략적 함의 3개:

1. **수집 레이어는 이미 상품화(commoditized)됐다.** 10억 달러 밸류에이션 기업이 이미 관측을 판다. "데이터를 수집해드립니다"로 서면 그 링에 오르는 것 — 진다. 수집은 빌려 써도 되는 부품이다(MONK OS 주권 원칙과 동일 구조: 벤더 표준은 부품이지 상위가 아니다).
2. **리더들도 관측에 머문다.** "가시성이 12% 떨어졌다"는 데이터지 결정이 아니다. 해석→실행 번역 레이어는 도메인 맥락+판단이 필요해서 렌트가 안 된다. **여기가 유일하게 방어 가능한 층이고, 우리는 이미 여기서 산다** (V1 소각 판정, 반려 게이트, 4주 게이트 — 전부 해석→실행 실적).
3. **자체 DB의 정의가 바뀐다.** 자체 DB = 키워드 테이블이 아니라 **"우리 시스템이 돌면서만 생성되는 결정 이력"** — 어떤 실측에 어떤 판단을 했고 게이트 결과가 어땠는지. 이건 Profound도 Semrush도 못 가진다. 이걸 쌓는 스키마가 아래 §3-S1이다.

## 3. 도입 스키마 — 4종

### S1. 결정 레코드 (MD: Market Decision) — 해석 엔진의 정형화 ★핵심

관측→해석→실행→결과의 회로를 파일 단위로 적립한다. 7/19 방향설정 제안서의 구조를 반복 가능한 스키마로 추출한 것.

```yaml
---
type: market_decision
id: MD_YYYYMMDD_{슬러그}
date: YYYY-MM-DD
agent: {판독 주체}
status: open | gated | closed
---
observation:      # 실측 사실만. 각 항목에 출처+실측일 필수
interpretation:   # 이 숫자들이 의미하는 것 (판독)
options:          # 검토한 대안과 기각 사유
decision:         # 선택 + 근거
gate:             # 검증 지표 + 기한 (기본 4주)
outcome:          # 게이트 도래 시 실측 결과 (사후 기입, append)
lesson:           # 다음 판독에 반영할 규칙 (사후 기입)
```

- **정본 위치(제안)**: `monkos-ops/ops/decisions/YYYY-MM/` — ch4 파일명 패턴 신설 필요. 법률 개정 사안이므로 쌍아 합의 대상.
- outcome/lesson까지 닫힌 MD 레코드의 누적 = **팔 수 있는 해석 엔진의 원료**이자 제안서 §6 수행 실증의 자동 생성원.
- 즉시 적용 후보: 7/19 제안서의 4주 게이트 5종을 MD 레코드로 이관 개설.

### S2. 테넌트 config — 측정기의 제품화 추상화

측정·순찰 러너가 몽크스 하드코딩 대신 config를 읽게 한다.

```yaml
tenant: monkos          # 테넌트 0 = 우리 자신 (자기 몸 증명 원칙)
domain: monkos.ai
properties:
  ga4: {property_id}
  gsc: sc-domain:monkos.ai
  naver: {서치어드바이저 등록}
conversions: [signup, purchase]    # 2단 전환 정의
keywords_seed: [...]               # 수요 실측 시드
competitors: [...]                 # 경쟁 3~5사
report: {cycle: monthly, locale: ko}
```

- 몽크스가 tenant 0으로 먼저 돌고, 클라이언트는 config 1장 추가로 온보딩 — "도메인만 갈아끼우면 재조준"의 실체.
- PF_CITADEL 대시보드 v0.2 구체화(7/14 제안서)와 접점 — 대시보드 데이터 소스를 tenant config 경유로 설계하면 이중 작업이 없다. **설계 주체는 쌍아**(민아 스코프 밖: 인프라 설계), 본 제안은 요구사항 정의까지.

### S3. KIT B 산출물 갱신 — "살아있는 대시보드" 옵션

- KIT B §3 형식 조항에 추가: STANDARD 이상 = 리포트 + **갱신되는 대시보드**(Looker Studio, 고객 계정 소유로 개설) 납품. 데이터 소스가 고객 소유 GA4/GSC라 원가 0, 차별은 크다.
- KIT A 월간 대시보드도 동일 스택으로 통일 — S2 config가 그대로 데이터 소스.
- 철창이의 "PDF가 아니라 살아 움직이는 대시보드" 지적의 직접 반영. 1시간 내 반영 가능한 문안 수정.

### S4. SEED 프로토콜 — 외부 협업 심사 필터의 양식화

새벽 대화 후반부(씨앗 = 컨텍스트+방향성+레퍼런스)의 운영 편입. 내부 지시서(ORDER) 체계가 이미 이 구조의 내부 구현이므로, **외부 협업자용 변형 템플릿**만 신설한다:

```
SEED_{대상}_{주제}.md
├─ 컨텍스트: 착지 지반 (본체 비공개, 전개 가능한 압축만)
├─ 방향성: 판단 기준선 (뭘 우선하는가)
├─ 레퍼런스: 품질 하한 + 톤
└─ 심사 기준(내부 비공개): "명세의 빈칸을 자기 전문성으로 채웠는가"
```

- 위치(제안): `monkos-ops/ops/templates/SEED_TEMPLATE.md`
- 심사 결과도 S1 MD 레코드로 적립 → "어떤 씨앗에 어떤 반응이 왔는지"가 협업자 DB로 축적 — 새벽 대화의 "자체 DB" 정의와 정확히 맞물린다.
