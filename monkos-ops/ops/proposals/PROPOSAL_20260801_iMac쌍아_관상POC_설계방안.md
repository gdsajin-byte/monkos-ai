## 0. 요약

셀카 1장으로 세 가지를 동시에 뽑을 수 있다 — **관상 지표**, **퍼스널 컬러 샘플**, **면접 인상 코칭**. 셋 다 얼굴 위 좌표·픽셀에서 나오므로 **검출 1회로 3축 산출**이 성립한다. 이것이 이 POC의 실질 레버리지이며, 관상은 그중 가장 재미있는 표면일 뿐 엔진의 본질은 "얼굴 계측 정본"이다.

POC의 진짜 난이도는 AI가 아니라 **DB 스키마 설계**에 있다. 원전 텍스트를 어떤 수치 구간에 어떻게 붙일지가 정해지면 나머지는 노가다다.

## 1. 개념 분리 — 3축은 각각 다른 입력을 먹는다

작가님 원문의 "사주 관상"을 그대로 한 엔진으로 묶으면 설계가 깨집니다. 입력이 다릅니다.

| 축 | 입력 | 셀카로 가능? | 엔진 성격 |
|----|------|------------|----------|
| **관상(觀相)** | 얼굴 이미지 | ✅ 가능 | 랜드마크 → 비율 지표 → 룰 매칭 |
| **사주(四柱)** | 생년월일시 | ❌ 불가 (별도 1줄 입력) | 만세력 계산 (음양력 변환 + 60갑자). 이미지 무관 |
| **퍼스널 컬러** | 얼굴 이미지 픽셀 | ✅ 가능 | 영역 마스크 → 색상 샘플 → Lab 분류 |

**판단**: POC는 **관상 축 단독**으로 간다. 사주는 순수 계산 문제(만세력 DB + 간지 로직)라 얼굴 파이프라인과 공유하는 코드가 0이며, 나중에 독립 모듈로 붙여도 손실이 없다. 퍼스널 컬러는 관상과 **같은 마스크를 공유**하므로 Phase 4에서 저비용 편입.

## 2. 기술 자산 실측 (2026-08-01)

### 있는 것

| 자산 | 실체 | 위치 |

| **106점 랜드마크** | `2d106det.onnx` — `POST /landmarks` 엔드포인트 **이미 가동** | 동일 |

| 인덱스 검증맵 | 눈·코·입·턱·컨투어 인덱스 **교차검증 완료 (delta 0.0px, 07-09)** | `crop-engine/lib/face-detect-insight.js` |
| 정수리 추정 | 눈중심 − (턱 − 눈중심) 공식. **특허 출원 자산** | `crop.js` / PATENT_20260323 |

**즉, 랜드마크 API는 신규 개발 대상이 아니다.** 이미 라이브다.

### ⚠️ 작가님 표현과 현행의 갭

작가님이 말씀하신 **"페이스 메시 점"(MediaPipe FaceMesh 478점)은 현행 정본이 아닙니다.** 07-18 민아 추적에서 확인된 대로 FaceMesh는 `crop-app` 클라이언트 등에 잔존하는 레거시이고, 서버 정본은 **InsightFace 106점**입니다. POC는 106점 위에 세웁니다.

**106점으로 충분한가** — 관상 지표 대부분은 충분합니다. 단 두 가지 결손이 있습니다.

| 결손 | 관상학적 의미 | 대응 |
|------|-------------|------|
| **귀(耳)** 랜드마크 없음 | 오관 중 採聽官(채청관) — 초년운·수명 | 정면 셀카는 원리적으로 귀를 못 봄. **오관→4관으로 축소** or 측면 사진 옵션(Phase 5 이후) |
| **발제(髮際, 헤어라인)** 없음 | 삼정(三停) 상정의 기준선 | 아래 3안 중 택1 — POC 실증 항목 |

**헤어라인 확보 3안**
- (a) 이마 수직 색상 프로파일 급변점 탐지 — 추가 모델 0, 정확도 미검증. 탈모·앞머리·조명에 취약
- (b) 정수리 추정값 기반 비례 근사 — 기존 자산 재활용이나 헤어라인 ≠ 정수리, 오차 큼
- (c) **face-parsing 모델 추가**(BiSeNet 계열, 19클래스에 hair·skin·lips·eyes 포함, 경량) ← **추천**

(c)를 추천하는 이유는 관상 때문이 아니라 **퍼스널 컬러가 같은 마스크를 그대로 먹기 때문**입니다. 모델 1개 추가로 삼정 기준선 + 피부/입술/모발/홍채 색상 샘플 영역이 동시에 해결됩니다. 한 축만 보면 과투자, 두 축을 보면 정확히 맞는 투자입니다.

## 3. POC 범위 정의

### 하는 것
1. 106점 → **관상 지표 계산기** (수치 12~18종)
2. **원전 룰 DB** (JSON 정본) — 지표 구간 → 원문 인용 + 해석
3. **인터랙트 UI** — 얼굴에 부위 오버레이 + 클릭 시 해당 원문·해석 표출 (작가님 원문의 "도식")
4. 정면성 게이트 재사용 (기존 `gate` 그대로) — 부적합 셀카는 명시 반려

### 안 하는 것 (POC 범위 밖, 명시)
- 사주 만세력 (별도 모듈)
- 귀(採聽官) 판정
- 결제·크레딧 연동 (POC는 무료 표면으로 실증)
- 다국어 (ZH는 원문이 한문이라 오히려 쉬우나 POC는 KO 단일)

## 4. DB 설계 — 이 POC의 본체

### 4-1. 지표 스키마 (계산기 출력)

원전 용어를 그대로 수치 이름으로 씁니다. 코드와 원문이 같은 단어를 쓰면 매핑 사고가 사라집니다.

| 구분 | 지표 | 산출 |
|------|------|------|
| **삼정(三停)** | `upperRatio` 상정 | 발제~인당 / 전체 |
| | `middleRatio` 중정 | 인당~준두 / 전체 |
| | `lowerRatio` 하정 | 준두~지각 / 전체 |
| **오행형(五行形)** | `faceShape` | 컨투어 1~17 → 목·화·토·금·수 5형 분류 |
| | `widthHeightRatio` | 관골 폭 / 얼굴 높이 |
| **눈(監察官)** | `eyeLengthRatio` | 눈 가로 / 얼굴 폭 |
| | `eyeSlantDeg` | 내안각→외안각 각도 (봉안·삼백안 판별축) |
| | `eyeSpacingRatio` | 양안 간격 / 눈 길이 (원전 "1눈 간격" 기준) |
| **눈썹(保壽官)** | `browLengthRatio` | 눈썹 길이 / 눈 길이 |
| | `browEyeGapRatio` | 눈썹~눈 거리 (원전 田宅宮) |
| **코(審辨官)** | `noseLengthRatio` | 산근~준두 / 중정 |
| | `noseWingRatio` | 콧방울 폭 / 얼굴 폭 |
| **입(出納官)** | `mouthWidthRatio` | 입 폭 / 얼굴 폭 |
| | `lipThicknessRatio` | 상순·하순 두께 비 |
| **부위** | `philtrumRatio` 인중 | 인중 길이 / 하정 |
| | `chinRatio` 지각 | 턱 높이 / 하정 |
| **품질** | `frontality` | 기존 gate 재사용 — 신뢰도 표기용 |

⚠️ 눈썹·콧방울·인중의 106점 인덱스는 **아직 검증되지 않았습니다.** 눈·코끝·입·턱·컨투어만 07-09에 delta 0.0px로 확정된 상태입니다. **Phase 1 첫 태스크 = 미확정 인덱스 오버레이 실측 확정**입니다. (교훈 준용: 헤더·설정값은 능력의 증거가 아니다 — 인덱스도 문서가 아니라 오버레이로 실증)

### 4-2. 룰 DB 스키마 (원전 정본)

`specs-data.json` 패턴을 그대로 따릅니다 — 정적 JSON 정본, 코드에 분산 정의 금지.

```json
{
  "id": "sanjeong_upper_long",
  "part": "삼정/상정",
  "metric": "upperRatio",
  "range": [0.36, 1.00],
  "source": {
    "book": "마의상법(麻衣相法)",
    "chapter": "三停論",
    "quote": "上停長者 少年得志",
    "license": "public-domain"
  },
  "reading": { "ko": "이마가 넓고 반듯하면 초년의 학업·시작운이 순조롭다는 해석." },
  "tone": "positive",
  "confidence": "high",
  "interview_tip": { "ko": "이마가 드러나는 헤어스타일이 신뢰 인상에 유리합니다." }
}
```

**필드 설계 근거**
- `source` 필수 — 원전 인용 없는 해석은 등재 금지. 작가님의 "엉터리가 아닌 정통 학문 기반" 요건을 스키마 레벨에서 강제
- `license: public-domain` — 마의상법·신상전편·유장상법은 저작권 만료. 현대 저술 인용 금지를 필드로 못박음
- `tone` — 부정적 단정 배제 규칙의 훅 (§7 참조)
- `interview_tip` — 취업 축 연결점. 관상 해석과 **분리된 필드**로 둬야 "관상 = 채용 근거"로 읽히지 않음

### 4-3. 저장소 판단

정적 JSON 정본 (`portal/data/physiognomy-rules.json`). Firestore 불필요 — 룰은 읽기 전용이고 배포 단위로 갱신되며, specs가 같은 구조로 3,500+ 페이지를 이미 운용 중입니다. 사용자별 결과 저장이 필요해지는 시점(Phase 4 이후)에만 Firestore를 검토합니다.

## 6. 취업·퍼스널 컬러 연결 설계

작가님 지시의 "취업 이력서 사진과 연결"은 두 방향이 있고, **방향을 잘못 잡으면 브랜드 사고**가 납니다.

- ❌ **잘못된 연결**: "관상 판정 → 이 얼굴은 취업에 유리/불리" — 외모 차별 논란 직결
- ✅ **옳은 연결**: "계측 결과 → **연출 코칭**" — 헤어라인이 가려져 있다 / 시선 각도 / 표정 대칭. 얼굴을 평가하는 게 아니라 **사진 연출을 조언**

후자는 이미 MONKOS가 하고 있는 일(촬영 코칭 `coaching.js`)의 자연스러운 확장이고, 관상 DB는 그 조언에 **문화적 서사**를 입히는 레이어가 됩니다. 관상이 판정관이 아니라 이야기꾼 위치에 서야 합니다.

퍼스널 컬러는 face-parsing 마스크(피부·입술·모발·홍채) → sRGB 샘플 → Lab 변환 → 웜/쿨·명도·채도 분류. **화이트밸런스가 최대 난제**입니다(조명이 결과를 뒤집음). 흰자(sclera)를 기준 백색점으로 삼는 보정 트릭이 있으나 **실증 전까지 정확도를 주장하지 않습니다.**

**8월 취업 패키지와의 관계**: 민아가 오늘 오전 제언한 "8월 단일 베팅 = 취업사진 프리미엄 패키지"와 이 POC는 충돌하지 않습니다. Phase 5(면접 인상 코칭)가 정확히 그 패키지의 차별화 훅이 되기 때문입니다. 다만 **Phase 1~3은 패키지와 독립된 선행 투자**이므로, 8월 자원 배분상 어느 쪽이 앞인지는 작가님 결정 사항입니다 (결정 요청 ③).
