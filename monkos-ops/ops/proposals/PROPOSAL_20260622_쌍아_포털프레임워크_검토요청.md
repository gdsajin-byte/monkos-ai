# 제안서: 포털 프론트엔드 프레임워크 검토 요청

## 배경 — 왜 지금인가

6/22 세션에서 포털 home.js(510행)의 replace 체인 방식이 실제로 깨졌다. 텍스트팩(P1-b) 치환과 Firestore 동적 콘텐츠(FAQ, 블로그) 삽입이 같은 replace 체인에서 순서 충돌 → 영어 페이지에 한국어 FAQ가 잔존.

이건 home.js만의 문제가 아니라 **현 아키텍처의 한계**:
- 모든 SSR 렌더 함수가 HTML 문자열 조립 → replace로 데이터 주입
- 페이지마다 중복 패턴 (render-headshot, render-pricing, render-static 등 각각 독립)
- 상태 관리 없음 (DOM 직접 조작)
- 디자인 시안 적용 = HTML 문자열 수동 매핑

그런데 지금 예정된 작업들:
- **클로드 디자인 시안 → 포털 메인 리뉴얼** (즉시)
- **어드민 대시보드 확장** — 유저 상세, 타임라인, 실시간 뷰 (D5~D7)
- **마이페이지** — 유저 히스토리, 크레딧, GCS 파일 갤러리
- **언어 스위처 UI** (P2)

바닐라로 시안 입힌 뒤 프레임워크 전환하면 **이중 작업**. 프레임워크 결정 먼저 → 시안을 새 스택으로 적용이 올바른 순서.

## 민아에게 요청하는 것

**포털 프론트엔드 프레임워크 도입 여부 + 후보 비교 + 전환 전략 제안서** 작성.

### 검토 범위

1. **후보 비교** — 최소 아래 포함:
   - React (Next.js SSR) — 생태계 최대
   - Svelte (SvelteKit) — 경량, 빌드 최적
   - Astro — SSR 특화, 아일랜드 아키텍처
   - 바닐라 구조화 — 프레임워크 없이 컴포넌트 패턴만 도입
   - 기타 민아 판단에 따라

2. **우리 제약 조건** 반영:
   - ch2 코딩 규칙 "순수 JS, 새 프레임워크 도입 시 설계 선행 필수"
   - SSR 필수 (SEO + 첫 페이지 로드)
   - Cloud Run Node.js 배포
   - 에이전트(막내) 학습 비용 — 지시서 방식 변경
   - 클로드 디자인 시안 연동 — 디자인 → 코드 파이프라인
   - 기존 코드 자산 (render 함수 20+개, CSS, auth, credits 등)

3. **전환 전략** — 현실적 경로:
   - 신규 페이지만 (마이페이지, 대시보드 확장) vs 전체
   - 점진 교체 (기존 렌더 함수 하나씩 전환) vs 일괄
   - 전환 중 기존 서비스 연속성 보장 방법

4. **판정 기준** — 왜 이걸 고르는가:
   - 디자인 적용 속도 (시안 → 코드 전환 비용)
   - 에이전트 지시서 작성 편의 (컴포넌트 단위 지시 가능성)
   - SEO 영향
   - 배포 복잡도 변화
   - 바닐라 유지 옵션의 한계선 (어디까지 버틸 수 있는가)

## 왜 민아인가

코더(쌍아/막내)는 자기가 익숙한 스택에 편향된다. 민아는 코드를 안 쓰니까 기술 선호 없이 **사업·운영 관점에서** 판단할 수 있다. 감사 본령(6/14 작가님 확정)의 연장.
