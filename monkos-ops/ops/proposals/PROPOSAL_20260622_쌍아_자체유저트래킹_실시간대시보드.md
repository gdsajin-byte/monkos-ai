# 제안서: 자체 유저 트래킹 + 실시간 어드민 대시보드

## 배경 — 왜 GA4로는 안 되는가

GA4는 **집계**(어제 headshot 페이지 42명 방문)는 되지만, **유저 단위 스토리**는 못 본다.

6/22 세션에서 실측 확인한 케이스:
- `kakao_4817724214` (map3939@naver.com) — **3/27 가입 → 증명사진 프리뷰만 확인(무과금) → 87일 공백 → 6/21 재방문 → 결제(₩9,900) → 증명사진 생성+다운로드(generate -10c + download -70c)**
- 이 리텐션 전환 스토리를 재구성하는 데 Firestore 직접 조회 + GCS 버킷 수동 탐색 + 토스 영수증 대조가 필요했음
- 어드민 대시보드에서는 이 유저가 결제했는지조차 식별 불가 (크레딧 0으로 표시 = 무료 유저와 구분 안 됨)

현재 상태:

| 있는 것 | 한계 |
|---|---|
| GA4 퍼널 센서 (6/12 삽입) | 페이지 단위 집계만. 유저 매핑 안 됨 |
| Firestore transactions | 결제/사용 기록 쌓임. 페이지 동선 없음 |
| Firestore users | 가입·크레딧만. 행동 이력 없음 |
| Telegram 알림 | 가입/결제 시점 알림. 히스토리 미보존 |
| 어드민 대시보드 | 유저 목록 + 크레딧 분포. 결제 유저 구분 불가, 동선 없음 |

## 목표

**포털 + 각 서비스의 모든 페이지에서 유저 행동을 자체 수집하고, 어드민에서 실시간으로 한눈에 보는 것.**

구체적으로:

1. **가입자 명단** — 결제 이력(총액, 최근 결제일, 결제 횟수) 포함. 결제 유저 즉시 식별
2. **유저별 타임라인** — 클릭 한 번으로 해당 유저의 전체 행동 이력 조회
3. **유저 동선** — 페이지 진입 → 기능 사용 → 이탈 지점까지 경로 추적
4. **비가입자 동선** — 로그인 전 세션도 sessionId 기반 추적. 가입 시 기존 세션과 머지
5. **실시간** — 현재 활성 유저, 현재 페이지, 최근 이벤트 스트림

## 수집 이벤트 설계 (안)

### 서버단 (SSR 요청 — 확실한 페이지 진입)

| 이벤트 | 시점 | 데이터 |
|---|---|---|
| `page_view` | 모든 SSR 렌더 | path, lang, userId/sessionId, referer, userAgent |
| `auth_login` | 로그인 성공 | userId, provider, sessionId(머지용) |
| `auth_signup` | 가입 | userId, provider, email |
| `credit_charge` | 결제 확인 | userId, amount, provider(toss/lemon), credits |
| `credit_use` | 크레딧 사용 | userId, amount, type(generate/download), service |
| `api_generate` | AI 생성 요청 | userId, service(idphoto/headshot), style, inputSize |

### 클라이언트단 (인터랙션 — 버튼 클릭, UI 전환)

| 이벤트 | 시점 | 데이터 |
|---|---|---|
| `click_cta` | CTA 버튼 클릭 | buttonId, page, userId/sessionId |
| `upload_image` | 사진 업로드 | page, fileSize, resizedSize |
| `select_style` | 스타일 선택 | style, page |
| `open_credit_shop` | 충전 모달 오픈 | currentCredits, page |
| `start_payment` | 결제 시작 | package, amount |
| `session_end` | 탭 닫기/이탈 | lastPage, duration, userId/sessionId |

### 비가입자 추적

- 첫 방문 시 `monkos_sid` 쿠키(UUID) 발급
- 모든 이벤트에 sessionId 포함
- 가입/로그인 시 해당 sessionId의 과거 이벤트를 userId에 머지

## 저장

| 선택지 | 장단점 |
|---|---|
| **Firestore `events` 컬렉션** | 현재 인프라 그대로. 쿼리 유연. 비용은 쓰기 건수 비례 |
| **BigQuery 스트리밍** | 대량 분석 최적. 초기 세팅 필요. GA4 raw 데이터와 조인 가능 |
| **Cloud Logging → BigQuery** | 서버 로그 기반. 코드 변경 최소. 실시간성 약간 지연 |

→ 민아 설계 시 판단. 초기는 Firestore, 규모 커지면 BigQuery 전환이 현실적일 수 있음.
