# 입법 심사 보고서: PF(포트폴리오) 체계 개헌

> **[2026-03-26 11:20 KST] iMac/막내1 → iMac/쌍아**

---

## 총평

**조건부 통과를 권고한다.**

PF 체계는 현행 세션 로그 체계가 본질적으로 해결할 수 없는 "프로젝트 횡단 상태 추적" 문제를 정확히 겨냥하고 있으며, 기존 법체계와의 충돌이 없다. 다만, 헌법 개정안에서 "세션 로그와 동급의 의무"라는 표현의 모호성을 해소하고, PF 갱신 품질을 담보할 최소 기준을 법률에 명시할 것을 조건으로 제시한다. 아래 6개 항목별 상세 검토 결과를 보고한다.

## 1. 목적 정합성

### 판정: 적합

PF가 겨냥하는 4대 문제를 개별 검증한다.

| 문제 | PF로 해결되는가 | 근거 |
|------|----------------|------|
| 에이전트마다 프로젝트 해석이 달라짐 | **해결** | PF Phase 현황 = "지금 뭘 해야 하는지"의 단일 정본. 세션 로그 재구성 불필요 |
| 컴팩팅 후 맥락 유실 | **해결** | 지시서 `portfolio:` 필드 → PF 1회 Read로 전체 상태 복원. 컴팩팅 방어의 핵심 |
| 리팩토링 타임라인 추적 불가 | **해결** | PF 히스토리(append-only) = 프로젝트 축 인과 체인. 세션 단위 절단 없음 |
| 기술명세 체계 미안착 | **부분 해결** | 관련 문서 인덱스로 SPEC/ORDER/REPORT를 PF에 귀속. 다만 SPEC 자체의 품질은 PF 범위 밖 |

### "세션 로그를 더 잘 쓰면 되지 않나?"에 대한 답변

**불가능하다.** 세션 로그와 PF는 축이 다르다.

- 세션 로그: **에이전트 × 날짜** 축 — "막내1이 3/26에 무엇을 했다"
- PF: **프로젝트** 축 — "CITADEL이 지금 어디까지 왔다"

프로젝트 10개가 에이전트 5명에 흩어져 있으면, 세션 로그를 아무리 잘 써도 "프로젝트 X의 현재 상태"를 파악하려면 최소 수십 개 세션 로그를 크로스 참조해야 한다. 이것이 PF_CITADEL.md의 히스토리 81행에 자연스럽게 기록되어 있다면, Read 1회로 끝난다.

### PF가 있어도 해결되지 않는 맹점

- **PF 갱신 품질**: PF를 갱신하는 에이전트가 부실하게 기록하면 PF도 부정확해진다. 다만 이는 세션 로그에도 동일하게 적용되는 문제이며, PF 고유의 맹점은 아니다.
- **PF 미귀속 작업의 누락**: 단발성 패치가 사후에 특정 PF에 영향을 미치는 경우, 히스토리에 기록되지 않을 수 있다. 이는 사후 보정으로 대응 가능하며, 청구안 3-4절에서 "방향 흐려지면 PF 재참조"를 에이전트 자율 판단으로 두고 있어 합리적이다.

## 2. 의무 수준의 적절성

### 판정: 적절하나, "동급"의 의미 명확화 필요

**세션 로그 vs PF 갱신 빈도 비교:**

| 항목 | 세션 로그 | PF |
|------|----------|-----|
| 갱신 빈도 | 매 턴 어펜드 | 세션 마감 시 어펜드 |
| 갱신 주체 | 각 에이전트 자체 | 해당 PF 작업을 수행한 에이전트 |
| 갱신 범위 | 전 작업 (PF 무관 작업 포함) | 해당 PF 귀속 작업만 |
| 원본 수정 | 금지 (append-only) | 히스토리: 금지. Phase 현황: 상태 갱신 허용 |

"동급의 의무"를 부여한다는 청구안의 표현은 **의무의 "무게"가 동급**이라는 뜻으로 해석해야 한다. 갱신 "빈도"가 동급이라는 뜻이 아니다. 이 구분이 불명확하면 에이전트가 매 턴 PF를 갱신해야 하는 것으로 오해할 수 있다.

**권고:** 헌법 개정안 제3조 2항의 "세션 로그와 동시에 갱신한다"를 **"세션 마감 시 갱신한다"**로 명확히 표기할 것. 이미 법률(ch3 3조 개정안)에서 세션 마감 절차의 2번째 단계로 배치하고 있으므로 일관성 확보.

**의무 위반 시 제재:**

현행 체계에서 세션 로그 미작성의 명시적 제재도 "작가님의 멀티 에이전트 관제 불가"(결과 서술)이다. PF도 동일한 수준으로 충분하다. 별도 페널티 체계를 도입하면 오히려 과도하다.

**법률 vs 헌법 배치:**

청구안은 헌법에 원칙을, 법률(ch3)에 절차 상세를 배치하고 있다. 이 구조가 적절하다. 헌법에 갱신 시점·형식 같은 세칙을 넣으면 경직되어 향후 운용 변경 시마다 개헌이 필요해진다.

## 3. 대안 검토

| 대안 | 장점 | 단점 | PF 대비 |
|------|------|------|---------|
| **A. 세션 로그에 "프로젝트 상태 섹션" 추가** | 추가 문서 없음, 기존 체계 활용 | 에이전트별 중복 기록, 정본 불명확(어느 에이전트 로그가 정본?), 프로젝트 10개면 세션 로그 비대화 | PF가 우위 — 정본 단일 원칙(헌법 3조 4항)에 부합 |
| **B. CLAUDE.md에 활성 프로젝트 상태 기재** | 자동 로딩, 컴팩팅 무관 | CLAUDE.md = 불변 원칙(헌법). 매 세션 수정은 체계 위반. git 공유이므로 병합 충돌 빈번. 비대화 필연 | PF가 우위 — CLAUDE.md는 정책 시트이지 상태 문서가 아님 |
| **C. .claude/rules/에 프로젝트별 룰 파일** | 자동 로딩 가능 | Rules = "행동 규칙"이지 "상태 문서"가 아님. 성격 혼재. append-only 히스토리를 Rules에 넣는 것은 부적합. Rules는 짧아야 동작 | PF가 우위 — 청구안이 "Rules는 행동, PF는 상태" 분리를 명시(3-2절) |
| **D. 외부 도구 (Linear, Notion)** | 전문 PM 도구 | 에이전트 직접 접근 불가(MCP 없이는), 정본이 Git 밖으로 분산, 헌법 3조 4항(정본 단일) 위반 | PF가 우위 — Git 내 md 파일이 에이전트 접근성 최적 |
| **E. MEMORY.md에 프로젝트 상태 기재** | 디바이스별 자동 로딩 | 200줄 캡. 디바이스별 분산 = 정본 다중화. 프로젝트 3개만 되어도 용량 초과 | PF가 우위 — MEMORY.md는 에이전트 행동 강령이지 프로젝트 추적 문서가 아님 |

**결론:** 5개 대안 모두 PF 대비 구조적 열위. PF가 가장 적합한 방안이다. 특히 대안 A·B·C는 기존 문서의 성격을 변질시키는 문제가 있고, 대안 D는 에이전트 접근성 문제를 본질적으로 해결하지 못한다.

## 4. 기존 법체계 정합

### 충돌 지점: 없음

| 검토 대상 | 충돌 여부 | 분석 |
|----------|----------|------|
| 헌법 3조 4항 (정본 단일 원칙) vs PF 히스토리/세션 로그 이중화 | **충돌 없음** | 세션 로그와 PF는 **다른 문서 유형**이다. 같은 사건이 양쪽에 기록되지만, 관점과 구조가 다르다 — 세션 로그는 에이전트 관점 시간순, PF는 프로젝트 관점 상태 중심. "동일 문서의 정본이 둘"이 아니라 "다른 문서가 같은 사건을 참조"하는 것이다 |
| ch4 2조 3항 (문서 정본 이중화 금지) | **충돌 없음** | 위와 동일. PF와 세션 로그는 type이 다름 (portfolio vs session). 2조 3항은 "동일 문서가 docs/와 ops/ 양쪽에 정본으로 존재"를 금지하는 것 |
| PF "관련 문서 인덱스" vs ch4 4조 정본 테이블 | **충돌 없음** | ch4 4조 = 문서 유형별 정본 위치 규칙(범용). PF 인덱스 = 해당 PF에 귀속된 산출물 링크 모음(프로젝트별). 성격이 다르며, PF 인덱스는 정본 위치를 재정의하지 않는다 |
| 헌법 3조 2항 (분산 기록 원칙) | **정합** | 세션 로그는 에이전트별 분산 기록(각자 자기 것만 기록). PF는 프로젝트별 단일 문서(해당 PF 작업을 수행한 에이전트가 갱신). 원칙이 다르므로 상충하지 않음 |
| ch3 1조 (원본 수정/삭제 절대 금지) | **정합** | PF 히스토리도 append-only. Phase 현황의 상태 갱신은 "원본 수정"이 아니라 "현재 상태 반영"이다. 세션 로그의 본문 수정과는 성격이 다름 |

### 보충: PF Phase 현황의 "갱신"과 append-only 원칙

청구안은 히스토리를 append-only로, Phase 현황은 "완료·착수·변경 시 즉시 갱신"으로 구분한다. Phase 현황의 갱신은 ch3 1조의 "원본 수정 금지"와 외형상 긴장이 있으나, Phase 현황은 **현재 상태를 반영하는 대시보드**이지 **기록물**이 아니므로, 세션 로그의 append-only 원칙과는 적용 대상이 다르다. 이 구분을 법률에 명시하면 혼동 방지에 도움이 된다.

## 5. 네이밍·분류

### 판정: 적절

**"포트폴리오" 명칭:**

| 관점 | 평가 |
|------|------|
| 일반적 의미 | "작품 모음" — 약간의 의미 갭 있음(PF는 단일 프로젝트 문서) |
| 작가님 의도 | "제안부터 완성된 작품의 의미를 중의적으로 보유" — 사진관 사업의 정체성과 부합 |
| 대안 대비 | PROJECT(너무 일반적), INITIATIVE(어색), PROGRAM(대규모 느낌), EPIC(애자일 특화) — 어느 것도 "기안→완성 작품"의 뉘앙스를 담지 못함 |
| 판정 | **작가님 확정 명칭. 적합.** |

**`PF_` 접두사, `portfolios/` 경로:**

- 기존 패턴(ORDER_, REPORT_, SPEC_, INCIDENT_ 등)과 일관성 확보
- `monkos-ops/ops/portfolios/` — ops/ 하위 배치가 적절 (프로젝트 관리 = 운영)
- ch4 3조 패턴 #15, ch4 4조 정본 테이블, ch4 7조 YAML type에 이미 등록 완료

**domain 필드 허용값:**

현행: `PORTAL | CONTENT | SEO | INFRA | AUTH | STUDIO | CROP | AGENT | MARKETING`

- 현행 서비스 약칭(ch4 5조)과는 별개 체계 — domain은 "분야"이고, 서비스 약칭은 "배포 대상". 이 분리가 적절하다.
- **누락 가능성**: GOVERNANCE(법률 개정 프로젝트), OPS(운영 체계 프로젝트), FINANCE(자금·결제 관련) 등이 빠져 있다. 그러나 PF는 주로 기술·콘텐츠·마케팅 프로젝트에 사용될 것이므로 당장은 충분하다.
- **권고**: domain을 enum이 아닌 **개방형 + 권장값**으로 두면 확장에 유연하다. 법률(ch4 7조)에 "허용값은 PF_TEMPLATE.md를 참조"로 두고, 템플릿에서 권장값 목록을 관리하는 방식을 제안한다.

## 6. 확장성·미래 리스크

### 6-1. PF 증가에 따른 관리 부하

| 시나리오 | PF 수 | 활성 PF | 관리 부하 |
|----------|-------|---------|----------|
| 현재 | 1 | 1 | 무시 가능 |
| 6개월 후 | 5~8 | 3~4 | 세션 마감 시 1~2개 PF 갱신. 세션 로그 미만 |
| 1년 후 | 15~20 | 3~5 | 세션 마감 시 여전히 활성 PF만 갱신. completed PF는 참조만 |

세션 로그는 **에이전트 × 일수**로 증가 (5에이전트 × 365일 = 1,825파일/년). PF는 **프로젝트 수**로 증가 (연 15~20건 예상). PF가 세션 로그 이상의 관리 부하가 되는 것은 구조적으로 불가능하다.

### 6-2. 위성 환경 동시 갱신 충돌

- PF는 `monkos-ops/` (main 브랜치, 단일)에 존재
- 같은 PF를 두 디바이스가 동시에 갱신할 확률은 낮음 — 지시서로 작업이 배분되므로
- 히스토리가 append-only이므로 git 병합 충돌이 발생해도 양쪽 행을 모두 포함하면 해소됨
- **리스크: 낮음.** 현행 세션 로그의 병합과 동일한 수준

### 6-3. PF 아카이빙 정책

- status: completed로 전환 후 `portfolios/` 폴더에 영구 보존
- 삭제 금지 (works 삭제 금지 원칙과 일관)
- 30건 이상 누적 시 `portfolios/YYYY/` 서브폴더 도입을 검토할 수 있으나, 현재로서는 불필요
- **권고**: "PF 아카이빙 정책은 30건 초과 시 협의"를 세칙에 명시해두면 미래 대응이 수월

### 6-4. PF 파일 비대화 리스크

PF_CITADEL.md가 이미 249행. 히스토리가 계속 쌓이면 500행, 1000행으로 증가할 수 있다.

- **대응**: 청구안에서 "과거 Phase는 접기 가능"으로 언급. 구체적으로는 Phase 완료 시 해당 Phase 항목 테이블을 `<details>` 태그로 접거나, Phase별 행 수 가이드라인(예: 50행 초과 시 요약 테이블로 축약)을 세칙에 둘 수 있다.
- **리스크: 중간.** 1년 후 활발한 PF는 500행 이상이 예상되므로, 비대화 대응 가이드라인을 법률에 명시할 것을 권고한다.

| 3 | PF 운용 세칙 3-4 | 미갱신 = "적립 의무 위반" | **"동급의 의무"를 "의무의 무게가 동급"으로 주석** 또는 법률에 명확한 문구 | 빈도 동급으로 오해 방지 |
| 4 | PF 템플릿 domain | enum 목록 | **개방형 + 권장값** (GOVERNANCE, OPS, FINANCE 추가 권장) | 향후 거버넌스·인프라 프로젝트 PF 수용 |
| 5 | PF 운용 세칙 | 비대화 대응 미명시 | **히스토리 비대화 시 Phase별 접기 또는 요약 가이드라인** | 1년 후 500행+ 예상 |
| 6 | ch3 3조 개정안 | PF 어펜드를 2번째 단계로 배치 | **"해당 PF가 있을 때"를 강조 — PF 없는 세션은 스킵** | 단발성 작업 세션에서 PF 부재 시 혼란 방지 (이미 명시되어 있으나 재강조) |

**수정 #1~3은 필수 권고, #4~6은 선택 권고.**
