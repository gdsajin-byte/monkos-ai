**결론**: ESM 분리 시 CSS를 그대로 복사했기 때문에, v1.0의 이중 스크롤 구조가 v2.0에 **그대로 이전**됨. 분리 과정에서 레이아웃 문제가 새로 생긴 것이 아니라, **기존 기술부채가 그대로 전파**된 것.

## 5. 근본원인 가설 — 왜 반복 재발하는가

### 가설 A: 이중 스크롤 컨테이너 (CSS 구조적 원인) — 확률 40%

**메커니즘**: `.editor-right`(overflow-y:auto) > `.tab-content`(높이 제약 없음) > `#imageLibrary`(max-height:60vh, overflow-y:auto) 3중 구조에서, `.tab-content`가 높이 제약 없이 끼어들면서 내부 그리드 셀의 `aspect-ratio:1` 계산이 왜곡됨.

**근거**:
- 03-19 `388253e` 커밋에서 `.tab-content` 래퍼 삽입이 직접적 트리거
- 03-22 `eafde7c` 커밋에서 flex column + overflow 위임으로 수정

**현재 상태**: eafde7c에서 **구조적으로 수정됨**. CSS 코드 확인 결과 올바른 상태.

### 가설 B: 배포 캐시 — 수정이 프로덕션에 반영되지 않음 — 확률 35%

**메커니즘**: Google Frontend(GFE) 캐시 + 브라우저 캐시가 이전 CSS를 서빙. 코드는 수정되었으나 사용자에게 도달하지 않음.

**근거**:
- M1 세션 로그: "캐시 문제 발견 — Cache-Control 헤더 없이 운용"
- 8회 CSS 시도 중 4번째에서 캐시 문제 발견
- `blog-editor.css?v=20260322d` 수동 캐시 버스팅에 의존
- 배포 URL 불일치 (deploy 명령 출력 URL ≠ 실제 서비스 URL)

**현재 상태**: 캐시 버스팅 파라미터가 `?v=20260322d`로 설정되어 있으나, 서버 측 Cache-Control 헤더 설정 여부 미확인.

### 가설 C: Dev/Prod 환경 불일치 — 확률 15%

**메커니즘**: 수정이 dev에만 배포되고 prod에는 반영되지 않은 상태에서 검증.

**근거**:
- M1 세션 로그: "배포 URL 불일치 — 라우팅 구조 미파악"
- monkos-portal (prod) vs monkos-portal-dev (dev) 분리 운용

### 가설 D: 난독화(obfuscate) 과정에서 CSS 변형 — 확률 10%

**메커니즘**: deploy.sh의 obfuscate.mjs가 CSS/JS를 처리할 때 클래스명이나 속성이 변형됨.

**근거**: 추정만 가능. 실제 obfuscate.mjs 코드 미확인.

1. CSS 수정 후 배포가 prod에 반영되었는지 불확실
2. Google Frontend 캐시가 이전 CSS를 서빙할 가능성
3. 캐시 버스팅 파라미터(?v=) 수동 관리의 불안정성

**권장 조치**:
1. prod 배포 상태 확인 (현재 서빙 중인 CSS 파일이 eafde7c 이후 버전인지)
2. Cache-Control 헤더 설정 확인/추가
3. 캐시 버스팅 자동화 (빌드 해시 기반)
4. `toggleImageLibrary()`의 `display='grid'` → `display=''` (CSS 기본값 복원) 수정 검토
