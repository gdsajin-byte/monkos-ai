### A-2. 앵커 의존성 분석

**교체 순서 의존성**: 현재 체인에는 **순서 의존 충돌 없음**. 각 regex가 서로 다른 DOM 영역을 타겟하며, 교체 결과가 다른 regex의 앵커 문자열을 변경하지 않음.

- Gallery(0): `gallery-track` → `<!-- Sticky Nav -->` 사이
- Intro(1): `<p class="intro-text">` 독립 매칭
- Magazine(2): `sb-magazine` → `sb-tags` 사이
- Tags(3): `sb-tags` 내부 (`<div class="sb-tags">`)
- Blog(4): `최근 블로그` ~ `</main>` 사이
- FAQ(5): `faqPreview` → `sec-board` 사이
- Board(6): `boardPreview` → `sec-blog` 사이

### A-4. 핵심 위험 요약

1. **Gallery 앵커 `<!-- Sticky Nav -->`**: hero/user-bar/gallery/nav 순서로 교체할 경우, gallery regex의 종료 앵커 `<!-- Sticky Nav -->`를 nav 블록 교체가 변경할 수 있음. **해결**: gallery 교체를 nav 교체보다 먼저 실행하거나, nav 교체 시 `<!-- Sticky Nav -->` 주석을 보존
2. **Blog 앵커 `</main>`**: blog regex 종료 앵커가 `</main>`인데, howto/faq/board 교체가 main 내부 구조를 바꿀 가능성. **해결**: blog 교체를 마지막에 실행하거나 앵커를 `id` 기반으로 변경
3. **Board empty 분기**: board가 0건일 때 sec-board 섹션 자체를 제거하는 regex(178~181)가 FAQ 앵커와 겹침 → FAQ 교체 이후에 board를 처리해야 함 (현재도 그러함)

### B-4. 이중 적용 위험

**핵심 위험**: 홈 페이지 진입 시 `setLang()` → `window.location.href = '/?lang=...'` 리다이렉트 경로로 SSR이 정상 반영됨. **그러나** SSR이 이미 언어별 렌더링한 텍스트를, `applyLang()`이 로드 후 다시 한국어 기본값으로 덮어쓸 위험 있음.

**흐름 추적**:
1. 유저가 `/?lang=ja` 접속 → SSR이 일본어로 hero/nav/서비스카드 렌더링
2. 브라우저 로드 → i18n.js 실행 → `var lang = ...` 계산 (region=global이면 localStorage 또는 detectLang())
3. `applyLang()` 호출 → **SSR이 이미 렌더링한 일본어 텍스트를 다시 같은 일본어로 덮어씀 (무해)**
4. **하지만**: `region=kr`일 때 `lang`이 강제 `ko`로 설정됨 → SSR이 `?lang=ja`로 일본어 렌더링했더라도 `applyLang()`이 한국어로 덮어쓸 수 있음

**결론**: Phase 0에서 i18n.js의 SSR 이관 키를 제거하면 이 이중 적용 문제가 자연스럽게 해결됨. 단, 제거 전까지는 SSR 렌더링 결과와 `applyLang()` 결과가 동일 언어인지 보장해야 함.

### B-5. `setLang()` → SSR 블록 데이터 반영 흐름

```
setLang('ja')
  → localStorage.setItem('monkos_lang', 'ja')
  → region = 'global', setCookie
  → 홈이면 window.location.href = '/?lang=ja'
    → SSR renderHome() 호출
      → lang = req.query.lang || 'ko' → 'ja'
      → [현재] FAQ/블로그는 lang 필터 적용됨
      → [Phase 0] layout 블록 데이터에서 lang별 텍스트 선택 필요
```

**위험**: 현재 `renderHome()`은 블록 데이터의 다국어 텍스트 `{ ko, ja, en }` 처리 로직이 없음. Phase 0에서 `lang` 파라미터 기반 텍스트 선택 로직 추가 필수.

### C-3. FAQ 프리뷰 → 전문 앵커 수신 분석

**현재 FAQ 전문 페이지 (render.js:600~609)**:
```html
<details class="faq-item">
  <summary class="faq-question">질문</summary>
  <div class="faq-answer">답변</div>
</details>
```

**문제**: FAQ 전문 페이지에서 각 `<details>` 요소에 **id 속성이 없음**. `/faq#faq-{id}` 앵커 링크가 동작하려면:
1. `faqFragment()`에서 `<details id="faq-${doc.id}">` 형태로 id 추가 필요
2. 앵커로 이동 후 해당 `<details>`를 `open` 상태로 전환하는 JS 추가 필요

이는 render.js 수정이 필요한 사항 (지시서 #5 범위).

## D. 어드민 layout.html 분석

### D-1. 현재 API 호출 구조

| 엔드포인트 | 메서드 | 역할 | 현황 |
|-----------|--------|------|------|
| `/api/admin/layout` | GET | 레이아웃 데이터 로드 | ✅ 동작 (home.js:202~213) |
| `/api/admin/layout` | PUT | 레이아웃 데이터 저장 | ✅ 동작 (home.js:215~233) |

API는 `sections[]` 배열을 받아 `site_config/layout` 문서에 저장. **스키마 검증 없음** — 클라이언트가 보내는 데이터를 그대로 저장.

### D-2. 현재 저장 데이터 vs 기안서 스키마 차이

| 항목 | 현재 layout.html | 기안서 스키마 |
|------|-----------------|--------------|
| 섹션 수 | 7개 (hero, beforeAfter, magazine, blog, guide, credit, tags) | 14개 (15 블록) |
| 필드 | `{ id, visible, size, order }` | `{ id, type, visible, order, data{}, items[] }` |
| 다국어 | 없음 | `{ ko, ja, en }` 객체 |
| 내용 편집 | ❌ 표시/순서/크기만 | ✅ 텍스트·링크·아이콘 편집 |
| 편집 모달 | 없음 | 블록별 편집 모달 필요 |

**핵심 차이**: 현재는 메타데이터(visible/order/size)만 관리. 기안서는 실제 콘텐츠(텍스트, 링크, 다국어)까지 확장.

### D-3. 재사용 가능 vs 재작성 필요

**재사용 가능 (약 40%)**:
- CSS 변수·디자인 시스템 (`--bg`, `--surface`, `--accent` 등)
- 네비게이션 바 (`.nav`, `.nav-logo`, `.nav-back`)
- 토글 스위치 컴포넌트 (`.toggle`)
- 순서 변경 버튼 (`.order-btns`, `.order-btn`)
- API 호출 패턴 (`loadLayout()`, `saveLayout()`)
- 토스트 알림 (`showToast()`)

## E. Firestore 스키마 정합성

### E-1. `site_config` 컬렉션 현재 구조

| 문서 | 필드 | 용도 |
|------|------|------|
| `site_config/main` | `{ intro, updatedAt }` | 인트로 텍스트 (SSR 주입) |
| `site_config/layout` | `{ sections[], updatedAt }` | 레이아웃 설정 (현재 미사용) |

### E-2. Firestore 문서 크기 제한 검증

기안서의 14개 블록 전체를 JSON으로 추정:
- 순수 데이터 블록 (hero, user-bar, nav, service-cards, howto, guide, credit-info, footer): ~15KB
- Firestore 동적 블록 설정 (faq-preview, board-preview, blog-cards, magazine, tags): ~3KB
- 총 예상 크기: **~20KB**
- Firestore 문서 크기 제한: **1MB (1,048,576 bytes)**
- **결론**: 문서 크기 제한 문제 없음 (약 2% 사용)

### E-3. 다국어 패턴 차이 분석

| 기존 패턴 (faq_items, blog_posts) | 기안서 블록 패턴 |
|-----------------------------------|-----------------|
| 문서별 `lang` 필드 (ko/ja/en) | 필드 내부 `{ ko, ja, en }` 객체 |
| 같은 FAQ가 3개 문서로 존재 | 1개 블록에 3개 언어 내포 |
| 컬렉션 쿼리: `.where('lang', '==', lang)` | 단일 문서 로드 후 `data.title[lang]` 접근 |

**향후 통합 시 문제점**:
- FAQ/블로그는 개별 아이템이 많아 문서별 lang 분리가 합리적 (쿼리 필터)
- 블록 데이터는 고정 개수(14개)이므로 인라인 다국어가 합리적
- **두 패턴이 공존해도 구조적 충돌 없음** — 용도가 다름
- 주의점: 블록의 FAQ 프리뷰 `maxItems` 설정은 layout 문서, 실제 FAQ 데이터는 `faq_items` 컬렉션 → 두 곳에서 읽어야 함 (이미 기안서에 명시됨)

## F. 종합 리스크 판정

| # | 리스크 | 위험도 | 대응 방안 |
|---|--------|--------|-----------|
| 1 | **CTA 바인딩 깨짐** (.btn-shoot, .svc.live) | 🔴 高 | SSR 교체 시 class명 100% 보존. main.js DOMContentLoaded 바인딩이므로 SSR HTML에 class 존재하면 정상 |
| 2 | **inline onclick 핸들러** (headerLogin, openCreditShop 등) | 🟡 中 | user-bar SSR 교체 시 onclick 속성 보존. 또는 main.js에서 addEventListener로 전환 (권장) |
| 3 | **i18n.js 이중 적용** (SSR 렌더링 후 applyLang 덮어쓰기) | 🟡 中 | 단계3(#6) i18n 정리 시 SSR 이관 키 제거하면 자연 해소. 그 전까지는 SSR과 i18n 언어가 동일하므로 시각적 문제 없음 (같은 값 덮어쓰기) |
| 4 | **FAQ 앵커 미구현** (render.js에 id 없음) | 🟢 低 | 지시서 #5에서 `<details id="faq-{id}">` 추가 + JS auto-open 구현 |
| 5 | **regex 앵커 순서** (Gallery ↔ Nav 경계) | 🟢 低 | 교체 순서 설계 시 gallery → hero → nav 순서 지정하면 해소 |
| 6 | **Firestore 크기** | ⚪ 무 | 20KB / 1MB 한도 = 2%. 문제 없음 |
| 7 | **다국어 패턴 차이** (lang필드 vs 인라인) | ⚪ 무 | 용도가 다르므로 공존 가능. Phase C 마이그레이션 시에도 구조적 장벽 없음 |

**종합 판정**: Phase 0 진행에 **구조적 블로커 없음**. 위험도 高 항목(#1)은 class명 보존이라는 단순 규칙으로 완전 해소 가능. 중간 위험(#2, #3)은 설계 시 고려하면 되는 수준.
