### 그루핑 판단 근거

**PF_FUNNEL vs PF_PORTAL 분리**:
- v5 퍼널은 결제·과금 핵심 로직(camera → prep → charge → result → thankyou). 포털 메인(index.html, 3컬럼 레이아웃, CMS)과 독립적.
- 코드 영역이 거의 겹치지 않음(퍼널 = camera.js/charge.html/result.js, 포털 = render.js/home.js/index.html).
- 다만 **향후 포털과 퍼널이 더 통합되면** 합칠 여지 있음.

**PF_GOVERNANCE 통합**:
- P2(데이터운영), P10(문서정비), P11(헌법개편)은 모두 "법/규정/문서 체계"에 대한 작업.
- 각각 PF를 만들면 너무 잘게 쪼개짐. "포트폴리오로 내보일 수 있는 단위"로서 거버넌스 진화사 전체가 한 PF.
- 다만 이 PF는 성격상 **종료 시점이 없음**(지속적 진화). status가 영구 active.

**PF_JAPAN 독립**:
- 일본 서비스는 KR과 코드 영역이 상당 부분 겹치지만, 결제(LemonSqueezy vs 토스), 법적(APPI), 시장(편의점, 취활), 채널(LINE)이 전부 별개.
- 3/9~3/10 4일간 일본에만 집중한 리서치가 15건 이상 — 독립 PF로 관리해야 맥락 유지 가능.

- **Phase 현황**: 선형 Phase가 아님. 헌법 개정, 법률 신설, 문서 정리가 비동기적으로 발생. → Phase 대신 **"활성 어젠다"** 섹션으로 대체.
- **성과**: 정량 지표가 불분명. → "개정 이력 + 현행 조 수 + 사문화 조항 수" 등 구조적 지표로 대체.
- **결론**: 7섹션 중 3개를 변형해야 함. **별도 템플릿(PF_GOVERNANCE_TEMPLATE)** 또는 CITADEL 템플릿의 유연 적용(빈 섹션 허용) 권고.

**PF_INFRA**:
- **비전**: "레포 분리"처럼 명확한 목표가 있으나, 보류 중. → 비전 자체는 적합하지만 Phase가 "리서치 → 보류" 상태.
- **Phase 현황**: 리서치만 완료되고 실행이 없어 Phase 0에 머물러 있음. → 적합하나 내용이 빈약.
- **성과**: 인프라 작업의 성과 지표가 불분명. → "안정성(장애 횟수)", "배포 시간", "레포 수" 등으로 대체 가능.
- **결론**: CITADEL 템플릿 그대로 적용 가능하나, 현 시점 내용이 빈약할 것. **향후 실행 착수 시 PF 발족**하는 것이 현실적.

### 판정 요약

- **8개 PF 중 6개**: CITADEL 7섹션 **그대로 적용 가능**.
- **1개(GOVERNANCE)**: 3개 섹션 변형 필요. 별도 템플릿 또는 유연 적용.
- **1개(INFRA)**: 구조 적합하나 현 시점 내용 빈약. 발족 시점 조정 권고.

### 분류 필요성 판단

- PF 파일명에 코드네임이 포함되어 있어 `PF_CITADEL`, `PF_PORTAL`, `PF_JAPAN` 등으로 자연 정렬.

**대분류가 필요한가?**:
- 도메인별 분류(서비스/인프라/콘텐츠/사업)를 시도하면:
  - 서비스: FUNNEL, JAPAN, CROP, STUDIO → 4개
  - 플랫폼: PORTAL, CMS(→PORTAL에 합칠 수도) → 1~2개
  - 전략: SPREAD, CITADEL → 2개
  - 거버넌스: GOVERNANCE → 1개
  - 인프라: INFRA → 1개
- 대분류 자체는 가능하지만, **폴더를 나누면 PF 위치를 기억해야 하는 부담**이 생김.

**권고**: **flat 구조 유지 + PF YAML `domain` 필드로 소프트 분류.** 폴더 분리 불필요. README.md에 도메인별 인덱스를 유지하면 탐색 가능.

## 플랫폼
