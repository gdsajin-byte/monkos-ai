## 3. 전환 전략 비교 (3-C) ⭐ 핵심

### 옵션 A: 빅뱅 전환

**설명**: v5 배포 시 구키 전부 폐기, 신키로 시작. prep.js/camera.js/result.js 동시 교체.

| 평가 항목 | 점수 | 상세 |
|----------|------|------|
| **구현 복잡도** | ⭐ (낮음) | 어댑터/분기 로직 불필요. 깔끔하게 교체 |
| **위험도** | 🔴 (높음) | 배포 중간 상태에서 유저가 접속하면 깨진 UI. 현재 퍼널 진행 중인 유저의 sessionStorage 무효화 |
| **롤백 가능성** | ⭐⭐ (보통) | 이전 버전 재배포로 롤백 가능. 단, v5 키가 이미 쓰인 유저는 수동 sessionStorage 클리어 필요 |
| **기존 유저 영향** | 🔴 (높음) | 배포 시점에 퍼널 중간에 있는 유저 = 즉시 실패. 탭 새로고침 시 키 불일치로 camera.js → prep.html 리다이렉트 (데이터 유실) |

**핵심 리스크**: sessionStorage는 탭 수명과 동일. **배포 즉시** 기존 유저 탭에 영향. 단, 이 앱의 특성상 세션 당 사용 시간이 짧고(촬영→생성→다운로드 = 수 분), 트래픽이 대규모가 아니므로 **영향 범위는 제한적**.

### 옵션 B: 점진적 전환 (어댑터 레이어)

**설명**: 구키 읽기 시 v5 형식으로 변환하는 어댑터 함수 도입. 세션 시작 시 마이그레이션 실행.

```
// 어댑터 예시 (개념)
function migrateSessionV4toV5() {
  const purpose = loadSessionData('purpose');
  if (purpose && !loadSessionData('format')) {
    // purpose → format 변환
    const formatMap = { passport: 'passport', student_id: 'id', employee_id: 'id', resume: 'id', color_portrait: 'id' };
    saveSessionData('format', formatMap[purpose] || 'id');
    // gender 값 축약
    const gender = loadSessionData('gender');
    if (gender === 'male') saveSessionData('gender', 'm');
    if (gender === 'female') saveSessionData('gender', 'f');
    // ... 이하 모든 키 변환
  }
}
```

| 평가 항목 | 점수 | 상세 |
|----------|------|------|
| **구현 복잡도** | 🔴 (높음) | 모든 키의 양방향 매핑 함수 작성. camera.js/result.js에서 구키/신키 양쪽 읽기 로직 필요 |
| **위험도** | ⭐ (낮음) | 기존 유저 세션 자연 전환. 구키→신키 변환이 투명하게 동작 |
| **롤백 가능성** | ⭐⭐⭐ (높음) | 어댑터 비활성화로 즉시 롤백 |
| **기존 유저 영향** | ⭐⭐⭐ (없음) | 진행 중 세션도 어댑터가 변환 |

**핵심 리스크**: 어댑터 레이어가 **영구적 우회**로 고착될 위험 → **헌법 10조 (프록시 금지 원칙) 위반 가능성**. 기한을 명시하여 임시 우회로 한정해야 함.

**추가 문제**: purpose 5값 → format 2값 변환은 **정보 손실**이 발생. `student_id`, `employee_id`, `resume`, `color_portrait`가 모두 `"id"`로 합쳐지면 원래 목적을 복원할 수 없음. 이는 어댑터 변환의 본질적 한계.

### 옵션 C: 버전 태그

**설명**: `monkos_schema_version` 키를 추가하고, 버전에 따라 읽기 로직 분기.

```
// 버전 태그 예시 (개념)
const SCHEMA_VERSION = 2; // v5
saveSessionData('schema_version', SCHEMA_VERSION);

function loadField(key) {
  const ver = loadSessionData('schema_version');
  if (ver === '2') return loadSessionData(key); // v5 키 직접 읽기
  // v4 레거시 변환
  if (key === 'format') return convertPurposeToFormat(loadSessionData('purpose'));
  // ...
}
```

| 평가 항목 | 점수 | 상세 |
|----------|------|------|
| **구현 복잡도** | ⭐⭐ (중간) | 분기 로직이 필요하나 어댑터보다 구조적. 버전별 스키마 정의 명확 |
| **위험도** | ⭐⭐ (중간) | 분기 로직 누락 시 일부 키 미처리 가능 |
| **롤백 가능성** | ⭐⭐⭐ (높음) | schema_version 체크로 분기하므로 v4 코드 복원 시 자연 호환 |
| **기존 유저 영향** | ⭐⭐ (최소) | schema_version이 없는 기존 세션 = v4로 간주 → 레거시 변환 |

**핵심 리스크**: 옵션 B와 유사한 **프록시 고착** 위험. 또한 버전 분기 코드가 모든 읽기 지점에 파편화될 수 있음.

### 추천안: **옵션 A (빅뱅 전환)** + 안전장치

| 추천 근거 | 상세 |
|----------|------|
| **앱 특성** | SPA가 아닌 MPA (prep.html → camera.html → result.html). 페이지 간 이동이 sessionStorage 기반. 유저 세션이 짧음 (5~10분) |
| **sessionStorage 수명** | 탭 닫기 시 자동 소멸. 영구 저장이 아님. 배포 후 기존 탭 유저가 새 탭에서 접속하면 자동으로 깨끗한 상태 |
| **어댑터 불가** | purpose→format 변환이 **정보 손실**(5값→2값). 역변환 불가. 어댑터의 의미가 반감 |
| **헌법 10조** | 어댑터/버전 태그 = 우회 레이어. 영구화 위험. 빅뱅이 근원 해결 |
| **복잡도** | 어댑터(옵션B) 구현 비용 > 빅뱅 배포 시 유저 영향 비용 |

**안전장치 (빅뱅 시 적용)**:

1. **세션 클리어 가드**: v5 prep.js init()에서 구키 감지 시 자동 클리어
   ```
   // v5 prep.js init 시점
   if (loadSessionData('purpose') && !loadSessionData('format')) {
     // v4 세션 잔재 → 전부 클리어하고 1p부터 시작
     STEP_KEYS.forEach(k => sessionStorage.removeItem('monkos_' + k));
     sessionStorage.removeItem('monkos_style');
   }
   ```
2. **camera.js 가드**: `store.format`(v5) 또는 `store.style`(v4) 중 하나라도 없으면 prep.html로 리다이렉트 (현행과 동일 동작)
3. **심야 배포**: 트래픽 최저 시간대(03:00~06:00 KST) 배포로 진행 중 유저 최소화
4. **원자적 배포**: prep.js + camera.js + result.js + shared.js를 **한 커밋, 한 배포**로 처리. 부분 배포 금지

### 4-2. 풀페이지 라우팅 설계

#### 4-2-1. 돌아올 페이지 (return URL) 전달 방식

**추천: URL 파라미터 방식**

```
charge.html?return=result.html&action=download
```

| 방식 | 장점 | 단점 | 추천 여부 |
|------|------|------|----------|
| URL 파라미터 `?return=` | 토스 리다이렉트 체인과 일관성. 디버깅 용이 | URL에 경로 노출 (보안 무관) | ⭐ **추천** |
| sessionStorage `monkos_charge_return` | origin 내 유지. URL 깔끔 | 토스 리다이렉트 시 origin이 바뀔 수 있음 (토스→charge.html 복귀 시) | 보조 수단으로 병행 가능 |
| `history.back()` | 가장 단순 | 결제 후 토스 리다이렉트가 history 스택을 오염. 복귀 대상 불확실 | ❌ 비추천 |

#### 4-2-2. pending action 보존 방식

현행 `monkos_pending_action` 패턴 **그대로 유지** 가능.

```
[result.js] 잔액 부족 감지
  → sessionStorage.setItem('monkos_pending_action', 'download')
  → navigateTo('charge.html?return=result.html&action=download')

[charge.html] PG 결제 완료
  → navigateTo('result.html') (return 파라미터 사용)

[result.js] init()
  → initCredits() (크레딧 갱신)
  → monkos_pending_action === 'download' && credits >= 70
  → 자동 다운로드 진행
  → sessionStorage.removeItem('monkos_pending_action')
```

v5에서도 이 패턴이 유효한 이유:
- sessionStorage는 동일 origin(`idphoto-kr.monkos.ai`) 내에서 탭 수명 동안 유지
- `charge.html`도 같은 origin → sessionStorage 공유
- `monkos_pending_action` 키는 변경 대상이 아님

#### 4-2-3. PG 결제 후 리다이렉트 체인

**현행 흐름**:
```
result.html → ChargeModule.show() (모달) → 토스 결제 → result.html?toss=success → initFromTossResult() → 크레딧 갱신
```

**v5 흐름**:
```
result.html → navigateTo('charge.html?return=result.html')
  → charge.html 표시
  → 유저가 상품 선택 → buyCreditsKR(amount, credits)
  → 토스 결제창 (외부)
  → charge.html?toss=success (successUrl = charge.html)
  → charge.html: initFromTossResult() → 크레딧 갱신 → alert
  → 복귀: navigateTo(returnUrl) → result.html
  → result.html: initCredits() → 크레딧 재확인
  → monkos_pending_action 확인 → 자동 다운로드
```

**핵심 설계 결정**:

| 결정 사항 | 선택 | 근거 |
|----------|------|------|
| successUrl 대상 | `charge.html?toss=success` | charge.html이 결제 완료 처리의 주체. result.html에 결제 완료 로직을 남기면 두 곳에서 처리해야 함 |
| initFromTossResult 위치 | `shared.js` (현행 유지) | charge.html도 sharedInit() 호출 → 자동으로 토스 결과 처리 |
| 복귀 타이밍 | 결제 완료 alert 후 자동 | `return` 파라미터를 읽어 navigateTo() |

**charge.html 필요 모듈**:
- `shared.js` (sharedInit, initFromTossResult, buyCreditsKR)
- 상품 카드 렌더링 (charge.js에서 모달 빌더를 페이지 빌더로 리팩토)
- 복귀 로직 (`return` 파라미터 → navigateTo)

#### 4-2-4. 전체 리다이렉트 체인 (worst case)

```
[1] result.html (잔액 부족)
  → [2] charge.html?return=result.html&action=download
  → [3] 토스 결제창 (외부 도메인)
  → [4] charge.html?toss=success&paymentKey=...&orderId=...&amount=...
  → [5] charge.html: initFromTossResult() → /api/payments/toss/confirm → 크레딧 적립
  → [6] charge.html: navigateTo(return파라미터) → result.html
  → [7] result.html: sharedInit() → initCredits() → 크레딧 갱신
  → [8] result.html: monkos_pending_action='download' → 자동 다운로드
```

**생존하는 데이터**:
- sessionStorage: `monkos_pending_action`, `monkos_generated`, `_mo_p`, `monkos_captured` — 모두 동일 origin 내 유지 ✅
- cookie: `monkos_session` — `.monkos.ai` 와일드카드, 30일 ✅

### 4-3. buyDirect 경로

#### 현행 buyDirect 플로우

```
result.js downloadResult()
  → if (!store.user.id) → GateModule.buyDirect()
  → gate.js _buyDirect(): amount=9900, successUrl=현재페이지?toss=direct
  → 토스 결제 → result.html?toss=direct
  → result.js init() → GateModule.initDirectPayment()
  → /api/payments/toss/direct → downloadToken → 즉시 다운로드
```

#### v5에서의 buyDirect 결정

**v5 기획안 §7**: "로그인 게이트: 1p 이전, 촬영실 진입 시 소셜 원탭 로그인 + 10c 셀레브레이션"

이 설계대로 구현되면:
- **모든 유저가 로그인 상태**로 result.html에 도달
- `!store.user.id` 조건이 **절대 참이 되지 않음**
- buyDirect는 **dead path** (도달 불가능 코드)

**그러나**: 기획안에 buyDirect 삭제가 **명시적으로 언급되지 않음**.

| 방안 | 장점 | 단점 |
|------|------|------|
| A) buyDirect 유지 | 로그인 게이트 우회 시 안전망. 비로그인 유저 매출 확보 | dead path 코드 잔존 |
| B) buyDirect 삭제 | 코드 단순화. 로그인 게이트 설계 의도에 부합 | 로그인 게이트 구현 전에 삭제하면 비로그인 유저 결제 불가 |

**추천**: **로그인 게이트 구현 완료 확인 후 buyDirect 삭제**. 로그인 게이트가 완성되기 전까지는 유지.

⚠️ **쌍아/작가님 결정 필요**: 비로그인 1회 무료 생성 정책 + buyDirect 경로의 존폐.

### 5-1. v5 배포 후 치명적 문제 발생 시 롤백 전략

| 단계 | 조치 | 상세 |

| 1 | **v4 코드 재배포** | Git에서 v4 태그/커밋 체크아웃 → Cloud Run 재배포. 모든 정적 파일(prep.js, camera.js, result.js, shared.js, charge.html)을 v4로 복원 |

| 3 | **v5 키 잔재 처리** | v4 prep.js init()에 v5 키 감지 → 클리어 가드 추가 (사전 대비) |

### 5-2. v5 키가 이미 쓰인 유저 처리

| 시나리오 | 유저 상태 | 롤백 시 영향 | 대응 |
|---------|----------|-------------|------|
| v5 prep 진행 중 | sessionStorage에 v5 키(format, m/f 등) 존재 | v4 camera.js가 `store.style` 필수값 체크 실패 → prep.html 리다이렉트 → **처음부터 재시작** | 유저 데이터 손실 없음 (아직 촬영/생성 전). UX 불편만 발생 |
| v5 촬영 완료 | `monkos_captured` + v5 키 존재 | v4 result.js가 `loadSessionData('purpose')` 실패 → API 요청 시 purpose=null → 서버 에러 또는 디폴트 처리 | 유저가 재촬영 필요. 촬영본은 sessionStorage에 남아있으나 퍼널 선택 불일치 |
| v5 생성 완료 + 다운로드 대기 | `monkos_generated` + v5 키 존재 | 생성 이미지는 보존. 다운로드는 크레딧 차감 + 이미지 전달이므로 키 불일치와 무관하게 동작 가능 | v4 result.js가 생성 이미지 복원 → 다운로드 가능 (프리뷰 표시는 가능하나 규격 정보 불일치) |
| v5 결제 진행 중 | 토스 리다이렉트 → charge.html?toss=success | v4에 charge.html이 없음 → 404 | 유저가 수동으로 result.html 접속 필요. 결제는 서버에서 완료되어 크레딧 적립은 정상 |

**사전 대비 (v5 배포 전 v4에 삽입)**:

v4 코드에 v5 키 감지 가드를 미리 삽입해두면, 롤백 시 자동으로 v5 세션을 클리어하고 v4로 재시작:

```javascript
// v4 prep.js init()에 사전 삽입
if (loadSessionData('format') || loadSessionData('schema_version')) {
  // v5 세션 잔재 감지 → 전체 클리어
  Object.keys(sessionStorage)
    .filter(k => k.startsWith('monkos_'))
    .forEach(k => sessionStorage.removeItem(k));
}
```

### 5-3. 서버 API 롤백

v5에서 서버 `/api/idgen` 프롬프트 빌더도 변경된 경우:
- 클라이언트와 서버를 **동시에 롤백**해야 함
- 서버가 v5 스키마를 수신하는 도중 클라이언트만 v4로 돌리면 → 서버가 v4 키를 인식 못함
- **원자적 롤백**: 클라이언트 + 서버 동시 복원 필수
