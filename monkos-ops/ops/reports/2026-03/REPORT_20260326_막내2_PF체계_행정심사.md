# 행정 심사 보고서: PF(포트폴리오) 체계 개헌

> **[2026-03-26 11:19 KST] iMac/막내2 → iMac/쌍아**

## 총평

PF 체계는 **행정적으로 실행 가능**하다. "지금 어디까지 왔는가"를 추적하는 정본의 부재가 실제로 기획↔실행 갭(CITADEL Phase 1 8일 미착수)과 컴팩팅 후 맥락 유실을 반복 야기하고 있으며, PF는 이를 해결하는 현실적 수단이다. 다만 **6가지 운영 마찰**이 식별되었고, 이 중 3건(다중 디바이스 충돌, PF 비대화, 갱신 누락)은 청구안에 프로세스 수준 대응이 부재하여 **보완이 필요**하다. 소급 정리는 비용 대비 효과가 낮으므로 신규분 적용을 권고한다.

## 1. 운영 워크플로우 마찰

### 1-1. 세션 마감 부하 증분

**현행 절차** (ch3 3조):
```
1. 세션 로그 작성
2. 커밋
3. push
```

**개정안 절차**:
```
1. 세션 로그 작성
2. 활성 PF 히스토리 어펜드
3. 커밋
4. push
```

**마찰 분석**:
- PF 어펜드 1건당 소요: 히스토리 테이블 1~3행 추가 + Phase 현황 갱신 시 추가 수정. **예상 2~5분**.
- 현재 세션 마감 시간: 세션 로그 작성(5~10분) + 커밋+push(1~2분) = **약 7~12분**.
- PF 어펜드 추가 시: **약 9~17분**. 증분율 **25~40%**.
- **1세션 1PF인 경우**: 수용 가능. 현재 CITADEL 같은 집중 세션이 대부분.
- **1세션 다중 PF인 경우**: 예컨대 "오전 CITADEL SEO + 오후 PORTAL_V4 리팩토링" 세션이면 2건 어펜드. PF가 5개 이상 활성화되면 마감 시 "어떤 PF에 무엇을 어펜드해야 하는가"를 판별하는 것 자체가 인지 부하.

**결론**: PF 1~2건/세션은 수용 가능. 3건 이상 동시 활성 시 마감 체크리스트가 필요.

### 1-2. 막내의 PF 읽기 부하

**시나리오**: 막내3이 `PF_PORTAL_V4` 관련 지시서를 받았다. PF가 200줄이다.

- PF 200줄 ≈ **약 3,000~4,000 토큰** (마크다운 테이블 밀도 기준)
- 지시서 평균 100~150줄 ≈ 2,000~3,000 토큰
- 관련 코드 파일 읽기: 수천~수만 토큰
- **PF 읽기의 컨텍스트 비중**: 전체의 **3~5%**. 무시할 수 있는 수준.
- **다만 PF가 500줄(현 CITADEL 성장세 기준 3개월 후 예상)을 넘으면**: 8,000~10,000 토큰 → 전체의 **8~10%**. 무시할 수 없는 수준.

**결론**: 현 규모에서 마찰 미미. 비대화 관리(5항)와 연동하여 선제 대응 필요.

### 1-3. 쌍아 세션 마감 시 PF 갱신 병목

3/26 M1/쌍아 세션 로그를 실측한 결과:
- 타임라인 테이블 50행 + 산출물 4건 + TODO + 종료 → **세션 로그만 상당히 큼**.
- 여기에 PF_CITADEL 히스토리 4행 추가 + Phase 현황 갱신 → **추가 5분**.
- 3/26 야간 세션에서 **배포 누락**이 발생한 원인: 세션 마감 시 쌍아가 처리할 항목이 과다(코드 리뷰 + 완료 보고 + CITADEL 갱신 + 배포 지시 전달)하여 누락.
- PF 갱신이 추가되면 이런 누락 리스크가 **구조적으로 증가**.

**권고**: 세션 마감 체크리스트를 명문화하라 (세션 로그 → PF 어펜드 → 커밋 → push). 쌍아용 마감 템플릿 권고.

## 2. 폴더·파일 구조 정합

### 2-1. ops/projects/ 처리

**현상**: `ops/projects/README.md`에 "폐지 → portfolios/"로 리다이렉트 노트만 존재.

**판정**:
- `PROJECT_CITADEL.md`는 `PF_CITADEL.md`로 전환 완료.
- projects/ 폴더 자체는 **즉시 삭제 가능** 조건: README만 잔류, 실물 없음.
- 다만 ch4 2조 7항(README 미보유 폴더 금지)의 역은 아님 — README만 있는 빈 폴더도 혼란 유발.

**권고**: PF 체계 발효 시 `ops/projects/` 폴더를 삭제하고, ch4 4조 정본 테이블에서 제거. **삭제는 개헌 발효 후 1회성 정리 지시서로 처리.**

### 2-2. ops/proposals/ ↔ ops/portfolios/ 관계

**현상**: PROPOSAL 13건 중 PF로 승격된 것은 현재 0건(CITADEL은 PROJECT에서 전환). 청구안 §3-1 생애주기에 "PROPOSAL 승인 → PF 생성"이 명시됨.

**미해결 사항**:
- PROPOSAL이 PF로 승격되면 proposals/에서 **삭제하는가, 유지하는가**?
- 헌법 제3조 4항(정본 단일 원칙)과 제3조 2항(원본 수정/삭제 금지)이 충돌 가능:
  - PROPOSAL은 "기안 문서"로서의 정본이다. PF는 "생애주기 허브"로서의 정본이다. 성격이 다르므로 이중화가 아니다.

**권고**: PROPOSAL은 proposals/에 영구 보존(append-only 준용). PF의 관련 문서 인덱스에 링크. **이것은 세션 로그가 세션 종료 후에도 삭제하지 않는 것과 같은 원리.** 청구안에 "PROPOSAL은 PF 승격 후에도 원본 유지"를 명시하라.

### 2-3. tech/specs/ 기존 문서의 귀속

**현상**: `tech/specs/`에 서비스별 SPEC 문서가 존재. PF 도입 후 이들의 위치는?

**판정**:
- SPEC은 SPEC이다. PF는 허브다. SPEC의 물리 위치(`tech/specs/`)는 변경할 이유가 없다.
- PF의 §6(관련 문서 인덱스) 기술명세 섹션에 링크만 추가.
- PF_TEMPLATE에 이미 "기술명세 (SPEC)" 인덱스 섹션이 존재.

**결론**: 현행 유지. 정합 문제 없음.

### 2-4. 월별 서브폴더 필요성

**현상**: sessions/, orders/, reports/는 `YYYY-MM/` 서브폴더 사용 중(ch4 4조). portfolios/는 어떻게 할 것인가?

**판정**:
- PF는 **프로젝트별 단일 파일**이다. 시간 축이 아닌 **프로젝트 축**으로 정리된다.
- 세션 로그(일별) · 지시서(건별)와 근본적으로 다른 성격.
- 활성 PF가 10개를 넘어도 flat 구조로 관리 가능.
- 완료된 PF를 `portfolios/archive/` 서브폴더로 이동하는 것은 고려 가능하나, PF 자체가 "에셋으로 영구 보존"이므로 아카이브 이동의 의미가 불분명.

**권고**: **월별 서브폴더 불필요.** flat 구조 유지. 완료 PF는 status를 completed로 변경하는 것만으로 충분. README.md에 활성/완료 PF 인덱스를 유지하면 탐색 가능.

## 3. 다중 디바이스 동시 갱신

### 3-1. 구조적 차이: 세션 로그 vs PF

| | 세션 로그 | PF |
|---|---|---|
| 파일 단위 | 에이전트별 1파일 | 프로젝트별 1파일 |
| 동시 편집 가능성 | **없음** (각자 자기 파일) | **있음** (같은 PF를 여러 디바이스가 편집) |
| 충돌 확률 | 0% | **중간~높음** |

### 3-2. 현실 시나리오

**시나리오 A**: M1/쌍아가 PF_CITADEL Phase 1 "배포 완료"를 기록하는 동안, iMac/막내2가 같은 PF에 새 오더를 추가.

- 양쪽 모두 히스토리 테이블 하단에 행을 추가 → **git merge 시 동일 위치 삽입으로 충돌 발생**.
- 마크다운 테이블은 git의 3-way merge가 깨지기 쉬운 구조(행 구분자 `|`가 동일 패턴).

**시나리오 B**: M1/쌍아가 Phase 현황의 상태를 "⏳ → ✅"로 변경하는 동안, iMac/막내가 같은 Phase에 새 항목을 추가.

- Phase 현황은 테이블 중간 수정 → 충돌 확률 **높음**.

### 3-3. 발생 빈도 추정

- 현재 세션 패턴: M1(집, 야간/아침) → iMac(사무실, 낮) → M1(집, 저녁). **순차적**.
- 동시 세션: 이례적. 3월 로그 114건 중 동일 날짜 M1+iMac은 3/22, 3/25 등. 그러나 세션 시간대가 겹치지 않는 경우가 대부분.
- **현실 충돌 확률**: 낮음(월 1~2회). 그러나 **발생 시 복구 비용이 높음**(마크다운 테이블 수동 머지).

### 3-4. 대응안

**권고 (프로세스 수준)**:

1. **PF 갱신 권한자 제한**: PF 히스토리·Phase 현황의 직접 갱신은 **쌍아만** 수행. 막내는 완료 보고서(COMPLETION)에 내용을 기재하고, 쌍아가 세션 마감 시 통합 갱신. 이는 현행 "쌍아 = 세션 인덱스 관리" 역할(ch3 1조)과 일관.
2. **세션 시작 시 pull 의무**: ch3 5조가 이미 `git fetch --all`을 의무화. PF 갱신 전 반드시 최신 상태 확인.
3. **충돌 발생 시 규칙**: PF 히스토리는 append-only이므로, 양쪽 추가분을 모두 살리고 시간순 정렬. Phase 현황 충돌 시 최신 상태를 우선.

### 5-4. 비대화 대응 방안

**권고 (구체적 수치 기준)**:

1. **히스토리 100행 초과 시**: 완료된 Phase의 히스토리를 별도 파일로 분리.
   - 파일명: `PF_{코드네임}_HISTORY_{PhaseN}.md`

2. **Phase 현황 완료 Phase 접기**: 완료된 Phase는 요약 1행으로 축소.
   - Before: Phase 0 상세 테이블 15행

3. **PF 500줄 초과 시**: 강제 아카이브 트리거. 쌍아가 세션 마감 시 줄 수 체크.

4. **관련 문서 인덱스**: 누적 특성상 가장 빠르게 비대화. **20건 초과 시** 타입별로 최근 5건만 본문에 유지, 나머지는 히스토리 파일에 이관.

## 6. 자동화 가능성

### 6-1. 현실적으로 자동화 가능한 영역

| 항목 | 난이도 | 효과 | 권고 |
|------|--------|------|------|
| 세션 시작 시 활성 PF 목록 표시 | **낮음** | 높음 | ✅ 즉시 시행 |
| 지시서 portfolio 필드로 PF 존재 확인 | **낮음** | 중간 | ✅ 막내 행동 규칙에 포함 |
| PF 줄 수 체크 (비대화 경고) | **낮음** | 중간 | ✅ 세션 마감 스크립트에 추가 |
| 커밋 메시지에서 PF 히스토리 자동 생성 | **높음** | 높음 | ❌ 비현실적 |
| ORDER → PF 히스토리 자동 파싱 | **높음** | 중간 | ❌ 비현실적 |

### 6-2. 즉시 시행 가능한 자동화

**A. 세션 시작 시 활성 PF 표시**

```bash
# scripts/ 또는 세션 시작 절차에 포함
grep -l 'status: active' monkos-ops/ops/portfolios/PF_*.md 2>/dev/null
```

쌍아가 세션 시작 시 `git fetch` 후 활성 PF 목록을 확인하고 작가님에게 보고. **ch3 5조 개정안에 이미 "활성 PF 현황 확인"이 포함됨** — 구현은 위 1줄이면 충분.

**B. PF 비대화 경고**

```bash
# 세션 마감 시 PF 줄 수 체크
for pf in monkos-ops/ops/portfolios/PF_*.md; do
  lines=$(wc -l < "$pf")
  if [ "$lines" -gt 500 ]; then
    echo "⚠️ $(basename $pf): ${lines}줄 — 아카이브 필요"
  fi
done
```

### 6-3. 커밋 메시지 기반 자동 생성이 비현실적인 이유

- 커밋 메시지는 "무엇을 변경했는가"이지 "PF의 어떤 Phase에 해당하는가"가 아님.
- ORDER YAML에서 portfolio 필드를 파싱하여 히스토리 행을 자동 생성하려면: ORDER의 내용 요약 + 산출물 링크 + 상태 판정이 필요 → 이것은 **쌍아의 판단 영역**이지 스크립트의 영역이 아님.
- **수동 운영 보완책**: 세션 마감 체크리스트에 "PF 어펜드 완료?" 항목 포함 + 다음 세션 시작 시 전 세션의 PF 갱신 누락 여부 확인.

## 행정 실행 계획

PF 체계 승인 시, 아래 순서로 시행한다:

### Step 1: 법률 발효 (쌍아, 즉시)

1. 헌법 제3조 2항 개정 (수정 권고 #1 반영)
2. ch3 3조·5조 개정 (수정 권고 #3, #6 반영)
3. PF 갱신 권한자 규정 신설 (수정 권고 #2)
4. 비대화 관리 조항 신설 (수정 권고 #4)
5. 소급 정리 규정 명시 (수정 권고 #5)
6. PROPOSAL 보존 규정 명시 (수정 권고 #7)

### Step 2: 인프라 정리 (막내, 지시서 1건)

1. `ops/projects/` 폴더 삭제 (수정 권고 #8)
2. ch4 4조 정본 테이블에서 projects/ 제거
3. 세션 시작 스크립트에 활성 PF 목록 출력 추가
4. 세션 마감 스크립트에 PF 줄 수 경고 추가

### Step 3: PF 그루핑 매핑 (쌍아, 1세션)

1. PROPOSAL 13건 → PF 그루핑 매핑 테이블 작성
2. 활성 프로젝트(CITADEL 외)의 현재 상태 스냅샷 PF 생성 (히스토리 역추적 없이)
3. portfolios/README.md 갱신

### Step 4: 일상 운영 전환 (전원)

1. 신규 지시서에 `portfolio:` 필드 기재 시작
2. 세션 마감 시 PF 어펜드 실행
3. 1주 후 운영 마찰 점검 → 필요 시 세칙 보정
