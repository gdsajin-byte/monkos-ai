### 설계 판단 근거

1. **blog-edit.html만 우선 분리**: 1,495줄 단일 파일이 버그의 진앙. 나머지 7개 페이지는 135~291줄로 관리 가능 수준.
2. **admin-common.css/js 추출**: 8개 페이지 공통 요소를 1회 정의. 나머지 페이지도 점진적으로 공통 파일 참조로 전환 가능.
3. **ESM `<script type="module">` 사용**: Cloud Run 환경에서 브라우저 ESM 정상 동작. `import/export`로 모듈 간 의존성 명시.
4. **bare import 불가**: 브라우저 ESM은 상대 경로만 허용. `import { showToast } from './js/admin-common.js'` 형태.
5. **나머지 페이지 점진적 전환**: blog-edit 분리 안정화 후, 다른 페이지들도 `admin-common.css/js`를 `<link>`/`<script>` 참조하고 인라인 중복 제거.

### 3-6. ESM 모듈 간 공유 전략

Toast UI Editor 인스턴스 (`editor`)를 여러 모듈이 참조해야 하는 문제:

**해법: blog-editor.js에서 `editor` 인스턴스를 export**

```javascript
// blog-editor.js
export let editor;  // Toast UI Editor 인스턴스

export function initEditor() {
  editor = new toastui.Editor({ ... });
  return editor;
}
```

```javascript
// blog-image.js
import { editor } from './blog-editor.js';
```

> Toast UI Editor는 전역 CDN (`<script>` 태그)으로 로드되므로 `toastui.Editor`는 전역 접근. ESM 모듈 내에서 `new toastui.Editor()`로 인스턴스 생성 후 export.

### onclick → ESM 호환 전략

현재 HTML에 `onclick="save(true)"`, `onclick="switchTab('seeds')"` 등 인라인 이벤트가 다수.
ESM `<script type="module">`에서는 이 함수들이 전역에 노출되지 않음.

**해법 2가지**:

| 방법 | 장단점 |
|------|--------|
| **A: window에 명시적 등록** | `window.save = save;` — 기존 HTML 변경 최소화, 실용적 |
| **B: addEventListener로 교체** | HTML 마크업 수정 필요, 더 깔끔하지만 변경량 큼 |

**추천: 방법 A** (기존 HTML onclick 유지, JS에서 `window.함수명 = 함수`로 등록)
→ Phase 2에서 HTML 변경을 최소화하여 리스크 감소

## 부록 A: ESM `<script type="module">` Cloud Run 호환성

Cloud Run은 Node.js HTTP 서버가 정적 파일을 서빙. 브라우저가 `.js` 파일을 요청하면 서버는 그대로 전달. 별도 번들링 불필요.

**확인 사항**:
- `server.js`의 정적 파일 서빙에서 `.js` 파일의 Content-Type이 `application/javascript`인지 확인 필요
- `.mjs` 확장자 사용 시 MIME 타입 문제 가능 → `.js` 확장자 유지 권장
- `<script type="module">`은 CORS 정책 적용 → 같은 origin이므로 문제 없음
