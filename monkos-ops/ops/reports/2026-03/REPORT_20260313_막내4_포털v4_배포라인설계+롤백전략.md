## 산출물 2: 배포 전략 비교표

### Cloud Run 트래픽 관리 기능

Cloud Run은 리비전(revision) 기반 트래픽 분할을 네이티브 지원한다:
- `gcloud run deploy --to-latest` → 새 리비전에 100% 트래픽 즉시 라우팅
- `gcloud run deploy --no-traffic` → 새 리비전 배포하되 트래픽 0%
- `gcloud run services update-traffic --to-revisions=REV=N%` → 특정 리비전에 N% 배포
- `gcloud run deploy --tag=TAG` → 별도 URL 부여 (TAG---서비스명.run.app)

### 전략별 비교

| 전략 | 구현 방법 | 장점 | 단점 | 복잡도 | 롤백 속도 |
|------|----------|------|------|--------|----------|
| **A) Big Bang** | `deploy.sh prod` 그대로 실행 (현재 방식) | 단순, 추가 작업 없음 | 문제 시 전체 사용자 영향, 롤백 수동 | ★☆☆ | ~5분 (재배포) |
| **B) 블루/그린** | `--no-traffic` 배포 → `--tag v4`로 태그 URL 검증 → `update-traffic --to-latest` | 검증 후 전환, 즉시 롤백 가능 | 태그 URL 검증 시간 필요 | ★★☆ | **즉시** (트래픽 전환) |
| **C) 카나리** | `--no-traffic` 배포 → `update-traffic --to-revisions=NEW=10,OLD=90` → 점진 확대 | 점진적 위험 분산, 메트릭 관찰 가능 | 일부 사용자 v3/v4 혼재 경험, 모니터링 필요 | ★★★ | **즉시** (트래픽 전환) |
| **D) Feature Flag** | 쿼리 파라미터 `?v=4` 또는 쿠키로 서버에서 v3/v4 HTML 분기 | 유연한 대상 선택 | 코드 복잡도 증가, 두 버전 유지보수 | ★★★★ | 플래그 끄기 |
| **E) 별도 서비스** | `monkos-portal-v4` 새 Cloud Run 생성 → 도메인 매핑 전환 | 완전 격리, 독립 테스트 | DNS 전환 시간(TTL), 환경변수 이중 관리 | ★★★ | DNS 롤백 (TTL 의존) |

### 추천안: **B) 블루/그린** (Cloud Run 네이티브)

**이유:**
1. **현재 deploy.sh에 `--to-latest` 미적용** — 이미 블루/그린에 가까운 상태
2. Cloud Run이 리비전 기반 트래픽 관리를 네이티브 지원
3. 태그 URL로 프로덕션 환경에서 사전 검증 가능
4. 롤백이 트래픽 전환뿐이라 **수초 내 완료**
5. 코드 변경 최소 (deploy.sh에 플래그 추가 수준)

**구현 절차:**

```bash
# Step 1: v4 코드 배포 (트래픽 0%)
gcloud run deploy monkos-portal \
  --image gcr.io/monkos/monkos-portal \
  --no-traffic \
  --tag v4 \
  [기존 옵션들...]

# Step 2: 태그 URL로 검증
# → v4---monkos-portal-XXXXXXXX.run.app 접속하여 테스트
# → 인증, 결제, 챗봇, 다국어 전부 확인

# Step 3: 검증 완료 → 100% 전환
gcloud run services update-traffic monkos-portal \
  --region us-central1 \
  --to-latest

# (문제 발생 시) 즉시 롤백
gcloud run services update-traffic monkos-portal \
  --region us-central1 \
  --to-revisions=monkos-portal-XXXXX=100  # v3 리비전
```

### 전략 D, E를 권장하지 않는 이유

- **D (Feature Flag)**: 포털 v4는 index.html 전면 재설계 — 부분 분기가 비현실적. 두 버전의 HTML/CSS/JS를 동시 유지하면 코드 복잡도가 폭증
- **E (별도 서비스)**: 환경변수 24개 + Firestore + GCS + OAuth 콜백 URL 전부 이중 설정 필요. DNS TTL 때문에 롤백도 느림. 관리 부채 과다

## 산출물 3: 롤백 절차서 초안

### 롤백 시나리오

| 단계 | 상황 | 롤백 방법 |
|------|------|----------|
| 배포 전 (태그 검증 중) | v4 태그 URL에서 문제 발견 | 아무것도 안 함 (트래픽 0%) |
| 전환 직후 | 100% 전환 후 즉시 문제 | Cloud Run 트래픽 롤백 |
| 전환 후 수시간 | 점진적 문제 발견 | Cloud Run 트래픽 롤백 |
| 전환 후 수일 | v3 리비전 만료 위험 | v3 코드 재배포 |

### 롤백 명령 절차

```bash
# 1. 현재 리비전 확인
gcloud run revisions list --service=monkos-portal --region=us-central1

# 2. v3 리비전으로 트래픽 100% 전환
gcloud run services update-traffic monkos-portal \
  --region us-central1 \
  --to-revisions=monkos-portal-[v3리비전ID]=100

# 3. 헬스체크 확인
curl https://monkos.ai/health

# 4. idphoto 서비스 정상 확인
curl https://idphoto-kr.monkos.ai/health
curl https://idphoto-jp.monkos.ai/health
```

### 롤백 판단 기준

| 메트릭 | 임계값 | 확인 방법 |
|--------|--------|----------|
| 헬스체크 실패 | /health 응답 ≠ 200 | curl 또는 Cloud Run 콘솔 |
| 5xx 에러 급증 | 배포 전 대비 2배 이상 | Cloud Run 메트릭 |
| 인증 실패 | 로그인 불가 보고 | OAuth 콜백 테스트 |
| 크레딧 API 오류 | idphoto에서 크레딧 차감/환불 실패 | idphoto 로그 |
| 결제 실패 | Toss/LemonSqueezy 결제 불가 | 테스트 결제 |
| 페이지 깨짐 | CSS/JS 로딩 실패 | 브라우저 콘솔 |

### Firestore 스키마 관련 롤백 이슈

**현재 상태**: v4 프로토를 분석한 결과, Firestore 스키마 변경이 있을 수 있음.

**원칙:**
- v4에서 **새 필드 추가**만 있으면 → v3 롤백 시 무시됨 (안전)
- v4에서 **기존 필드 구조 변경** 있으면 → v3 롤백 시 데이터 호환성 문제
- v4에서 **새 컬렉션 생성** → v3 롤백 시 고아 데이터 (정리 가능)

**권장**: v4 설계 시 Firestore 스키마를 **하위 호환(backward compatible)**으로 설계. 새 필드 추가는 OK, 기존 필드 삭제/변경은 v3 롤백 불가 만듦.

### 롤백 자동화 스크립트 (필요 시)

현재 단계에서 자동화 스크립트까지는 불필요. 이유:
1. Cloud Run 롤백은 단일 명령어 (수동으로 충분)
2. 배포 빈도가 낮음 (대규모 변경 위주)
3. 판단 기준이 자동화하기엔 맥락 의존적 (결제 실패 vs 일시 지연 구분 필요)

v4 안정화 후, 정기 배포가 늘어나면 그때 `rollback.sh` 스크립트 도입 검토.


### `--to-latest` 미적용 상세

현재 `gcloud run deploy` 명령에 `--to-latest` 플래그가 **없다**.

**의미:**
- 배포 시 새 리비전이 생성되지만, 트래픽이 자동으로 새 리비전으로 라우팅되지 않을 수 있음
- Cloud Run의 기본 동작: `gcloud run deploy`는 기본적으로 `--to-latest`가 암시적으로 적용됨
- **단, 이전에 수동으로 트래픽을 특정 리비전에 고정한 적이 있다면**, 이후 배포에서 자동 라우팅이 해제됨
- 즉, 한 번이라도 `update-traffic --to-revisions=REV=100`을 실행했다면, 이후 모든 배포에서 `--to-latest`를 명시해야 함

**권장 조치:**
- 평상시 배포: `--to-latest` 명시 추가
- v4 블루/그린 배포: `--no-traffic` 사용 (의도적 트래픽 차단)

### v4 대응 추가 사항

| # | 항목 | 설명 | 우선도 |
|---|------|------|--------|
| 1 | `--no-traffic` 옵션 추가 | v4 블루/그린 배포용. `deploy.sh prod --no-traffic` 형태 | 🔴 필수 |
| 2 | `--tag` 옵션 추가 | 태그 URL 생성용. `deploy.sh prod --tag v4` | 🔴 필수 |
| 3 | `--to-latest` 명시 | 평상시 배포 안전장치 | 🟡 권장 |
| 4 | 롤백 서브커맨드 | `deploy.sh rollback [리비전]` 형태 | 🟢 선택 |
| 5 | 리비전 목록 조회 | `deploy.sh revisions` — 현재 리비전 + 트래픽 비율 확인 | 🟢 선택 |
| 6 | 환경별 .env 분리 | `.env.dev` / `.env.prod` 분리 (현재 단일 .env) | 🟡 권장 |

### 구조적 개선 권장

**1. dev/prod Firestore 분리**
- 현재: dev와 prod가 **동일 Firestore** 사용
- 위험: dev 테스트가 프로덕션 사용자 데이터에 영향
- 권장: `monkos-dev` GCP 프로젝트 분리 또는 컬렉션 접두어 분기

**2. 환경변수 분리**
- 현재: dev/prod 동일 .env, 동일 키 (OAuth 콜백 URL 등이 같음)
- 권장: `.env.dev` / `.env.prod` 분리하여 dev에서 테스트용 키 사용

**3. `--update-env-vars` vs `--set-env-vars`**
- 현재: portal은 `--update-env-vars` (기존 변수 보존)
- idphoto 서비스들은 `--set-env-vars` (전체 교체)
- 주의: `--update-env-vars`는 삭제된 변수가 Cloud Run에 잔존할 수 있음

## 스테이징 환경 검토 (조사범위 6번)

### 현재 dev 환경의 실질적 역할

| 항목 | 상태 |
|------|------|
| 서비스명 | `monkos-portal-dev` |
| URL | `monkos-portal-dev-XXXXXXXX.run.app` (태그 없음) |
| Firestore | **prod와 동일** (monkos 프로젝트) |
| 환경변수 | **prod와 동일** (.env 단일 파일) |
| OAuth 콜백 | **prod와 동일** (리다이렉트 URL 공유) |
| 용도 | 실질적으로 "prod 미러" 수준 |

### dev를 staging으로 쓸 수 있는가?

**현재 상태로는 불가.** dev와 prod가 동일 DB·동일 키를 쓰기 때문에, dev에서 테스트한 결제가 실제 과금되고, dev에서 생성한 사용자가 prod에 노출됨.

### staging 신설 vs dev 강화

| 방안 | 장점 | 단점 |
|------|------|------|
| dev 강화 (DB분리+키분리) | 기존 인프라 활용 | OAuth 콜백 URL 추가 등록 필요 |
| staging 별도 신설 | 완전 격리 | 3-track 관리 부담 |

**권장**: v4 배포에는 **블루/그린 전략으로 충분**. staging 신설은 서비스 규모가 커진 후 검토.
- 블루/그린의 태그 URL 검증이 사실상 staging 역할을 대체함
- `v4---monkos-portal-XXXXXXXX.run.app`에서 프로덕션 DB로 직접 검증 가능

## 종합 추천

### v4 배포 실행 계획 (순서)

```
1. deploy.sh에 --no-traffic, --tag 옵션 추가
2. deploy.sh에 --to-latest 명시 추가 (평상시용)
3. v4 코드 완성 → dev 배포 → 기본 동작 확인
4. prod에 --no-traffic --tag v4 배포
5. 태그 URL로 전수 검증:
   - 인증 (Google, Kakao, LINE OAuth)
   - 크레딧 API (idphoto-kr/jp에서 호출 테스트)
   - 결제 (Toss, LemonSqueezy)
   - 챗봇, CMS, Admin
   - 다국어 라우팅
6. 작가님 최종 승인
7. update-traffic --to-latest (100% 전환)
8. 모니터링 (1시간)
9. 이상 없으면 v3 리비전 유지 (롤백용, 자동 만료까지 보존)
```
