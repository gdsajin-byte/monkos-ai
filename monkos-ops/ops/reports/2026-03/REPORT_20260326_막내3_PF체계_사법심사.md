# 사법 심사 보고서: PF(포트폴리오) 체계 개헌

> **[2026-03-26 11:20 KST] iMac/막내3 → iMac/쌍아**

## 총평

**권고: B. 수정 후 통과**

PF 체계는 현실적으로 필요하며 PF_CITADEL 실례가 이미 그 효과를 입증했다. 그러나 청구안에는 **권한 매트릭스 부재**, **히스토리-세션로그 이중화에 대한 정본 판정 기준 부재**, **PF 비대화 방어책 부재**의 3가지 결함이 있다. 이를 보정하면 통과에 장애가 없다. 헌법 개정의 범위(제3조 2항 확장)는 최소 침습적이며 기존 체계와의 충돌도 경미하다. 다만, **"세션 로그와 동급의 적립 의무"라는 표현의 무게**가 실제 운용에서 의도 이상의 부담으로 작용할 가능성을 경계해야 한다.

## 1. 권한 침해 우려

### 분석

청구안 제3조 2항 개정문: *"활성 포트폴리오(PF)가 존재하는 작업의 경우, 해당 PF의 히스토리를 세션 로그와 동시에 갱신한다."*

"모든 에이전트"에게 PF 갱신 의무를 부여하는데, PF 파일에는 성격이 다른 두 영역이 있다:

| 영역 | 성격 | 판단 수준 |
|------|------|----------|
| **히스토리 테이블** | 사실 기록 ("무엇을 했다") | 자기 작업의 기계적 기록 — 판단 불필요 |
| **Phase 현황** | 상태 판단 ("Phase N 완료") | 설계 판단 — "이 Phase가 정말 끝났는가?" |

**문제점**: 막내가 Phase를 "✅ 완료"로 마킹할 수 있는가? 이것은 쌍아의 설계·검증 역할(ch1 1조: "코드 리뷰, 정합 검토")과 충돌한다. 막내가 자기 작업이 끝났다고 Phase 완료를 선언하면, 쌍아의 검증 없이 프로젝트가 다음 단계로 진입할 수 있다.

민아의 경우도 유사하다. 민아 권한표(ch1 1조)에 따르면 "커밋·푸시 → 쌍아 경유 또는 작가님 명시 승인 필요"인데, PF 파일 수정은 커밋을 수반하므로 민아가 독립적으로 PF를 갱신하려면 매번 쌍아 경유가 필요하다. 이는 PF 갱신의 즉시성을 해친다.

### 권한 매트릭스 제안

| 에이전트 | 히스토리 어펜드 | Phase 현황 변경 | 비전/리스크 변경 | 성과 데이터 입력 |
|----------|:-------------:|:--------------:|:--------------:|:--------------:|
| **작가님** | ✅ | ✅ | ✅ | ✅ |
| **쌍아** | ✅ | ✅ | ✅ | ✅ |
| **민아** | ✅ (커밋은 기존 권한표 준용) | ⚠️ 쌍아 사후 보정 대상 | ❌ 쌍아 전권 | ✅ |
| **막내** | ✅ (세션 마감 시 자동) | ❌ 쌍아/작가님만 | ❌ | ✅ (실측값만) |
| **코웍이** | ✅ (works 경유) | ❌ | ❌ | ❌ |
| **소넷이** | ✅ (데몬 규칙 준용) | ❌ | ❌ | ✅ (자동 수집) |

**핵심 원칙**: 히스토리 어펜드는 사실 기록이므로 전원 허용. Phase 변경은 설계 판단이므로 쌍아/작가님 전권.

**청구안의 공백**: 이 권한 구분이 없다. "PF의 히스토리를 갱신한다"는 문구가 Phase 현황 갱신까지 포함하는지 불명확하다.

## 2. 의무 과잉 우려

### 현행 세션 마감 부담

| 절차 | 소요 시간(추정) | 토큰 비용 |
|------|:-------------:|:---------:|
| 세션 로그 작성 | 3~5분 | 중간 |
| 커밋+push | 1~2분 | 낮음 |
| **합계** | **4~7분** | — |

### PF 추가 시 증가분

| 추가 절차 | 소요 시간(추정) | 토큰 비용 |
|----------|:-------------:|:---------:|
| PF 히스토리 1줄 어펜드 | 1~2분 | 낮음 |
| Phase 현황 갱신 (해당 시) | 2~3분 | 중간 |
| **합계** | **1~5분** | — |

세션 마감 총 부담: 기존 4~7분 → 5~12분. **최대 70% 증가**.

### 비교 분석: 세션 로그 의무 도입 전후

MEMORY.md 교훈에서 확인 가능한 패턴:
- "세션 로그 즉시 어펜딩 원칙" (03-15 작가님 지적) — 세션 끝에 몰아쓰는 문제 발생
- 세션 로그 03-10~03-14 공백 4일 (헌법 재편 청구 배경) — 의무 존재에도 누락

**이 패턴이 PF에 반복될 가능성**: 높음. 세션 로그보다 PF가 "내 것"이 아니라 "프로젝트의 것"이라는 인식이 강해, 귀속감이 낮으면 형식적 갱신(내용 없는 1줄)이 유발될 수 있다.

### 의무 과잉 판정

**경미~중간 수준의 우려**. 이유:
1. PF 갱신은 히스토리 1줄이 대부분 — 세션 로그보다 가볍다
2. PF 대상 작업이 없는 세션은 면제 (청구안 §3-4에 명시)
3. 그러나 Opus 토큰 제한 환경에서 **컨텍스트 압축 직전에 PF까지 읽고 갱신하는 부담**은 무시할 수 없다

### 대안: 단계적 적용

청구안이 즉시 의무화를 제안하지만, PF_CITADEL 이외의 PF가 아직 존재하지 않으므로 사실상 단계적 도입이 자연스럽게 진행되고 있다. 별도의 유예기간 규정은 불필요하나, **"PF가 3건 이상 동시 활성화될 때"의 운용 부담**은 향후 재검토가 필요하다.

## 3. 정보 이중화 및 정합성

### 핵심 문제: 히스토리 테이블 ≠ Phase 현황

청구안의 논리: *"세션 로그 = 시간축, PF = 상태축"*

이 논리를 해부하면:

| PF 섹션 | 축 | 세션 로그와의 관계 |
|---------|:--:|:---------------:|
| **히스토리 테이블** | **시간축** | ⚠️ 세션 로그와 동일 축 — **이중화** |
| **Phase 현황** | **상태축** | ✅ 세션 로그에 없는 정보 — **보완** |
| **성과** | **측정축** | ✅ 세션 로그에 없는 정보 — **보완** |
| **복기** | **지식축** | ✅ 세션 로그에 없는 정보 — **보완** |

**허점 발견**: 청구안이 주장하는 "시간축 vs 상태축" 구분은 PF 전체에는 성립하지만, **히스토리 테이블만 놓고 보면 세션 로그와 동일한 시간축 기록**이다.

구체 예시:
- PF 히스토리: `| 3/26 | 막내2 | Step 2+3 완료 — specs 허브 7규격×3언어 | specs-data.json, render.js | ✅ |`
- 세션 로그: `### [09:30] 막내2 완료 보고 — specs 허브 7규격×3언어 구현`

같은 사건, 같은 축, 두 문서. 이것은 이중화다.

### 정본 단일 원칙 위반인가?

**위반은 아니다.** 그러나 **정합성 리스크가 있다.**

헌법 제3조 4항: *"동일 문서의 정본은 하나만 존재한다."*

PF와 세션 로그는 **동일 문서가 아니라 다른 문서**에서 같은 사건을 기록하는 것이다. 이는 DB의 정규화 위반(denormalization)과 유사한 구조로, 의도적 중복(read 성능 확보)일 수 있지만, **두 문서의 내용이 어긋날 때의 판정 기준이 없다.**

### 정합성 판정 기준 제안

| 분쟁 유형 | 정본 | 이유 |
|----------|------|------|
| **"이 작업이 실행되었는가?"** (사실 판단) | 세션 로그 | 타임스탬프 기반 실시간 기록 — 사후 기억 아님 |
| **"이 프로젝트가 지금 어디인가?"** (상태 판단) | PF Phase 현황 | 이것이 PF의 존재 이유 |
| **"이 Phase는 완료되었는가?"** (완료 판단) | PF (쌍아/작가님 갱신분) | 설계자의 판단이 정본 |

이 기준이 청구안에 없다. 추가가 필요하다.

## 4. 법체계 복잡도

### 현재 문서 유형: 15종

패턴 #1(TASK, 레거시) 제외 시 실질 14종 + PF = **15종**.

### 프로젝트 문서 체인 분석

일반적인 기능 개발 프로젝트의 문서 발생 체인:

```
PROPOSAL → (승인) → PF 생성/인입 → ORDER → 막내 실행
  → COMPLETION → PF 히스토리 어펜드 → 세션 로그
    → (Phase 완료 시) PF Phase 갱신
      → (전체 완료 시) REPORT → PF status: completed
```

**문서 5종 × 2회 갱신(PF) = 7회 문서 작업** per project cycle.

### "새 에이전트가 이해하는 데 걸리는 시간" 평가

현재 신규 막내가 읽어야 하는 문서:
1. CLAUDE.md (헌법 5조) — 필수, 자동 로딩
2. MEMORY.md — 필수, 자동 로딩
3. 지시서 (ORDER) — 1건
4. ch7 (막내 행동 강령) — 상황에 따라

PF 추가 시:
5. 해당 PF 파일 — 1건 (지시서 엔드라인의 `portfolio:` 필드로 참조)

추가 인지 부하: **PF 1건 읽기** = 경미. PF의 존재 자체는 오히려 "세션 로그 N건을 뒤지는 것"을 대체하므로 **순인지부하는 감소할 수 있다**.

### PROPOSAL과 PF 통합 가능성

| 통합 방안 | 장점 | 단점 |
|----------|------|------|
| PROPOSAL을 PF로 흡수 | 문서 유형 1종 감소 | PROPOSAL은 "제안"이고 PF는 "추적" — 성격 다름. 미승인 제안도 PF가 되면 혼란 |
| 유지 (현행) | 역할 구분 명확 | 유형 15종 유지 |

**판단**: 통합은 비권고. PROPOSAL은 승인 전 문서이고 PF는 승인 후 문서다. 합치면 "아직 승인 안 된 PF"가 생기는데, 이는 PF의 "정본" 지위를 훼손한다.

### 인지 부하 임계점

15종은 많다. 그러나:
- 막내가 실제로 다루는 유형: ORDER, COMPLETION, (세션 로그) = **3종 + PF 1종**
- 15종 전체를 알아야 하는 주체: 쌍아뿐
- PF 추가의 한계 비용은 낮다 (기존 14종 → 15종의 차이는 미미)

**판단**: 임계점을 넘지 않는다. 다만, 16종 이상 추가 시에는 유형 통폐합을 검토하는 트리거 규정이 있으면 좋겠다.

## 5. 실패 시나리오

### 시나리오 1: Stale PF — 유령 문서화

**상황**: PF_PORTAL_V4가 생성되었으나, 3개월간 갱신되지 않음. 이후 신규 막내가 이 PF를 읽고 3개월 전 Phase 현황 기준으로 작업 수행. 이미 완료된 Phase를 재실행하거나, 변경된 아키텍처를 무시하고 구(舊) 설계로 코드 작성.

| 항목 | 평가 |
|------|------|
| **발생 확률** | **중간** — 세션 로그 03-10~03-14 공백 사례가 PF에서 반복될 수 있다. 특히 병렬 프로젝트가 많아지면 "이번 세션에서 이 PF를 갱신했나?" 확인이 빠질 수 있다. |
| **피해 규모** | **심각** — 방향 역행이 하류 작업 전체에 파급. Phase 0에서 수정한 hreflang을 Phase 2에서 되돌리는 등의 사태. PF_CITADEL 교훈 1("기획→실행 전환 병목")이 PF 자체에서 재현. |
| **예방 방안** | 세션 마감 체크리스트에 PF 갱신 여부 확인 항목 추가. 소넷이 데몬이 `status: active`인 PF의 최종 갱신일을 모니터링하고 N일 경과 시 알림. |
| **감수 가능성** | 예방 방안이 있으므로 감수 가능 |

### 시나리오 2: PF 비대화 — 읽기 부담 역전

**상황**: PF_CITADEL 히스토리가 200줄 초과. 막내가 PF를 읽기 위해 400+ 줄의 마크다운을 로딩. 원래 "세션 로그 대신 PF를 읽으면 빨리 파악"이 목적이었으나, PF 자체가 세션 로그급 분량이 되어 목적 무효화. 컨텍스트 윈도우 압박.

| 항목 | 평가 |
|------|------|
| **발생 확률** | **높음** — PF_CITADEL이 이미 249줄. 히스토리 테이블만 81줄(30행). Phase 2~3 완주 시 400줄 초과 예상. 6개월 운영 시 PF 파일 1개가 600줄 이상 가능. |
| **피해 규모** | **중간** — PF 존재 가치(빠른 상태 파악) 상실. Opus 컨텍스트 윈도우에서 PF 로딩만으로 상당량 소모. |
| **예방 방안** | 히스토리 100줄(약 30행) 초과 시 아카이브 절차 도입 — 완료된 Phase의 상세 히스토리를 별도 파일(`PF_CITADEL_ARCHIVE_Phase0.md`)로 이관하고 본문에 요약 1줄 + 링크만 잔류. Phase 현황은 현재 Phase만 유지. |
| **감수 가능성** | 예방 방안이 없으면 감수 불가. 있으면 감수 가능 |

### 시나리오 3: 동시 갱신 충돌 — Git Merge Conflict

**상황**: 막내1이 PF_CITADEL 히스토리에 자기 작업을 어펜드하고 커밋. 동시에 막내2도 같은 PF의 같은 히스토리 테이블에 어펜드하고 커밋. 두 번째 push에서 merge conflict 발생. 해결 과정에서 한쪽 기록이 유실되거나 테이블 형식이 깨짐.

| 항목 | 평가 |
|------|------|
| **발생 확률** | **중간** — 현행 멀티에이전트 환경에서 2~3명이 같은 PF 대상 작업을 병렬 수행하는 경우 자주 있다 (Phase 1에서 막내1+막내2 동시 투입 사례). |
| **피해 규모** | **경미~중간** — Git conflict 자체는 해결 가능하나, PF가 "정본"인데 conflict 해결 과정에서 에이전트가 잘못 resolve하면 히스토리 유실. |
| **예방 방안** | 1) 막내는 PF 어펜드 직전 반드시 `git pull` 실행 (ch7 1조 직접지시 의무 ②항 준용). 2) 히스토리 테이블은 append-only이므로 충돌 시 양쪽 모두 보존하는 것이 원칙 — 이를 명시. |
| **감수 가능성** | 예방 방안으로 충분히 감수 가능 |

### 시나리오 4: PF 과다 생성 — 좀비 PF 누적

**상황**: 모든 기안서(PROPOSAL)에 PF를 생성하도록 문화가 형성됨. 소규모 패치, 1회성 긴급 수정에도 PF가 생성. 6개월 후 PF 20건 중 15건이 `status: active`이나 실질 비활성. 세션 시작 시 "활성 PF 확인" 절차에서 20건 모두 체크? → 오버헤드 폭증.

| 항목 | 평가 |
|------|------|
| **발생 확률** | **낮음** — 청구안 §3-1에서 PF 생성을 "기안(PROPOSAL) 승인 시 협의"로 제한하고, 단발성 작업은 PF 면제를 명시함. |
| **피해 규모** | **중간** — 좀비 PF 누적 자체보다, 활성 PF 체크의 오버헤드가 문제. |
| **예방 방안** | PF 생성 시 반드시 쌍아/작가님 합의. 90일 이상 미갱신 PF는 자동으로 `status: paused` 전환 권고(소넷이 데몬). |
| **감수 가능성** | 발생 확률 낮고 예방 가능 |

## 6. 최종 권고

### 권고: B. 수정 후 통과

PF 체계의 필요성은 명확하다:

1. **작가님이 직접 문제를 제기**했다 — "세션로그만 뒤지다보니 에이전트들이 리서치할때마다 해석이 달라지고"
2. **PF_CITADEL이 이미 실증**했다 — Phase 0+1 합계 53분 실행, 에이전트 간 맥락 공유에 즉시 효과
3. **헌법 개정 범위가 최소 침습적**이다 — 기존 제3조 2항에 1문장 추가. 신조 신설이 아님
4. **기존 체계와 충돌이 없다** — 청구안 §4-1 영향 평가 테이블이 정확함

그러나 아래 3가지 결함의 보정이 필요하다:

### 수정 권고 사항

#### 수정 1: 권한 매트릭스 명시 (필수)

청구안 또는 법률에 PF 갱신 권한을 역할별로 명시한다.

- **히스토리 어펜드**: 전 에이전트 (자기 작업의 사실 기록)
- **Phase 현황 변경**: 쌍아/작가님만 (설계 판단)
- **비전·리스크 변경**: 쌍아/작가님만

이것이 없으면 막내가 Phase 완료를 자의적으로 선언하는 문제가 발생한다.

#### 수정 2: 정합성 판정 기준 추가 (필수)

PF 히스토리와 세션 로그가 어긋날 때의 판정 기준:

- **사실 판단** ("이 작업이 실행되었는가?") → 세션 로그가 정본
- **상태 판단** ("프로젝트가 지금 어디인가?") → PF Phase 현황이 정본

이 기준이 없으면 정본 단일 원칙의 취지가 훼손된다.

#### 수정 3: PF 비대화 방지 규정 추가 (권고)

히스토리 테이블이 일정 분량(30행 또는 100줄)을 초과하면:
- 완료된 Phase의 상세 히스토리를 아카이브 파일로 이관
- 본문에는 Phase 요약 1줄 + 아카이브 링크만 잔류
- Phase 현황은 현재 Phase + 직전 1개만 상세 유지

이것이 없으면 PF가 비대화되어 "빠른 상태 파악"이라는 본래 목적이 무효화된다.
