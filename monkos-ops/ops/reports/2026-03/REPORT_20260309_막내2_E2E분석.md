## 임무 A: KR E2E 흐름 전체

### 결제 진입 → 결제 완료 → 크레딧 적립 전체 흐름

```
사용자 "충전" 클릭
  → charge.js: 카드 더블탭 (1탭=하이라이트, 2탭=결제)
  → shared.js buyCreditsKR(amount, credits)
    ├─ 로그인 미확인 → GateModule 리다이렉트
    ├─ Toss SDK requestPayment('카드', {...}) 호출
    │   - orderId: MONKOS_{userId8자}_{timestamp}_{random}
    │   - successUrl: ?toss=success
    │   - failUrl: ?toss=fail
    └─ 사용자가 Toss 모달에서 결제
        │
        ├─ 성공 → Toss가 ?toss=success&paymentKey=...&orderId=...&amount=... 리다이렉트
        │   → initFromTossResult() 호출 (페이지 로드 시 sharedInit에서 실행)
        │   → POST portal/api/payments/toss/confirm (15초 타임아웃)
        │   → Portal: Toss API 승인 확인 → Firestore 트랜잭션 크레딧 적립
        │   → 응답 수신 → store.user.credits 즉시 갱신
        │   → alert("결제가 완료되었습니다!\n현재 크레딧: Nc")
        │
        ├─ 취소 → PAY_PROCESS_CANCELED / USER_CANCEL → 조용히 로그만
        └─ 실패 → ?toss=fail&message=... → alert(message)
```

### Toss redirect 후 `initFromTossResult()` 처리 경로

**위치**: `shared.js` (sharedInit 내에서 페이지 로드 시 자동 호출)

1. URL 파라미터 파싱: `?toss=success|fail`
2. **fail 경로**: message 추출 → URL 정리(`history.replaceState`) → alert → return
3. **success 경로**:
   - `paymentKey`, `orderId`, `amount` 추출
   - URL 정리 (쿼리 파라미터 제거)
   - 3개 파라미터 중 하나라도 누락 시 → 조용히 return
   - `_showTossLoading()` → 전체 화면 반투명 오버레이 + 스피너
   - `POST /api/payments/toss/confirm` 호출 (body: paymentKey, orderId, amount, userId)
   - 성공 시 → `store.user.credits` 갱신 + alert
   - 실패 시 → alert("결제 확인 실패")
   - `_hideTossLoading()` → 오버레이 제거

### Portal `/api/payments/toss/confirm` 엔드포인트

**위치**: `portal/lib/payments.js` handleTossConfirm()

1. **파라미터 검증**: paymentKey, orderId, amount, userId 필수
2. **크레딧 계산**:
   - PRODUCTS 딕셔너리에서 amount로 상품 검색 → `credits + bonus`
   - 매칭 없으면 맞춤 충전: `amount ÷ 145` → 10c 배수 검증
   - 검증 실패 → 400 ("유효하지 않은 결제 금액")
3. **Toss API 승인**: Basic auth(`TOSS_SECRET_KEY`)로 Toss confirm API 호출
4. **Firestore 트랜잭션**: `credits += N`, `lastPurchase` 갱신
5. **결제 로그**: `payments` 컬렉션에 기록 (실패해도 결제는 유지)
6. **응답**: `{ success, credits(잔액), creditsAdded, orderId }`

### 결제 실패/취소 시 처리 방식

| 시점 | 상황 | 처리 |
|------|------|------|
| Toss 모달 | 사용자 취소 | `PAY_PROCESS_CANCELED` → 로그만 (alert 없음) |
| Toss 리다이렉트 | 결제 실패 | `?toss=fail&message=...` → alert(message) |
| Portal confirm | Toss API 거부 | 400 + 에러 메시지 → alert |
| Portal confirm | 금액 검증 실패 | 400 → alert |
| Portal confirm | 네트워크 에러 | catch → alert("결제 확인 실패") |

### 크레딧 적립 후 UI 갱신 방식

- **직접 갱신**: Portal 응답의 `data.credits` → `store.user.credits` 즉시 반영
- **보조 갱신**: `visibilitychange` 이벤트 → 탭 포커스 시 `fetchLatestCredits()` 호출
- **polling/webhook 없음** — 동기식 요청-응답 패턴

### thankyou 페이지

- **라우트 존재**: `server.js`에 `GET /thankyou` → `thankyou.html` 제공
- **showThankYou() 함수**: 빈 스텁 (v5에서 별도 페이지로 전환, export만 유지)
- **결제 흐름과 직접 연결 안 됨** — 다운로드 완료 후 이동하는 페이지

## 임무 B: JP E2E 흐름 전체

### Lemon Squeezy 결제 진입 → 새 탭 → Webhook → 크레딧 적립 흐름

```
사용자 "チャージ" 클릭
  → charge.js: 카드 더블탭 → buyCreditsJP(opt)
    ├─ 로그인 미확인 → GateModule 리다이렉트 (재귀 호출 구조)
    │
    ├─ ★ 빈 탭 선점: window.open('about:blank', '_blank')
    │   (사용자 제스처 컨텍스트에서 즉시 실행 → 팝업차단 우회)
    │
    ├─ POST portal/api/checkout { variantId, userId, email }
    │   → Portal: Lemon Squeezy API v1/checkouts 호출
    │   → 체크아웃 URL 수신
    │
    ├─ 빈 탭에 URL 리다이렉트: win.location.href = data.url
    │   (win이 null이면 현재 창으로 fallback)
    │
    └─ 사용자가 Lemon Squeezy 체크아웃 완료
        │
        ├─ ★ LS → Portal webhook (POST /api/webhooks/lemonsqueezy)
        │   - event: order_created
        │   - HMAC 서명 검증
        │   - custom_data.user_id로 사용자 식별
        │   - VARIANT_CREDITS 매핑으로 크레딧 산출
        │   - Firestore 트랜잭션: credits += N
        │
        └─ ★ 클라이언트 폴링 (initLemonSqueezy 이벤트 핸들러)
            - T+2초: fetchLatestCredits() 1차
            - T+4초: fetchLatestCredits() 2차 + alert("決済が完了しました！")
```

### `initLemonSqueezy()` 폴링 로직

**위치**: `shared.js`

```javascript
window.LemonSqueezy.Setup({
  eventHandler: (event) => {
    if (event.event === 'Checkout.Success') {
      setTimeout(() => fetchLatestCredits(), 2000);   // 1차: 2초
      setTimeout(() => {
        fetchLatestCredits();                          // 2차: 4초
        alert('決済が完了しました！\nクレジットが追加されました。');
      }, 4000);
    }
  }
});
```

**설계 의도**:
- Webhook → Firestore 트랜잭션 = 100~500ms 소요
- 2초: 대부분 webhook 처리 완료. 조기 크레딧 반영
- 4초: 보장된 반영 + 사용자 알림
- KR과 달리 직접 confirm API가 없으므로 polling 필수

### 팝업 차단 우회 로직

**위치**: `shared.js` buyCreditsJP() 내

```javascript
const win = window.open('about:blank', '_blank');
```

- **핵심**: 사용자 클릭 이벤트 핸들러 내에서 즉시 `window.open` 호출
- 비동기 fetch 이전에 팝업 슬롯을 선점
- 이후 fetch 완료 시 `win.location.href = data.url`로 리다이렉트
- `win === null`이면 (여전히 차단된 경우) `location.href`로 현재 창에서 진행
- 에러 시 `win.close()`로 빈 탭 정리

### 결제 완료 후 thankyou 페이지 흐름

**위치**: `thankyou.js`

```
result.js doDownload() 성공
  → navigateTo('thankyou.html')
  → displayPhoto() 실행
  │
  ├─ pending_action 확인 (sessionStorage 'monkos_pending_action')
  │   └─ 'full_original' + 로그인 + 원본 존재 시:
  │       → fetchLatestCredits()
  │       → 잔액 >= CREDIT_COST.fullOriginal이면 → 자동 다운로드
  │
  └─ "フルショット" 버튼 클릭 시:
      ├─ 이미 구매 (monkos_fullshot_purchased) → 캐시된 JPEG 재다운로드 (무료)
      └─ 미구매:
          ├─ 잔액 부족 → pending_action 설정 + 충전 모달
          └─ 잔액 충분 → POST /api/credit/use → 크레딧 차감 → 다운로드
```

## 개선 필요 항목

### 1. [JP] Webhook 중복 처리 미비 (중요도: 높음)

**현황**: Portal의 `/api/webhooks/lemonsqueezy`에서 `order_created` 이벤트를 수신할 때, 동일 주문의 중복 webhook 호출에 대한 idempotency 검증이 없음.

**위험**: Lemon Squeezy가 webhook을 재전송하면 동일 주문에 대해 크레딧이 중복 적립될 수 있음.

**제안**: webhook 수신 시 `orderId` 또는 LS의 `meta.id`를 `payments` 컬렉션에서 조회하여 이미 처리된 건인지 확인.

### 2. [KR] orderId 중복 체크 미비 (중요도: 중간)

**현황**: `handleTossConfirm()`에서 동일 orderId의 재처리 방지 로직 없음. Toss API 자체 idempotency에 의존.

**위험**: 실질적으로 Toss API가 방어하므로 낮지만, 방어적 코드 부재.

### 3. [JP] 결제 취소 시 빈 탭 미정리 (중요도: 낮음)

**현황**: 사용자가 LS 체크아웃을 취소하면 `about:blank` 탭이 열린 채 남아있을 수 있음. `Checkout.Success` 이벤트만 핸들링하고 취소/실패 이벤트는 미핸들링.

### 4. [JP] 폴링 실패 시 사용자 인지 부재 (중요도: 중간)

**현황**: `fetchLatestCredits()`가 2초/4초에 실패하면(네트워크 에러 등) 로그만 남고 사용자에게 알림 없음. webhook은 처리되었으나 클라이언트 크레딧이 미갱신된 상태가 될 수 있음.

**완화**: `visibilitychange` 보조 갱신이 존재하므로 탭 전환 시 복구됨.

### 5. [공통] showThankYou() 스텁 잔재 (중요도: 낮음)
