### 그루핑 논거

**PF_PHOTOPRO**: 프로젝트의 핵심 상품. Image Pro MVP(01-11) → idphoto-kr(01-16) → idphoto-jp(02-08) → REST v2.0(02-14) → image.monkos.ai 이관(02-28)로 이어지는 단일 서비스 라인. 일본 시장(§1-9)과 포털 서비스 부분(§1-6)은 동일 서비스의 확장이므로 병합. 포털의 "브랜드 통일" 측면은 GOVERNANCE에 가깝지만, 기술 구현(monk.kr 정적화, monkos.ai 전환)은 PHOTOPRO 서비스 배포와 직결.

**PF_DIDIMSTONE**: 유일하게 외부 기관(KOITA/IRIS)과의 접점이 있는 사업 프로젝트. 시작(01-15)과 종료(01-23)가 명확. 이의신청 전략(02월)까지 포함해도 생애주기가 뚜렷. "포트폴리오로 내보일 수 있는 완성 단위"로서 가치 높음.

**PF_ENGINE**: PHOTOPRO와 기술적으로 연관되나 목표가 다름. PHOTOPRO = "서비스 출시/운영", ENGINE = "자체 모델 확보/학습". 4060 GPU 학습, 데이터 크롤링(7,897장), 야간 자동화는 서비스 운영이 아닌 R&D 활동. MONKOS Chat은 기술 실험(Vertex AI 직접 연동 검증)으로 ENGINE에 귀속. 현재 휴면 상태이나 향후 재활성 가능성.

**PF_GOVERNANCE**: 01월 세션 로그 규칙 → 02월 헌법 5축 체계로 발전. 문서 정리(§1-12)는 거버넌스의 실행 과정. 코인 이코노미의 규정 측면(ch4 데이터 운영)도 여기 포함. 현재까지 가장 꾸준히 진화하는 PF.

**PF_INFRA**: GCS/Git/SSH/쿠키/보안 등 기술 인프라 전반. 서비스(PHOTOPRO) 및 운영(GOVERNANCE)을 받치는 기반. 보안/인증(§1-11)과 D1 원장 구현(§1-7 기술 부분)을 포함. PHOTOPRO와 겹치는 영역(배포 인프라)이 있으나, "서비스 기능" vs "운영 기반"으로 구분 가능.

## 4. 분류 체계 판단

### 4-1. 현재 PF 총수

| 출처 | PF 수 |
|------|-------|
| 막내3 분석 (01-02월) | 5건 |
| 기존 PF_CITADEL (03월) | 1건 |

| **총 추정** | **8~10건** |

### 4-2. 분류 필요성 판단

PF 10건 미만이면 flat 목록으로 충분하다는 것이 지시서의 기준이다.

**flat 목록 권고** 이유:
1. **현재 8~10건**: 분류 없이도 한 화면에 전체 파악 가능
2. **분류 기준의 모호성**: "서비스/인프라/콘텐츠/사업" 분류 시, PHOTOPRO는 서비스이면서 사업이고, INFRA는 인프라이면서 서비스 기반 — 경계가 불분명
3. **관리 오버헤드**: 분류 체계 자체가 법률 한 조항을 더 만드는 셈. PF가 20건 넘기 전까지는 불필요
4. **이미 domain 필드 선택 사항**: 개헌 합의안 C.6에서 `domain` 필드를 선택으로 둔 것은 현 시점에 분류 불필요를 전제

**단, 향후 PF 15건 초과 시** 아래 분류를 도입 권고:

| 대분류 | 설명 | 해당 PF |
|--------|------|---------|
| **SERVICE** | 사용자 대면 서비스 | PF_PHOTOPRO, PF_CITADEL 등 |
| **BUSINESS** | 외부 기관 연동 사업 | PF_DIDIMSTONE 등 |
| **PLATFORM** | 내부 인프라/거버넌스 | PF_GOVERNANCE, PF_INFRA 등 |
| **R&D** | 기술 연구/실험 | PF_ENGINE 등 |

소분류는 **불필요**. 대분류 4종만으로 충분한 해상도.

### 4-3. 결론

> **현재: flat 목록. PF 15건 초과 시: 대분류 4종(SERVICE/BUSINESS/PLATFORM/R&D) 도입.**
> **소분류: 불필요.**

### 5-2. 무귀속 비율

| 구분 | 커밋 수 (추정) | 비율 |
|------|---------------|------|
| PF 귀속 | ~770건 | **96%** |
| 무귀속 단발성 | ~30건 | **4%** |

**분석**: 무귀속 비율이 4%로 매우 낮다. 대부분의 작업이 5개 PF 중 하나에 자연스럽게 귀속된다.

### 5-3. 처리 방안 권고

**"기타 PF" 신설 불필요**. 이유:
1. 무귀속 비율 4%는 PF 1건을 정당화하기에 너무 적음
2. "기타"라는 PF는 의미 없는 쓰레기통이 됨
3. 단발성 작업 중 긴급 패치는 해당 PF에 사후 귀속 가능 (예: iOS Safari 수정 → PF_PHOTOPRO)
4. 진정한 무귀속(BWYA, NotebookLM)은 세션 로그에만 기록하면 충분

**권고**: 무귀속 작업은 **세션 로그에 기록**, PF 히스토리에는 미기재. 향후 무귀속 비율이 10% 초과 시 재검토.

### CITADEL 모델 범용성 판정

CITADEL 7섹션 구조는 **범용 프레임워크로 유효하나, 2가지 확장이 필요**하다:

1. **Phase 상태 확장**: `진행(IN_PROGRESS)` / `완료(COMPLETED)` / `휴면(DORMANT)` / `영속(ONGOING)` — 4종으로 확장. R&D 중단, 인프라/거버넌스 영구 활성 케이스를 커버.
2. **완료 PF 아카이브**: Phase 현황·리스크 섹션을 동결(수정 불가, 열람만 가능)하는 "아카이브 모드" 규정 추가.

이 2가지만 반영하면 서비스/사업/R&D/체계/인프라 **전 유형**에 단일 템플릿 적용 가능.
