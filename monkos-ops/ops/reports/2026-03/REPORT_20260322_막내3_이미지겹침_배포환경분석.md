## 2. 난독화 영향 분석

### 2.1 obfuscate.mjs 작동 범위

```javascript
const files = readdirSync(PUBLIC_DIR)          // ./public/ 루트만
  .filter(f => f.endsWith('.html'))            // HTML만
  .map(f => join(PUBLIC_DIR, f));              // 재귀 탐색 없음
```

| 처리 대상 | 처리 여부 |
|-----------|----------|
| `public/*.html` (인라인 `<script>`) | ✅ 처리 |
| `public/admin/*.html` | ❌ **미처리** (하위 디렉토리) |
| `public/admin/js/*.js` (ESM 모듈) | ❌ **미처리** (외부 JS 파일) |
| `public/admin/css/*.css` | ❌ **미처리** (CSS) |
| `<script src="...">` 블록 | ❌ **미처리** (src 속성 있는 태그 스킵) |
| `<script>` 100자 미만 | ❌ **미처리** (임계값 미달) |

**결론**: 블로그 에디터의 ESM 모듈(`blog-image.js`, `blog-editor.js` 등)과 CSS(`blog-editor.css`)는 난독화를 **전혀 거치지 않는다**. 난독화는 이미지 겹침 버그의 원인이 아니다.

## 3. 정적 파일 서빙 검증

### 3.1 서빙 로직 (server.js:252-278)

```javascript
const cacheHeader = ['.css', '.js'].includes(resolvedExt)
  ? 'no-cache'                    // CSS/JS: 매번 재검증 필요
  : 'public, max-age=3600';       // 기타: 1시간 캐시
```

| 항목 | 상태 |
|------|------|
| MIME 타입 | ✅ `.js` → `application/javascript; charset=utf-8` (정상) |
| CSS 캐시 | `Cache-Control: no-cache` |
| JS 캐시 | `Cache-Control: no-cache` |
| ETag 헤더 | ❌ **미설정** |
| Last-Modified | ❌ **미설정** |

### 3.2 캐시 동작 분석

`no-cache`는 "캐시하지 마라"가 아니라 "캐시하되 매번 재검증하라"의 의미. 그러나:

1. **ETag/Last-Modified가 없음** → 브라우저가 조건부 요청(304) 불가
2. **결과**: 브라우저는 사실상 매번 전체 파일을 새로 다운로드해야 함
3. **ESM 모듈 import**: `type="module"` 스크립트는 브라우저 모듈 캐시에 의존 — 일부 브라우저에서 URL이 동일하면 캐시를 유지할 수 있음

### 3.3 ESM 모듈 서빙

`blog-edit.html`에서 ESM import:
```html
<script type="module">
  import { initEditor, ... } from './js/blog-editor.js';   // 캐시 버스팅 없음
  import { setupImageHandlers } from './js/blog-image.js';  // 캐시 버스팅 없음
  import { loadSeedCatalog } from './js/blog-seed.js';      // 캐시 버스팅 없음
  import { initResearch } from './js/blog-research.js';      // 캐시 버스팅 없음
  import './js/blog-share.js';                               // 캐시 버스팅 없음
</script>
```

Cloud Run에서 ESM `type="module"` import는 정상 작동한다 (MIME 타입 `application/javascript` 정확).
