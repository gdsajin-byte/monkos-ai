## 4. 중복 탐지 (3-D)

### 핵심 의심 지점: `monkos_user` sessionStorage vs `monkos_session` cookie

| 데이터 | sessionStorage | cookie | 동시 존재? | 어느 쪽이 실제 사용? | 나머지는 레거시? |
|--------|---------------|--------|-----------|--------------------|--------------|
| 사용자 인증 정보 | `monkos_user` (JSON: id/email/name/picture/credits) | `monkos_session` (JWT 토큰) | **YES — OAuth 콜백 시 동시 주입** | **cookie (`monkos_session`)** — verify-cookie API가 현역 인증 체계 | **sessionStorage (`monkos_user`)는 레거시** |

#### 근거

1. **현역 idphoto-kr(`shared.js`, `result.js`, `camera.js`, `prep.js`)에서 `monkos_user` sessionStorage를 직접 읽는 코드가 단 한 줄도 없다.**
   - `monkos_user`를 grep한 결과: idphoto-kr/public/*.js에서 0건
   - 인증은 전부 `verify-cookie` API를 호출하여 쿠키 기반으로 처리

2. **portal auth.js의 인라인 JS에서 `monkos_user` sessionStorage를 주입하는 4곳**:
   - auth.js:138 — Kakao 팝업 fallback (`window.opener`가 없을 때)
   - auth.js:153 — Kakao 리다이렉트 방식
   - auth.js:302 — LINE 팝업 fallback
   - auth.js:327 — LINE 리다이렉트 방식
   - **이 4곳 모두 동시에 `monkos_session` 쿠키도 Set-Cookie로 발급한다.**

3. **`monkos_user` sessionStorage를 읽는 코드는 `_legacy_spa/index.html`에만 존재** (L1189, 1211, 1269, 1320)

4. **`verify-cookie`가 성공하면 `monkos_user` sessionStorage는 완전히 불필요**:
   - idphoto-kr의 `initCredits` (shared.js:216) = verify-cookie 호출 → `store.user`에 직접 할당
   - portal의 `restoreSession` (index.html:1452) = verify-cookie 호출 → `currentUser`에 직접 할당

**결론: cookie 전환 후 `monkos_user` sessionStorage는 레거시 잔재다. 삭제해도 현역 앱 동작에 영향 없음.**

```
  │ → monkos_credits_from 읽음 → 복귀 URL로 리다이렉트 → 삭제
  │
  ▼ [idphoto-kr/result.html 복귀]
  │ sharedInit() → initCredits() (크레딧 갱신)
  │ monkos_pending_action = 'download' 확인 → 자동 다운로드
```

### 6-4. 탭 닫기 / 토스 리다이렉트 시 생존 분석

| 이벤트 | sessionStorage | cookie | localStorage |
|--------|---------------|--------|-------------|
| **탭 닫기** | 전부 소멸 (퍼널 선택, 이미지, pending_action 모두) | `monkos_session` 생존 (30일) | `monkos_free_gen`, `monkos_lang` 생존 |
| **토스 리다이렉트 (같은 탭)** | **전부 생존** — 동일 origin 내 리다이렉트이므로 sessionStorage 유지 | 생존 | 생존 |
| **토스 리다이렉트 (credits.html → idphoto-kr)** | **각 origin의 sessionStorage는 별도** — portal의 `monkos_credits_from`과 idphoto-kr의 `monkos_pending_action`은 각자 도메인에서 유지 | 생존 (.monkos.ai 와일드카드) | 각 도메인별 유지 |

**중요**: idphoto-kr의 sessionStorage 키들은 `idphoto-kr.monkos.ai` origin에 귀속. portal의 `monkos_credits_from`은 `monkos.ai` origin에 귀속. 서로 접근 불가.

## 8. 발견사항 요약 및 권고

### 발견사항

1. **`monkos_user` sessionStorage = 레거시 잔재 (확정)**
   - portal/lib/auth.js의 OAuth 콜백 인라인 JS 4곳에서 Set-Cookie와 동시에 주입
   - 현역 idphoto-kr 코드에서 이 키를 읽는 곳이 **0건**
   - `_legacy_spa/index.html`에서만 사용 (구 인증 체계)
   - verify-cookie API가 완전히 대체하고 있음

2. **`monkos_cropped` sessionStorage = 미사용 (확정)**
   - setItem 하는 코드가 현역 어디에도 없음
   - clearSessionImages()에서 removeItem만 존재

3. **`_mo_p` = 접두사 없는 예외 키**
   - 의도적 난독화로 판단되나, 일관성 차원에서 향후 정리 고려 대상

4. **cookie는 깔끔한 상태**
   - 서버: `monkos_session` 1종 (HttpOnly, JWT, 30일)
   - 클라이언트: `monkos_region` 1종 (지역 설정, 1년)
   - 쿠키 전환은 완료된 상태

5. **localStorage도 깔끔한 상태**
   - `monkos_free_gen` (비로그인 제한), `monkos_lang` (언어 설정) 2종만 존재

6. **sessionStorage 대용량 키 주의**
   - `monkos_captured`, `monkos_generated`, `_mo_p` = base64 이미지
   - sessionStorage 용량 제한(보통 5~10MB)에 근접할 수 있음
   - 특히 `_mo_p`(풀 원본) + `monkos_generated`(워터마크) + `monkos_captured`(촬영본) = 3장이 동시에 존재하는 구간 있음
