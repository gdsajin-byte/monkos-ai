## 검토 항목 1: env 인증 관리와 헌법 4조(비밀정보 보호) 충돌 여부

### 판정: **적합**

**근거:**

헌법 4조 1항: "API 키, 프로젝트 ID, 비밀번호, 토큰 **절대 생성/추측 금지**. 모르면 질문. 수정 전 승인: `.env`, `secrets/`, `deploy.sh`"

기안서의 보안 설계:
- 에이전트가 키를 **생성/추측하지 않음** — 작가님이 직접 발급, 쌍아가 등록 (7절 명시)
- 로컬 전용(`~/.claude/` 또는 `.env`), Git 커밋 금지, Cloud Run 미등록
- `.env` 수정 시 작가님 승인 전제

이 설계는 4조 1항·2항과 **직접 충돌하지 않는다**. 키 발급 주체가 작가님이고, 등록 행위에 승인이 수반되며, 저장소 노출 경로가 차단되어 있다.

**부기**: 기안서에서 "쌍아가 env 등록"이라 했으나, 쌍아는 VSCode 샌드박스(ch1 1조)라 직접 파일 수정이 제한적이다. 실무적으로는 막내 또는 민아가 등록하고 쌍아가 검증하는 흐름이 될 것이다. 이는 법적 충돌이 아닌 실무 절차 이슈이므로 하위 규정에서 정비하면 충분하다.

## 검토 항목 2: 브라우저 자동화 콘텐츠 게시와 헌법 5조 1항(윤리적 운용) 저촉 여부

### 판정: **조건부적합**

**근거:**

헌법 5조 1항: "불법/비윤리 자동화 (가짜 트래픽/리뷰) **절대 금지**"

기안서의 아웃바운드 용도:
- 자체 콘텐츠를 자체 채널(작가님 소유 계정)에 게시
- 허위 리뷰, 가짜 트래픽 목적 아님

**5조 1항과의 직접 충돌은 없다.** 자체 채널에 자체 콘텐츠를 게시하는 것은 "가짜 트래픽/리뷰"에 해당하지 않는다. 이것은 작가님이 직접 네이버에 글을 올리는 것과 동일한 행위를 에이전트가 대행하는 것이다.

**그러나 조건이 있다:**

각 외부 플랫폼의 **서비스 이용 약관(ToS)**이 브라우저 자동화를 금지하거나 제한할 수 있다. 기안서 4-3에서 "각 플랫폼 ToS 준수"를 언급했으나, **실제 ToS 확인은 미완료**이다.

- **네이버**: 블로그 Open API는 공식 지원하나, 세션 쿠키 기반 자동화는 ToS 위반 가능성
- **note.com**: 자동화 정책 확인 필요
- **X(Twitter)**: API 기반 게시는 허용, 브라우저 자동화는 ToS 위반 가능성
- **Instagram**: Business API 기반만 허용, 브라우저 자동화는 명시적 금지

**ToS 위반 = "불법 자동화"로 5조 1항 저촉.** 따라서:

| 조건 | 내용 |
|------|------|
| **선행 조건** | 각 플랫폼 env 등록 **전에** 해당 플랫폼 ToS의 자동화 정책을 확인하고 기록할 것 |
| **원칙** | 공식 API가 있는 플랫폼은 API 우선 사용. 브라우저 직접 조작은 API 미지원 시에만 |
| **기록** | 확인 결과를 `monkos-ops/tech/` 하위에 플랫폼별 ToS 준수 가이드로 문서화 |

## 검토 항목 3: "작가님 브라우징 대행" 정의의 법적 적절성

### 판정: **적합**

**근거:**

기안서의 정의: "브라우저 직접 탐색은 자동화 공격이 아니라, 작가님의 브라우징을 에이전트가 대행하는 것"

이 정의는 법적으로 **위임(delegation)** 개념에 해당하며, 다음과 정합한다:

1. **헌법 2조 역할 체계** — 작가님=총괄. 에이전트는 작가님의 지시를 실행하는 존재. "대행"은 이 위계의 자연스러운 연장이다.
2. **민아 권한 테이블(보정 2)** — "게시(publish) 행위는 작가님 사전 승인 필요". 대행의 전제인 사전 승인 체계가 이미 확립되어 있다.
3. **ch1 2조 ③항** — "작가님 → 민아 직접 지시 → 민아 실행". 브라우저 대행은 이 경로의 구체적 구현이다.

**부기**: "대행"의 법적 효과는 **행위의 주체가 작가님**이라는 것이다. 따라서 게시된 콘텐츠의 책임도 작가님에게 귀속된다. 이 점을 에이전트가 명확히 인지해야 하며, "에이전트 판단에 의한 자율 게시"는 대행의 범위를 벗어난다. 기안서 4-2에서 이를 정확히 방어하고 있다("게시는 작가님 사전 승인 필요").

## 검토 항목 4: 레퍼런스 수집 시 초상·저작권 리스크 방어

### 판정: **조건부적합**

**근거:**

기안서의 방어:
- "특정인 초상 카피·노출 절대 금지" (5조 1항 인용)
- "수집 대상: 패션코드, 포즈, 배경, 컬러팔레트 등 스타일 맥락"
- "MONKOS 엔진이 새 이미지를 생성 — 카피가 아닌 창작"

**원칙은 적절하다.** 저작권법상 "스타일"은 보호 대상이 아니며(표현만 보호), 스타일 참조 후 새 이미지를 생성하는 것은 법적으로 창작에 해당한다.

**그러나 실무 경계가 불명확하다:**

1. **"스타일 맥락 수집"과 "이미지 복제"의 경계** — 수집한 레퍼런스 이미지를 Imagen에 img2img 입력으로 직접 넣는 경우, 출력이 원본과 유사하면 "카피"에 해당할 수 있다. 기안서에 이 경계에 대한 기술적 가이드라인이 없다.
2. **초상권 범위** — "특정인 초상" 금지는 명확하나, "특정인이 아닌 모델의 포즈 참조"는 어디까지 허용되는가? 스톡 사진의 포즈 참조와 특정 브랜드 룩북의 포즈 참조는 법적 리스크가 다르다.

| 조건 | 내용 |
|------|------|
| **가이드라인 추가** | "수집한 이미지를 AI 모델에 직접 입력(img2img, reference image)하는 것은 카피 위험 행위로 분류하고, 작가님 승인을 필수로 한다" |
| **수집원 분류** | 저작권 프리(Unsplash, Pexels 등) / 공식 스톡 / 일반 웹 — 수집원별 허용 범위를 하위 규정으로 정비 |
