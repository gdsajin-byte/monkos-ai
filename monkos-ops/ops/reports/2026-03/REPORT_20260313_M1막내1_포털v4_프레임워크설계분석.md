### server.js 서빙 방식

- `index.html`은 **정적 파일**로 서빙 (`/public/index.html`)
- SSR 없음 (index.html은 순수 클라이언트 SPA)
- 별도 SSR 렌더링: `/blog`, `/faq`, `/gallery`, `/board` → `lib/cms/render.js`에서 전체 HTML 생성
- 각 SSR 페이지는 독립 HTML (index.html과 무관한 별도 레이아웃)
- Fallback: 확장자 없는 경로 → `.html` 자동 추가 → `/public/` 탐색

## 산출물 2: 전환 전략 비교표

### 현재 → v4 핵심 변경점

1. **레이아웃**: 단일 컬럼(max-width:1000px) → 3컬럼 그리드(200px+1fr+180px, max-width:1280px)
2. **테마**: 다크(#0a0a1a) → 라이트(#FAFAF8)
3. **히어로**: 단순 타이틀 → 컴팩트 다크 배너 + 유저바 + 갤러리 스트립
4. **네비게이션**: 하단 텍스트 링크 → sticky 상단 네비바
5. **서비스 카드**: 3장(LIVE+COMING SOON×2) → 2장(LIVE+FREE 크롭)
6. **사이드바**: 없음 → 좌(매거진+태그) + 우(가이드+크레딧)
7. **챗봇**: FAB+패널 → 하단 고정 입력바 + 모달
8. **콘텐츠**: 없음 → 블로그 목록, 활용법 3단계, 업계 소식
9. **푸터**: 최소 법적 링크 → SNS 채널 + 사업자 정보 풀텍스트
10. **라우팅**: 정적 SPA + 별도 SSR 페이지 → 사이드바 유지 + 메인만 교체 (SPA식)

### 전환 방식 비교

| 항목 | A) 전면 교체 | B) 점진적 마이그레이션 | C) 레이아웃 셸 분리 |
|------|------------|---------------------|-------------------|
| **설명** | v4 프로토 기반 새 index.html 작성. 기존 JS 기능을 새 구조에 이식 | 현재 파일에서 CSS 변수→라이트, 레이아웃→3컬럼으로 변경. 단계적 전환 | layout-shell.html(3컬럼+네비+챗봇) + 컴포넌트 JS 파일로 분리 |
| **수정 파일 수** | 1~2개 (index.html + 스타일) | 1개 (index.html 대규모 수정) | 5~8개 (셸 + 컴포넌트별 JS) |
| **기능 누락 위험** | ⚠️ 높음 — Auth, 결제, 챗봇, i18n 모두 재이식 필요 | ✅ 낮음 — 기존 코드 유지 | ⚠️ 중간 — 분리 과정에서 참조 깨짐 가능 |
| **혼합 기간** | 없음 (일괄 전환) | ⚠️ 김 (CSS 혼재, 구조 불일치) | ⚠️ 중간 (컴포넌트 분리 완료까지) |
| **SPA 라우팅 대응** | ✅ 처음부터 설계 가능 | ❌ 기존 단일 컬럼 구조에 끼워넣기 어려움 | ✅ 셸이 라우팅 담당으로 자연스러움 |
| **SSR 공존** | 별도 처리 필요 | 현행 유지 | 셸+SSR 통합 설계 가능 |
| **테스트 용이성** | ✅ A/B 배포 가능 (v3/v4 파일 분리) | ❌ 단일 파일이라 롤백 곤란 | ✅ 컴포넌트별 테스트 가능 |
| **공수** | 중 (JS 이식이 핵심) | 대 (리팩토링 범위가 넓음) | 대 (구조 재설계) |

### 추천안: **A) 전면 교체** (조건부)

**근거:**
1. 현재 index.html(2510줄)의 80%는 CSS(1280줄)이며, JS는 ~1200줄. CSS 변수 체계가 완전히 다르므로 점진적 전환은 오히려 복잡도가 높음
2. v4 프로토(HTML 36줄)가 이미 레이아웃+CSS 완성체 → 이것을 셸로 사용하고 기존 JS를 이식하는 것이 가장 효율적
3. SSR 페이지(blog/faq/gallery/board)는 이미 index.html과 독립 → index.html만 교체해도 SSR은 영향 없음
4. 기존 index.html을 `index-v3.html`로 백업 → 롤백 안전

**조건:**
- 이식 대상 JS 기능을 명확히 목록화 (Auth, 결제, 챗봇, i18n, 리전) → 누락 방지
- SSR 렌더링 함수(render.js)의 레이아웃을 v4 스타일로 통일하는 후속 작업 필요
- COMING SOON 카드 2장 제거 → v4 설계 문서 §2에 의거

## 산출물 3: SPA+SSR 공존 설계안

### 현재 라우팅 구조

```
[요청] → server.js 라우팅
├─ /blog, /blog/:slug      → renderBlogList/Post()  → 전체 HTML 반환 (독립 레이아웃)
├─ /ja/blog, /ja/blog/:slug → renderBlogList/Post('ja')
├─ /faq                     → renderFaq()            → 전체 HTML 반환
├─ /gallery                 → renderGallery()         → 전체 HTML 반환
├─ /board, /board/:id       → renderBoardList/Post()  → 전체 HTML 반환
├─ /api/*                   → JSON API
├─ /auth/*                  → OAuth 핸들러
└─ 나머지                   → 정적 파일 (public/)
```

**문제: SSR 페이지들이 각각 독립 HTML → 사이드바 없음, 네비 없음, 디자인 불일치**

### v4 라우팅 설계안

v4 문서 §3: "좌우 사이드바는 전 페이지 공통, 메인 영역만 교체"

#### 방안 1: SSR 유지 + 공통 레이아웃 함수 (✅ 추천)

```
[서버 렌더링 흐름]
renderPage(req, res, { title, body, lang }) {
  return layoutShell({
    head: seoHead(title, og, hreflang),
    hero: heroSection(),
    userBar: userBarSection(),
    galleryStrip: galleryStripSection(),
    nav: navSection(activePage),
    leftSidebar: leftSidebarSection(),
    mainContent: body,           ← 이 부분만 페이지마다 다름
    rightSidebar: rightSidebarSection(),
    chatbar: chatbarSection(),
    footer: footerSection(),
  });
}

// 사용:
renderBlogList → renderPage(req, res, { title, body: blogListHTML, lang })
renderBlogPost → renderPage(req, res, { title, body: blogPostHTML, lang })
renderFaq      → renderPage(req, res, { title, body: faqHTML, lang })
```

**장점:**
- SEO 완벽 (각 페이지가 완전한 HTML, OG 태그 포함)
- 소셜 공유 정상 동작 (서버에서 메타태그 생성)
- 3컬럼 레이아웃이 모든 페이지에서 일관
- 클라이언트 JS 최소화

**단점:**
- 페이지 이동마다 전체 HTML 새로 로드 (느린 전환)
- 사이드바 상태(스크롤 위치 등) 초기화

#### 방안 2: SPA 클라이언트 라우팅 + SSR Fallback

```
[클라이언트 네비게이션]
nav 클릭 → e.preventDefault() → fetch('/api/page/blog') → JSON → mainContent.innerHTML = data.html

[SSR Fallback - 직접 접근/크롤러]
/blog 직접 접근 → 서버에서 전체 HTML 반환 (방안 1과 동일)
```

**장점:**
- 페이지 전환이 빠름 (메인 영역만 교체)
- 사이드바 상태 유지
- 크롤러에는 SSR 제공 → SEO 유지

**단점:**
- 이중 렌더링 코드 필요 (서버 HTML + 클라이언트 fetch)
- 브라우저 히스토리 관리 (pushState) 필요
- OG 태그가 클라이언트 라우팅 시 갱신 안 됨 (소셜 공유는 SSR에서만)

### 추천: 방안 1 (SSR 유지 + 공통 레이아웃 함수)

**근거:**
- 현재 서비스 특성상 페이지 전환 속도보다 SEO가 중요 (블로그·FAQ가 검색 유입의 핵심)
- Cloud Run 서버 응답이 충분히 빠름 (SSR 1~3ms)
- 구현 복잡도가 낮음 (render.js의 layout 함수만 통일)
- 후속으로 방안 2(SPA 전환)를 추가하는 것은 방안 1 위에 올릴 수 있음 (역방향 불가)

### SPA 전환 로드맵 (선택적)

방안 1 완료 후, 체감 속도가 이슈가 되면:
1. 네비 클릭 인터셉트 → fetch로 메인 영역만 교체
2. `pushState` + `popstate` 히스토리 관리
3. 직접 접근(북마크/크롤러)은 기존 SSR 유지
4. 이 작업은 v4 안정화 이후 별도 Wave에서 진행

### v4 프로토 반응형 현황

프로토에는 미디어쿼리 **없음**. 3컬럼 고정(`200px 1fr 180px`).

### v4 반응형 설계안

```

│  좌 200px    │     메인 1fr       │  우 180px    │
└──────────────┴────────────────────┴──────────────┘
- 3컬럼 풀 레이아웃
- 히어로+유저바+갤러리 스트립 풀 너비

[Tablet] 768px ~ 1023px
┌────────────────────┬──────────────┐

└────────────────────┴──────────────┘
- 좌 사이드바 숨김 → 햄버거 메뉴 안으로 (v4 문서 §1)
- 우 사이드바 유지 (가이드 영상은 모바일에서도 가치 있음)

[Mobile] ≤767px
┌────────────────────────────────┐
│          메인 1fr               │
└────────────────────────────────┘
- 양쪽 사이드바 숨김
- 좌 사이드 매거진 → 햄버거 메뉴
- 우 사이드 가이드 → 메인 하단에 인라인 배치 (v4 문서 §1)
- 챗봇 바 하단 고정 유지
- 갤러리 스트립: 가로 스크롤 유지 (터치 제스처)

[Small Mobile] ≤480px
- 히어로 타이틀 축소
- 네비 오버플로우: 가로 스크롤 또는 햄버거 통합

/* 챗봇 바 — 모바일 키보드 겹침 방지 */
@media (max-width: 767px) {
  .chatbot-bar {
    position: fixed;
    bottom: 0;
    /* visualViewport API로 키보드 높이 대응 */
  }
}
```

### 키보드 겹침 테스트 포인트

v4 문서에서 "키보드 올라올 때 겹침 테스트 필요"로 명시:
- iOS Safari: `visualViewport.resize` 이벤트로 챗봇 바 위치 조정
- Android Chrome: `resize` 이벤트 + `innerHeight` 비교
- 구현 패턴: `chatbar.style.bottom = (window.innerHeight - visualViewport.height) + 'px'`

## 종합 의견

### 전환 전략 요약

```
[Step 1] v4 프로토 HTML → 새 index.html 셸 작성
         CSS 변수 라이트 테마 + 3컬럼 그리드 + 반응형 적용
         기존 index.html → index-v3-backup.html 보존

[Step 2] 기존 JS 기능 이식 (분리 권장)
         auth-client.js  — Auth 전체
         payment-client.js — 결제 모달
         chatbot-client.js — 챗봇
         i18n-client.js   — 다국어
         → <script src="..."> 로 v4 셸에 로드

[Step 3] render.js 레이아웃 통일
         layoutShell() 공통 함수로 SSR 페이지도 3컬럼 + 라이트 테마

[Step 4] 콘텐츠 연동
         좌 사이드바 매거진 → Firestore blog_posts fetch
         우 사이드바 가이드 → 정적 HTML (후속 짤방 추가)
         갤러리 스트립 → GCS 실제 이미지
```

### 막내 의견

- v4 전환은 **레이아웃+테마 변경**이 핵심이고 **비즈니스 로직(Auth/결제/챗봇)은 보존**이 핵심
- JS를 파일 분리하면 v4 전환뿐 아니라 향후 유지보수에도 유리 (현재 2510줄 단일 파일)
- SSR 페이지 레이아웃 통일은 별도 Wave에서 진행하는 것이 안전 (index.html 먼저 안정화 → SSR 후속)
