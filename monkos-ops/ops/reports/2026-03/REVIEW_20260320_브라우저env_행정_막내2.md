### 항목 1: env 저장 위치가 현행 인프라와 호환되는가

**판정: `보정필요`**

#### 기안서 제안

> 로컬 전용: `~/.claude/` 하위 또는 프로젝트 `.env` (gitignore 대상)

#### 문제 분석

**2개 후보지 모두 문제가 있다:**

**후보 A — `~/.claude/` 하위:**
- `~/.claude/`는 Claude Code/Desktop의 설정 디렉토리. 에이전트 고유 영역
- `process.env`로 자동 로드되지 않음 → 별도 로딩 메커니즘 필요
- 장점: 서버 env와 완전 분리, Git 추적 불가능 (프로젝트 외부)
- 단점: 에이전트가 명시적으로 파일을 읽어야 함. 표준화된 로딩 방법이 없음

**후보 B — 프로젝트 `.env`:**
- `.gitignore`에 `.env` 등록 확인 → Git 커밋 방지는 됨
- **그러나**: 프로젝트 `.env`는 관례상 **서버 환경변수**의 로컬 오버라이드 파일
- 현행 `config.js`는 `dotenv`를 사용하지 않고 `process.env` 직접 참조이지만, 향후 누군가 `dotenv`를 추가하면 에이전트 env(세션 쿠키, OAuth 토큰)가 서버 컨텍스트에 노출될 위험
- 에이전트 전용 env와 서버 env가 같은 파일에 혼재하면 관리 혼동

#### 보정 제안

**`.env.agent` 분리 파일 방식 권장:**

```
monk_project/
├── .env              ← 서버 환경변수 (기존, config.js용)
├── .env.agent        ← 에이전트 전용 env (신설, 브라우저 인증용)
└── .gitignore        ← .env.*.local 이미 있으므로 .env.agent 추가 필요
```

- `.gitignore`에 `.env.agent` 명시 추가 필요 (현행 `.env.*.local` 패턴은 매칭 안 됨)
- 에이전트가 필요 시 이 파일을 직접 읽어서 사용
- 서버 `config.js`와 완전 격리
- 디바이스별로 물리적으로 다른 파일이므로, 각 디바이스(iMac, M1)에서 독립 관리 가능

### 항목 2: Cloud Run env와 로컬 에이전트 env의 분리가 명확한가

**판정: `보정필요`**

#### 문제 분석

기안서 4조 1항에서 "Cloud Run env에는 등록하지 않음"이라고 선언했으나, **기안서 3-1에 이미 `ADMIN_UIDS`가 Cloud Run env에 배포 완료**로 기재되어 있다.

| env | 위치 | 성격 |
|-----|------|------|
| `ADMIN_UIDS` | Cloud Run env (**서버**) | 서버 인증 — 어드민 API 접근 제어 |
| `NAVER_BLOG_AUTH` 등 | 로컬 (**에이전트**) | 에이전트 브라우저 자동화 인증 |

이 구분은 올바르나, 기안서 내에서 혼재되어 있다. `ADMIN_UIDS`는 기안서 3-1에서 "구축 완료"로 나열되었지만, 이것은 **서버측 env**이지 에이전트 로컬 env가 아니다.

또한 `AGENT_API_KEYS`(config.js line 66)도 Cloud Run 서버측 env이다. 기안서에 미기재.

#### 보정 제안

- 기안서에서 **서버측 env**(ADMIN_UIDS, AGENT_API_KEYS)와 **에이전트 로컬 env**(NAVER_BLOG_AUTH 등)를 명확히 구분하는 분류표 추가
- "이 기안서의 범위는 에이전트 로컬 env만이며, 서버측 env는 기존 config.js 체계를 따른다"라는 범위 선언 필요

### 항목 3: 각 플랫폼별 인증 방식의 운영 부담 비교

**판정: `보정필요`**

#### 인증 방식별 운영 부담 분석

| 인증 방식 | 해당 플랫폼 | 유효 기간 | 갱신 방법 | 운영 부담 |
|----------|-----------|----------|----------|---------|
| **Open API 키** | 네이버 (옵션A) | 무기한 (rate limit만) | 불필요 | **낮음** |
| **OAuth 2.0** | X (Twitter) | access token 2시간, refresh token 6개월 | 자동 refresh 구현 필요 | **중간** |
| **Instagram Business API** | Instagram (옵션A) | 60일 (long-lived token) | 갱신 API 호출 | **중간** |
| **세션 쿠키** | note.com, Pinterest, Google, Instagram(옵션B), 네이버(옵션B) | 수 시간~수 일 (플랫폼마다 다름) | 브라우저 재로그인 | **높음** |

#### 문제점

1. **세션 쿠키 의존도가 과도함.** 8개 env 중 5개가 세션 쿠키 방식. 세션은 만료되면 에이전트가 자력으로 갱신할 수 없어 작가님이 수동 재로그인해야 함
2. **갱신 전략 미기재.** 세션 만료 시 에이전트가 어떻게 감지하고, 어떻게 작가님에게 갱신을 요청하는지 플로우가 없음
3. **각 플랫폼 ToS 검토 미완.** 기안서 6조 3항에서 "사전 조사" 요청은 했으나, 실제 조사 결과가 없는 상태에서 env 체계 구축을 선행하는 것은 순서가 역전

#### 보정 제안

- 우선 **Open API / OAuth 2.0 방식**이 가능한 플랫폼(네이버 Open API, X OAuth, Instagram Business API)부터 구축
- 세션 쿠키 전용 플랫폼(note.com, Pinterest)은 **ToS 확인 후** 2차로 진행
- env 갱신 플로우 추가: 만료 감지 → 텔레그램 알림 → 작가님 재발급 → env 갱신

### 항목 4: env 키 네이밍이 기존 config.js 24개 환경변수와 충돌하지 않는가

**판정: `보정필요` (1건 충돌 위험)**

#### 네이밍 충돌 전수 대조

| 기안서 제안 키 | 기존 config.js 키 | 충돌 여부 |
|-------------|-----------------|----------|
| `NAVER_BLOG_ID` | `NAVER_CLIENT_ID` | ⚠️ **NAVER_ 접두사 충돌** |
| `NAVER_BLOG_AUTH` | `NAVER_CLIENT_SECRET` | ⚠️ **NAVER_ 접두사 충돌** |
| `NOTE_COM_AUTH` | — | 없음 |
| `X_AUTH_TOKEN` | — | 없음 |
| `IG_AUTH` | — | 없음 |
| `PINTEREST_AUTH` | — | 없음 |
| `GOOGLE_IMAGE_AUTH` | `GOOGLE_CLIENT_ID` | ⚠️ **GOOGLE_ 접두사 근접** |
| `G2B_AUTH` | — | 없음 |
| `MSSMIV_AUTH` | — | 없음 |

#### 분석

- **NAVER_ 접두사**: 기존 `NAVER_CLIENT_ID`/`NAVER_CLIENT_SECRET`은 네이버 **검색 API**용. 신규 `NAVER_BLOG_*`는 네이버 **블로그 게시**용. 같은 `NAVER_` 네임스페이스에서 용도가 완전히 다른 키가 공존
- `.env.agent` 분리 파일을 채택하면 물리적 충돌은 없으나, 인간이 관리할 때 혼동 위험
- **GOOGLE_** 접두사도 `GOOGLE_CLIENT_ID`(OAuth 로그인)와 `GOOGLE_IMAGE_AUTH`(이미지 검색)로 용도 분리가 필요

#### 보정 제안

에이전트 전용 env에 `AGENT_` 접두사를 추가하여 서버 env와 네임스페이스 분리:

| 현재 제안 | 보정 제안 | 이유 |
|----------|----------|------|
| `NAVER_BLOG_AUTH` | `AGENT_NAVER_BLOG_AUTH` | 서버 NAVER_*와 분리 |
| `X_AUTH_TOKEN` | `AGENT_X_AUTH_TOKEN` | 일관성 |
| `GOOGLE_IMAGE_AUTH` | `AGENT_GOOGLE_IMAGE_AUTH` | 서버 GOOGLE_*와 분리 |
| 기타 | `AGENT_` 접두사 통일 | 에이전트 env 전체가 한 네임스페이스 |

## 종합 판정

### `조건부적합`

기안서의 **방향성**(에이전트 브라우저 연동 env 체계 구축)은 SPREAD 엔진 구현에 필수적이며, 보안 원칙(4조)도 헌법 4조 1항에 부합한다. 그러나 아래 4건의 보정 없이 시행하면 기존 인프라와의 정합성 문제가 발생한다.

#### 보정 조건 (4건)

| # | 보정 사항 | 중요도 | 미보정 시 영향 |
|---|----------|--------|---------------|
| **1** | env 저장을 `.env.agent` 분리 파일로 표준화 + `.gitignore` 추가 | 높음 | 서버 env와 혼재 → 보안 사고 위험 |
| **2** | 서버측 env(ADMIN_UIDS 등)와 에이전트 로컬 env의 범위를 기안서에서 명확히 분리 | 중간 | 관리 혼동 |
| **3** | 세션 쿠키 방식 플랫폼은 ToS 확인 후 2차 진행 + 만료 감지·갱신 플로우 추가 | 높음 | 세션 만료 시 에이전트 동작 불능, ToS 위반 리스크 |
| **4** | 에이전트 env 키에 `AGENT_` 접두사 통일 | 중간 | 기존 서버 env와 네이밍 충돌·혼동 |

#### 부가 권고

- 구현 우선순위에 동의하되, 1순위 네이버는 **Open API 방식**을 먼저 검토할 것 (세션보다 안정적)
- 정부·비즈니스 env(7, 8번)는 사업 진행 시점에 별도 기안서로 분리할 것
- env 갱신 이력 로깅 체계 도입 검토 (누가 언제 어떤 env를 갱신했는지 추적)
