# 꾸 역할 확장 삼권심사: 사법

> **[2026-06-12 13:29 KST]** iMac/막내3 → iMac/쌍아

## 1. 권한 경계 리스크

specs-data.json은 **규격 수치(size/pixels/dpi)와 텍스트(details/faqs/rejectionReasons)가 동일 JSON에 혼재**. 꾸가 텍스트 보강 중 인접 필드(dpi: 300 → 삭제, size 오타)를 실수로 변경하면 서비스에서 잘못된 규격을 표시한다.

**리스크: 중간.** 텍스트 필드는 중첩 객체(`details.ko`, `rejectionReasons.ja`)여서 최상위 수치 필드와 구조적으로 분리되어 있으나, JSON 편집 미숙 시 구문 오류로 전체 파싱 실패 가능.

**보정 권고**: PR 리뷰 필수 (꾸→M2/쌍아 확인 후 머지). `size`/`pixels`/`dpi` 필드 변경이 diff에 포함되면 플래그.

## 2. PF 충돌

꾸(M2)와 막내(iMac)가 동시에 specs-data.json을 편집하면 git conflict 발생. main 단일 브랜치이므로 push 선착순.

**리스크: 낮음.** 꾸의 편집 범위(텍스트)와 막내의 편집 범위(규격·코드)가 다른 JSON 키를 건드리므로 conflict 확률 자체가 낮고, 발생해도 머지 가능. 단, **동시 세션 시 한쪽이 pull 없이 push하면 reject** → 운영 교육 필요.

**보정 권고**: 청구안 ④경로에 "specs-data.json 편집 시 직전 pull 필수" 주석 추가.

## 3. 보안 누락

권한표에서 금지된 영역: 서비스 코드, 배포, 거버넌스, 크레딧/고객 데이터.

**누락 항목**:
- `monkos-ops/ops/` (세션 로그·보고서·지시서): 타 에이전트 문서 열람은 허용하되, **수정 금지** 명시 필요.
- `.claude/` (rules/skills/settings): M2에도 동일 구조 존재. 꾸가 M2 settings를 실험적으로 수정할 리스크 → "M2 .claude/ 수정은 작가님 승인" 한 줄 추가 권고.
- **시크릿**: M2에 .env가 있다면 ch4 10조 동일 적용 명시.

**리스크: 낮음.** 꾸 환경(M2)은 본진과 물리 분리되어 있어 직접 피해 범위 제한적.

## 4. 헌법 4조 충돌

"되는 것만 응답"은 **챗봇/RAG 응답** 규정(4조 4항). 꾸의 블로그·specs 콘텐츠 작성과는 적용 범위가 다르다.

단, specs 페이지는 사용자에게 **규격 정보를 제공하는 서비스 UI**이므로, 미확인 규격을 추가하거나 비공식 출처의 정보를 기재하면 4조 4항 취지에 반한다.

**보정 권고**: 권한표 `specs 콘텐츠` 비고에 "공식 출처 확인된 정보만 기재" 한 줄 추가.

## 5. 반론 — 해가 되는 시나리오

**시나리오 A**: 꾸 1인에 대해 헌법 개정(만장일치) + 법률 개정 + 규정 갱신을 진행하는 것 자체가 **거버넌스 과부하**. 실질적으로 작가님이 직접 지시하면 되는 범위에 헌법적 형식을 부여하면 이후 모든 팀원 역할 변경에 동일 절차가 요구된다.

→ **반박**: 그러나 미반영 상태에서 에이전트들이 꾸의 권한 범위를 모르면 충돌이 반복된다. **형식 비용 < 충돌 비용**.

**시나리오 B**: specs-data.json이 서비스 코드 경로(`monkos_AI/portal/`)에 위치. 꾸에게 "서비스 코드 ❌"이면서 그 내부 JSON만 "✅"인 예외가 모호함을 유발할 수 있다.

→ **보정 권고**: 권한표에 "monkos_AI/portal/lib/cms/specs-data.json 텍스트 필드만 허용. 같은 디렉토리의 다른 파일 수정 불가" 명시.
