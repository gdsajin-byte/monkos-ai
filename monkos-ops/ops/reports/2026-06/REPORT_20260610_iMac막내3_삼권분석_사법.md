```

  1. 변경된 MD 파일의 basename 추출
  2. docs/ ↔ monkos-ops/ 양쪽에 동일 basename 존재 여부 확인
  3. 존재 시 MD5 비교 → 동일 내용이면 이중화 경고, 다르면 정본 충돌 에러

난이도: 중 — basename 충돌이 의도적인 경우(README.md 등) 화이트리스트 필요
효과: ★★★ — "과거가 현재를 뒤집는 버그" (작가님 03-08) 방지의 물리적 게이트
```

| 대책 | 적용 대상 | 효과 | 구현 방식 |
|---|---|:---:|---|
| **1. 이원 유지** | git-safety, deployment | ★★★ | rules에 잔류 (skills로 이관하지 않음). 안전 규칙은 "항상 로딩"이 본질 |
| **2. CI 이관** | session-log 폴더 규칙, YAML 검증, 커밋 메시지 | ★★★ | rules에서 삭제해도 CI가 강제. "코드로 정착"(하네스 원리) |
| **3. hooks 연동** | makne-guard (착수 전 PF 확인) | ★★ | Claude Code hooks: `on_tool_call` → 지시서 파일 열 때 자동으로 PF 확인 스킬 호출 |
| **4. 자동 skill 호출 체인** | pf-ops (PF 갱신 의무) | ★★ | 세션 마감 skill에 PF 갱신 체크를 체이닝 |
| **5. 경고 skill** | data-access | ★☆ | credits.sh 자체 방어가 있으므로 skill 미호출 시에도 실행 단계에서 차단 |

### 3-3. 권고: 3계층 강제력 배치

```
┌─────────────────────────────────────────────┐
│  Layer 1: CI (코드 강제)                      │
│  → secret-scan, 정본이중화, YAML검증,         │
│    폴더규칙, 커밋메시지, 내부호칭유출          │
│  → 위반 시 push 차단 또는 경고 Issue          │
├─────────────────────────────────────────────┤
│  Layer 2: Rules (항상 로딩, 에이전트 강제)     │
│  → git-safety, deployment, data-access       │
│  → 안전/보안/배포 = 이관 금지 영역            │
├─────────────────────────────────────────────┤
│  Layer 3: Skills (호출 시 로딩, 판단 보조)     │
│  → session-log, pf-ops, cdp-browser,         │
│    portal-seo, references, makne-guard       │
│  → 작업 컨텍스트 제공, 절차 가이드            │
│  → Layer 1 CI가 최종 안전망                   │
└─────────────────────────────────────────────┘
```

**원칙**: "위반하면 안 되는 것"은 CI(자판기)로, "위반하면 안 되지만 판단이 필요한 것"은 rules(게이트)로, "알면 좋은 것"은 skills(판단 보조)로. 하네스 아키텍처의 자판기/판단/게이트 3계층과 정합.

## 4. 위성 산출물 검증 체계

### 4-1. 현행 PR 게이트

| 검사 | 위성 PR 대상 | 작동 여부 |
|---|---|:---:|
| secret-scan (push) | ✅ main push 시 | ✅ |
| secret-scan (PR) | ✅ PR to main | ✅ |
| YAML 검증 | ❌ 미구현 | ❌ |
| 파일 네이밍 검증 | ❌ 미구현 | ❌ |
| 내부 호칭 검사 | ❌ 미구현 | ❌ |
| 코드 리뷰 required | ❌ branch protection 미설정 | ❌ |

### 4-2. "PR 경유 필수" 규정과 현행 CI 결합 분석

**현황**: secret-scan만이 PR에서 작동하는 유일한 품질 게이트.

**충분성 판정**: **불충분**.

| 검증 필요 영역 | 현행 게이트 | 갭 |
|---|---|---|
| 비밀정보 유출 | ✅ secret-scan | 충분 |
| 코드 품질 | ❌ lint/test 없음 | 🔴 갭 |
| 문서 규격 (YAML) | ❌ 없음 | 🟡 갭 |
| 브랜딩 준수 | ❌ 없음 | 🟡 갭 (C7로 해소 가능) |
| 정본 위치 준수 | ❌ 없음 | 🟡 갭 (C1으로 해소 가능) |
| 인적 리뷰 | ❌ branch protection 미설정 | 🔴 갭 |

### 4-3. 위성 문서 (보고서·청구안) 검증

위성이 올리는 문서의 검증:
- **보고서**: YAML frontmatter 검증(C6)이 도입되면 자동 게이트
- **청구안(PETITION)**: 현행은 삼권심사 절차(거버넌스 프로세스). CI로 대체 불가 — 내용의 법적 적합성은 인적 판단 영역. 다만 형식 검증(YAML, 파일명 패턴)은 C6/C8로 자동화 가능

### 4-4. 권고: 위성 PR 최소 게이트

| 순위 | 게이트 | 대상 | 차단/경고 |
|:---:|---|---|:---:|
