## 1. 요약 (TL;DR)

- **증상**: 한국어(kr)·일본어(ja)는 발행됐으나 **영어(en) 버전이 누락**.
- **근본원인**: EN 번역 응답이 **`maxOutputTokens: 8192` 한계로 truncation** → 반환 JSON이 **position 7053에서 미완결(Unterminated string)** → 파싱·복구 3단계 전부 실패 → 저장 누락.
- **번역 자체는 성공**(영어 텍스트는 정상 생성됨). 실패 지점은 **JSON 직렬화/파싱 단계**.
- **구조적 문제**: 본건만의 우연이 아니라, **장문·특수문자 밀집 글에서 상존하는 위험**. OPUS 플라이휠로 장문 콘텐츠가 늘면 빈발 가능.

## 4. 근본원인 — 코드 분석

### 4-1. 번역 호출 설정 (`translate.js:112-119`)
```js
const response = await ai.models.generateContent({
  model: 'gemini-2.5-flash',
  contents: [{ role: 'user', parts: [{ text: prompt }] }],
  config: {
    maxOutputTokens: 8192,          // ← 병목
    temperature: 0.3,
    responseMimeType: 'application/json',  // ← JSON 강제
  },
});
```

- 본건 원문 content = **약 11KB**. 게다가 **코드블록(```), 다이어그램(│ ┼), 다수 큰따옴표** 등 JSON 이스케이프 대상 특수문자가 밀집.
- 영어 번역문 + JSON 구조 + 이스케이프 오버헤드가 **8192 출력 토큰을 7053자 지점에서 초과** → 응답이 거기서 잘림 → JSON이 닫히지 못함(Unterminated string).

### 4-2. 복구 3단계 전부 실패 (`translate.js:126-153`)
1. `JSON.parse(text)` → Unterminated string (실패)
2. sanitize(제어문자·역슬래시 보정) 후 재파싱 → 여전히 **미완결**이라 실패
3. regex로 `"content":"..."` 추출 → 닫는 따옴표가 없어 **매칭 실패**
→ `throw` (150행). en은 `continue` 없이 루프 종료, **저장되지 않음**.

> 복구 로직은 "깨진 JSON"(이스케이프 오류)은 수리하도록 설계됐으나, **"잘린 JSON"(truncation)은 복구 불가** — 닫는 구조 자체가 응답에 없기 때문.

## 5. 왜 ja는 성공하고 en은 실패했나

- **동일한 8192 한계**를 공유. 차이는 출력 길이.
- 일본어 번역 JSON은 8192 토큰 내에 **완결**됐고, 영어 번역 JSON은 **초과**했다.
- 영어 번역문 길이 + 본건의 특수문자(코드블록·다이어그램·따옴표) JSON 이스케이프 오버헤드가 겹쳐 en에서 한계 도달.
- 즉 **"장문 + 특수문자 밀집"이 임계점을 넘긴 언어에서 truncation** 발생. 언어 순서(ja 먼저, en 나중)는 무관 — 각 언어 독립 호출.

## 6. 부차 발견 — 번역본 색인 미발송 (별건, 구조적)

- `translate.js`의 번역본 저장부(set/update, 185·197행)에 **`requestIndexing`·sitemap ping·llms.txt 호출이 전혀 없음**.
- 6/7 추가한 Google Indexing API는 `blog.js`의 `handleBlogCreate`(215)·`handleBlogUpdate`(289) — **한국어 원본 발행에만** 결선됨.
- → ja(및 미래 모든 번역본)는 published=true여도 **색인 요청 미발송**. GSC "unknown" 상태의 일부 원인.
- 추가로 Google Indexing API는 공식적으로 `JobPosting`/`BroadcastEvent` 전용 — 일반 블로그는 **sitemap 의존이 정석**(별도 검토 필요).
