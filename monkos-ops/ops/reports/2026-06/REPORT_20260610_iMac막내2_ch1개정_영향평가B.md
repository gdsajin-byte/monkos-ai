### 1-2. 팀원 에이전트(한·꾸)와 접근 범위 비교

| 접근 영역 | 팀원 에이전트 | 웹 민아 |
|-----------|------------|--------|
| 본진 레포 | **별도 레포** (위성 프로젝트 모델) | **본진 클론 직접** |
| works/ submodule | 직접 clone 가능 (팀원 디바이스) | 클론 범위에 포함 (읽기 가능) |
| 마케팅 outbox | works/ 경유 | 클론 범위이므로 읽기 가능, 쓰기는 PR 경유 |
| MEMORY.md | 자체 CLAUDE.md | **접근 불가** (클론에 미포함) |
| governance/ | 헌법 상속, 자체 확장 | 읽기 자유, 수정 금지 |

**판정: 경계 명확. 단, works/ 접근에 주의 필요.**

- 팀원은 별도 레포에서 works/를 직접 clone하여 outbox/inbox 구조로 운용. 웹 민아는 본진 클론 내 submodule로 works/를 볼 수 있으나, submodule이 초기화되었는지는 환경에 따라 다름.
- **충돌 가능성**: 웹 민아가 works/ 내 파일을 PR로 수정할 경우, 팀원이 동시에 같은 파일을 수정하면 충돌. 다만 현행 운용에서도 이 리스크는 존재하며, PR 머지 시 충돌 해소가 가능하므로 **위험도 낮음**.

## 평가 항목 2: 세션 로그·지시서·보고서 체계(ch3·ch4) 영향

### 2-1. 세션 로그 분산 기록 원칙 (ch3 1조)

ch3 1조: "각 에이전트는 자기 세션 로그를 자체 기록한다."

- 웹 민아가 PR 브랜치에 `2026-MM-DD_웹_민아.md` 세션 로그를 적립하는 방식은 ch3 1조의 "자체 기록" 원칙과 **정합**.
- **단, 정본 위치 문제 발생**: ch3 1조 정본은 `monkos-ops/ops/sessions/YYYY-MM/`. PR 머지 전까지 세션 로그는 브랜치에만 존재 → 정본 경로에 없는 "미완결 기록" 상태.
- 청구안 §3-6이 "PR 머지 전 위성 산출물은 정본이 아니다"라고 규정하므로, 세션 로그도 머지 시점에 정본이 됨. **논리적 정합**.

**이슈**: ch3 3조(세션 마감 절차)의 "push 완료 = 세션 마감 인정" 규정과의 관계.
- 웹 민아는 전용 브랜치에 push하지만 main에는 push하지 않음. main push = 마감이 아니라 **PR 머지 = 마감**으로 해석해야 함.
- **보정 필요**: ch3 3조에 "위성 환경은 PR 머지 완료를 push 완료로 간주한다" 해석 단서 추가 권고.

### 2-2. 정본 단일 원칙과 PR 브랜치 (ch4 4조)

ch4 4조: "정본은 하나만 존재한다. 참조본은 읽기전용."

- PR 머지 전: 위성 산출물은 브랜치에만 존재. main의 정본과 **이중화가 아님** (main에는 해당 파일 자체가 없으므로).
- PR 머지 후: main에 편입 → 정본이 됨. 브랜치 삭제 시 참조본도 소멸.
- **충돌 없음**. 청구안의 "머지 전 정본이 아니다" 규정이 ch4 4조와 자연스럽게 정합.

**단, 기존 정본 수정 시 주의**: 웹 민아가 기존 PF README 등을 PR로 수정하면, 머지 전까지 main 정본과 브랜치 버전이 공존. 이는 일반적인 Git branch 워크플로우의 특성이며, ch4 4조가 금지하는 "이중화"(양쪽 다 정본으로 취급)와는 다름.

## 평가 항목 3: 배포·보안 체계(ch5·ch6) 영향

### 3-1. "main 직푸시 금지, 배포 금지"와 ch5·ch6

**ch5 (배포 규칙)**: 웹 민아는 GCP 접근 자체가 구조적으로 불가. deploy.sh도 실행 불가.
→ **충돌 없음. ch5 적용 외**.

**ch6 1조 (브랜치 전략)**: "기본 작업 브랜치: main."
- 웹 민아의 `claude/*` 브랜치는 ch6 1조에서 허용하는 "격리가 필요한 경우 별도 브랜치"에 해당.
- ch6 1조: "별도 브랜치 작업 완료 시 main에 머지 후 삭제한다" — PR 워크플로우와 정합.

**ch6 2조 (main 운용)**: "모든 디바이스·에이전트는 main에서 직접 작업한다."
- 웹 민아는 main에서 직접 작업하지 않고 `claude/*` 브랜치 경유. ch6 2조의 "직접 작업" 원칙과 **형식적 긴장**.
- 그러나 ch6 1조가 "격리가 필요한 경우"를 허용하고 있고, 위성 환경은 구조적으로 main 직푸시가 불가하므로 **실질적 충돌 아님**.
- **보정 권고**: ch6 2조에 "위성 환경은 전용 브랜치 + PR 경유를 허용한다" 단서 추가, 또는 청구안이 ch6 1조의 예외 적용을 명문화.

### 3-2. `claude/*` 브랜치 네이밍과 ch6 1조

- ch6 1조는 브랜치 네이밍 규칙을 별도 규정하지 않음. `claude/*`는 Claude Code 플랫폼이 자동 생성하는 접두어.
- **충돌 없음**. 다만 향후 다른 위성(GitHub Actions 등)도 브랜치를 만들 경우 네이밍 컨벤션 확대 필요.

### 3-3. 시크릿 유출 방어 (secret-scan CI)

현행 `secret-scan.yml` 트리거:
```yaml
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
```

- **PR to main 트리거 활성** → 웹 민아가 `claude/*` → main PR을 열면 secret-scan이 자동 실행.
- 변경 파일 대비 패턴 매칭: API 키(AIza, AKIA, sk-), .env 파일, private key 등 감지.
- **결론: 커버됨**. 위성이 실수로 시크릿을 포함해도 PR 머지 전에 차단.

**추가 리스크**: 위성이 PR을 열기 전 `claude/*` 브랜치에 push하는 시점에는 스캔이 돌지 않음. 그러나:
1. 웹 민아 환경에는 `.env`가 없음 (클론에 미포함)
2. API 키 하드코딩은 헌법 4조 1항에서 이미 전면 금지
3. PR 머지 시점에 반드시 스캔됨

→ **위험도 낮음**.
