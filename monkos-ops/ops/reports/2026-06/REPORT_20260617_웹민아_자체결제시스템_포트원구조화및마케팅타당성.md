## 0. 한 장 요약 (TL;DR)

1. **"자체 결제시스템"의 정확한 정의가 핵심.** 카드 승인·자금 정산을 우리가 직접 하는 것(=PG/VAN)은 전자금융업 등록(자본금·금융위 인가·보안인증) 장벽으로 1인기업엔 비현실. 하지만 작가님이 그린 "여러 카드사·페이를 개별 연동해주고 건당/정액으로 받는" 모델은 **결제 오케스트레이션(통합연동) 레이어**로 합법·실현 가능하며, **포트원이 정확히 그 모델**이다.
2. **우리는 이미 절반 와 있다.** 토스페이먼츠(KR)·레몬스퀴지(JP/글로벌)를 웹훅 기반으로 실운용 중. 자금은 각 PG가 정산(우리 계좌 직접 경유 X). 즉 우리는 이미 "자금 미보유 + 연동/회계 소유" 구조다.
3. **인크루트 연동(대안A 웹훅)이 곧 오케스트레이션의 첫 외부 실증.** 제3자(인크루트) 결제 → 웹훅 수신 → 우리 엔타이틀먼트/크레딧 부여. 이 패턴을 일반화하면 "홈페이지 납품 + 결제 모듈 내장" 상품이 된다.
4. **마케팅 결론**: "자체 결제 시스템 **구축**(통합·연동·정산 모듈)"은 사실에 부합 → ✅ 사용 가능. 단 "우리가 PG/결제대행사다", "수수료 없는 자체 결제"처럼 **자금 정산 주체를 우리로 오인시키는 표현은 표시광고법·전자금융거래법 리스크** → ❌. 카피는 "구축·연동·내장" 프레임으로 잡아야 안전.

## 1. 현재 결제 인프라 실측 (사실 베이스)

> 출처: `monkos_AI/portal/lib/payments.js`, `monkos_AI/portal/lib/shared/config.js`

| 결제수단 | 상태 | 시장 | 흐름 | 자금 정산 주체 |
|---------|------|------|------|--------------|
| **토스페이먼츠** | ✅ 프로덕션 | KR | client SDK → `POST /api/payments/toss/confirm` → Toss 승인 API → Firestore 크레딧 적립 | **토스** (수수료 차감 후 사업자 계좌 입금) |
| **레몬스퀴지** | ✅ 프로덕션 | JP/글로벌 | `POST /api/checkout` → 체크아웃 URL → 결제 → `POST /api/webhooks/lemonsqueezy`(HMAC 검증) → 크레딧 적립 | **레몬스퀴지** (MoR — VAT·세무 대행 후 정산) |
| 카카오페이·네이버페이·포트원·KCP·이니시스 | ❌ 미구현 | — | — | — |

**핵심 구조적 사실 3가지:**
- **자금은 우리 계좌를 거치지 않는다.** 토스·레몬스퀴지가 자기 명의로 결제를 수령·정산하고, 우리에겐 정산금만 입금된다. 즉 우리는 이미 **"자금 미보유"** 위치 — 전자금융업 규제 밖.
- **크레딧 = 가상자산.** 결제 성공 → Firestore `users.credits` 트랜잭션 증가 + `transactions`/`payments` 원장 기록. 멱등성(중복지급 차단)·환불 회수 구현됨.
- **웹훅 + HMAC 검증 패턴이 이미 가동 중**(레몬스퀴지). 이것이 인크루트·향후 외부 결제 연동의 재사용 본보기.

> ℹ️ 키 운용 정정(2026-06-17 작가님 확인): **프로덕션은 라이브키로 정상 동작.** `TOSS_SECRET_KEY`는 GCP Secret Manager 정본(24종 중 18번, 2026-06-03 광역오더 #8 등록)에서 런타임 주입된다. 로컬 `monkos_AI/.env`의 `test_sk…`는 개발용 기본값으로, 운영/로컬 키 분리는 **정상 상태**다. (초안에서 로컬 .env만 보고 "프로덕션 테스트키"로 단정했던 것을 정정 — SECRET_INVENTORY가 정본.)

## 2. 포트원과의 구조화

### 2.1 한국 결제 생태계에서 우리의 좌표

| 레이어 | 역할 | 과금 방식 | 자금 보유 | 진입 장벽 |
|--------|------|----------|----------|----------|
| 카드사 | 발급·매입 | — | — | — |
| **VAN사** | 카드사↔가맹점 통신중계 (오프라인 POS 본령) | **건당 정액** | 일부 | 카드사 직접계약·보안인증·과점 |
| **PG사** (토스페이먼츠 등) | 온라인 결제대행·자금 정산 | 거래액 % | **O** | **전자금융업 등록** |
| **오케스트레이션 SaaS** (포트원) | 여러 PG·페이를 단일 API로 통합연동 | **자유 (건당·정액·구독)** | **X** | **라이선스 불필요** |
| **애플리케이션** (현재 MONKOS) | 결제 위에서 서비스·크레딧 회계 | 자유 | X | 없음 |

**작가님이 묘사한 "VAN처럼 개별 연동 + 건당/정액"의 정체 = 오케스트레이션 SaaS 레이어.** 진짜 VAN(자금·카드사 직접계약)이 아니라, 자금을 안 건드리고 연동 기술만 파는 모델이다. 포트원이 이 모델로 이미 시장에 존재한다 = 진입 가능성의 증거.

### 2.2 포트원과 결합하는 3가지 구조

```
[모델 A] 포트원을 우리가 백본으로 채택
  MONKOS/고객사 서비스 → 포트원 1개 연동 → N개 PG·페이 자동 확보
  · 장점: 카카오/네이버/PG 다수를 직접 연동 안 하고 한번에. 개발 공수 최소.
  · 우리 위치: 포트원 위 애플리케이션. "자체 결제 인프라"라기엔 약함.

[모델 B] 우리가 오케스트레이션 레이어를 자체 구축  ★ 작가님 구상
  고객사 PG가맹(자기명의) ─┐
                          ├→ [MONK 결제모듈] → 통합 결제창·엔타이틀먼트·정산회계 → 고객사
  토스/레몬스퀴지 연동 추상화 ┘
  · 자금: PG→고객사 직접. 우리는 안 건드림 → 라이선스 불필요.
  · 과금: 우리가 SaaS 이용료(건당/월정액) 자유 설계.  ← "VAN식 과금"이 여기서 성립
  · 우리 위치: 포트원과 같은 레이어(경쟁/대체). "자체 결제시스템" 명분이 가장 강함.

[모델 C] PG 리셀러/파트너
  토스페이먼츠·포트원·이니시스 파트너 등록 → 고객사 모집·연결 → 수수료 셰어
  · 라이선스 불필요. 단 과금·정책이 PG사 종속 → 자율성 낮음.
```

### 2.3 현실 권고 — 하이브리드 (B를 지향하되 A를 백본으로)

처음부터 N개 PG를 무(無)에서 직접 연동(포트원 없이)하는 것은 공수·유지보수가 크다. **현실적 자체 구축 = 포트원(또는 직접 연동한 토스/레몬스퀴지)을 백본으로 두고, 그 위에 우리만의 ⟨엔타이틀먼트·크레딧·정산·멀티테넌트 회계⟩ 레이어를 얹어 "MONK 결제 모듈"로 패키징**하는 것이다.

| 레이어 | 자체 구축? | 근거 |
|--------|-----------|------|
| 카드 승인·자금 정산 | ❌ (포트원/PG 위임) | 라이선스·PCI 장벽 |
| 멀티 PG 통합 연동 | △ (포트원 백본 + 자체 추상화) | 공수 최적화 |
| **엔타이틀먼트·크레딧 회계** | ✅ **이미 보유** | `payments.js` 트랜잭션·원장 |
| **멀티테넌트 정산 대시보드** | ✅ 자체 구축 | 신규(BIZ 부서 관할) |
| **결제 모듈 SDK/위젯 (납품용)** | ✅ 자체 구축 | 신규 (홈페이지 상품화 핵심) |

→ **"자체 결제시스템"의 실체 = PG 위에 얹은 우리 소유의 결제·정산 오케스트레이션 모듈.** 이것이 자금규제를 피하면서 상품화 가능한 정확한 형태다.

## 3. 인크루트 결제 연동구조 — 오케스트레이션의 첫 실증

> 출처: `DESIGN_20260616_인크루트_화이트라벨_결제연동.md`, `REPORT_20260616_M1민아_PARTNER_인크루트회신보완본.md`, `PF_PARTNER/README.md`

### 3.1 확정된 구조

| 항목 | 결정 |
|------|------|
| 결제 수령 | **인크루트가 수령** (우리는 웹훅 신호만 수신) |
| 연동 방식 | **대안 A — 실시간 웹훅** (HMAC 서명검증 + 멱등성 + 역검증). 레몬스퀴지 패턴 재사용 |
| 결제 퍼널 | **선결제형** — 인크루트 스토어에서 미리 구매 → 웹훅으로 엔타이틀먼트 선충전 → 우리 `charge.html`(토스) 스킵 |
| 정산 | 도매 단가 **₩1,000/건** 기반 + **우리 API 호출 카운트가 정산 베이스**(인크루트 결제데이터 의존 제거) |
| 브랜딩 | **코브랜딩** "Incruit with MONKOS AI" (화이트라벨 거부) |
| 엔타이틀먼트 | 미결정 — "다운로드권 N컷" vs "크레딧 충전" (쌍아 PF_PARTNER 설계 시 확정) |

### 3.2 흐름도

```
① 인크루트 스토어 결제(인크루트 PG 수령)
   ↓ 웹훅
② POST /api/webhooks/incruit   ← 레몬스퀴지 HMAC 패턴 복제(기존 코드 재사용)
   ├─ HMAC 서명검증  ├─ 멱등성 체크  └─ 역검증(인크루트에 "진짜 결제냐" 재조회)
   ↓
③ 호출 카운트 기록(정산 베이스)
   ↓
④ 유저 엔타이틀먼트 부여(크레딧 충전 or 다운로드권)
```

### 3.3 구조적 의미

인크루트 건은 **"제3자 결제 → 우리 엔타이틀먼트 부여"의 첫 외부 사례**다. 이 웹훅 어댑터를 **provider 추상화**(`provider: 'incruit' | 'toss' | 'lemon' | ...`)로 일반화하면, 그대로 **"어떤 외부 결제든 받아서 우리 회계로 환원하는" 오케스트레이션 코어**가 된다. 즉 인크루트 연동은 §2.3 자체 모듈의 **첫 벽돌**이다.

- 신규 개발 규모: ~400~500줄 / 1~2주 (설계서 실측)
- 인프라 여유: Cloud Run 50배·Gemini Tier2 500배 — 충분
- 선행 보안 과제: `/health` 모델명 노출 등 노출표면 3건 + 토스 라이브키 전환

## 4. "자체 결제시스템 구축" 마케팅 타당성

### 4.1 법적 프레임 (헌법 4조 4항 — "되는 것만", 표시광고법·전자금융거래법)

마케팅 카피의 적법성은 **"누가 자금을 정산하는가"를 오인시키는가**로 갈린다.

| 표현 | 판정 | 사유 |
|------|------|------|
| "맞춤 **결제 시스템 구축**" / "결제·정산 모듈 **내장**" | ✅ | 사실(우리가 연동·회계·위젯을 구축해 납품) |
| "결제 **연동** 일체 제공" / "멀티 결제수단 통합" | ✅ | 사실 |
| "**자체** 결제 시스템(엔타이틀먼트·크레딧 회계)" | ✅ (한정 시) | 우리 소유 레이어가 실재. 단 범위 명시 권장 |
| "**수수료 없는** 자체 결제" | ❌ | PG 수수료는 존재. 허위·과장 |
| "우리가 **결제를 대행**합니다" / "MONKOS **PG**" | ❌ | 무등록 결제대행 표방 → 전자금융거래법 |
| "**카드 결제를 직접 처리**" | ❌ | PCI·라이선스 미보유. 허위 |

### 4.2 안전하고 강력한 카피 방향

- ✅ **"결제 시스템까지 구축해 드립니다"** — 홈페이지 납품 + 멀티 PG 연동 + 크레딧/정산 모듈을 한 패키지로. (사실)
- ✅ **"증명사진 AI + 결제·정산 일체형 홈페이지"** — 우리 차별화(AI 콘텐츠 + 결제 내장)를 묶음. (사실)
- ✅ **"자체 엔타이틀먼트·정산 엔진 탑재"** — 크레딧/이용권 회계가 실제 우리 자산. (사실)
- ⚠️ "자체 결제시스템"을 단독·무한정으로 쓰면 PG/대행 오인 소지 → **반드시 "구축/연동/내장/정산 모듈"과 결합**해 자금 정산 주체 오인을 차단.

### 4.3 결론

**홈페이지 납품 시 "자체 결제시스템 구축"이라는 마케팅은 붙일 수 있다.** 단 그 의미가 **"PG·간편결제를 통합 연동하고, 그 위에 MONKOS가 소유한 엔타이틀먼트·크레딧·정산 모듈을 얹어 구축·납품한다"**로 정의될 때에 한한다. "우리가 결제를 대행/정산한다"는 인상은 금지선. 이 선만 지키면 사실에 부합하는 강력한 차별화 메시지다.

## 5. 종합 판단 & 로드맵

### 5.1 판단

- 작가님 구상(VAN식 개별연동+건당/정액)은 **결제 오케스트레이션 SaaS = 모델 B**로 정확히 성립하며 합법이다.
- 우리는 토스·레몬스퀴지 실운용 + 크레딧 회계 보유로 **이미 모델 B의 절반**을 구축했다.
- 인크루트 웹훅(대안A)을 **provider 추상화**로 만들면 그것이 오케스트레이션 코어의 첫 모듈이 된다.
- 마케팅 "자체 결제시스템 구축"은 **"구축/연동/내장" 프레임 한정으로 적법·유효**.

### 5.2 단계 로드맵 (제안 — 실행은 작가님/쌍아 판단)

| 단계 | 내용 | 담당 | 비고 |

| **2. 인크루트 실증** | 대안A 웹훅 어댑터 구현 (1~2주) | 쌍아→막내 | 첫 외부 결제원 |
