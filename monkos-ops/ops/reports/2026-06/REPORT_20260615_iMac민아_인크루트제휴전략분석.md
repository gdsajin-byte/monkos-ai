## 2. 핵심 통찰 — 두 개의 축을 분리하라

작가님 답변에서 "단독이 가능하냐 → 커스터마이징·별도 서버로 갈 생각"이라 하셨는데, 여기 **서로 다른 두 질문이 섞여 있습니다.** 협상에서 이걸 분리하지 않으면 손해 봅니다.

| | **축 A — 독점성 (Exclusivity)** | **축 B — 납품 아키텍처** |
|---|---|---|
| 질문 | 잡코리아·사람인에도 입점하나, 인크루트에만? | 어떤 기술 구조로 납품하나? |
| 인크루트가 물은 것 | ✅ 이것 ("단독이냐 동시냐") | — |
| 작가님이 답한 것 | — | ✅ 이것 ("별도 엔드포인트·그쪽 결제·수수료 정산") |
| 성격 | **사업·협상** 결정 | **기술·정산** 결정 |
| 비용 | 독점=우리 시장 절반 포기 | 화이트라벨=1~2주 개발 |

**결정적 포인트**: 작가님이 택한 화이트라벨 별도 엔드포인트 구조는 **같은 패턴을 잡코리아·사람인에 그대로 복제**할 수 있게 만든다(아래 5장). 즉 **기술적으로는 멀티 입점이 더 자연스럽다.** 따라서 독점을 줄 이유는 기술에 없다 — 오직 "독점 대가를 충분히 받을 때"만 전략적으로 선택하는 것이다.

> ⚠️ 흔한 함정: "단독으로 해달라니 별도 서버 만들면 되겠네"로 두 축을 합쳐버리면, 별도 서버는 만들어주고 독점 대가는 못 받는 최악이 된다. 별도 서버는 멀티 입점에도 어차피 필요한 우리 자산이다.

## 4. 정산 구조 설계 — "별도 엔드포인트"의 숨은 무기

작가님 구상의 최대 가치는 커스터마이징이 아니라 **정산 신뢰성**입니다.

> **우리 API를 통과하지 않으면 사진이 나오지 않는다 → 우리 호출 카운트가 곧 정산 베이스다.**
> 인크루트 결제 시스템을 신뢰하거나 들여다볼 필요가 없다. 우리 엔드포인트의 호출 로그를 우리가 직접 집계해 청구한다. CPA(성과형)에서 가장 위험한 "판매량 불투명" 문제가 구조적으로 해소된다.

### 두 가지 정산 모델 비교

| | (A) 도매단가 (Wholesale) — **권장** | (B) 매출 쉐어 (Rev-share) |
|---|---|---|
| 방식 | 우리가 건당/번들당 고정 단가를 받음. 인크루트가 위에 마진 얹어 판매 | 인크루트 판매가의 N%를 우리가 가져감 |
| 예시 | 5컷 번들 도매 **₩4,000~5,000** → 인크루트가 ₩9,900에 판매 | 판매가 ₩10,000의 40~50% = ₩4,000~5,000 |
| 우리 원가 | ~₩1,000/번들(컷당 ₩200) → 도매 ₩4,000이면 마진 ~75% | 동일 |
| 장점 | 우리 수익 예측 가능, 호출 카운트로 검증 간단 | 인크루트가 비싸게 팔수록 우리도 이득 |
| 단점 | 인크루트 판매가 통제 어려움 | 인크루트 매출 데이터 의존(불투명) |
| 인크루트가 부른 것 | — | "CPA 매출 쉐어" = 이쪽 선호 |

**협상 전략**: 저쪽은 "매출 쉐어(B)"를 불렀지만, 우리는 **도매단가(A) 기반 + 최소판매가(MAP) 합의**로 끌고 가는 게 유리. 정산 검증이 깔끔하고(우리 호출 카운트=근거), 직판 가격 방어(아래 6장)와도 맞물린다. 명목상 "매출 쉐어"로 포장하되 실질은 도매단가 하한을 두는 하이브리드도 가능.

### 참고 — 현행 단가 (자료: pricing.html, 과금재설계 REPORT 20260614)
- 직판 현행: 1장 완성 80c ≈ **₩11,600**
- 직판 제안 번들: **₩10,000 / 5컷** + 무제한 규격·다운로드 (마진 KR ~86%/74%, 글로벌 ~77%)
- 원가: ~₩200/컷 (5컷 ₩1,000)
- 결제 수수료: 토스 3.74%(일반)/0.63%(영세), 레몬 5%+$0.5 → **인크루트 납품 시 이 수수료는 인크루트 부담**(그쪽이 결제하므로) = 우리 마진에 유리

## 5. 기술 실현성 — 가능, 1~2주 (자료: 아키텍처 조사)

현재 monkos.ai는 이미 마이크로서비스 구조(Portal=인증·크레딧·결제 / idphoto-kr·jp=생성 엔진)라 화이트라벨 분리가 쉽다.

| 작업 | 난이도 | 기간 |
|------|--------|------|
| 별도 도메인·Cloud Run 인스턴스(`idphoto-recruit`) | 쉬움 | 1~2일 |
| 크레딧/결제 분기 (인크루트 선결제 → 호출권 변환) | 보통 | 3~5일 |
| API 키 기반 파트너 인증 (현 HMAC 확장) | 보통 | 2~3일 |
| 테넌트 격리 (Firestore/GCS 경로 분리) | 다소 높음 | 별도 |
| **Option A 전체 (권장)** | **보통** | **1~2주** |

- 권장 구현(조사 Option A): `monkos-idphoto-kr-recruit` 신규 배포 → `PARTNER=recruit` 분기 → 기존 로직 최대 재사용. 결제는 인크루트 PG, 우리는 호출 시 차감/카운트.
- 같은 템플릿으로 잡코리아·사람인 복제 가능 → **멀티 입점 확장 비용이 거의 0** (= 독점 줄 기술적 이유 없음의 근거).
- ⚠️ 막내 실행 시 헌법 준수: 배포는 `deploy.sh` 경유(ch5), 크레딧 변경은 `scripts/credits.sh` 경유(ch4 10조), 시크릿 생성·추측 금지(헌법 4조).
