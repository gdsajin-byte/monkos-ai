### Cloud Run 태그 기반 라우팅 메커니즘

Cloud Run 태그는 **특정 리비전에 고정된 전용 URL**을 부여하는 기능:

```
https://v4-preview---monkos-portal-4jeplpqpua-uc.a.run.app
       ^^^^^^^^^^
       태그명이 서브도메인으로 삽입
```

**핵심 특성:**
1. 태그 URL로 접속하면 **해당 리비전의 코드가 그대로 실행**됨
2. 환경변수, 시크릿, 인증은 **서비스 레벨에서 공유** — 태그 리비전도 동일한 Firestore, GCS, 결제 키 등에 접근
3. 하나의 서비스에 **여러 태그 동시 존재 가능** (v4-preview, v5-preview 등)
4. 커스텀 도메인(`monkos.ai`)은 **트래픽 분할 대상 리비전에만 연결** — 태그 URL은 `.run.app` 도메인만 사용
5. 태그 URL 접속 시 `monkos.ai` 쿠키가 **전송되지 않음** (도메인 불일치) → 인증 세션은 태그 URL 내에서 새로 수립 필요

### v4-preview 접속 시 예상 동작

- **CMS (blog/faq/gallery)**: 정상 — 같은 Firestore, 같은 데이터
- **인증**: 부분 정상 — Google OAuth redirect_uri가 `monkos.ai`로 고정이므로 태그 URL에서 로그인 후 `monkos.ai`로 리다이렉트됨 → 태그 URL로 돌아오지 않음
- **결제**: 같은 시크릿 사용이므로 웹훅은 정상이나, 결제 후 리다이렉트 URL이 `monkos.ai`로 고정
- **Telegram 웹훅**: 서비스 URL(`monkos.ai`) 고정이므로 태그 URL에는 도달하지 않음

⚠️ **태그 URL은 디자인/렌더링 검증 전용으로 적합. 인증·결제 플로우 검증에는 한계가 있음.**

## §2 시나리오 비교표

### A안 — v5-preview 태그 방식

**구조:**
```
main 브랜치에 v5 코드 포함
  → deploy.sh preview → --tag v5-preview --no-traffic
  → 태그 URL로 v5 확인
  → 확정 시 --to-latest로 트래픽 전환
```

**v4/v5 코드 공존 문제 — "코드 공존 불필요":**
태그는 리비전(= 특정 배포 시점의 코드 스냅샷)에 고정되므로, **같은 코드베이스에 v4/v5 분기 로직이 필요하지 않음**. v5 코드를 커밋하고 preview 배포하면, 그 리비전이 v5를 렌더하고 프로덕션 리비전은 기존 코드를 계속 실행.

단, **개발 중 프로덕션 배포(prod)를 하면 v5 코드가 프로덕션에 나감** → v5 완성 전까지 prod 배포 시 v5 변경이 포함되지 않도록 관리 필요.

| 항목 | 평가 |
|------|------|
| 복잡도 | ★☆☆ 낮음 — 기존 패턴 재활용 |
| 코드 변경 | render.js/home.js에 v5 렌더러 추가 (기존 함수 교체) |
| 인증/결제 테스트 | ⚠️ 태그 URL에서 제한적 |
| 개발 중 prod 배포 | ⚠️ v5 미완성 코드가 prod에 나갈 위험 |
| 전환 비용 | ★☆☆ 최소 — 트래픽 전환만 |
| 롤백 | ★☆☆ 즉시 — 이전 리비전으로 트래픽 복귀 |
| SEO 영향 | 없음 — URL 불변 |
| deploy.sh 수정 | 태그명 `v4-preview` → `v5-preview` 변경만 |

**개발 중 prod 배포 위험 해법:**
- 방법 1: v5 관련 파일을 별도 경로(`lib/cms/render-v5.js`)에 작성하고, server.js import만 전환
- 방법 2: Git 브랜치 전략 — v5 작업은 feature 브랜치에서 진행, preview 배포만 해당 브랜치에서 수동 실행. 단, deploy.sh가 main 브랜치를 강제하므로 **preview의 브랜치 체크를 완화**해야 함

### B안 — 서버 내 라우트 분기 (/v5/*)

**구조:**
```
server.js에 /v5/* 라우트 추가
  → /v5/ → renderHomeV5()
  → /v5/blog → renderBlogListV5()
  → ... (모든 SSR 라우트 복제)
프로덕션에서 monkos.ai/v5/ 로 직접 비교
```

| 항목 | 평가 |
|------|------|
| 복잡도 | ★★★ 높음 — 모든 SSR 라우트 복제 |
| 코드 변경 | server.js 대량 수정, v5 렌더러 병렬 유지 |
| 인증/결제 테스트 | ✅ 완전 — 같은 도메인·쿠키 |
| 개발 중 prod 배포 | ✅ 안전 — /v5/ 경로는 의도적 접근만 |
| 전환 비용 | ★★☆ 중간 — 라우트 교체 + 구코드 삭제 |
| 롤백 | ★★☆ 코드 롤백 필요 (트래픽만으로 불가) |
| SEO 영향 | ⚠️ /v5/ URL이 크롤링되면 중복 콘텐츠 문제 (robots.txt Disallow 필요) |
| deploy.sh 수정 | 불필요 |

**치명적 단점:**
- SSR 라우트가 30개+ → 전부 `/v5/` 버전 복제 = server.js 2배
- v5 확정 후 `/v5/` 라우트 전부 삭제 + 기존 라우트를 v5 렌더러로 교체 = 대규모 리팩토링
- `/v5/blog/slug`에서 게시된 글의 canonical URL이 `/blog/slug`로 가야 하는데, v5 렌더러에서 별도 처리 필요

### C안 — 환경변수 플래그 분기

**구조:**
```
PORTAL_VERSION=v5 환경변수
  → server.js에서 렌더러 선택:
    if (PORTAL_VERSION === 'v5') renderBlogListV5()
    else renderBlogList()
preview 배포에 v5 플래그, prod에는 미설정
```

| 항목 | 평가 |
|------|------|
| 복잡도 | ★★☆ 중간 — server.js에 분기 로직 산재 |
| 코드 변경 | server.js 분기 + v5 렌더러 파일 추가 |
| 인증/결제 테스트 | ⚠️ 태그 URL에서 제한적 (A안과 동일) |
| 개발 중 prod 배포 | ✅ 안전 — 환경변수 미설정 시 v4 유지 |
| 전환 비용 | ★★☆ 중간 — 환경변수 전환 + 분기 코드 정리 |
| 롤백 | ★☆☆ 즉시 — 환경변수 제거만 |
| SEO 영향 | 없음 — URL 불변 |
| deploy.sh 수정 | preview에 `PORTAL_VERSION=v5` 추가 |

**실질 문제:**
- if/else가 SSR 라우트마다 산재 → 코드 가독성 악화
- v5 확정 후 v4 분기 전부 삭제 필요 — B안과 비슷한 정리 비용
- 환경변수로 "어느 렌더러를 쓸지" 분기하는 것은 사실상 C안 = A안 + 불필요한 분기 레이어

### D안 — render.js 모듈 교체 방식 ★추천★

**핵심 아이디어:**
v5는 **렌더링 계층만 변경** (디자인 전환). 데이터 소스(Firestore)·라우팅·인증·결제는 불변.
→ render.js의 **Fragment 함수 반환값 형식이 동일**하므로, Shell(레이아웃) 함수만 교체하면 됨.

**구조:**
```
현재:
  server.js → render.js (layoutShell + Fragment)

v5:
  server.js → render.js (Fragment 유지) + layout-v5.js (layoutShellV5)
  preview: layoutShellV5 사용
  prod: 기존 layoutShell 사용 → 전환 시 import 교체
```

**상세 설계:**

```
lib/cms/
├── render.js          ← Fragment 함수들 (데이터 로직, 불변)
├── layout.js          ← layoutShell, layoutHead, layoutNav, layoutFooter (v4)
├── layout-v5.js       ← layoutShellV5 (v5 타일 그리드 셸)
└── home-v5.js         ← renderHomeV5 (홈은 별도 구조이므로 분리)
```

render.js에서 현재 `layoutHead`, `layoutNav`, `layoutFooter`는 **내부 함수** (export 안 됨). 이것들을 `layout.js`로 추출하고, v5 버전을 `layout-v5.js`에 작성.

**server.js 변경은 최소:**
```js
// 전환 전
import { layoutShell } from './lib/cms/layout.js';
// 전환 후
import { layoutShell } from './lib/cms/layout-v5.js';
```

또는 환경변수 하나로:
```js
const layout = process.env.PORTAL_LAYOUT === 'v5'
  ? await import('./lib/cms/layout-v5.js')
  : await import('./lib/cms/layout.js');
```

| 항목 | 평가 |
|------|------|
| 복잡도 | ★☆☆ 낮음 — Fragment/Shell 분리가 자연스러움 |
| 코드 변경 | layout 함수 추출 (리팩토링) + v5 레이아웃 신규 작성 |
| 인증/결제 테스트 | ⚠️ 태그 URL 한계 (A안과 동일) |
| 개발 중 prod 배포 | ✅ 안전 — v5 파일은 import 안 하면 사용 안 됨 |
| 전환 비용 | ★☆☆ 최소 — import 경로 1줄 변경 |
| 롤백 | ★☆☆ 즉시 — import 원복 또는 환경변수 제거 |
| SEO 영향 | 없음 — URL 불변, Fragment(SEO 메타) 불변 |
| deploy.sh 수정 | 태그명 변경 + 선택적 환경변수 |
| render.js 분리 연계 | ★★★ 최적 — 분리의 자연스러운 첫 단계 |

## §3 전환(cutover) 절차 설계

### D안 기준 절차

#### Phase 1: 준비 (개발 중)

1. render.js에서 layout 함수 추출 → `lib/cms/layout.js` (순수 리팩토링, 동작 불변)
2. `lib/cms/layout-v5.js` 작성 (v5 타일 그리드 셸)
3. `lib/cms/home-v5.js` 작성 (홈 전용 v5 렌더러)
4. server.js에 환경변수 분기 추가:
   ```js
   const layoutMod = process.env.PORTAL_LAYOUT === 'v5'
     ? await import('./lib/cms/layout-v5.js')
     : await import('./lib/cms/layout.js');
   export const { layoutShell } = layoutMod;
   ```
5. deploy.sh에 v5-preview 태그 추가

#### Phase 2: Preview 배포 + 검증

1. `./deploy.sh preview` (v5-preview 태그, `PORTAL_LAYOUT=v5` 환경변수)
2. 태그 URL로 디자인 검증:
   - 전 SSR 페이지 (blog, faq, specs, pricing, guide, gallery, board) 렌더 확인
   - 모바일/데스크톱 반응형 확인
   - SEO 메타(og:, canonical, hreflang) 불변 확인
3. 프로덕션 도메인에서 인증/결제 플로우는 **기존 v4에서 이미 검증된 상태** — 레이아웃 교체는 프론트 셸만이므로 재검증 불필요

#### Phase 3: 트래픽 전환 (2가지 옵션)

**옵션 A — 즉시 전환 (권장):**
```bash
# 프로덕션 배포에 PORTAL_LAYOUT=v5 추가
./deploy.sh prod  # (deploy.sh 수정 후)
```
→ 새 리비전이 v5 레이아웃으로 배포, 100% 트래픽.

**옵션 B — 점진적 전환:**
```bash
# 1. v5 코드로 preview 배포
./deploy.sh preview

# 2. 5% 트래픽 배분
gcloud run services update-traffic monkos-portal \
  --region us-central1 \
  --to-revisions NEW_REVISION=5,CURRENT_REVISION=95

# 3. 모니터링 후 100%
gcloud run services update-traffic monkos-portal \
  --region us-central1 \
  --to-latest
```

점진적 전환의 **한계**: 같은 사용자가 새로고침마다 v4/v5를 번갈아 볼 수 있음 (Cloud Run은 sticky session 미지원). 디자인 전환에서는 혼란 유발 → **즉시 전환 권장**.

#### Phase 4: 롤백 (문제 발생 시)

```bash
# 즉시 롤백 — 이전 리비전으로 트래픽 복귀
gcloud run services update-traffic monkos-portal \
  --region us-central1 \
  --to-revisions monkos-portal-00230-fkv=100
```
→ 30초 이내 롤백 완료. 코드 변경 불필요.

또는 환경변수만 제거하고 재배포:
```bash
# PORTAL_LAYOUT 제거 → v4로 복귀
./deploy.sh prod
```

#### SEO 영향

- **URL 불변** → canonical, hreflang, sitemap 전부 그대로
- **HTML 구조 변경** → Google이 재크롤링하면 "레이아웃 시프트" 감지할 수 있으나, URL 동일이므로 색인 영향 없음
- **JSON-LD 불변** → Fragment에서 생성하므로 레이아웃과 무관

#### 인증 세션

- **쿠키 기반 인증 (`monkos.ai` 도메인)** → 레이아웃 변경과 무관, 세션 유지
- **인메모리 토큰 (`directTokens` Map)** → 리비전 변경 시 초기화 (Cold Start). 5분 TTL이므로 실질 영향 미미

## §4 render.js 분리와의 연계 평가

### 현재 render.js 구조 (2362줄)

```
render.js
├── 유틸 (escapeHtml, stripHtml, getSeoDescription)          ~40줄
├── 레이아웃 (layoutHead, layoutNav, layoutFooter, layoutShell)  ~130줄
├── Blog (blogListFragment, blogPostFragment, render*)        ~400줄
├── FAQ (faqFragment, renderFaq)                              ~110줄
├── Gallery (galleryFragment, renderGallery)                  ~100줄
├── Board (boardListFragment/Post/Write, render*)             ~310줄
├── Guide (guideFragment, renderGuide)                        ~180줄
├── Specs (specsListFragment, specsDetailFragment, render*)   ~400줄
│   ├── SPECS_I18N (3개 언어 번역 테이블)                      ~60줄
│   └── SPECS_PAGE_STYLE (CSS)                                ~220줄
├── Sitemap (renderSitemap)                                   ~70줄
└── Pricing (pricingFragment, renderPricing)                  ~180줄
```

### Fragment/Shell 인터페이스 (이미 존재)

render.js는 이미 Fragment 패턴을 사용:
```js
// Fragment 반환 형식 (모든 페이지 공통)
{
  title: string,
  description: string,
  seoMeta: string,      // <head> 삽입용 HTML
  htmlLang: string,     // 'ko' | 'ja' | 'en'
  pageStyle: string,    // <style> 내용
  bodyContent: string,  // <body> 내 HTML
  pageScript: string,   // <script> 내용
}
```

이 인터페이스가 **v5 전환의 핵심 분리점**:
- Fragment = 데이터 + SEO + 콘텐츠 (불변)
- Shell = 전체 페이지 래핑 (v5에서 교체)

### 자연스러운 분리 단계

| 단계 | 작업 | 파일 |
|------|------|------|
| 1 | layout 함수 추출 | `layout.js` (layoutHead, layoutNav, layoutFooter, layoutShell) |
| 2 | v5 레이아웃 작성 | `layout-v5.js` (layoutShellV5 + 타일 그리드 CSS) |
| 3 | (선택) 페이지별 Fragment 분리 | `fragments/blog.js`, `fragments/specs.js` 등 |
| 4 | (선택) render.js → 얇은 라우터 | render.js는 import + render 함수만 유지 |

**단계 1~2만으로 v5 전환 가능.** 단계 3~4는 향후 유지보수 편의를 위한 추가 리팩토링.

### 각 시나리오별 render.js 분리 적합도
