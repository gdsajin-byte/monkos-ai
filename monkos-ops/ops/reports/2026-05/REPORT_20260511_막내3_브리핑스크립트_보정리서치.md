## 이슈 1: 기업마당 크롤링 — 셀렉터 과잉 + URL 조립 오류

### 현상

브리핑 출력에서 3가지 문제 확인:

1. **`javascript:void(0)` URL 혼입**: `[창업(92)](https://www.bizinfo.go.krjavascript:void(0); return false;)`
2. **텍스트 가비지**: `1272창업2026년 광주광역시 여성창업지원 사업 공고2026-05-07 ~ 2026-05-27광주광역시한국여성경제인협회광주지회2026-05-0` — 행 번호+분야+제목+기간+부처+기관+등록일이 한 줄로 뭉침
3. **중복 항목**: 같은 공고가 다른 형태로 2회 노출

### 원인 (코드 라인)

`daily_briefing.py:178` — `soup.select("tr, li, .list-item, a")`

- **셀렉터가 과도하게 범용적**: `tr`은 테이블 전체 행을 잡으므로 `get_text(strip=True)`가 모든 `<td>` 셀(번호, 분야, 제목, 기간, 부처, 기관, 등록일, 조회수)을 하나로 합침
- **`a` 태그 무차별 매칭**: 네비게이션 메뉴의 `<a href="javascript:void(0)">`까지 포함
- `:181~183` URL 조립: `row.get("href")`가 `<tr>` 태그(href 없음)에 대해 None 반환 → `row.find("a")`로 폴백 시 첫 번째 `<a>` (네비게이션 링크)를 잡음

### 리서치 결과

#### 1) 기업마당 페이지 HTML 구조 (실측 확인)

목록 페이지(`/web/lay1/bbs/S1T122C128/AS/74/list.do`)는 `<table>` 구조:

```
<tr>

  <td>경영</td>                              ← 지원분야

      [경기] 2026년 사회적가치지표(SVI)...
  </a></td>                                  ← 지원사업명 (제목+링크)
  <td>2026-04-30 ~ 2026-09-30</td>           ← 신청기간
  <td>고용노동부</td>                         ← 소관부처
```

HTML 크롤링으로 고치려면 `tr` 내 3번째 `<td>` → `<a>` 태그만 정밀 타겟해야 하지만, 깨지기 쉬운 접근.

#### 2) 공식 API 존재 확인 (핵심 발견)

**기업마당 공식 API가 존재한다.**

- **엔드포인트**: `https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do`
- **인증**: `crtfcKey` 파라미터 (데모 키 `QP6yn2` 공개 — 실측 동작 확인)
- **응답 형식**: JSON (`dataType=json`) / XML (`dataType=xml`)

**주요 파라미터**:

| 파라미터 | 설명 | 예시 |
|----------|------|------|
| `crtfcKey` | API 키 | `QP6yn2` (데모) |
| `dataType` | 응답 형식 | `json` |
| `pageUnit` | 페이지 당 건수 | `5` |
| `pageIndex` | 페이지 번호 | `1` |
| `hashtags` | 키워드 필터 | `AI` |

**응답 JSON 구조**:
```json
{
  "jsonArray": [
    {
      "pblancNm": "[경기] 2026년 사회적가치지표(SVI)...",
      "pblancUrl": "https://www.bizinfo.go.kr/sii/siia/selectSIIA200Detail.do?pblancId=PBLN_...",
      "jrsdInsttNm": "고용노동부",
      "hashtags": "경영,경기,2026,AI,...",
      "reqstBeginEndDe": "2026-04-30 ~ 2026-09-30",
      "creatPnttm": "2026-05-08 15:15:15"
    }
  ]
}
```

- 실측: `hashtags=AI`로 검색 시 정상 JSON 반환 확인
- GitHub 참조 구현: [kwanGDss/mcp-bizinfo](https://github.com/kwanGDss/mcp-bizinfo) (Node.js, 동일 API+데모 키 사용)

#### 3) API 키 운용

- 데모 키(`QP6yn2`)는 rate limit/폐기 가능성 있음
- 프로덕션용: `https://www.bizinfo.go.kr/web/lay1/program/S1T175C174/apiList.do`에서 전용 키 발급 가능
- `BIZINFO_API_KEY` 환경변수 / GitHub Secrets 등록 권장

### 보정안

**HTML 크롤링 전면 폐기 → 공식 JSON API로 전환**

```python
def fetch_bizinfo(url, keywords):
    api_url = "https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do"
    items = []
    for kw in keywords:
        params = {
            "crtfcKey": os.environ.get("BIZINFO_API_KEY", "QP6yn2"),
            "dataType": "json",
            "pageUnit": "5",
            "pageIndex": "1",
            "hashtags": kw,
        }
        resp = requests.get(api_url, params=params, timeout=15)
        resp.raise_for_status()
        data = resp.json()
        for entry in data.get("jsonArray", []):
            title = entry.get("pblancNm", "")
            detail_url = entry.get("pblancUrl", "")
            pub_date = entry.get("creatPnttm", "")[:10]  # YYYY-MM-DD
            if title and detail_url and len(items) < 3:
                if not any(i["url"] == detail_url for i in items):
                    items.append({"title": title[:80], "url": detail_url, "date": pub_date})
        if len(items) >= 3:
            break
    return items[:3]
```

**변경 범위**: `daily_briefing.py:173~186` 전체 교체. `url` 파라미터는 무시(API 엔드포인트 고정).

**추가 작업**: `BIZINFO_API_KEY`를 GitHub Secrets에 등록 (데모 키 폴백 포함).

## 이슈 2: RSS 날짜 잘림

### 현상

브리핑 출력:
```
- [...] — Fri, 08 Ma
- [...] — Wed, 06 Ma
- [...] — Tue, 05 Ma
```

RFC 2822 날짜 `Fri, 08 May 2026 15:00:00 +0000`의 앞 10자만 잘려서 `Fri, 08 Ma` — 의미 없는 문자열.

### 원인 (코드 라인)

`daily_briefing.py:168` — `pub_date.text.strip()[:10]`

`[:10]` 슬라이싱은 ISO 8601(`2026-05-08T...`)에서만 유효. RSS 2.0의 RFC 2822 형식에서는 10자가 날짜 중간에서 잘림.

### 리서치 결과

#### 1) RSS 2.0 pubDate 표준

RSS 2.0은 RFC 822/RFC 2822 날짜 형식 사용:
```
Day, DD Mon YYYY HH:MM:SS timezone
```

Google AI Blog 실측 예시:
- `Fri, 08 May 2026 15:00:00 +0000`
- `Wed, 06 May 2026 16:00:00 +0000`
- `Mon, 04 May 2026 17:00:00 +0000`

timezone 표기는 `+0000`, `GMT`, `EST`, `PDT` 등 혼재 가능.

#### 2) Python 파싱 방법 비교

| 방법 | 장점 | 단점 |
|------|------|------|
| `email.utils.parsedate_to_datetime()` | **stdlib**, RFC 2822 전용 설계, 의존성 0 | 비표준 형식 거부 |
| `dateutil.parser.parse()` | 거의 모든 형식 처리 | 서드파티 (`python-dateutil`) |
| `time.strptime()` 수동 패턴 | 의존성 0 | timezone 변형마다 패턴 추가 필요, 취약 |

#### 3) 권장 방식

`email.utils.parsedate_to_datetime()`이 최적: stdlib이고, RSS pubDate가 정확히 이 함수의 설계 대상.

### 보정안

`daily_briefing.py:168` 교체:

```python
# Before:
date_str = pub_date.text.strip()[:10] if pub_date else ""

# After:
from email.utils import parsedate_to_datetime

if pub_date:
    try:
        dt = parsedate_to_datetime(pub_date.text.strip())
        date_str = dt.strftime("%Y-%m-%d")
    except (ValueError, TypeError):
        date_str = ""
else:
    date_str = ""
```

**변경 범위**: `daily_briefing.py:168` 1행 → 5~6행. import 1줄 추가 (stdlib, 의존성 없음).

## 이슈 4: GSC 데이터 지연 미처리

### 현상

브리핑 출력:
```
🔴 GSC 노출 전주 대비 -100% 하락 (89 → 0)
GSC 클릭 | 0 | 3 | -100%
GSC 노출 | 0 | 89 | -100%
```

GSC 상위 검색어/페이지 테이블도 완전 비어있음. 실제 하락이 아닌 **데이터 미도착 오탐**.

### 원인 (코드 라인)

`daily_briefing.py:308` — `yesterday = date.today() - timedelta(days=1)`

어제(1일 전) 데이터를 쿼리하지만, GSC는 이 시점에 데이터가 없음 → 0 반환 → 이상 감지 로직이 `-100% 하락`으로 판정.

### 리서치 결과

#### 1) GSC 공식 데이터 지연 사양

| 항목 | 값 |
|------|-----|
| 확정(final) 데이터 지연 | **~2~3일** |
| 예비(fresh) 데이터 지연 | ~1~2일 (`dataState: "all"` 필요) |
| 장애 시 최대 지연 | 5~6일 (2025-02, 2024-07 사례) |

Google 공식 문서: "finalized data has a ~2 day processing delay"

#### 2) `dataState` 파라미터

2020년 12월 도입:

| 값 | 동작 |
|-----|------|
| `"final"` (기본) | 확정 데이터만. ~2일 지연 |
| `"all"` | 예비 데이터 포함. 1~2일 지연. 변동 가능 |
| `"hourly_all"` | 시간별 분할. 부분/미완 데이터 포함 |

#### 3) 최신 가용일 자동 감지

Google 공식 권장: "날짜 그룹핑으로 가용 날짜 범위를 먼저 확인"

`dataState: "all"` 사용 시 응답에 `first_incomplete_date` 메타데이터 포함 — 이 날짜 이전은 확정, 이후는 예비.

#### 4) 업계 관행

- **고정 오프셋**: `days=3`이 가장 보편적 (정상 시 안전, 장애 시에도 대부분 커버)
- **동적 감지**: 5일 범위 쿼리 후 데이터 있는 가장 최근 날짜 사용
- **폴백 체인**: 2일→3일→4일 순차 시도

#### 5) 자동 알림에서의 핵심 원칙

**예비 데이터(`dataState: "all"`)로 이상 감지하면 안 됨** — 변동성이 커서 매일 오탐 발생. 이상 감지는 반드시 `final` 데이터 기반.

### 보정안

**`days=1` → `days=3` 변경 + 빈 데이터 방어**

```python
# Before:
yesterday = date.today() - timedelta(days=1)
last_week_same_day = yesterday - timedelta(days=7)

# After:
target = date.today() - timedelta(days=3)
compare = target - timedelta(days=7)
```

**추가 방어**: `detect_anomalies()`에서 today 값이 전부 0이면 "데이터 미도착"으로 분류, 하락 알림 스킵:

```python

    alerts = []

    # GSC 데이터 미도착 방어
    if gsc_today["clicks"] == 0 and gsc_today["impressions"] == 0:
        alerts.append("- 🟡 GSC 데이터 미도착 (3일 전 기준). 정상 지연 가능성 높음.")
    else:
        # 기존 이상 감지 로직
        ...
```

**선택적 강화**: 동적 가용일 감지 (5일 범위 쿼리 → 데이터 있는 최신 날짜 자동 선택). 단, 복잡도 대비 `days=3` 고정이 충분히 안정적.

**변경 범위**: `daily_briefing.py:308~309` (날짜 계산) + `:189~205` (이상 감지 방어).
