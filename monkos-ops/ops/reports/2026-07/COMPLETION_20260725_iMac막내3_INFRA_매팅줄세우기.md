### 4-2. ⚠️ 검증 #1 — 상한 초과의 원인은 노크 간격이다

| N | 최장 대기 | 노크 수 | 폴백 |
|---|---|---|---|
| 4 | 5,919 ms | 3 | 0 |
| 8 | 11,024 ms | 7 | 0 |
| **16** | **21,609 ms** | 15 | **0** |

**실측 처리율 = 1.32초/건.** 회귀식 `최장대기 ≈ (N−1) × 1.32 + 1.6초` — 세 구간 전부 오차 0.3초 이내로 맞는다.

**지시서 근거 산수는 0.8초/건(표 회전)을 가정해 16건 12초로 봤다. 실측은 1.32초/건이라 21.6초다.** 차이 0.54초/건의 정체:

- 서버 처리 0.78초가 끝난 뒤, 빈 슬롯은 **다음 노크가 도착할 때까지 유휴**로 남는다. 노크 간격 1초 > 회전 0.78초이므로 매 회전마다 평균 약 0.5초가 버려진다.
- 즉 **노크 간격이 표 회전보다 길면 처리율이 회전이 아니라 노크 간격에 지배된다.**

**그렇다면 노크를 촘촘히 하면 되는가 — 아니다.** 노크마다 **이미지 페이로드(약 180KB)를 전량 재업로드**한다. 15개 클라이언트가 1초 간격이면 이미 약 2.7MB/s가 터널로 간다. 400ms로 줄이면 6.75MB/s다. **터널 대역과 Cloud Run 이그레스 비용이 절약한 몇 초보다 비싸다.**

또한 `MATTE_QUEUE_WAIT_MS`는 **노크 예산**이지 총 대기가 아니다. 마지막 노크가 예산 안에서 통과한 뒤 실제 호출(약 1초)이 더 붙는다. 21,609ms = 노크 20,935ms + 호출 0.7초.

### ② §5-3 — 🔴 지목 지점은 이미 막혀 있었고, 실제 누출은 다른 곳이었다

지시서는 *"매팅 전 엔드포인트 실패로 종료되는 경로에서 환급"*을 요구했다. **그 경로는 이미 환급한다** — `server.js`의 `gateMode === 'free' && !finalBase64` 분기가 `fireRefundGate()`를 부르고 `FREE_UNAVAILABLE`을 반환한다.

**07-25 사건이 새어나간 곳은 거기가 아니다.** 그날 매팅은 RunPod으로 **결국 성공**했다(15:46:36). 서버 기준 성공이라 `!finalBase64` 분기에 애초에 걸리지 않았고, 유저는 이미 15:45:37에 504로 끊긴 뒤였다. **성공했는데 아무도 받지 못한 것**이 누출의 형태다.

## §5-B. 소켓 절단 감지는 Cloud Run에서 쓸 수 없다 (실측)

1차 구현으로 `res.on('close')` 훅을 넣고 dev에서 **실제로 abort를 걸어 시험했다.**

```
abort: {"ms":4004,"aborted":true,"err":"AbortError"}
→ 서버 로그: [IDPhoto] 생성 완료: 규격=kr-passport, 게이트=free …   ← 완주
→ '클라이언트 연결 종료' 로그: 없음
→ remainingFree: 999985 → 999984 → 소모 확정 (반환 안 됨)
```

**Cloud Run 프록시가 클라이언트 절단을 컨테이너로 전파하지 않는다.** `res` `close` 이벤트가 발화하지 않고, 죽은 연결에 대한 응답 쓰기도 조용히 성공한다. 즉 **컨테이너에서 절단은 관측 불가**다.

> 코드가 그럴듯하게 동작할 것 같아도 시켜보기 전에는 모른다 — 배포 없이 넘어갔으면 "구현 완료"로 보고했을 지점이다.

## §5-C. 채택한 기전 — 경과 시간 마감선

절단이 관측 불가이므로 **신뢰할 수 있는 유일한 신호는 경과 시간**이다.

- `GEN_DELIVERY_DEADLINE_MS`(기본 **115,000**, Cloud Run 예산 120초 대비) 신설. `deploy.sh` ENV_VARS 등재로 조정 가능.
- 산출물 확정 시점에 경과가 마감선을 넘었으면 → **소모분 반환 + 쿼터 미확정**.
- **응답은 그대로 보낸다.** 닿으면 유저는 사진을 받고 횟수도 안 깎인다(관대한 방향의 오차). 닿지 않으면 07-25형 누출이 차단된다.
- `res.on('close')` 훅은 절단을 전파하는 환경(로컬·타 프록시)을 위해 남겨 뒀다.

### 실증 — 임계 5초로 낮춰 dev 배포 후 실측

```
[IDPhoto] 전달 불확실(경과 5148ms) — 소모분 반환·쿼터 미확정(free)
[IDPhoto] 전달 불확실(경과 7518ms) — 소모분 반환·쿼터 미확정(free)
```

| 회차 | 경과 | 마감선 초과 | remainingFree | 소모 |
|---|---|---|---|---|
| 1 | 5,148ms | ✅ | 999985 | **미소모** |
| 2 | 4,9xx ms | ❌ | 999984 | 소모 |
| 3 | 7,518ms | ✅ | 999984 (불변) | **미소모** |

**3회차에서 카운트가 움직이지 않았다 — 반환 실증.** 이후 기본값 115,000으로 재배포하고 정상 소모 복귀를 확인했다(999983 → 999982).

## §5-D. `MATTE_TIMEOUT_MS` 60초 → 25초

`lib/matte.js`. 환경변수 `MATTE_TIMEOUT_MS`로 조정 가능(기본 25000).

- 근거: RunPod 콜드 실측 **16.1초**(07-25 18:10) < 25초. 정상값 4060 0.37초 · RunPod warm 0.35~0.42초로 **정상 요청 무영향**.
- prod 7일 최악 `matteSec`은 9.868초 — 25초 안에 여유롭게 들어온다. 하향에 따른 회귀 위험 없음.
- 재시도 1회 유지 (작가님 "두 번째 의자").

## §5-F. 병렬 작업 사고 기록

§5-1 `MATTE_TIMEOUT_MS` 25초 하향(`lib/matte.js`)과 §5-3 1차 구현분(`server.js`의 `res.on('close')` 훅)이 **동시 작업 중이던 막내1의 커밋 `3cc9b5f7`(SPECS HEIC)에 함께 실려 들어갔다.** 같은 파일을 동시에 편집한 결과, 먼저 커밋한 쪽이 상대의 미커밋 변경을 쓸어담았다. 본 커밋에는 그 이후의 델타(마감선 기전)만 담긴다.

- 기능상 문제 없음(코드 일관, 전량 main에 존재). **귀속만 갈렸다.**
- 착수 시점에 경합을 인지하고 있었고 문법 검사 후 진행했으나, 커밋 타이밍까지는 통제하지 못했다.
- 교훈: **병렬 막내가 같은 파일을 편집하면 선커밋 쪽이 상대 변경을 흡수한다.** 착수 전 `git status`로 경합 확인 + 경합 시 커밋 조율이 필요하다.
