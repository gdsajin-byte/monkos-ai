## 2. 전제 검증 — 4060 Windows 실기 재측정

### 2-1. 레지스트리 Content Type (HKEY_CLASSES_ROOT)

| 확장자 | 레지스트리 |
|---|---|
| .jpg / .jpeg / .png / .jfif | image/jpeg · image/png · image/jpeg |
| .bmp | image/bmp |
| **.webp** | **(none)** |
| **.heic** | **(none)** |

> ⚠️ 새벽 실측은 `HKLM:\SOFTWARE\Classes` 경로였고, 이번에 `Registry::HKEY_CLASSES_ROOT`로 재측정했다. 전자는 `.jpg`조차 `(none)`으로 나온다 — 즉 **새벽 수치는 경로 오류 가능성이 있었고, 이번 값이 정본**이다.

### 2-2. 브라우저가 실제로 반환하는 `file.type` (Edge 150, CDP `DOM.setFileInputFiles`)

```
t_jpg.jpg   => image/jpeg      t_webp.webp => image/webp     ← 레지스트리 (none) 인데도 채워짐
t_jpeg.jpeg => image/jpeg      t_heic.heic => (EMPTY STRING) ← 진짜 빈 문자열
t_png.png   => image/png       t_heif.heif => (EMPTY STRING) ← 진짜 빈 문자열
t_jfif.jfif => image/jpeg      t_bmp.bmp   => image/bmp
t_tiff.tiff => image/tiff      t_JPG.JPG   => image/jpeg
```

**⭐ 핵심: 레지스트리 미등재 ≠ 빈 문자열.** Chromium은 자체 내장 MIME 표로 레지스트리 공백을 메운다. `.webp`가 정확히 그 사례다.

### 2-3. 실 HEIC(Apple `sips` 생성, `ftypheic`/HEVC) 실기 통과 시험

```
file.type      : (EMPTY STRING)
ext            : heic
OLD gate (prod): REJECT          ← 현재 프로덕션이 실제로 거부
NEW gate (fix) : PASS            ← 대기 중인 수정본은 구제 성공
dataURL prefix : data:application/octet-stream;
preview <img>  : RENDER FAIL (broken image)
```

### 2-4. 전제 대조

| 지시서·새벽 진단의 서술 | 실측 결과 |
|---|---|
| "민아 4060 실측: `.webp`가 Content Type 미등록" → 빈 문자열 위험의 대표 사례 | ⚠️ **레지스트리는 미등록이 맞으나 브라우저는 `image/webp`를 반환.** `.webp`는 위험 사례가 아니다. **동일 문구가 코드 주석에도 박혀 있다** |
| "정상 JPG를 올려도 게이트가 거부할 수 있다" (작가님 최우선 지목) | ❌ **이 실기에서 재현 불가.** `.jpg`는 레지스트리·내장표 양쪽에 있어 항상 `image/jpeg` |
| (양쪽 모두 미언급) | 🔴 **진짜 빈 문자열 = `.heic` / `.heif`** — 레지스트리·Chromium 내장표 **둘 다 미보유** |

**결론: 처방은 맞고 근거는 틀렸다.** 확장자 폴백이 실제로 구해내는 것은 JPG도 WEBP도 아닌 **HEIC/HEIF**다.

## 3. 🔴 이로써 확정되는 신규 결함 — HEIC 자기모순

현재 프로덕션은 Windows에서 **HEIC를 거부하면서, 거부 문구로 "JPG, PNG, HEIC 파일만 업로드 가능합니다"를 띄운다.**

- 유저 입장: **안내가 허용한다고 적은 포맷을 올렸는데 그 안내가 다시 뜬다.** `.bmp` 거부보다 훨씬 나쁜 형태다 — 유저가 스스로 고칠 방법을 안내에서 찾을 수 없다.
- 유입 경로의 현실성: **아이폰 기본 촬영 포맷이 HEIC**다. 아이폰 사진을 Windows PC로 옮겨 올리는 동선은 `.bmp`(그림판·캡처)보다 증명사진 맥락에서 훨씬 자연스럽다.
- 즉 **새벽에 제가 지목한 `.bmp`보다 이쪽이 실트래픽 설명력이 높다.** 새벽 진단의 방향 자체를 이 건이 교체한다.

서버는 문제없다 — 실측으로 확인:
- `server.js:71` 이 `,` 기준 분리라 `data:application/octet-stream;base64,…` 도 정상 파싱 ✅
- `sharp` heif input=true / libheif 1.20.2 → **Apple HEVC HEIC 디코드 실증**(`format=heif, 600x800, compression=hevc`) ✅
- → BMP에서 쌍아가 차단한 "클라이언트만 열고 서버에서 실패" 패턴은 **HEIC엔 해당 없음**

## 5. 잔여 갭 3건

1. **⚠️ HEIC 미리보기 깨짐 (실측)** — 게이트를 통과시켜도 `v2-check-img`에 꽂히는 `data:application/octet-stream;base64,…` 를 **Chromium이 렌더하지 못한다**(RENDER FAIL 실측). precheck는 서버에서 정상 처리되므로 흐름은 진행되나, 유저는 **깨진 썸네일을 보며 진행**하게 된다. 지시서 검증 항목은 "정상 JPG 완주"뿐이라 **이 경로가 검증망 밖**이다. → HEIC일 때 미리보기 대체 처리(캔버스 변환 또는 안내 문구) 필요 여부 판단 요청.
2. **`.jfif` 폴백 목록 누락** — `ALLOWED_EXT`에 `jfif`가 없다. 이 PC에선 레지스트리에 등재돼 MIME으로 통과하므로 영향 없으나, Windows 고유 JPEG 확장자를 폴백 목록에서 뺀 것은 설계 의도와 어긋난다. 우선순위 낮음.
3. **문구 정합** — 수정 후 HEIC가 실제 통과하므로 새 문구("JPG, PNG, WEBP, HEIC")는 **정직해진다**. 단 §5-1이 미해결이면 "통과는 되는데 미리보기가 깨지는" 상태를 안내가 보증하는 셈.
