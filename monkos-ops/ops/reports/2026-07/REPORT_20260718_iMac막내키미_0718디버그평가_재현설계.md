## 2. 평가

4. **교차검증의 실효** — 쌍아 오진 2건 교정("이식 누락" 오인·"+2 정합" 오인), 막내1 br 교정안 기각(어제 vn 역방향 패턴 재발 방지), 런팟 통합안 반대 4근거(사실 기반).

### 🔴 문제점 (실행 단계에 집중)

## 3. 나라면 어떻게 했을 것인가 (막내2 실행 위치에서)

> 설계·검증은 쌍아/민아 영역이므로, 나는 실행자 위치의 자기 검증 강화에 한정한다.

### ① 착수 전 — 기준선과 의존성 맵 (30분 투자로 F2·F3·F5·V2강등 예방)
1. **`npm test` 먼저 실행해 baseline 확정** — 기존 실패 유무를 기록해야 "내가 깼는지, 원래 깨져 있었는지" 구분 가능.
2. **변경 필드/응답의 소비자 전수 grep으로 계약 맵 작성**:
   - `T1_GENERATE_FAILED` → 퍼널 `data.code` 분기 소비자 확인 (F2 예방)
   - render-specs.js의 반환 경로(662행 isV2Spec 조기 반환 → V2 프래그먼트 실서빙) 확인 후 배너 위치 결정 (F3 예방)
   - E블록(데이터) 착수 시 `background` 참조 전수 grep → `isEngineCompatibleSpec`의 "흰색" 하드코딩 발견 → **지시서 범위 밖이므로 임의 수정 않고 쌍아·민아에 보고 후 대기** (V2 강등 사전 차단)
3. **설계서 §9 검증 기준을 순서 고정 체크리스트로 변환**: 코드 → jest 녹색 → 배포 → prod 스모크 → COMPLETION(증거 첨부).

### ② 실행 중 — 블록 단위 검증
4. 5블록 일괄 배포 대신 **블록별 관련 jest 스위트 실행**. 특히 D블록(테스트 4파일 삭제+커버 제거)은 남은 테스트가 새 에러 경로(FACE_NOT_DETECTED) 기대로 현행화됐는지 배포 전 확인 — 깨진 테스트 4건을 여기서 발견.
5. **서버-클라 계약은 같은 커밋에서** — 응답 스키마 변경 시 소비자 분기를 함께 수정.

### ③ 배포 전/후 — 강제 게이트
6. **jest 전량 녹색 아니면 배포 안 함** — "스테일 테스트"라면 테스트도 같은 커밋에서 현행화. 방치는 없음.
7. 배포 직후 **3종 스모크 실주행**: kr(정상군)·vn(사고규격)·de(데이터 변경군) — 오늘 민아가 17:41에 한 것을 실행자가 먼저.
8. 렌더 변경은 **라이브 DOM 실측**(curl|grep 배너) — "코드에 넣었다" ≠ "유저에게 보인다".
9. COMPLETION에 **검증 증거 명시**: jest tail, 스모크 결과, DOM grep 결과. 증거 없는 "완료" 주장 금지.

### ④ 범위 밖 발견 — 보고 후 대기
10. 암묵 게이트·의존성 문제 발견 시 임의 확장 수정 않고 보고(오늘 결정 A/B를 작가님이 내린 절차가 정석).

## 5. 총평

오늘은 **진단(민아)·설계(쌍아)는 A급, 실행 1차 품질(막내2)은 C급, 검증 루프는 A급** — 그래서 최종 산출물은 정합이나 비용이 컸다. 나라면 동일 지시서를 받아도 "baseline jest → 의존성 맵 → 블록별 검증 → jest 게이트 → 스모크 3종 → 증거 첨부"의 6단 자기 절차로 **1차 배포에서 F2·F3·F5를 제거하고, V2 강등은 배포 전 보고로 차단**했을 것이다. 단, hairTop 오검출·가드 순서(18:36 발견분) 같은 실물 품질 이슈는 나도 1차에 못 잡았을 것 — 이것이 작가님 품질 테스트 매트릭스(민아 제안 5+1종)가 정례화돼야 할 이유다.
