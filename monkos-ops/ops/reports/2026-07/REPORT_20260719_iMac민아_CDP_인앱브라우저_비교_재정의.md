# REPORT — 자체 CDP vs 클로드 인앱 브라우저 비교 + CDP 재정의 제안

**[2026-07-19 15:51 KST]** iMac/민아 → 작가님, iMac/쌍아

> 발단: 클로드 인앱 브라우저(세션 내장 브라우저 페인) 정식 등장 — 검색이 아닌 CDP급 직접 통제(클릭·타이핑·JS·네트워크·멀티탭). 작가님 질의: 성능 비교 + 우리 CDP의 갈 길 + 브라우저 작업 효율화 + PF_CDP 정리.
> 근거: 오늘 실사용 실측 — 인앱으로 스포크 ① 검증 전체(업로드 주입→T0 완주→픽셀 검증) 완료, 막내2는 자체 CDP로 eVisa JS SPA 원문 돌파. 양 스택을 같은 날 실전 투입한 비교.

**한 줄 판정**: 인앱 브라우저는 "전 에이전트 브라우저 무장"이라는 PF_CDP 원래 비전의 **범용 절반을 플랫폼 차원에서 달성**시켰다 (클로드 인 크롬의 계정당 1탭 한계도 세션당 페인으로 해소). 자체 CDP의 대체 불가 영역은 **4개로 압축**된다.

## 2. 자체 CDP 재정의 — "범용 무장"에서 "4대 특수 계층"으로

남는 독점 영역:
1. **실프로필 계층** — 로그인 상시 유지 작업: 네이버 블로그 발행, X, GA4·GSC·Ads·GCP 콘솔 화면 전용 데이터(오늘 404 목록·색인 상세 = API 부재 데이터), 작가님 탭 공유.
2. **세션 밖 상시 가동** — 소넷이 데몬 순찰 러너(L1~L3), cron 스케줄 배포(Phase 4). Claude 세션에 묶이지 않는 유일한 스택.
3. **OS 통합** — 실파일 업로드·다운로드 처리·클립보드 (인앱 샌드박스 밖).
4. **고빈도 반복 루프** — PageProfiler 캐시가 유효한 대량 스캔(수백 슬러그 순회 등).

방향 제안 (쌍아 합의 대상):
- **신규 범용 기능 개발 동결** — smart_extract·smart_scroll류는 인앱 read_page가 대체. cdp_utils는 4대 계층 유지보수만. 1500줄 리팩토링 트리거는 사실상 소멸 → 보류.
- **Phase 3(Stagehand, LLM 비용) 보류 격하** — "자연어→브라우저" 계층은 세션 내에선 인앱+에이전트 자체가 이미 수행. 네이버 SmartEditor 난제는 Stagehand가 아니라 실프로필+클립보드 페이스트 우회(04/07 막내4 제안 노선)로 재도전.
- **Phase 4(스케줄 배포)가 실질 다음 단계** — 순찰 러너와 인프라 합류(같은 세션 밖 러너). 순찰 설계서(쌍아 예정)와 통합 설계 권고.
- 도구 선택 기준(전 에이전트 공통): ① 단발 검증·진단·읽기 → 인앱 ② 로그인·콘솔 화면 데이터·실파일 → 자체 CDP ③ 세션 밖 정기 실행 → 자체 CDP/Playwright 러너 ④ API 있으면 브라우저 자체를 안 씀 (교훈 8 확장 — GA4·GSC·Ads는 MCP 직행이 상위 호환, 오늘 GSC 순위 실측이 실례).

## 3. 브라우저 기반 실무 효율화 — 2대 작업

### 3-1. 블로그 직접 타이핑 (CDP→포스팅 파이프라인)

- **원칙: 본문은 파일로 완성, 브라우저는 "부어넣기+발행"만** — 타이핑을 창작 시간에서 분리. 꾸(원본 작성)↔에이전트(발행 대행) 분업과 정합.
- 채널 라우팅 현행화: MONKOS 어드민=API 직접(교훈 8, 브라우저 불요) / 티스토리·미디움·note=기존 CDP 패턴 유지 / **네이버=실프로필 CDP+클립보드 페이스트 우회 재검증** (서식·링크 소실 난제의 현실 노선. ClipboardEvent에 HTML 실어 페이스트 — note에서 검증된 패턴의 이식) / X·깃헙=기존 패턴.
- 이미지: 미디움식 backendNodeId 업로드(자체 CDP) 또는 API 직행. 인앱 불가 영역.

### 3-2. 실유저 동선 체크 (순찰과 합류)

- 오늘 확립한 계층 그대로: **L2/L3=인앱급 경량 러너+DataTransfer 주입** (무로그인·무실파일·무비용, 오늘 전 구간 실증) / **로그인 동선·외부 실검색·JS SPA=자체 CDP** / L1=HTTP 스캔(소넷이 즉시 가능).
- 유입 문맥 재현(referrer·UTM 세팅)은 양 스택 모두 가능 — 러너에 내장.
- 모바일 반응형은 인앱 resize_window가 최속.
- 지표 오염 방어(utm_source=patrol) 순찰 설계 필수 항목 (금일 별도 의견 기제출).

## 5. 결론

인앱 브라우저의 등장은 위협이 아니라 **우리 CDP의 유지보수 부담을 절반으로 줄여주는 분업**이다. 범용 제어는 플랫폼에 이양하고, 자체 CDP는 대체 불가 4계층(실프로필·세션 밖·OS 통합·고빈도 캐시)에 집중한다. 다음 실행 단위는 ① 순찰 러너×Phase 4 통합 설계(쌍아) ② 네이버 클립보드 우회 재검증(막내, 실프로필) ③ PF 아카이브 정리(쌍아 확인). "병행 추적" 원칙(Phase 현황 §말미)이 정확히 예견한 국면 — 벤더 표준은 부품이지 상위가 아니다.
