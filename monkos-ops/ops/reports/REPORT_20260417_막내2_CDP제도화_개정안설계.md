# CDP 제도화 개정안 설계 보고서

> 지시 요지: rules(자동)·skills(호출)·법률(행동강령) 3계층에 적확한 내용을 배치하여,
> 에이전트가 구조적으로 기존 기록을 참조하도록 제도화한다. 코드 수정 없음, 초안까지.

---

## 요약 (TL;DR)

- **3계층 각각의 역할 정의** 후 **방안 B(rules 경량 포인터 + skill 상세 + law 조항)**를 추천한다.
- CDP 전용이 아니라 **"활성 PF 일반 원칙"** 으로 법률을 설계한다. 지금은 PF_CDP 하나만 대상이지만, 향후 타 PF가 같은 구조를 갖출 수 있도록 범용 조항으로 둔다.
- 헌법(CLAUDE.md) 제3조 2항은 "PF **갱신** 의무"만 규정 → "PF **참조** 의무"가 공백. 이 공백을 법률 차원에서 메운다. 헌법 개정은 피한다(만장일치 비용).
- Phase 1(이번 주): rules 포인터 10줄 + skill 신설 + ch7 6조 신설 → 막내 우선 적용.
- Phase 2(검증 후): ch1/ch3 보편 규범으로 승급 또는 헌법 3조 2항 개정 청구.

## 1. 3계층 역할 분석

### 1-0. 현행 구조 스캔

| 계층 | 위치 | 파일 수 | 로딩 | 평균 분량 |
|------|------|--------|------|----------|
| rules (자동) | `.claude/rules/` | 3 | 매 세션 또는 paths 매칭 시 | 36~99줄 |
| skills (호출) | `.claude/skills/` | 8 | Skill 도구가 description 매칭 시 | 37~67줄 |
| laws (정의) | `governance/laws/` | 8장 | 수동 읽기 | 46~508줄 |
| 규정 (MEMORY) | `MEMORY.md` | 1 | 매 세션 자동 (200줄 캡) | — |

**포인트**: `portal_seo.md`는 이미 **paths 기반 조건부 자동 로드** 패턴을 채택하고 있다(`monkos_AI/portal/**` 등 접근 시만 로드). CDP 계열 파일 접근 시만 로드되는 조건부 rules 패턴을 차용할 수 있다.

### 1-1. rules (자동 로딩) — 무엇을 맡길까

현행 `cdp-browser.md` (99줄, globs: `"**"` 매 세션 자동):
- 역할: 포트 배당, 도구 사용법, 금지 MCP 목록 — **"시작할 때 반드시 알아야 하는 상수성 정보"**
- 여기에 장애 대응 프로토콜을 통째로 추가하면 → 120~150줄로 비대해지고, CDP를 안 쓰는 세션에도 매번 파싱됨 → 토큰 낭비.

**rules에 배치할 최소 정보**:
- "막힘 트리거 감지 시 PF_CDP 참조 + `/cdp-troubleshoot` skill 호출" 포인터 **5~10줄**
- 상세 절차는 skill로 위임

### 1-2. skills (호출형) — 상세 절차의 보관소

현행 skills(`escalation.md`, `session-start.md` 등)는 **"절차형 · 번호 매겨진 단계별 실행"** 패턴.

CDP 장애 진단은 정확히 이 패턴에 부합:
1. 증상 키워드 추출
2. case_studies.md grep
3. golden_paths.md 매칭
4. editor_adapters/ 확인
5. 일치 없음 시 신규 CASE 등록 가이드
6. 5회 실패 시 에스컬레이션

**이 내용은 평소 읽힐 필요 없고, 장애 포착 시에만 필요** → skill이 최적.

**호출 트리거 보장 장치**:
- rules에 "막힘 감지 시 `/cdp-troubleshoot` 호출 의무" 명시 (1줄)
- skill description에 "CDP 브라우저 자동화 예외 발생 시" 키워드 박음 → Skill 도구가 자동 매칭

### 1-3. laws (법률) — 행동 강령

현행 법률 매핑:

| 장 | CDP 관련 현 상태 |
|---|------------------|
| ch1 (에이전트 체계) | 민아 CDP 크롤·진단·검증 자유 권한 명시 (2026-03-29 PETITION) |
| ch2 (코딩) | CDP 관련 없음 |
| ch3 (세션 로그) | 헌법 3조 2항(PF 히스토리 갱신) 하위 절차 |
| ch7 (막내 행동 강령) | 4조 에스컬레이션, 5조 MEMORY.md 확인 의무 — 민아에게도 준용 |

**공백**: 어느 장에도 "활성 PF **참조** 의무"가 없다. 헌법 3조 2항은 **갱신(append)**만 규정. 기안서 §2 현실 진단 그대로: "적립은 있고, 참조·활용·구조화가 약하다."

**조항 배치 후보**:

| 후보 | 장점 | 단점 |
|------|------|------|
| (α) ch7 6조 신설 | 행동 강령 묶음 — 자연스러움. 민아 준용 확장(기존 4·5조 패턴) 가능 | 막내 중심 장이라 "전 에이전트 규범"으로 읽기는 애매 |
| (β) ch1 7조 신설 | 에이전트 체계 전반에 적용 자연스러움 | ch1은 "누가 무엇을 하나" 위주 — "어떻게 참조하나"는 다소 이질 |
| (γ) ch3 6조 신설 | PF 갱신 조항과 짝으로 "참조" 조항 — 대칭성 좋음 | ch3는 세션 로그 전문, PF는 로그와 다른 트랙 |
| (δ) 헌법 3조 2항 개정 | 근본 위치 — 가장 강력 | 만장일치 비용. 개정 실패 시 법률 경로 재설계 비용 |

**추천**: (α) ch7 6조 신설 + 말머리 "보편 적용 목록(4·5조)"에 **6조 편입**. 민아·쌍아에도 적용 확보. (β~δ)는 Phase 2에서 검증 후 승급 여지.

## CDP 장애 진단 절차

### 1단계 — 증상 키워드 추출

1. 이상 동작을 1-3개 키워드로 요약한다 (예: `paste`, `click`, `selection`, `typing`, `screenshot`, `file-input`).
2. 플랫폼명을 함께 추출한다 (예: `google-docs`, `naver`, `toastui`, `x`, `medium`, `note`, `tistory`, `line`).

### 2단계 — case_studies.md grep

1. `grep -iE "{증상키워드}|{플랫폼}" monkos-ops/ops/portfolios/PF_CDP/case_studies.md` 실행.
2. 일치 CASE-NNN 전체를 리드한다.
3. "재현성: 100%" + 조건이 현재 상황과 동일하면 기재된 해결책을 그대로 적용한다.
4. "재현성: 조건부/미확인"이면 조건 매트릭스 점검 후 적용.

### 3단계 — golden_paths.md 매칭

1. 대상 에디터 플랫폼의 검증된 성공 패턴(GP-NNN) 존재 여부를 확인한다.
2. 현재 방식이 해당 GP의 "실패 조건" 에 해당하는지 점검한다.
3. GP 순서대로 전환한다.

### 4단계 — editor_adapters/ 확인

1. `monkos-ops/ops/portfolios/PF_CDP/editor_adapters/{에디터}.md` 존재 시 리드한다.
2. "금지 패턴" 표에서 현재 방식이 해당되는지 확인한다.
3. "검증된 입력 방식 우선순위" 순으로 대안을 시도한다.

### 5단계 — 일치 케이스 없음 시 신규 CASE 등록

1. `case_studies.md` 최하단에 append. 번호는 기존 최대+1.
2. 필수 필드:
   - 번호(CASE-NNN), 일시(`date` 명령), 에이전트, 대상 에디터
   - 증상, 조건, 원인(가설), 해결(또는 미해결 단서)
   - 재현성 (100%/조건부/간헐/미확인)
   - 태그 (grep용 키워드 5~8개)
3. 미해결 시 "다음 조치" 목록을 3~5개 기재한다.

### 6단계 — 조사 개시

1. 1~4단계에서 일치 없음을 확인한 뒤에만 새 가설을 세운다.
2. 가설은 동시에 3개 이하로 병렬 나열하지 않는다 (기안서 §1-1 교훈: 가설 반복 패턴 회피).
3. 5회 반복 실패 시 법률 ch7 4조 에스컬레이션 준용.

## 보고 의무

- 진단 중 신규 CASE 등록 시 세션 로그에 `[CASE-NNN 등록]` 태그 기록.
- 골든패스 신규 검증 시 `golden_paths.md` 에 GP-NNN 추가 후 세션 로그에 `[GP-NNN 등록]` 기록.

#### (B) 신설 6조 전문

```markdown
### 6조: 활성 PF 참조 의무

**원칙**: 작업 대상에 **활성 포트폴리오(PF)** 가 존재하고, 해당 PF에 **막힘 트리거
체크리스트**(또는 동격의 장애 대응 문서)가 정의되어 있을 경우, 에이전트는 예외·장애
감지 즉시 PF 기록을 선행 참조할 의무를 진다.

**참조 선행 원칙**:
- 가설 수립 전에 PF의 케이스 DB·골든패스·에디터 어댑터(또는 동격 문서)를 점검한다.
- "원리상 불가" 같은 큰 결론으로 뛰기 금지.
- 일치 케이스가 없을 때에만 새 가설을 세운다.

**신규 등록 의무**:
- 일치 케이스가 없는 장애는 해당 PF의 케이스 DB에 즉시 신규 등록한다 (append-only).
- 해결 시 원인·해법·재현성을 보강한다. 미해결 시 "다음 조치" 를 명시한다.

**스킬 위임**:
- PF별 절차 상세는 해당 PF 관할 skill로 위임한다.
- 현재 지정 skill: PF_CDP → `cdp-troubleshoot`.

**헌법 제3조(적립) 2항과의 관계**:
- 헌법은 PF **갱신(append)** 의무를 규정한다.
- 본 조는 PF **참조(read)** 의무를 규정한다.
- 두 의무는 적립-활용 사이클의 두 축이다.

**적용 범위**:
- 막내·민아·쌍아에 적용 (말머리 보편 적용 목록 참조).

```

### 3-4. CDP 전용 vs 범용 — 판단과 근거

**선택**: **범용 조항 + CDP는 최초 적용 사례**

**근거**:
1. 법률은 일회성 패치가 아니라 **행동 원칙**이어야 한다. "CDP에 한정"하면 다음 PF(예: PF_SEO, PF_블록에디터)마다 조항 증식.
2. 구현 비용 차이 없다 — 조문을 "활성 PF에 막힘 체크리스트가 있으면" 조건으로 두면 대상 PF가 하나든 N개든 동일 문장.
3. 현재 활성 PF는 PF_CDP 하나. 향후 PF가 장애 대응 문서를 갖출 때 자동 적용. **"인프라 갖추고 기다리기"** 패턴.

**트레이드오프**:
- 범용은 조문이 추상적 → CDP 특정 절차는 **skill 레벨**로 내려감 (본 설계 그대로)
- CDP 전용으로 좁히면 현재 유일 사례에 정확히 핏 → 그러나 확장성 0.

**Phase 2 승급 경로**:
- 6개월 운용 후 "활성 PF가 2~3개로 확장되고 참조 루틴이 안착"되면, ch3(세션 로그) 또는 헌법 3조 2항으로 **승급 청구** 고려.
