## 2. Top 5 리스크 상세 분석

### TOP 1: R3 — 인앱 브라우저 쿠키 격리 [CRITICAL]

**현상**: iOS/Android의 인앱 브라우저(KakaoTalk, LINE, Instagram)는 OS 레벨에서 Safari/Chrome과 **쿠키 저장소가 분리**됨.

**영향 시나리오**:
1. 사용자가 Safari에서 monkos.ai 로그인 → 쿠키 생성
2. 카카오톡에서 monkos.ai 링크 수신 → 카카오톡 인앱 브라우저에서 열림
3. 인앱 브라우저에는 쿠키가 **없음** → 비로그인 상태
4. 사용자는 "왜 로그인이 안 되어 있지?"라고 혼란

**한국 시장 특수성**: 카카오톡은 한국 DAU 4,800만+ 메신저. 마케팅 링크의 상당수가 카카오톡 경유. 이 시나리오는 **일상적으로 발생**.

**대응 방안**:
- 현행 2-phase 구조(①sessionStorage → ②쿠키)가 이미 방어. sessionStorage도 없고 쿠키도 없으면 비로그인 표시
- 인앱 브라우저 감지(`checkInappBrowser()` 이미 구현)는 있으나, 로그인 유도 UI는 미구현
- **추가 조치 불필요**: 쿠키 단일화는 "인앱에서 로그인하면 쿠키 생성 → 인앱 내 서브도메인 이동 시 유지"를 보장. 기존 대비 **동일 or 개선**
- 인앱 브라우저 내 로그인 → 동일 인앱 세션 내 쿠키 유지 → 서브도메인 이동 시 쿠키 전송 = **정상 동작**

**결론**: 인앱 브라우저 쿠키 격리는 쿠키 단일화 이전에도 존재하던 문제. 쿠키 단일화가 이 문제를 악화시키지 않음. 단, 쿠키를 **유일한** 인증 수단으로 전환하면 sessionStorage 폴백이 사라지므로 인앱 내 로그인이 필수가 됨.

### TOP 2: R11 — 로그아웃 불완전 (토큰 무효화 미구현) [HIGH]

**현상**: 현행 로그아웃은 클라이언트의 쿠키/sessionStorage 삭제만 수행. 서버 측 토큰 블랙리스트 **없음**.

**영향 시나리오**:
1. 공용 PC에서 로그인 → 쿠키 생성 (30일 유효)
2. 사용자 로그아웃 → 쿠키 삭제
3. 공격자가 쿠키를 미리 복사해둔 경우 (또는 브라우저 프로필 복원) → 토큰 여전히 유효
4. 30일간 해당 사용자로 API 호출 가능 (크레딧 사용 포함)

**현행 코드 분석** (`config.js:160-183`):
- `verifyAuthToken()`은 HMAC 서명 + 만료 시간만 검증
- 서버 측 세션 저장소/블랙리스트 없음 → 서명이 유효하면 무조건 통과
- `handleAuthRefresh()`는 만료 30일 이내 토큰을 새 토큰으로 갱신 → 영구 갱신 가능

**대응 방안**:
- **즉시**: 쿠키 단일화 전환과 무관한 기존 취약점. 전환 자체에는 무관하나 쿠키가 유일한 인증이 되면 영향 확대
- **권장**: Firestore에 `tokenVersion` 필드 추가 → 로그아웃 시 version 증가 → 검증 시 version 매칭 확인
- **대안**: Redis 블랙리스트 (인프라 추가 필요) 또는 토큰 유효기간 단축 (30일 → 7일 + refresh 토큰 분리)

### TOP 3: R8 — CSRF 공격 (SameSite=Lax 한계) [HIGH]

**현상**: `SameSite=Lax`는 cross-site POST를 차단하나, **서브도메인 탈취(subdomain takeover)** 시 same-site로 간주되어 CSRF 방어 무력화.

**현행 코드 분석**:
- 상태 변경 API: `/api/credits/use`(POST), `/api/payments/toss/confirm`(POST), `/api/auth/token`(POST) 등
- CSRF 토큰 **미구현** — 쿠키만으로 인증
- 서브도메인: `idphoto-kr.monkos.ai`, `idphoto-jp.monkos.ai`, 개발용 `*.run.app`

**공격 시나리오**:
1. `compromised.monkos.ai`가 탈취됨 (dangling DNS, 미사용 서브도메인)
2. 공격자가 해당 서브도메인에 악성 페이지 배치
3. 사용자가 해당 페이지 방문 → `.monkos.ai` 쿠키가 same-site로 자동 전송
4. 악성 스크립트가 `POST /api/credits/use` 호출 → CSRF 성공

**대응 방안**:
- **즉시 (전환 전)**: DNS 감사 — 모든 `*.monkos.ai` 서브도메인 레코드 확인, 미사용 레코드 제거
- **권장**: 결제/크레딧 관련 POST 엔드포인트에 CSRF 토큰 추가
- **대안**: 상태 변경 API에 `Origin` 헤더 검증 추가 (서버 측에서 요청 Origin이 화이트리스트에 있는지 확인)

---

### TOP 4: R16 — CORS 설정 미완 [HIGH]

**현상**: `fetchLatestCredits()`가 `credentials: 'include'` 없이 호출되어 크로스 도메인에서 쿠키 미전송.

**현행 코드 분석** (`shared.js:271-289`):

```javascript
// fetchLatestCredits — credentials 미포함
const res = await fetch(`${API.PORTAL_URL}/api/credits?userId=${...}`);
```

반면 `initCredits()`의 쿠키 복원은 정상:

```javascript
// initCredits — credentials 포함
const res = await fetch(`${API.PORTAL_URL}/api/auth/verify-cookie`, {
  credentials: 'include',
});
```

**영향**:
- `idphoto-kr.monkos.ai`에서 `fetchLatestCredits()` 호출 시 → `monkos.ai/api/credits`로 요청
- `credentials: 'include'` 없으므로 쿠키 미전송
- 현행은 `userId`를 쿼리 파라미터로 전달하므로 동작은 하나, userId를 URL에 노출하는 보안 문제
- 쿠키 단일화 후 userId URL 전달을 제거하면 이 API가 **작동 불능**

**대응 방안**:
- `fetchLatestCredits()`에 `credentials: 'include'` 추가
- 서버 측에서 쿠키로 userId 추출하도록 변경 (userId 쿼리 파라미터 제거)
- `initFromTossResult()`의 `/api/payments/toss/confirm` 호출도 동일 검토 필요

### TOP 5: R12 — 기존 유저 세션 끊김 [MEDIUM]

**현상**: 전환 배포 시점에 sessionStorage에만 세션이 있는 기존 로그인 유저.

**영향 시나리오**:
- 현재 설계서 방침: "기존 코드 삭제 0건, sessionStorage 로직 유지"
- 이 방침을 준수하면 기존 유저에게 영향 없음
- **위험 지점**: 향후 "sessionStorage 제거" 단계에서 빅뱅 전환 시 → 쿠키가 없는 기존 유저 전원 로그아웃

**대응 방안**:
- Phase 1 (현재): sessionStorage + 쿠키 병행 → **안전**
- Phase 2 (sessionStorage 제거 시): 전환 코드 삽입 — sessionStorage에 유저가 있으면 자동으로 `/api/auth/verify-cookie` 호출하여 쿠키 존재 확인. 없으면 재로그인 유도
- 최소 1~2주 병행 기간 필요 → 그 사이 로그인 유저 대부분 쿠키 생성

## 5. 롤백 플레이북

### 전제: 현 설계서 방침 (Phase 1 — 추가만, 삭제 없음)

```
[문제 감지]
  │
  ├── 쿠키 관련 문제인가?
  │     │
  │     ├── YES → 쿠키 세팅 코드 제거 (Set-Cookie 라인 주석/삭제)
  │     │         sessionStorage 로직은 건재 → 기존 동작으로 자동 폴백
  │     │
  │     └── NO → 일반 장애 대응
  │
  ├── verify-cookie 엔드포인트 문제인가?
  │     │
  │     ├── YES → 라우트 제거 (server.js 1줄)
  │     │         initCredits() 2차 fetch 실패 → catch문에서 무시 → sessionStorage 폴백
  │     │
  │     └── NO → 일반 장애 대응
  │
  └── CORS 문제인가?
        │
        ├── YES → ALLOWED_ORIGINS 목록 확인
        │         credentials: 'include' 일시 제거
        │
        └── NO → 일반 장애 대응
```

### 롤백 절차 (구체)

1. **감지**: 모니터링 (Cloud Run 로그에서 401 급증, Telegram 알림)
2. **판단**: 쿠키 관련 여부 확인 (verify-cookie 401 비율)
3. **실행**:
   - Git에서 쿠키 관련 커밋 revert (`git revert <commit>`)
   - Cloud Run 재배포 (portal + idphoto-kr)
   - 예상 소요: 5~10분
4. **확인**: 로그인 흐름 수동 테스트 (Google/카카오/LINE)
5. **보고**: 롤백 완료 보고 + 원인 분석

### 롤백 안전성

| 항목 | 롤백 가능 여부 |
|------|:-------------:|
| Set-Cookie 추가 | ✅ 제거하면 쿠키 미설정. 기존 sessionStorage 동작 |
| verify-cookie 엔드포인트 | ✅ 제거하면 404. initCredits() catch에서 무시 |
| initCredits() 2-phase | ✅ 2차 블록 제거하면 1차 sessionStorage only |
| CORS 화이트리스트 | ✅ 추가분만 제거 |

**모든 변경이 "추가"이므로 롤백 = 추가분 제거. 기존 코드에 대한 변경 없음 → 롤백 안전.**

## 6. 추가 발견 사항

### 6-1. HMAC 시크릿 이중 용도 문제

`config.js:152`:
```javascript
const secret = LEMONSQUEEZY_WEBHOOK_SECRET || 'monkos-default-secret';
```

- `LEMONSQUEEZY_WEBHOOK_SECRET`이 결제 웹훅 서명 검증과 인증 토큰 생성에 **동시 사용**
- 웹훅 시크릿은 LemonSqueezy 대시보드에서 조회 가능 → 시크릿 노출 시 토큰 위조 가능
- **권장**: 인증 토큰용 별도 시크릿 환경변수 분리 (`AUTH_TOKEN_SECRET`)

### 6-2. 폴백 시크릿 하드코딩

```javascript
const secret = LEMONSQUEEZY_WEBHOOK_SECRET || 'monkos-default-secret';
```

- `LEMONSQUEEZY_WEBHOOK_SECRET`이 미설정이면 `'monkos-default-secret'`으로 폴백
- 프로덕션에서 이 폴백에 도달하면 모든 토큰이 동일 시크릿으로 서명 → 위조 가능
- **권장**: 프로덕션에서 시크릿 미설정 시 서버 시작 차단 또는 경고 로그

### 6-3. idphoto-jp 누락

- `idphoto-jp/public/shared.js`가 존재하지 않음
- idphoto-jp의 인증 구조를 별도 확인 필요
- 쿠키 단일화 시 idphoto-jp에도 동일한 `initCredits()` 2-phase 적용 필요
