## 결론
끊김의 주원인은 음원이 아니라 **화면 시계 동기화(`syncClocks`)**입니다. 5초마다 서버 시계로 화면 시계를 통째로 바꾸는데, 그 사이에 지난 초 경계의 음성을 내지 않고 건너뜁니다. 그래서 숫자가 빠집니다. 터널 지연이 크면 같은 숫자를 두 번 읽을 수도 있습니다.
여기에 **10초 초읽기에서는 "하나"가 구조적으로 나오지 않고**, 남은 회수 안내가 다음 숫자와 겹칩니다.

## 1. 실측 (데스크톱 브라우저, 8767 테스트 인스턴스, 팩 monk-ko-sola-a)

**A. 실제 판 시계 그대로**(20초 3회, 수 없이 24초 대기 — `voice`·`syncClocks` 호출 기록)
```
 1.6s ⟲sync 화면 15.03 → 서버 14.96
 6.6s ⟲sync 화면 10.03 → 서버  9.96   ← 10초 경계를 건너뜀 → "하나" 안 나옴
 7.6s ▶count2 … 10.6s ▶count5
11.6s ⟲sync 화면  5.03 → 서버  4.96   ← 5초 경계를 건너뜀 → "여섯" 안 나옴
12.6s ▶count7 … 15.6s ▶count10
16.6s ⟲sync 화면  0.03 → 서버 19.96   ← 0초 경계를 건너뜀 → 남은 회수 안내 안 나옴
```
- 핑(5초, index.html 1585행 `S.clock = j.clock; syncClocks()`)과 초 경계가 같은 위상에 걸렸습니다. 그래서 동기화가 일어날 때마다 같은 자리(10·5·0초)의 음성이 빠집니다.
- 로컬에서는 보정량이 ±0.07s로 작습니다. 아이폰 터널 경유에서는 응답 지연만큼 화면 시계가 뒤로 돌아가, 이미 읽은 숫자를 **다시 읽는** 쪽으로도 어긋날 수 있습니다(추정, 아이폰 로그로는 미확인).

**B. 시계 로직만 단독 실행**(`tickClock`을 0.1초마다, 동기화 없음)

| 초읽기 | 결과 |
|---|---|
| 10초 3회 | 매 회 "둘"부터 시작 — **"하나" 0회**. 남은 회수 안내 길이(1.33~1.80s)가 다음 "둘"과 **0.33~0.80s 겹침** |

- "하나"가 안 나오는 이유: 시계 판정이 `before > k && period <= k`라서, 회가 정확히 10초로 시작하면 10초 경계를 "지났다"고 보지 않습니다(수를 둔 직후 `clockMoved`, 회 넘김 직후 모두 해당).
- 작가님의 08:13 판은 10초 5회였습니다(방 파일).

## 3. 고침안 (승인 후 수정)
1. **시계 동기화가 음성을 건너뛰거나 되풀이하지 않게** (주원인) — `syncClocks`가 대국 중 내 시계를 갱신할 때 아래처럼 바꿉니다.
   - 서버 값이 화면보다 **덜 남았으면**: 차이만큼 `tickClock(c, 차이, 음성)`으로 흘려 건너뛴 경계의 음성을 냅니다. 차이가 2초를 넘으면 소리 없이 맞춥니다.
   - 서버 값이 **더 남았으면**(뒤로 감): 이번 회에 이미 읽은 숫자는 다시 읽지 않습니다(회 번호 + 숫자로 한 번만).
   - 또는 보정량이 0.5초 안이면 화면 시계를 유지합니다(서버 정본은 시간패 판정에만).
2. **10초 초읽기 "하나"**: 판정을 `before >= k && period < k`로 바꿔 회 시작 때도 셉니다. 그러면 회 넘김 직후 "하나"가 남은 회수 안내와 겹치므로, 다음 중 하나를 고릅니다.
   - (a) 남은 회수 안내가 있는 회는 "하나"를 생략합니다.
   - (b) 안내를 짧게 바꿉니다("두 번 남음"·"마지막").
   - (c) 안내가 끝날 때까지 다음 숫자를 미룹니다.
3. **음량**: 팩 정규화를 피크 −1dBFS에서 말소리 RMS 기준(예: −18dBFS, 타이젬 수준)으로 바꿉니다. 음원 재가공만 하며 크레딧은 들지 않습니다.
4. (선택) Min-joon "열"(1.15s)은 1초 안으로 줄입니다(말 속도 1.1 재생성 또는 끝 여유 축소).
