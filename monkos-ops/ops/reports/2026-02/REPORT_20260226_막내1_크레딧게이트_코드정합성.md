**핵심 문제**: 서버에 두 개의 독립적인 보너스 지급 엔드포인트가 존재한다.

**문제 경로**:
1. 게이트 팝업에서 카카오 로그인 → `signup_bonus` +30c
2. 게이트 팝업에서 텔레그램 공유 → `sns_share` +40c (event API)
3. **별도 경로**로 `share-bonus` API 호출 → **+100c** (share-bonus API)

- `share-bonus`: `data.shareBonusClaimed` (server.js:1367)
- `event(sns_share)`: `data.events.sns_share` (server.js:1548)

따라서 **동일 유저가 양쪽 모두에서 크레딧을 수령할 수 있다**: 30c + 40c + 100c = **170c**

**현재 프론트엔드(result.js)의 게이트 팝업은 `/api/credits/event`만 호출**하므로, 게이트 경로만 사용하면 최대 70c (30+40). 그러나 `/api/credits/share-bonus`를 직접 호출하면 추가 100c 가능.

**질문**: `/api/credits/share-bonus` (100c)는 어디에서 호출되는가?
- `idphoto-kr/server.js:757`: `app.post('/api/credit/share-bonus', ...)` — 프록시 존재
- **현재 MPA 프론트엔드(result.js)에서는 이 엔드포인트를 호출하지 않음**

→ **잠정 결론**: share-bonus(100c)는 레거시 코드이며 현재 UI에서 호출되지 않지만, 엔드포인트가 살아 있어 직접 API 호출로 악용 가능.

### #4. 결제 금액 ↔ 크레딧 매핑 안전성 — ⚠️ MEDIUM

**로그인 사용자 결제** (`/api/payments/toss/confirm`, portal/server.js:1925-1937):

```
let credits = TOSS_AMOUNT_CREDITS[amount];
if (!credits) {
  const customCredits = amount / 145;
  if (customCredits >= 10 && Number.isInteger(customCredits) && customCredits % 10 === 0) {
    credits = customCredits;
  } else { ... 400 에러 ... }
}
```

**문제점**:
1. 클라이언트가 `amount`를 전송 → 서버가 이를 기준으로 크레딧 산출
2. **토스 API 확인 단계에서 실제 결제 금액을 검증**: 토스에 `{ paymentKey, orderId, amount }` 전송 → 토스가 금액 불일치 시 거부
3. 따라서 클라이언트가 amount를 조작해도, 토스 측에서 실제 결제 금액과 불일치하면 승인 거부

→ **토스 SDK의 서버 검증 흐름이 보호해주므로 금액 조작은 불가**.

**단, 맞춤 충전 폴백이 존재**:
- `₩145 × 10c 배수`이면 모든 금액 허용 (예: ₩1,450=10c, ₩14,500=100c 등)
- 이는 할인 없는 정가 환산이므로 경제적 손해는 없으나, 예상치 못한 금액이 들어올 수 있음

**비로그인 직접결제** (`/api/payments/toss/direct`, portal/server.js:1994-2056):
- 토스 결제 승인 후 **다운로드 토큰만 발급** (크레딧 미지급)
- 토큰: `randomBytes(32).toString('hex')` — 256비트, 추측 불가
- TTL: 5분 (`DIRECT_TOKEN_TTL = 5 * 60 * 1000`)
- 1분마다 만료 토큰 정리 (`setInterval`, server.js:167-172)
- in-memory Map 저장 → 서버 재시작 시 소멸

**문제**: 다운로드 토큰을 실제로 검증하여 다운로드를 허용하는 코드가 보이지 않음. `result.js:343`에서 `data.downloadToken`을 받아도, `cropAndGoToThankyou()`는 토큰 검증 없이 클라이언트 사이드에서 crop 후 thankyou 이동. 즉, **직접결제 후 토큰 검증이 서버사이드에서 이루어지지 않고 클라이언트가 토큰 존재만 확인** (`data.downloadToken`이 truthy이면 진행).

→ **수정 제안**: 다운로드 토큰을 서버에서 검증하는 단계 추가 (현재는 결제 성공 응답의 `downloadToken` 필드 유무로만 판단)

### #6. 크레딧 차감 시 Firestore 트랜잭션 안전성 — ✅ 정상

**차감 (portal/server.js:1307-1321)**:
```
const result = await firestore.runTransaction(async (tx) => {
  const userDoc = await tx.get(userRef);
  const currentCredits = userDoc.data()?.credits ?? 0;
  if (currentCredits < cost) {
    return { success: false, error: '크레딧 부족', credits: currentCredits, required: cost };
  }
  const newCredits = currentCredits - cost;
  tx.update(userRef, { credits: newCredits });
  return { success: true, credits: newCredits, used: cost, type };
});
```

- ✅ `runTransaction` 내에서 읽기 → 검증 → 업데이트 = **원자적**
- ✅ 잔액 부족 시 차감 거부 → **음수 잔액 불가**
- ✅ 동시 요청 시 Firestore가 트랜잭션 충돌 감지 → 자동 재시도
- ✅ 생성 실패 시 환불 로직 존재 (idphoto-kr/server.js:683, 690)

**단, 생성(10c)과 다운로드(70c)는 별도 API 호출**이므로 하나의 atomic 연산이 아님. 이는 설계 의도대로 (생성과 다운로드가 별개 행위).
