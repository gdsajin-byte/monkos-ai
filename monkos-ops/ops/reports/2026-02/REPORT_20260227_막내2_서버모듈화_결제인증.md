### 분리 시 주의점

#### 1. 트랜잭션 순서 (크리티컬)
- **결제 → 크레딧 충전**: 토스 API 승인 **성공 후** Firestore 트랜잭션. 이 순서가 뒤바뀌면 미결제 크레딧 지급 발생.
- **Lemon 웹훅**: 서명 검증 → 크레딧 지급 순서 보장 필수.
- 모듈 분리 시 `payments.js` → `credits.js` 함수 호출이 동기적 await 체인으로 유지되어야 함.

#### 2. 에러 롤백
- 현재 Firestore 트랜잭션 내에서만 원자성 보장. 외부 API(토스/Lemon) 호출과 Firestore 쓰기 사이에 **분산 트랜잭션 없음**.
- `logTransaction()`은 fire-and-forget → D1 원장 기록 실패가 크레딧 작업에 영향 없음 (의도된 설계).
- 모듈 분리 시 이 fire-and-forget 패턴을 유지해야 함.

#### 3. 공유 시크릿 이중 사용
- `LEMONSQUEEZY_WEBHOOK_SECRET`이 (a) LS 웹훅 서명 검증 + (b) HMAC 인증 토큰 생성 양쪽에 사용됨 (L84, L108, L2038, L1822, L1867).
- 모듈 분리 시 auth.js와 payments.js 양쪽에서 이 환경변수를 참조해야 함. 별도 `AUTH_TOKEN_SECRET` 도입을 검토할 것.

#### 4. in-memory 상태 (인스턴스 바운드)
- `pendingLineStates` Map (LINE CSRF) — auth.js
- `directTokens` Map (비로그인 결제 토큰) — payments.js
- `chatHistories`, `csHistories` Map (대화 히스토리) — 라우터/챗봇 파트
- Cloud Run 인스턴스 간 공유 불가. 현재 설계에서는 단일 인스턴스 전제. 모듈 분리 시에도 동일 프로세스 내 공유됨 (문제 없음).

#### 5. credits/event의 이중 성격
- `POST /api/credits/event` (L1620~1804)는 크레딧 모듈이면서 이벤트 검증 로직(카카오 채널 API, 텔레그램 getChatMember)을 포함.
- **권장**: 검증 로직을 events.js로 분리하고, credits.js는 순수 크레딧 증감만 담당. credits/event API에서 events.js의 검증 함수를 호출하는 구조.

#### 6. 라우팅 방식
- 현재 `if (req.url === ...)` 패턴으로 2,900줄 단일 핸들러.
- 모듈 분리 시 각 모듈이 `(req, res) => boolean` 형태의 핸들러를 export하고, server.js 메인에서 순차 호출하는 구조 권장.
- 또는 경량 라우터 라이브러리 도입 없이, `Map<string, handler>` 패턴으로 URL 매핑.
