### 핵심 문제 요약

1. **이중 진실 소스 (Dual Source of Truth)**: 쿠키와 sessionStorage에 동일 정보가 중복 저장. 하나가 만료/삭제되면 불일치 발생
2. **credits.html localStorage 이탈**: 다른 페이지는 sessionStorage인데 credits.html만 localStorage 사용 → 세션 격리 불일치
3. **토큰 미사용**: gate.js가 `monkos_token`을 sessionStorage에 저장하나, shared.js의 `checkTokenExpiry()`는 JWT 형식 파싱을 시도 (현행 토큰은 JWT가 아닌 HMAC 형식) → 항상 실패하여 세션 삭제 위험
4. **idphoto-kr API 인증 없음**: idphoto-kr 서버의 API 엔드포인트는 `req.body.userId`를 그대로 신뢰 → 쿠키 기반 서버사이드 인증 미구현

### Q1: MPA + 크로스 서브도메인 환경에서 HttpOnly 쿠키 단일 인증은 업계 표준인가?

**답변: 예, 제어된 서브도메인 환경에서는 실질적 업계 표준이다.**

MPA + 크로스 서브도메인 인증은 3개 티어로 구분된다:

| 티어 | 패턴 | 사용 서비스 |
|------|------|------------|
| A | HttpOnly 쿠키, 서브도메인 공유 안 함 | GitHub (보안 극대화) |
| B | HttpOnly 쿠키 + `Domain=.example.com` | **대부분의 SaaS/MPA** (Atlassian, 중소 SaaS) |
| C | OIDC/OAuth 2.0 SSO | Google, 대규모 엔터프라이즈 |

**MONKOS에 해당하는 티어 B**가 가장 현실적이다:
- `monkos.ai`, `idphoto-kr.monkos.ai`, `idphoto-jp.monkos.ai` 모두 **자사 제어 서브도메인**
- 사용자 생성 콘텐츠를 서브도메인에서 호스팅하지 않음
- 서비스 규모 대비 OIDC SSO는 과잉 설계

**주요 참고 사례:**
- GitHub: 사용자 콘텐츠 호스팅 서브도메인에서 쿠키 오버플로우 공격 발생 → `github.io`로 분리. 단, MONKOS는 사용자 콘텐츠를 서브도메인에 호스팅하지 않으므로 이 위험 없음
- OWASP 권장: `Domain` 속성 설정 시 서브도메인 위험 인지 필수, 단 모든 서브도메인이 자사 제어라면 수용 가능

**결론**: `HttpOnly + Secure + SameSite=Lax + Domain=.monkos.ai` 쿠키 단일 인증은 MONKOS 규모와 구조에 **적합한 업계 표준 패턴**이다.

### Q2: 현행 토큰 형식(`base64url(userId:expires:hmac)`)을 쿠키에 그대로 태우는 게 맞는가?

**답변: 현행 HMAC 형식을 유지하되, 2개 결함을 수정해야 한다.**

#### 현행 토큰 분석 (config.js 149~158행)

```
토큰 구조: base64url("userId:expiresTimestamp:hmacSha256Hex")
크기: ~140 bytes (쿠키 4KB 한도 대비 충분)
서명 키: LEMONSQUEEZY_WEBHOOK_SECRET (결제 웹훅과 공유!)
```

#### HMAC vs JWT 비교

| 항목 | 현행 HMAC | JWT (HS256) |
|------|----------|-------------|
| 쿠키 크기 | ~140 bytes | ~200 bytes |
| 암호 강도 | HMAC-SHA256 (동일) | HMAC-SHA256 (동일) |
| 타이밍 안전 비교 | **미구현** (`sig !== expectedSig`) | 라이브러리가 처리 |
| 구분자 안전성 | `:` 구분 — userId에 `:` 포함 시 파싱 실패 | 구조화된 claims |
| 외부 의존성 | 없음 | `jose` 또는 `jsonwebtoken` |
| 디버깅 도구 | 없음 | jwt.io 등 |
| 마이그레이션 비용 | 없음 | 전체 사용자 강제 재로그인 |

#### 결정적 판단 근거

현 아키텍처에서 **모든 토큰 검증이 Firestore 조회를 수반**한다 (`verify-cookie` → `usersCollection.doc(userId).get()`). JWT의 핵심 이점인 "무상태 검증"이 **적용되지 않는 구조**다.

#### 수정 필수 사항 (형식 무관)

1. **타이밍 안전 비교 도입** (보안 결함):
   ```javascript
   // 현행: if (sig !== expectedSig) return null;  ← 타이밍 공격 취약
   // 수정: crypto.timingSafeEqual(Buffer.from(sig, 'hex'), Buffer.from(expectedSig, 'hex'))
   ```

2. **인증 전용 시크릿 분리** (설계 결함):
   - 현재 `LEMONSQUEEZY_WEBHOOK_SECRET`을 결제 웹훅 서명 + 인증 토큰 서명에 이중 사용
   - `AUTH_SECRET` 환경변수 신설 필요 → 결제 시크릿 교체 시 전체 세션 무효화 방지

**결론**: HMAC 형식 유지 + 2개 결함 수정 권장. JWT 전환은 분산 검증이 필요해질 때 (예: 별도 마이크로서비스에서 세션 검증) 재검토.

### Q3: `SameSite=Lax` + `.monkos.ai` 도메인 쿠키로 세션 공유가 완전한가?

**답변: 기술적으로 완전하다. 단, 현재 코드가 쿠키를 활용하지 않는 구간이 있다.**

#### SameSite=Lax 시나리오별 분석

| 요청 방식 | 발신 → 수신 | 쿠키 전송 |
|-----------|------------|----------|
| 브라우저 최상위 탐색 (GET) | 어디서든 → monkos.ai 계열 | **전송됨** |
| `<a href>`, `location.href` | 어디서든 → monkos.ai 계열 | **전송됨** |
| `fetch(credentials: 'include')` | idphoto-kr → monkos.ai | **전송됨** (same-site) |
| `fetch` (기본, credentials 없음) | idphoto-kr → monkos.ai | 전송 안 됨 |
| `<form method="POST">` (크로스-사이트) | 외부 → monkos.ai | 전송 안 됨 |
| iframe 내 요청 | 외부 임베드 → monkos.ai | 전송 안 됨 |

**핵심**: `idphoto-kr.monkos.ai`와 `monkos.ai`는 **same-site** (eTLD+1 = `monkos.ai`)이므로 SameSite=Lax는 서브도메인 간 통신을 차단하지 않는다.

#### 누락 시나리오

1. **Safari ITP**: `monkos.ai` → `idphoto-kr.monkos.ai`는 퍼스트파티 접근이므로 ITP 영향 없음. 안전
2. **iframe**: `X-Frame-Options: DENY` 설정 확인 완료 → iframe 시나리오 해당 없음
3. **fetch credentials 누락**: 클라이언트에서 `fetch(portalUrl/api/auth/verify-cookie, { credentials: 'include' })` — shared.js 246행에 이미 설정됨. 안전

#### 현재 미구현 구간

- **idphoto-kr 서버 API**: `/api/credit/use`, `/api/generate` 등이 `req.body.userId`를 무조건 신뢰. 쿠키 기반 서버사이드 인증이 없음 → 쿠키 단일화 시 이 API들에 쿠키 검증 미들웨어 추가 필요

**결론**: 쿠키 전송 자체는 완전. 단, 서버사이드에서 쿠키를 읽어 인증하는 로직이 idphoto-kr에 미구현 → 구현 필요.

### Q4: 토스 결제 리다이렉트에서 세션 유지가 보장되는가?

**답변: 보장된다.**

#### 토스 결제 흐름

```
monkos.ai (결제 버튼)
  → toss.im/payment (토스 결제 페이지)
  → monkos.ai/toss-success?paymentKey=...&orderId=...&amount=... (GET 302 리다이렉트)
```

SameSite=Lax 규칙:
> "최상위 탐색(top-level navigation) + GET 메서드 → 쿠키 전송"

토스 성공 콜백은 **GET redirect**이므로 `monkos_session` 쿠키가 복귀 요청에 포함된다.

#### 엣지 케이스

| 상황 | 세션 유지 |
|------|----------|
| 토스 정상 리다이렉트 (GET) | **유지됨** |
| 3DS 인증 후 POST redirect | **차단 가능** (단, 토스 v1은 항상 GET) |
| iOS Safari + ITP | 쿠키 유지됨 (퍼스트파티) |
| Private Relay | 쿠키 유지됨 (도메인 기반) |
| 가상계좌 비동기 통보 | 서버-서버 웹훅이므로 쿠키 무관 |

#### 현행 코드의 이중 안전장치

현재 토스 결과 처리는 쿠키 의존 없이 URL 파라미터의 `paymentKey`, `orderId`, `amount` + body의 `userId`로 작동. 쿠키 단일화 후에도 이 흐름은 유지하되, userId를 쿠키에서 추출하는 방식으로 전환 가능.

**결론**: SameSite=Lax + GET redirect이므로 세션 유지 보장. 토스 v1 API는 항상 GET redirect를 사용하므로 안전.

### Q5: sessionStorage/localStorage 완전 제거 vs 보조 캐시로 유지?

**답변: 인증 저장소로는 완전 제거하되, UX 캐시로 제한적 유지 권장.**

#### 분석

| 구분 | 완전 제거 | 보조 캐시 유지 |
|------|----------|--------------|
| 아키텍처 | 깔끔함. 인증 = 쿠키 단일 | 약간의 복잡도 |
| 성능 | 매 페이지 로드마다 verify-cookie API 호출 | 캐시 히트 시 API 호출 생략 |
| 정합성 | 항상 서버와 일치 | 캐시 스테일 가능성 |
| UX | 페이지 전환 시 미세한 로딩 (API 응답 대기) | 즉시 UI 렌더링 |

#### 권장 전략: "쿠키 = 인증, sessionStorage = UI 캐시"

```
[페이지 로드]
  1. /api/auth/verify-cookie (credentials: include) → 서버 인증
  2. 성공 시: 유저 정보를 sessionStorage에 캐시 (UI 빠른 렌더링용)
  3. 실패 시: sessionStorage 삭제, 비로그인 UI

[다음 페이지 이동]
  1. sessionStorage 캐시 → 즉시 UI 렌더링
  2. 백그라운드에서 verify-cookie → 최신 크레딧 동기화
```

#### 제거 대상

| 키 | 현재 용도 | 판정 |
|----|---------|------|
| `monkos_user` (sessionStorage) | 인증 소스 | **캐시로 격하** (인증 소스 → 쿠키) |
| `monkos_token` (sessionStorage) | 토큰 저장 | **완전 제거** (HttpOnly 쿠키로 대체) |
| `monkos_user` (localStorage, credits.html) | 인증 소스 | **완전 제거** (쿠키로 통일) |
| `monkos_free_gen` (localStorage) | 무료생성 카운트 | **유지** (인증과 무관) |
| `monkos_style/gender/age` (sessionStorage) | 선택 상태 | **유지** (인증과 무관) |

**결론**: 인증 토큰(`monkos_token`)과 credits.html의 localStorage는 완전 제거. `monkos_user`는 UI 캐시로만 유지하되 인증 소스 역할은 쿠키로 이관.

### Q6: 로그아웃 엔드포인트에서 쿠키 삭제만으로 충분한가?

**답변: 현행 무상태 토큰 구조에서는 쿠키 삭제만으로 충분하다.**

#### 분석

현행 인증 토큰은 **무상태 HMAC 토큰**이다. 서버에 세션 테이블이 없으므로:
- 쿠키 삭제 = 클라이언트에서 토큰 소멸 = 실질적 로그아웃
- 서버 세션 무효화 대상이 없음 (세션 목록 미관리)

#### 권장 로그아웃 엔드포인트

```
GET /auth/logout

서버 동작:
1. Set-Cookie: monkos_session=; Domain=.monkos.ai; Path=/; Max-Age=0; HttpOnly; Secure
2. 302 Redirect → /
```

#### 보완 사항

| 항목 | 필요성 | 비고 |
|------|--------|------|
| 쿠키 삭제 | **필수** | Max-Age=0 |
| 서버 세션 무효화 | 불필요 | 서버 세션 테이블 없음 |
| 클라이언트 캐시 정리 | **권장** | 리다이렉트 후 페이지에서 sessionStorage 정리 |
| OAuth 제공자 로그아웃 | 선택 | 카카오/LINE/Google 세션은 분리 (SSO 아님) |
| CSRF 보호 | **권장** | 로그아웃을 GET으로 하면 이미지 태그 공격 가능 → POST 권장 |

#### 향후 토큰 블랙리스트 필요 시

즉시 무효화가 필요해지면 (예: 관리자 강제 로그아웃) Firestore에 `revoked_tokens` 컬렉션 추가:
- 로그아웃 시 토큰 해시 저장 (TTL = 토큰 만료까지)
- verify-cookie에서 블랙리스트 체크 추가

현 규모에서는 과잉 설계. 쿠키 삭제 방식으로 충분.

**결론**: 쿠키 삭제(Max-Age=0) + 클라이언트 캐시 정리면 충분. POST 메서드 권장.

## 3. 대안 A/B/C 비교표

### 대안 정의

| 대안 | 설명 |

### 대안별 상세 평가

#### A. 쿠키 단일화 (권장)

**장점:**
- 인증 소스가 하나이므로 12cr 버그 같은 불일치 원천 제거
- 크로스도메인 세션 공유가 자동 (쿠키가 same-site 서브도메인에 자동 전송)
- 구현 복잡도 최소: 기존 코드에 이미 쿠키 발급 + verify-cookie API 구현됨
- 서버 무상태 유지 → 인프라 추가 불필요

**단점:**
- 즉시 토큰 무효화 불가 (관리자 강제 로그아웃 등)
- 매 페이지 로드 시 verify-cookie API 호출 1회 (네트워크 의존)

#### B. 이중화 정리

**장점:**
- 변경 범위가 가장 작음 (현행 구조 유지, 정합성 코드만 추가)
- sessionStorage 캐시로 즉시 UI 렌더링 가능

**단점:**
- 근본 문제(이중 소스) 미해결 → 12cr 버그 재발 위험
- 동기화 로직이 복잡 (쿠키 ↔ sessionStorage 어느 것이 최신?)
- credits.html의 localStorage 문제 별도 해결 필요

#### C. 서버 세션

**장점:**
- 즉시 세션 무효화 가능
- 토큰에 민감 정보 불포함 (세션 ID만)

**단점:**
- Firestore 세션 컬렉션 또는 Redis 추가 필요 → 인프라 비용 + 복잡도
- 매 API 요청마다 세션 DB 조회 → 레이턴시 증가
- 세션 스토어 장애 시 전체 인증 불가 → 가용성 리스크
- MONKOS 규모(소규모 MPA)에 과잉 설계

## 4. 추천 방향

### 결론: **대안 A — 쿠키 단일화**

#### 근거

1. **아키텍처 적합성**: MONKOS는 소규모 MPA + 자사 제어 서브도메인. HttpOnly 쿠키 단일 인증이 업계 표준 패턴에 부합
2. **근본 해결**: 12cr 버그의 원인인 "이중 진실 소스"를 원천 제거
3. **기존 인프라 활용**: auth.js의 쿠키 발급 + verify-cookie API가 이미 구현됨. 추가 인프라 불필요
4. **구현 비용 최소**: 주요 변경은 클라이언트 쪽 sessionStorage 의존 제거 + idphoto-kr API에 쿠키 검증 추가
5. **프록시 금지 원칙** (헌법 제10조): 이중화(대안 B)는 근원 해결 없이 동기화 코드로 우회하는 프록시에 해당

#### 구현 시 전제 조건

1. `AUTH_SECRET` 환경변수 신설 (LEMONSQUEEZY_WEBHOOK_SECRET과 분리)
2. `verifyAuthToken()`에 `crypto.timingSafeEqual()` 적용
3. idphoto-kr API에 쿠키 검증 미들웨어 추가 (`req.body.userId` 신뢰 → 쿠키 검증으로 전환)
4. credits.html의 localStorage → 쿠키 기반으로 전환
5. `checkTokenExpiry()` 함수 제거 (JWT 형식 파싱 시도 → 불필요)
6. 로그아웃 엔드포인트 `POST /auth/logout` 신설

## 5. 주의사항

### 반드시 지켜야 할 사항

1. **쿠키 속성 일관성**: 모든 `Set-Cookie` 발급 지점에서 `Domain=.monkos.ai; Path=/; Secure; HttpOnly; SameSite=Lax` 동일 적용. 하나라도 다르면 브라우저가 별개 쿠키로 인식
2. **credentials: 'include' 필수**: 클라이언트의 모든 크로스 서브도메인 fetch 호출에 `credentials: 'include'` 명시. 기본값은 `same-origin`이므로 누락 시 쿠키 미전송
3. **CORS 설정 점검**: `Access-Control-Allow-Credentials: true` + `Access-Control-Allow-Origin`에 와일드카드(`*`) 사용 불가 → 구체적 origin 명시 필요 (현재 config.js의 ALLOWED_ORIGINS 활용)
4. **마이그레이션 경로**: sessionStorage 의존 코드 일괄 제거 시 기존 로그인 사용자의 세션이 끊김 → 쿠키가 있으면 자동 복원되므로 실질적 영향 최소
5. **토스 결제 흐름 보존**: 현행 URL 파라미터 기반 결제 흐름은 쿠키와 독립적으로 작동 → 병행 유지하되 userId를 쿠키에서 추출하는 방식 검토
6. **개발/로컬 환경**: `Domain=.monkos.ai`는 localhost에서 작동하지 않음 → 개발 환경용 분기 필요 (Domain 미설정 또는 localhost 전용 쿠키)

### 위험 요소

1. **서브도메인 침해 = 세션 탈취**: `Domain=.monkos.ai` 쿠키는 모든 `*.monkos.ai`에서 접근 가능. 사용하지 않는 서브도메인의 DNS 레코드 정리 필수 (서브도메인 테이크오버 방지)
2. **SameSite=Lax의 POST 제한**: 외부 사이트에서 monkos.ai로 POST 요청 시 쿠키 미전송. 향후 외부 연동(결제 웹훅의 POST redirect 등)에서 주의
3. **쿠키 만료 전략**: 현행 30일 (`Max-Age=2592000`). 적절하나, 리프레시 메커니즘이 없으면 30일 후 강제 재로그인. 현행 `/api/auth/refresh` 엔드포인트를 쿠키 갱신용으로 전환 검토
