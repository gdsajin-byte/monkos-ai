# iMac 로컬 바이너리 에셋 전수 조사 + 워크벤치 구성안 기안

> **[2026-06-21 12:01 KST]** iMac/쌍아 → 막내2
> 작가님 지시: 로컬 전체 바이너리 파일의 배치와 관계를 파악하고, 워크벤치 구성안을 기안하라.

## 1. 배경

### 현재 문제
- iMac Desktop에 **356개 이미지 바이너리**가 15+ 폴더에 흩어져 있음
- CROP APP 단독으로도 **222개**, 절반 이상 중복
- GCS(프로드)와 로컬 사이에 **"내 폴더 = 서버 폴더" 대응 관계**가 없음
- monk.kr 시절에는 FTP 구조 = 로컬 디렉토리여서 "여기 이미지는 여기 있지"가 직관적이었으나, monkos 전환 후 그 직관이 깨짐
- 꾸(M2)도 같은 문제 — 이미지프로 전후사진 등이 로컬에 흩어져 중복·소실 발생

### 클로드 디자인(Opus 4.8)과의 논의 결과
- 업계 표준 패턴: **워크벤치(자유) → 정위치(엄격)** 2층 구조
- 3층(워크벤치→스테이징→정위치)은 후보 더미가 많은 창작 파이프라인에 적합
- 핵심 원칙: **"도려내기를 없앤다"** — 마음에 드는 폴더를 통째로 올리고, 정위치만 깨끗하게 유지
- Git의 working tree→staging→committed, Lightroom의 카드→카탈로그→Export와 같은 구조

### MONK 현실의 4개 물리 장소
```
① 로컬 Mac 폴더           ← 크롤/생성물/스크린샷 축적 (Desktop 전역)
② 클로드 디자인 프로젝트    ← 디자인 시안/컨셉 (클로드 서버)
③ Git 레포 (monk_project)  ← 코드만. 바이너리 추적 안 함
④ GCS 버킷                ← 프로덕션 바이너리 정본
```

### PF_STYLER 서비스 로드맵 (에셋 구조 설계 시 감안)
```
증명사진 (규격) → 헤드샷 (스타일) → 모델스 (VTON) → 앱 (커머스 중개)
```
에셋 구조는 이 진화 선 전체를 담을 그릇이어야 함.

## 2. 미션

### Phase 1: 전수 조사 (보고서)

**Desktop 전역** 이미지 바이너리를 스캔하여 아래를 파악:

#### 1-1. 폴더별 에셋 인벤토리
각 폴더에 대해:
- 이미지 파일 수, 총 용량, 주요 포맷
- 용도 분류 (서비스 에셋 / 작업 산출물 / 리서치 소스 / 스크린샷·캡처 / 개인 서류 / 레거시)
- 서비스 연관성 (idphoto / headshot / studio / VTON / blog / 광고 / 없음)

#### 1-2. 중복 탐지
- **동일 파일명** 중복 (폴더 간)
- **동일 내용** 추정 중복 (파일 크기 일치 + 파일명 유사)
- 중복 그룹별 "원본 후보" 식별

### Phase 2: 워크벤치 구성안 기안 (제안서)

Phase 1 결과를 바탕으로 **가장 효율적인 로컬 워크벤치 구조**를 기안:

#### 필수 고려사항

1. **monk.kr 시절의 직관 복원**: 로컬 폴더를 열면 "이 이미지는 여기 있지"가 바로 파악되어야 함
2. **GCS 거울 구조**: 로컬 워크벤치 폴더 구조가 GCS prefix 구조를 반영해야 동기화가 자연스러움
3. **도려내기 금지**: 개별 파일을 골라서 옮기는 게 아니라 폴더째 승격하는 흐름
4. **PF_STYLER 로드맵 수용**: 현재 서비스(증명사진, 헤드샷) + 미래 서비스(모델스, 앱) 구조까지 포함
5. **팀원(꾸) 확장성**: M2에도 동일 구조를 적용할 수 있어야 함
6. **개인 서류 분리**: 서비스 에셋과 개인 서류(소송, 서류증명 등)는 완전 분리

#### 산출물 포맷

```
## 제안 구조
~/MONKOS_ASSETS/         (또는 다른 이름)
  {서비스별 디렉토리}/
    {용도별 하위}/

## 현재 → 제안 매핑
현재 위치 → 제안 위치 (이동/통합/아카이브/유지)

## GCS 대응표
로컬 경로 ↔ GCS prefix ↔ 동기화 방법(수동/스크립트/자동)

## 레거시 처리안
삭제/아카이브/유지 판정
```
