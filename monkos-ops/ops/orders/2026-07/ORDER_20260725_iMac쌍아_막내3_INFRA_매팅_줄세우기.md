## §2. portal — 503 재시도 루프 (`lib/matte.js`)

현행 `runMatteChain()`(190~220행)은 **호출 실패 시 같은 URL로 1회 재시도 후 즉시 다음 엔드포인트**로 넘어간다. 이를 **503에 한해** 다음으로 바꾼다.

```
for (url of MATTE_API_URLS) {
  if (!isAlive(url)) → continue                    ← 현행 유지 (진짜 장애는 즉시 폴백)
  loop (총 대기 ≤ MATTE_QUEUE_WAIT_MS) {
      call(url)
      ├─ 성공 → return
      ├─ 503  → Retry-After(없으면 2000ms) 만큼 sleep → 재시도
      └─ 그 외 에러 → 기존 1회 재시도 로직 유지 → 실패 시 다음 엔드포인트
  }
  상한 초과 → 다음 엔드포인트 (RunPod)
}
```

- **`MATTE_QUEUE_WAIT_MS` 신설, 기본 20000(20초).** 작가님 판단: *"20초 정도면 보통 10초 안에서 다 해결될 것."*
- **503만 대기 대상.** 그 외 에러(타임아웃·5xx·네트워크)는 기존 동작 유지 — 바쁜 것이 아니라 고장이다.
- **`isAlive()` 실패 시 즉시 다음 엔드포인트**는 그대로 둔다. 이 분기가 "장애 대비" 경로다.
- 대기 중 **로그를 남길 것** — 몇 번째 노크인지, 누적 대기 얼마인지. 무음 대기 금지.
- ⚠️ **`MATTE_TIMEOUT_MS`(60초)는 건드리지 말 것.** 개별 호출 타임아웃과 큐 대기는 다른 축이다.

## §3. Cloud Run 예산 검증 (필수)

대기 20초가 들어가면 **전체 생성 요청이 Cloud Run `timeoutSeconds=120`을 넘길 수 있다.**

- precheck·fit·crop·매팅·GCS 저장 각 구간의 실측 소요를 **로그로 뽑아 합산**할 것.
- **최악 시나리오**(4060 20초 대기 후 RunPod 콜드)에서 120초를 넘는지 계산.
- 넘는다면 **`MATTE_QUEUE_WAIT_MS`를 실측 기반으로 낮춰 제안**할 것. 20초는 상한 후보이지 확정이 아니다.
