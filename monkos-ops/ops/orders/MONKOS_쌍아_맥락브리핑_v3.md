## 1. 출발점: v2.1의 한계

v2.1은 "증명사진 N장"이 상품이었다:

```
70c 단건 = 1장, 140c 패키지 = 2장, 280c 패키지 = 4장
```

여기서 세 가지 문제가 드러났다:

**문제 1 — "4장 패키지"라는 이름의 함정**
280c를 "4장 패키지"로 하면, 유저는 "내가 쓸 4장"을 기대한다. 그런데 크레딧은 생성·풀샷·규격추가 어디서든 쓸 수 있다. 3장만 뽑고 풀샷을 받으면 "나머지 1장은?" 하는 불만이 생긴다. **상품은 크레딧이지 매수가 아니다.**

**문제 2 — 보너스율이 밋밋하다**
v2.1 보너스: +10c/+20c/+60c. 70c를 두 번 사면 +20c 보너스인데, 140c 패키지도 +20c. 패키지를 쓸 인센티브가 약하다.

**문제 3 — 풀샷 20c가 치사하다**
가입선물 10c + 단건 보너스 10c = 잔고 10c. 여기서 풀샷(20c)을 받으려면 10c가 부족 → 잔액충전 필수. 10c 때문에 ₩1,450 추가 결제를 강요하는 구조.

## 3. 상품 구조 재설계 과정

### 3-1. "상품은 크레딧이다" 원칙 수립

"증명사진 몇 장"이 아니라 "몇 c를 사는가"가 상품명이 되어야 한다. 크레딧은 자유 소비이므로 "장비 환산"은 무의미.

### 3-2. 70c 단건 앵커 유지

70c 단건(₩9,900)을 유지한다. 이유:
- 다운로드 1회(70c)에 딱 맞는 크레딧 → 유저가 직관적
- +10c 보너스 → 총 80c → 1장 완성에 정확히 맞음
- 앵커 상품 (첫 탑 유저용) → 반복 구매 가능

### 3-3. 패키지를 라운드 넘버로

140c/280c (×80c 기준) → **100c / 300c / 500c** (라운드 넘버)

라운드 넘버로 가면 심리가격대(₩X,900)에 정확히 잘 맞는데, 이 차이는 **보너스 크레딧으로 조절**한다.

### 3-4. 보너스율 계단 화

70c 반복구매보다 패키지가 확실히 이득이어야 한다 → 보너스율을 패키지 상위로 갈수록 크게 벌린다:

```
70c  단건: +10c  (14%)
100c 패키지: +30c  (30%)
300c 패키지: +120c (40%)
500c 패키지: +250c (50%)
```

14% → 30% → 40% → 50% 계단 구조.

### 3-5. 풀샷 20c → 10c

10c가 기본 단위로 통일: 생성(10c), 풀샷(10c), 규격추가(10c) 전부 같은 단가. 유저 입장에서 "10c짜리 행위"와 "70c짜리 행위(다운로드)" 두 종류뿐. 인지 부하 최소화.

잔고 10c에서 풀샷 10c를 딱 받을 수 있다. 치사하지 않다.

## 4. 취소선 기준 변경

v2.1: 취소선 = **상품 크레딧만** × 기축 단가
→ 70c × ₩145 = ₩10,150 (취소선)

v3: 취소선 = **총 크레딧(보너스 포함)** × 기축 단가
→ 80c × ₩145 = ₩11,600 (취소선)

**이유**: 유저가 받는 전체 가치를 정가로 표시해야 할인 체감이 극대화된다. 보너스를 빼고 취소선을 잡으면 보너스의 존재감이 사라진다.

### 산술 검증 (KRW)

```
기축: 10c = ₩1,450 → 1c = ₩145

단건:  총 80c × ₩145 = ₩11,600 → ₩9,900  (₩1,700 절약) ✓
100c: 총 130c × ₩145 = ₩18,850 → ₩12,900 (₩5,950 절약) ✓
300c: 총 420c × ₩145 = ₩60,900 → ₩34,900 (₩26,000 절약) ✓
500c: 총 750c × ₩145 = ₩108,750 → ₩49,900 (₩58,850 절약) ✓
```

할인율이 14.7% / 31.6% / 42.7% / 54.1%로 딱 떨어지지 않으므로 **할인율 퍼센트 등지는 삭제**. 취소선과 실결제가 나란히 표시하면 유저가 직접 체감. 퍼센트 불필요.

## 5. 충전 UI 구조 결정

### 5-1. "충전은 페이지가 아니라 이벤트"

잔고부족은 특정 페이지가 아니라 **모든 과금 행위에서 발생하는 이벤트**. 생성(10c 부족), 다운로드(70c 부족), 풀샷(10c 부족), 규격추가(10c 부족) → 전부 다른 화면, 다른 맥락.

그래서 충전 UI는 **하나의 컴포넌트(ChargePanel)**:
- 랜딩에서 진입 → 풀페이지
- 컨베이어 벨트 중간 잔고부족 → 바텀시트 모달
- **같은 컴포넌트, 다른 컨테이너**

### 5-2. 뒤로가기 = 원래 자리로 복귀

충전 안 해도 뒤로가기 누르면 원래 자리. 프리뷰에서 왔으면 프리뷰로, 생성에서 왔으면 촬영 화면으로.

### 5-3. 충전 화면에 없는 것

- ~~크레딧 개념~~ → 체험에서 체득
- ~~활용 힌트~~ → 크레딧 자유 소비
- ~~가입선물/발급보장/CTA/푸터~~ → 랜딩 역할
- ~~할인율 등지~~ → 취소선으로 충분

## 6. 결제 인프라 결정

Lemon Squeezy 조사 결과:
- **Checkout Overlay** 지원 → lemon.js로 우리 앱 안에서 모달 결제. 유저가 외부로 이탈하지 않음.

그래서 KR은 ChargePanel → 토스 결제창 모달, JP/USD는 ChargePanel → LS Checkout Overlay 모달. UX 거의 동일.

**이번 지시서는 KRW만.** JP/USD는 KRW 코드 완성 후 확장.

## 7. 컨베이어 벨트 잔고 흐름 검증

### 첫 방문자 (단건)
```
가입 → +10c → 잔고 10c
생성 → -10c → 잔고 0c → 프리뷰 확인
70c 단건 충전(₩9,900) → +70c +10c(보너스) → 잔고 80c
다운로드 → -70c → 잔고 10c
  → 잔여 10c로: 재생성(10c) / 풀샷(10c) / 규격추가(10c) 중 택 1
```

### 100c 패키지
```
충전(₩12,900) → +100c +30c(보너스) → 잔고 130c
다운로드 1회(-80c) → 잔고 50c
  → 자유 활용: 생성 5회(프리뷰 탐색) 또는 풀샷+규격추가+재생성 조합
```

### 500c 패키지
```
충전(₩49,900) → +500c +250c(보너스) → 잔고 750c
다운로드 9회(-720c) → 잔고 30c
  → 풀샷(10c) + 규격추가(10c) + 재생성(10c)으로 잔금 소진
```

**모든 시나리오에서 잔고 10c~30c 남음 → 10c 옵션으로 잔금 소진 → 재방문 유지.**

## 8. 70c 반복구매 vs 패키지 대조

이게 중요하다. 70c를 반복 구매하는 것보다 패키지가 이득이어야 패키지를 쓴다.

```
70c × 2 = ₩19,800에 160c
100c × 1 = ₩12,900에 130c → ₩6,900 저렴, 30c 적음 → 100c 충분히 매력적

70c × 3 = ₩29,700에 240c
300c × 1 = ₩34,900에 420c → ₩5,200 비싸지만 180c 더 많음 → 300c 확실히 이득

70c × 5 = ₩49,500에 400c
500c × 1 = ₩49,900에 750c → 가격 비슷, 350c 더 많음 → 500c 절대적 이득
```

## 10. config.js 구조 변경

### 현행 (v2.1)
```js
TOSS_AMOUNT_CREDITS: { 9900: 80, 13050: 90, 14500: 100, ... }
```
보너스가 총 크레딧에 합산된 플랫 매핑. 보너스 정책 변경 시 상품 가격까지 건드려야 함.

### v3
```js
PRODUCTS: {
  single_70:   { price: 9900,  credits: 70,  bonus: 10 },
  package_100: { price: 12900, credits: 100, bonus: 30 },
  package_300: { price: 34900, credits: 300, bonus: 120 },
  package_500: { price: 49900, credits: 500, bonus: 250 },
  topup_10:    { price: 1450,  credits: 10,  bonus: 0 },
}
```
상품c과 보너스c 분리 → 이벤트 보너스 증량 시 상품 가격 불변, 보너스만 조절.

**주의**: `TOSS_AMOUNT_CREDITS`를 참조하는 모든 코드 grep 필수. 토스 칠백 콜백에서 amount→credits 역참조 부분이 있을 것.
