## 작업 1: 전수 조사 + 분류

### 1-1. 한글 slug 58건 전수 목록 작성

sitemap.xml에서 한글 slug URL 전체를 추출하여 아래 분류표 작성:

| # | URL | 경로 | slug | Firestore ID | 영문 대응 URL 존재 여부 | 분류 |
|---|-----|------|------|-------------|----------------------|------|
| 1 | ... | ko | ... | ... | Y/N | A/B/C |

**분류 기준**:
- **A (JA/EN 교차오염)**: `/ja/blog/한글slug` 또는 `/en/blog/한글slug` — 최우선 처리
- **B (KO 초기 콘텐츠)**: `/blog/한글slug` — KO 경로이므로 기능 문제 없음. 장기 교정 대상
- **C (중복/유령)**: 영문 slug 버전이 이미 존재하는 한글 URL — 301 또는 삭제 대상

### 1-2. Firestore slug 데이터 확인

블로그 CMS의 Firestore에서 각 글의 slug 필드 구조 확인:
- slug가 단일 필드인지 다국어 분기인지
- 한글 slug 글에 영문 slug가 별도 존재하는지
- slug 변경 시 기존 URL이 자동 301 되는 로직이 있는지

## 작업 2: 교정 방안 설계

아래 3가지 교정 옵션을 비교 분석하여 추천안 제시:

### 옵션 A: server.js 301 리다이렉트 매핑
- 한글 slug URL → 영문 slug URL로 301 리다이렉트
- 장점: 기존 백링크/북마크 보존, SEO 링크 주스 전달
- 단점: 매핑 테이블 유지 필요, 58건 수동 매핑

### 옵션 B: Firestore slug 일괄 갱신 + 301
- Firestore에서 slug 필드를 영문으로 변경
- 변경 전 구 slug → 신 slug 301 리다이렉트 등록
- 장점: 근본 해결
- 단점: CMS 에디터/렌더러 영향 범위 확인 필요

### 옵션 C: sitemap에서 한글 slug 제거 + canonical
- sitemap에서 한글 slug URL 제외
- 한글 slug 페이지에 영문 slug canonical 태그 추가
- 장점: 코드 변경 최소
- 단점: 한글 URL 접속 시 페이지는 살아있으나 색인 제외

**각 옵션별 작업량, 리스크, 영향 범위를 표로 비교.**

## 작업 3: JA/EN 교차오염 24건 즉시 처리 방안

분류 A(교차오염) 24건에 대해:

2. 존재하면: 한글 slug → 영문 slug 301 리다이렉트 추가
3. 미존재: 영문 slug 생성 필요 여부 판단 (글 자체가 JA/EN 번역본이 있는지)
