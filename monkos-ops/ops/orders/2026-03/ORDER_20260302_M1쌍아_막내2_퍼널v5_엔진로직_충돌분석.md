## 3. 분석 항목 (보고서에 반드시 포함)

### 3-A. 상태 변수 매핑

v5 기획안의 상태 변수와 현재 shared.js store의 매핑을 전수 조사:

```
| v5 변수 | v5 타입/값 | 현재 store 대응 | 호환 여부 | 조치 |
|---------|-----------|----------------|----------|------|
| format  | "passport" | "id" | purpose/style | ❌ 매핑 필요 | 키 변경 or 변환 레이어 |
| gender  | "f" | "m" | gender | ✅ 동일? | 값 확인 |
| age     | "baby"|"child"|"teen"|"adult" | age | ? | 값 대조 |
| clothing | "default"|"change"|"casual"|"suit" | clothing | ? | 값 대조 |
| ...     | ... | ... | ... | ... |
```

**특히 중요**: camera.js가 sessionStorage에서 읽는 키 목록을 전수 확인. v5에서 키가 변경되면 camera.js가 깨진다.

### 3-B. sessionStorage 키 호환성

현재 앱의 sessionStorage 사용을 전수 조사:

```
| 키 | 쓰는 파일 | 읽는 파일 | v5 변경 여부 | 위험도 |
|----|----------|----------|-------------|--------|
```

- `saveSessionData()` / `loadSessionData()` 호출부 전수 조사
- v5에서 키 이름이 바뀌면 **camera.js, result.js가 깨질 수 있음**

### 3-C. 크레딧 로직 변경점

v5 과금 체계와 현재 코드의 차이:

```
| 항목 | 현재 코드 | v5 설계 | 변경 필요 |
|------|----------|---------|----------|
| 생성 비용 | CREDIT_COST.generate = 10 | 10c (동일) | |
| 다운로드 | CREDIT_COST.download = 70 | 70c (동일) | |
| 풀 원본 | CREDIT_COST.fullOriginal = 20 | 20c (동일) | |
| 추가 규격 | CREDIT_COST.extraCrop = 10 | 보류 | |
| 충전 상품 | CHARGE_OPTIONS [...] | 70c/140c/280c + 보너스 | 변경 필요 |
```

- `buyCreditsKR()` 호출 시 amount→credits 매핑이 v2.1과 일치하는지
- 포탈 `TOSS_AMOUNT_TO_CREDITS` 매핑과 동기화 여부

### 3-D. 충전 상품 동기화 (idphoto-kr ↔ portal)

**가장 위험한 충돌 지점**. 양쪽의 상품 매핑이 일치해야 결제가 정상 동작한다:

```
| 상품 | idphoto-kr charge.js | portal config.js | 일치 여부 |
|------|---------------------|------------------|----------|
| 단품 | amount:9900 credits:80 | TOSS_AMOUNT_TO_CREDITS[9900] = ? | ? |
| 패키지2 | amount:18900 credits:160 | ... | ? |
| 패키지4 | amount:34900 credits:340 | ... | ? |
| 소액 | amount:1450 credits:10 | ... | ? |
```

- 현재 portal config.js의 매핑을 정확히 읽고 v2.1과 대조
- **보너스 크레딧(+10c, +20c, +60c)은 어디서 지급되는가?** portal 측 payments.js에서 처리하는지, 아니면 idphoto-kr 프론트에서 표시만 하는지

### 3-E. PG 결제 흐름 영향

현재 토스페이먼츠 결제 플로우:
1. `buyCreditsKR(amount, credits)` → 토스 결제창 → 리다이렉트
2. `initFromTossResult()` → `/api/payments/toss/confirm` → 크레딧 적립

v5에서 충전 화면이 풀페이지로 바뀌면:
- 토스 리다이렉트 후 돌아올 페이지가 바뀌는가?
- `pending action` 저장/복원 로직에 영향이 있는가?
- 비로그인 `buyDirect()` 플로우는 어떻게 되는가?

### 3-F. API 엔드포인트 영향

v5 설계에서 필요한 새 API 또는 기존 API 변경사항:

```
| 엔드포인트 | 현재 용도 | v5 변경 필요 | 상세 |
|-----------|----------|-------------|------|
| /api/credit/use | 10c 차감 (생성 시) | 차감 시점 변경? | CONFIRM에서 차감 vs 생성 시 차감 |
| /api/idgen | AI 생성 | 프롬프트 구조 변경 | 3p 스타일 선택 → 프롬프트 빌딩 |
| /api/precheck | 사전분석 | 영향 확인 | |
```

**특히**: v5 기획안 섹션 3-3에서 "프롬프트 스택"이 정의되어 있다. 현재 AI 생성 API에 이 프롬프트 구조를 어떻게 전달하는지 확인.

### 3-G. 로그인 게이트 변경

v5에서 로그인 시점:
- 1p 진입 전 또는 촬영실 진입 시 소셜 원탭 로그인
- 로그인 성공 시 10c 셀레브레이션

현재 gate.js의 `showLoginRequired()` + `_startGoogleLoginSimple()` 등이 v5 플로우에 호환되는지:
- 로그인 후 리다이렉트 경로
- 10c 가입보너스 지급 시점 (portal events.js? 프론트?)
- 비로그인 `buyDirect()` 경로가 v5에서도 유지되는가?

### 3-H. 프롬프트 빌딩 로직

v5 기획안 섹션 3-3의 프롬프트 스택:
```
[1p] 규격 → [2p] 성별·연령 → [3p] 의상+헤어+배경 → [고정 프롬프트]
```

현재 앱에서 AI 생성 시 프롬프트를 어떻게 구성하는지 확인:
- prep.js selections → sessionStorage → camera.js/result.js → /api/idgen
- 이 체인에서 v5 상태 변수(format, suitColor, shirtColor 등)를 어떻게 매핑할지
