## 임무

### 1. 프로토 v4 정밀분석

JSX 코드를 **줄 단위로** 분석하여 다음을 보고:

- **기능 목록**: 구현된 기능 전수 (UI 구성요소, 인터랙션, 계산 로직)
- **상태 관리**: React state 목록 + 각각의 역할
- **핵심 알고리즘**: 스플라인 타원 path 생성, 수치 계산(faceMm, eyeRatio 등), 드래그 로직
- **하드코딩된 값**: SPECS, SAMPLE_POINTS, 색상 상수 등 — 서비스 전환 시 외부 설정화 필요 여부
- **FaceMesh 연동 포인트**: SAMPLE_POINTS가 실제 FaceMesh로 대체되는 지점
- **다운로드/동의 플로우**: 모달 구조, 동의 항목, 산출물 종류

### 2. vanilla JS 전환 실행 방안

React → vanilla HTML + JS 전환 시:

- **파일 구조 제안**: crop.html + crop.js (+ crop.css?) 분리 방안
- **React 의존성 제거 방법**: useState → 변수/DOM, useCallback/useEffect → 이벤트 리스너, JSX → DOM 조작
- **SVG 오버레이**: React JSX 내 SVG → 직접 SVG DOM 조작 방법
- **Pointer 이벤트**: 드래그 시스템 vanilla 전환 방법
- **모달**: React state 기반 → CSS class toggle 또는 dialog element
- **예상 코드량**: 전환 후 대략적 규모
- **배치 경로**: 기존 앱 구조 고려 시 어디에 배치할지 (idphoto-kr/public? 별도?)

### 3. crop-engine과의 연동 분석

- 프로토 v4에서 crop-engine API를 호출하는 부분이 있는지
- 프론트(좌표 결정) → 백엔드(최종 크롭 연산) 분리가 어떻게 이루어져야 하는지
- FaceMesh를 브라우저에서 실행(프론트)할지 서버(crop-engine)에서 실행할지 — 각 방식의 장단점

### 4. 문제점·리스크

- 프로토에서 미구현된 기능 (세션 로그 대조)
- vanilla 전환 시 예상되는 기술적 난점
- FaceMesh WASM/WebGL 브라우저 호환성 이슈
- 모바일 터치 이벤트 대응 여부
- 성능 우려 (SVG 실시간 업데이트 + 드래그)
