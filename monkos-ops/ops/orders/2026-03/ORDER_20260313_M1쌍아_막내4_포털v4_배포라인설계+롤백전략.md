## 조사 범위

### 1. 현재 배포라인 전수 파악

포털 (`monkos_AI/portal/`) 배포 체계:

- `deploy.sh` 내용 전수 분석
  - 빌드 단계 유무
  - 환경변수 주입 방식
  - Cloud Run 배포 명령 옵션 (`--to-latest` 포함 여부)
  - dev/prod 분기 방식
- 현재 리비전 이력 (Cloud Run 콘솔 기준은 못 보니 deploy.sh + git log에서 추정)
- dev 환경: `monkos-portal-dev` — 어떤 URL로 접근?
- prod 환경: `monkos-portal` — monkos.ai

### 2. v4 전환 배포 전략 설계

대규모 UI 변경의 안전한 배포 방법을 **비교 분석**:

| 전략 | 설명 | 장단점 |
|------|------|--------|
| A) Big Bang | v4 코드를 한 번에 배포 | 빠르지만 위험 |
| B) 블루/그린 | 새 리비전 배포 → 트래픽 0% → 검증 → 100% 전환 | Cloud Run 지원? |
| C) 카나리 | 10% → 50% → 100% 점진 전환 | Cloud Run 트래픽 분할 |
| D) Feature Flag | 쿠키/쿼리로 v3/v4 분기 | 코드 복잡도 ↑ |
| E) 별도 서비스 | monkos-portal-v4를 새 Cloud Run으로 | 완전 격리, URL 전환 필요 |

각 전략의 **Cloud Run에서의 구현 방법** 구체적으로 조사.
특히 Cloud Run의 트래픽 분할 (`--tag`, `--to-tags`, 리비전별 트래픽 %) 활용법.

### 3. 롤백 전략

v4 배포 후 문제 발생 시 즉시 v3로 복귀하는 방법:

- Cloud Run 리비전 기반 롤백 (`gcloud run services update-traffic`)
- 롤백 시 DB 마이그레이션 이슈 (Firestore 스키마가 바뀌었다면?)
- 롤백 자동화 스크립트 필요 여부
- 롤백 판단 기준 (어떤 메트릭으로?)

### 4. 3서비스 동시 배포 영향

포털 v4 배포 시 다른 서비스에 영향이 있는지:

- `idphoto-kr.monkos.ai` — 포털 변경과 무관한지 확인
- `idphoto-jp.monkos.ai` — 동일
- `crop.monkos.ai` — v4에서 통합 예정이지만 당장은 독립 유지?

서비스 간 API 호출 관계가 있다면 포털만 v4로 바꿔도 안전한지.

### 5. deploy.sh 미결 이슈 점검

M1 세션 미결 건:
- `--to-latest` 미적용 문제 — 매 배포 시 트래픽 고착 위험
- `ADMIN_UIDS` 쉼마 충돌 → `^::^` 구분자 전환 (커밋 `13e42b9`에서 해결)

deploy.sh의 현재 상태를 읽고:
- `--to-latest` 플래그가 dev/prod 양쪽에 적용되어 있는지
- 환경변수 누락 여부 (LINE 관련 등 최근 추가분)
- v4 배포를 위해 deploy.sh에 추가해야 할 것

### 6. 스테이징 환경 설계

v4 같은 대규모 변경은 dev → staging → prod 3단계가 이상적.

현재 dev 환경의 실질적 역할:
- dev와 prod의 환경변수 차이
- dev에서 테스트 가능한 범위 (Firestore는 같은 DB?)
- staging 환경 신설이 필요한지, dev를 staging처럼 쓸 수 있는지
