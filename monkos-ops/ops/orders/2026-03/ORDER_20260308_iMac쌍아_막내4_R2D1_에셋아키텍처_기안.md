# 지시서: R2 + D1 기반 이미지 에셋 관리 아키텍처 기안

**[2026-03-08 12:11 KST] iMac/쌍아 → 막내4**

## 배경

현재 이미지 에셋 서빙이 GCS(monk-ai-images/ads/) 직접 URL + manifest.json 방식이다.
앞으로 모델, 배경, 템플릿, 광고 등 에셋이 대량 축적될 예정이므로
**R2(오브젝트 스토리지) + D1(메타데이터 테이블)** 기반 통합 관리 체계를 설계한다.

### 기존 인프라 현황 (반드시 읽고 시작할 것)

#### R2 — 이미 사용 중
- 버킷: `monk-apps` (binding: `IMAGES_BUCKET`)
- 용도: monk_imagen4 (T2I 생성 이미지 저장)
- 설정: `apps/monk_imagen4/wrangler.toml`

#### D1 — 이미 사용 중
- DB: `monk-db` (id: `6fe2a64b-9144-436c-94f7-1e9375249a1e`)
- DB: `monk-services-db` (id: `1c88fa57...`)
- 용도: 포털 메타데이터, 서비스맵
- ⚠️ 결제/거래원장은 Firestore로 이관 결정됨 (2026-03-01 P0)

#### GCS — 현재 프로덕션
- `monk-ai-images/ads/` (14MB): 프로덕션 광고 로테이션 (manifest.json 기반)
- `monk-ai-images/generated/` (187MB): AI 생성 이미지
- `monk-project/assets/` (2.93GB): 크롤링 원본, 모델 에셋
- 🔴 monk-ai-images 버킷 전체 공개 (allUsers:objectViewer) — 보안 이슈
- ⚠️ monk-ai-images 리전: us-central1 (한국 대상인데 미국) — TTFB 150-200ms 페널티

#### 오늘 수립된 보고서 (필수 참조)
1. `docs/infrastructure/reports/REPORT_20260308_GCS_AUDIT_HOSTING_STRATEGY.md` — GCS 전수 감사 + 호스팅 방안 비교
2. `docs/infrastructure/reports/REPORT_20260308_IMAGE_SCHEMA_OPTIMIZATION.md` — 이미지 스키마 6카테고리 + 최적화 방안
3. `docs/infrastructure/reports/REPORT_20260308_PROJECT_SPLIT_IMAGE_MANAGEMENT.md` — 프로젝트 분기 시 이미지 관리

#### R2 제한 사항
- 무료 티어: 10GB 스토리지 (계정 합산), 100만 Class A/월, 1,000만 Class B/월
- 버킷 수: 계정당 1,000개까지
- **Egress 무료** (GCS 대비 최대 장점)
- 스토리지: $0.015/GB·월 (GCS $0.020 대비 25% 저렴)

## Phase A: 기존 R2/D1/GCS 전수 파악

### 조사 항목

1. **R2 현황 실사**
   - `monk-apps` 버킷 실제 사용량 확인 (wrangler 또는 CF 대시보드 API)
   - R2에 저장된 파일 목록, 포맷, 크기
   - monk_imagen4에서 R2를 어떻게 쓰고 있는지 코드 추적 (쓰기/읽기 패턴)

2. **D1 현황 실사**
   - `monk-db` 테이블 스키마 전수 파악 (CREATE TABLE 문 추출)
   - `monk-services-db` 테이블 스키마
   - 기존 테이블 중 이미지 에셋 관리에 재사용 가능한 구조가 있는지

3. **GCS → R2 이관 대상 판별**
   - 현재 GCS에서 **자주 서빙되는** 에셋 (ads/, generated/) → R2 이관 후보
   - 콜드 데이터 (raw_data/, corpus/) → GCS 아카이브 유지
   - 각 경로별 이관 가능 여부 + 영향 범위

## Phase B: R2 버킷 설계

작가님 요구: "모델, 배경, 템플릿 등을 에셋으로 남길 때 테이블이 명확해야 한다"

### 버킷 분리안 설계

버킷을 용도별로 분리하되, 10GB 합산 무료 범위를 고려:

```
(예시 구조 — 확정이 아닌 설계안으로 제출할 것)

r2://monkos-ads/           ← 광고 로테이션 (현 GCS ads/ 이관)
r2://monkos-gallery/       ← 쇼케이스/갤러리
r2://monkos-models/        ← AI 모델 포트폴리오/룩북
r2://monkos-backgrounds/   ← 배경 템플릿
r2://monkos-generated/     ← AI 생성 이미지 (현 monk-apps 통합?)
```

### 각 버킷별 정의 항목
- 버킷명
- 용도 및 대상 에셋
- 예상 용량 + 증가 추이
- 공개/비공개 정책
- FIFO/TTL 정책 (광고는 6장 FIFO 등)
- Workers 바인딩 필요 여부
- 기존 인프라와의 관계 (monk-apps, monk-ai-images 등)

### 10GB 예산 배분

현재 monk-apps 사용량 + 신규 버킷 예상 용량을 합산하여
무료 티어 내 운용 가능한지, 초과 시 비용 추정

## Phase C: D1 메타데이터 테이블 설계

manifest.json 방식의 한계를 넘어, **D1 테이블로 에셋 메타데이터를 체계적으로 관리**:

### 설계 대상 테이블 (최소)

1. **`assets`** — 에셋 마스터 테이블
   - id, bucket, key(R2 객체 키), category, subcategory
   - filename, format, size_kb, width, height
   - alt_text, tags, uploaded_at, updated_at
   - is_public, is_active

2. **`asset_categories`** — 카테고리 정의
   - id, code, name, bucket_name, policy_json
   - 기존 6카테고리: brand, gallery, ad, model, bg, user

3. **`asset_placements`** — 에셋이 어디에 배치되는지
   - asset_id, page, section, display_order
   - (예: asset_id=3, page='idphoto-kr/index', section='showcase', order=1)

4. **`ad_rotation`** — 광고 로테이션 설정 (현 manifest.json 대체)
   - asset_id, rotate_ms, transition_ms, start_date, end_date, priority

### 기존 D1과의 관계
- 신규 DB 생성 vs 기존 `monk-db` 확장 — 장단점 분석
- monk-db에 이미 있는 테이블과 충돌/중복 여부

### Workers API 엔드포인트 설계
- `GET /api/assets?category=ad` → 광고 이미지 목록 (manifest.json 대체)
- `GET /api/assets?category=gallery&page=index` → 페이지별 갤러리
- `POST /api/assets/upload` → R2 업로드 + D1 메타데이터 등록

## Phase D: 마이그레이션 경로

### GCS → R2 마이그레이션 계획
- ads/ 14MB → R2 이관 절차 (URL 변경 영향 분석)
- generated/ 187MB → R2 이관 or GCS 유지 판단
- manifest.json → D1 테이블 전환 절차 (하위 호환 기간)

### 프론트엔드 영향 분석
- result.js의 `AD_MANIFEST_URL` → Workers API 전환 시 변경 범위
- photolab/index.html, idphoto-kr/index.html의 GCS 하드코딩 URL → 변경 범위
- 하위 호환: 전환 기간 동안 GCS + R2 병행 가능한지

### ads_upload.sh / ads_sync.py 전환
- GCS 업로드 → R2 업로드로 변경
- manifest.json 갱신 → D1 INSERT로 변경
- 기존 FIFO 6장 로직 유지 방안

## ⚠️ 준수 조항

- **헌법 제10조 (프록시 금지)**: R2는 CF 네이티브 스토리지이므로 프록시 아님. 단, GCS↔R2 동기화 프록시는 금지
- **헌법 제6조 (인프라 보호)**: D1 database_id, API 키 등 생성/추측 금지. 기존 값만 참조
- **헌법 제8조 (파괴적 명령 금지)**: GCS 삭제는 마이그레이션 완료 확인 후에만. 보고서에서는 제안만
