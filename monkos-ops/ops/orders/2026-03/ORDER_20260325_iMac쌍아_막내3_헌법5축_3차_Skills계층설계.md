## 배경

2차 분석에서 5축 구조 정합성은 확정됐다. 이번 3차는 **작가님과 쌍아 간 논의에서 도출된 새로운 설계 방향**을 검증한다.

**작가님 핵심 통찰:**
> "헌법에 담자니 맥락이 길고, 안 담자니 운용이 마비되는 곳 — 그게 Skills다."
> "법률에서 맵트리, 목록, 절차 같은 참조형은 법률에 두고, 기능적 명령체계는 Skills에 분기하면 된다."
> "우리 안의 명령체계를 Skills로 매칭하면 되겠군 — 태그처럼 키워드 매칭으로."

이로부터 도출된 설계 방향: **현행 3계층(헌법/법률/규정)을 4계층(헌법/법률/명령/규정)으로 확장하고, "명령" 계층을 `.claude/skills/`로 구현한다.**

## 분석 항목

### A. 법률의 참조형/실행형 분류 — 전수 조사

현행 법률 ch1~ch8의 **모든 조항**을 읽고, 각 조항이 아래 둘 중 어디에 해당하는지 분류하라:

| 유형 | 정의 | 배치 후보 |
|------|------|----------|
| **참조형** — "이것은 이렇다" | 맵트리, 목록, 정의표, 폴더 구조, 파일명 패턴, 역할 정의 | `.claude/rules/` (경로 매칭 시 자동 로딩) |
| **실행형** — "이렇게 해라" (절차) | 세션 시작/마감 절차, 지시서 발행 순서, 완료 보고 형식, 삼권심사 프로세스, 배포 절차 | `.claude/skills/` (키워드 트리거 시 온디맨드 로딩) |

**산출물 형식:**

```
| 법률 | 조 | 제목 | 유형 | 분류 근거 | Skills명 (실행형인 경우) |
```

### B. Skills 설계안 — 구체 스펙

분류 결과에서 실행형으로 판별된 항목들을 Skills로 설계하라:

각 Skill에 대해:
1. **파일명**: `.claude/skills/{스킬명}.md` 형태
2. **트리거 키워드**: 작가님이 자연어로 말할 때 매칭될 키워드 목록
3. **내용 요약**: 해당 Skill에 담길 절차/지시 (현행 법률/MEMORY.md에서 이동할 원문 참조)
4. **토큰 절감 추정**: 현재 상시 로딩 vs Skills 전환 시 절감량

### C. 4계층 문서 위계 — 제5조(메타) 보정안

현행 5축 청구안의 제5조(메타) 1항 문서 위계 테이블을 4계층으로 확장하는 보정안 제시:

현행 (3계층):
```
| 헌법 (5조) | 불변 원칙 | 만장일치 |
| 법률 (8장) | 운용 규칙 | 쌍아+작가님 |
| 규정 (MEMORY 등) | 기술 상세 | 에이전트 자율 |
```

제안 (4계층):
```
| 헌법 | 왜 (원칙) | CLAUDE.md | 만장일치 |
| 법률 | 무엇 (정의·목록) | .claude/rules/ | 쌍아+작가님 |
| 명령 | 어떻게 (실행 절차) | .claude/skills/ | 쌍아+작가님 |
| 규정 | 디바이스 상세 | MEMORY.md | 에이전트 자율 |
```

이 확장이:
1. Anthropic 컨텍스트 설계와 정합하는지
2. 기존 5축 구조에 충돌 없이 삽입 가능한지
3. 실무적으로 어떤 이점이 있는지 (토큰 절감, 운용 효율)
4. 위험/단점은 무엇인지

### D. MEMORY.md에서 Skills로 이관할 항목

현재 MEMORY.md 139행 중 실행형 절차에 해당하는 항목을 식별하고, Skills 이관 시:
1. MEMORY.md 예상 행수 변화
2. 이관해도 안전한 항목 vs MEMORY.md에 잔류해야 하는 항목
3. 멀티디바이스 영향 (Skills는 Git 공유, MEMORY.md는 로컬)

### E. 구현 로드맵

위 분석을 종합하여, 실행 순서 제안:
- Phase 1: 5축 개헌 발효 (현행 청구안 기반)
- Phase 2: Skills 구현 + 법률 분리 (참조형→rules, 실행형→skills)
- Phase 3: MEMORY.md 경량화

각 Phase의 선행 조건, 리스크, 예상 효과를 명시.
