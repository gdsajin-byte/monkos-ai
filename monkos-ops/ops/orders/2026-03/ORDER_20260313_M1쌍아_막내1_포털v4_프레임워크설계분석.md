## 조사 범위

### 1. 현재 index.html 구조 전수 파악

- 현재 HTML 구조 (섹션별 ID/클래스 맵)
- 인라인 JS 함수 목록 + 각각이 하는 일 (Auth, 챗봇, 크레딧, 라우팅 등)
- CSS 변수 체계 (`:root` 전체)
- 외부 의존성 (CDN, SDK 로딩 목록)
- server.js에서 index.html을 서빙하는 방식 (정적? SSR 주입?)

### 2. v4 프로토 구조 분석

- 3컬럼 grid 구조 (`grid-template-columns: 200px 1fr 180px`)
- CSS 변수 체계 (프로토의 `:root`)
- 반응형 브레이크포인트 (현재 프로토에 없음 — 필요 사항 도출)
- 프로토에 있는 JS 기능 (갤러리 자동스크롤, 챗봇 모달)

### 3. 전환 전략 도출

현재 → v4 전환 시 가능한 접근법을 **비교 분석**:

| 방식 | 설명 | 장단점 |
|------|------|--------|
| A) index.html 전면 교체 | 프로토 기반 새 파일 작성 | 깔끔하지만 기존 기능 누락 위험 |
| B) 점진적 마이그레이션 | 현재 파일에 3컬럼 + 테마 적용 | 안전하지만 혼합 기간 복잡 |
| C) 레이아웃 셸 분리 | 레이아웃(3컬럼)+내용물(컴포넌트) 분리 | 구조적이지만 공수 큼 |

각 방식의 **예상 영향 범위** (수정 파일 수, 위험도) 포함.

### 4. SPA 라우팅 설계

v4 문서 §3에서 "좌우 사이드바는 전 페이지 공통, 메인 영역만 교체"라고 명시.

- 현재 라우팅 방식: server.js에서 각 경로를 SSR로 렌더링 (`renderBlogList`, `renderBlogPost` 등)
- v4 방식: 클라이언트 사이드에서 메인 영역만 교체
- **핵심 질문**: 현재 SSR 렌더링과 SPA 라우팅을 어떻게 공존시킬 것인가?
  - SSR 유지 + hydration?
  - SSR은 SEO용 fallback, 실제 네비게이션은 fetch + innerHTML?
  - 각 접근법의 SEO 영향

### 5. 모바일 반응형 설계

v4 문서에서:
- 좌 사이드 → 햄버거 메뉴
- 우 사이드 → 메인 하단 또는 숨김
- 챗봇 바 → 하단 고정 (키보드 겹침 테스트 필요)

현재 모바일 CSS를 분석하고, 3컬럼→1컬럼 전환에 필요한 미디어쿼리 설계안 제시.
