## 3. 분석 및 설계 항목

### 3-A. 현행→v5 키 매핑 테이블

현행 9스텝 퍼널의 키와 v5 키를 1:1 또는 1:N으로 매핑하라:

```
| 현행 키 | 현행 값 예시 | v5 키 | v5 값 예시 | 매핑 유형 | 변환 로직 |
|---------|-------------|-------|-----------|----------|----------|
| style | "id_photo" | format | "passport" | 1:1 리매핑 | "id_photo"→"passport", "resume"→"id" |
| purpose | "passport" | (삭제) | — | 흡수 | format이 대체 |
| gender | "male" | gender | "m" | 값 축약 | "male"→"m", "female"→"f" |
| age | ? | age | "adult" | 값 변경 | 현행 3값→v5 4값 |
| clothing | ? | clothing | "suit" | 확장 | 현행→v5 옵션 확대 |
| expression | ? | (삭제) | — | 삭제 | v5에서 제거 |
| ... | ... | ... | ... | ... | ... |
```

**전수 조사**: prep.js의 DEFAULTS 객체에 정의된 모든 키를 빠짐없이 매핑. v5에서 삭제되는 키도 명시.

### 3-B. 레거시 키 정리 계획

막내3 보고서에서 확정된 레거시 잔재:
- `monkos_user` (auth.js 4곳) — 쿠키 전환 후 잔재
- `monkos_cropped` (유령 키)

이 정리를 v5 전환과 **동시에 처리할지, 선행으로 별도 처리할지** 방안 제시.

### 3-C. 전환 전략 옵션 비교

3가지 전환 전략을 비교 분석하라:

**옵션 A: 빅뱅 전환**
- v5 배포 시 구키 전부 삭제, 신키로 시작
- 장단점 분석

**옵션 B: 점진적 전환 (어댑터 레이어)**
- 구키 읽기 시 v5 형식으로 변환하는 어댑터 함수
- 구키→신키 마이그레이션 함수를 세션 시작 시 실행
- 장단점 분석

**옵션 C: 버전 태그**
- `monkos_schema_version` 키 추가
- 버전에 따라 읽기 로직 분기
- 장단점 분석

각 옵션에 대해: 구현 복잡도, 위험도, 롤백 가능성, 기존 유저 영향을 평가하고 **추천안** 제시.

### 3-D. 충전 화면 라우팅 변경 설계

v5에서 충전 모달 → 풀페이지(`charge.html`) 전환:

**3-D-1. 현행 ChargeModule.show() 호출부 전수 확인**
막내1 보고서에서 11호출부로 파악. 코드에서 재확인:

```
| # | 호출 위치 (파일:함수:라인) | 호출 맥락 | v5 변경 방안 |
|---|-------------------------|----------|-------------|
```

**3-D-2. 풀페이지 라우팅 설계**

각 호출 시점에서 charge.html로 이동할 때:
- **돌아올 페이지**(return URL)를 어떻게 전달하는가
- **pending action**(예: 다운로드 대기 중)을 어떻게 보존하는가
- PG 결제 후 리다이렉트 체인: `charge.html → 토스 결제 → 리다이렉트 → ?`
- 결제 성공 후 원래 페이지로 복귀하는 흐름

**3-D-3. 비로그인 buyDirect 경로**
현행 gate.js의 buyDirect가 v5 풀페이지 충전에서 어떻게 동작할지:
- buyDirect는 유지되는가, 제거되는가
- 유지 시 charge.html에서의 처리 방안

### 3-E. 롤백 계획

v5 배포 후 치명적 문제 발견 시:
- 어떻게 v4로 되돌릴 수 있는가
- sessionStorage에 이미 v5 키가 쓰인 유저는 어떻게 처리하는가
