# 지시서: 레포 분리 — 문서·거버넌스·세션데이터 클론 방안

> **[2026-03-04 05:18 KST] M1/쌍아 → M1/막내5**

---

## 배경

monk_project 레포 분리 시, 코드뿐 아니라 **헌법 체계(CLAUDE.md + governance/) + 기술 문서(docs/) + 운영 데이터(monkos-ops/)** 의 소속과 클론 방식을 정밀 설계해야 한다.

**핵심 원칙**: 한쪽 레포에서 다른 쪽의 **존재와 맥락, 트리 구조는 인지하되**, 작업 시 **불필요한 맥락을 도입하지 않는 구조**.

---

## 조사 범위

### A. CLAUDE.md (헌법) 분리 설계

현재 CLAUDE.md는 단일 파일로 양쪽 프로젝트를 통합 관리.

**조사 항목**:
1. CLAUDE.md 내용 중 monk.kr 전용 / monkos.ai 전용 / 공통 부분 분류
2. 헌법 13조 각 조항이 어느 레포에 해당하는지 매핑
3. 법률 인덱스 8장 각 장이 어느 레포에 해당하는지 매핑
4. 디바이스 맵, 수발신 형식 등 공통 인프라의 처리

**설계 대안 비교**:

| 방안 | 설명 | 장점 | 단점 |
|------|------|------|------|
| A1: 양쪽 동일 복사 | CLAUDE.md 그대로 복사 | 간단, 누락 없음 | 한쪽 수정 시 동기화 필요 |
| A2: 공통 + 부록 | 공통 헌법 + 레포별 부록 | 깔끔 | 구조 재설계 필요 |
| A3: 한쪽 정본 + 참조 | monkos_ai에 정본, monk_kr에서 참조 | 단일 진실 | 참조 체계 필요 |

각 대안의 실현 가능성과 권장안 제시.

### B. governance/ 디렉토리 분류

```
governance/
├── constitution/     ← 헌법 개정 절차, 청원
├── laws/            ← 법률 ch1~ch8
├── special-laws/    ← 특별법
└── PERSONNEL_REGISTRY.md
```

**조사 항목 (파일별)**:
1. 어느 레포에 해당하는가 (monk.kr / monkos.ai / 공통)
2. 법률 각 장의 적용 범위:
   - ch1 에이전트 체계 → 공통?
   - ch2 코딩 규칙 → 공통?
   - ch3 세션 로그 → 공통?
   - ch4 문서/폴더 구조 → 레포별 차이?
   - ch5 배포 규칙 → 레포별 차이?
   - ch6 브랜치/커밋 → 공통?
   - ch7 막내 행동 강령 → 공통?
   - ch8 브랜딩/마케팅 → 공통?
3. 특별법이 어느 레포 작업에서 발생한 것인지

### C. docs/ 디렉토리 분류

```
docs/
├── archives/        ← 아카이브
├── corpus/          ← 코퍼스/자료
├── infrastructure/  ← 기술 인프라 문서
├── monkos/          ← monkos 관련 문서
├── rnd_2026/        ← R&D 자료
└── ...
```

**조사 항목 (하위 디렉토리별)**:
1. 소속 분류: monk.kr 전용 / monkos.ai 전용 / 공통 / 아카이브
2. 양쪽 레포에서 참조하는 문서 식별
3. 분리 후 한쪽에만 두면 다른 쪽에서 접근 불가한 문서 목록
4. 기술 문서(CODING_STANDARDS, DESIGN_SYSTEM, GCS 구조 등)의 소속

### D. monkos-ops/ 분류

```
monkos-ops/
├── ops/
│   ├── orders/      ← 지시서
│   ├── reports/     ← 보고서
│   ├── sessions/    ← 세션 로그
│   ├── config/      ← 설정
│   └── decisions/   ← 결정문
└── tech/
    └── archive/     ← 기술 아카이브
```

**조사 항목**:
1. 지시서/보고서가 어느 레포 작업을 대상으로 하는지 (파일명/내용 기반)
2. 세션 로그가 양쪽 레포 작업을 혼합 참조하는 경우 처리
3. **ops를 양쪽 레포에 복사 vs 별도 ops 레포 vs 한쪽에만 유지** 장단점 비교

**설계 대안**:

| 방안 | 설명 | 장점 | 단점 |
|------|------|------|------|
| D1: 양쪽 복사 | ops 그대로 양쪽에 | 이력 보존 | 동기화 문제 |
| D2: 별도 ops 레포 | monkos-ops를 독립 레포로 | 깔끔한 분리 | 레포 3개 관리 |
| D3: monkos_ai에 유지 | 주 프로젝트에 ops 유지 | 심플 | monk_kr에서 ops 접근 불가 |
| D4: 클론 후 분기 | 분리 시점 이후 각 레포별 ops | 자연스러운 전환 | 과거 이력 양쪽에 잔존 |

### E. 상대 레포 인지 구조 설계

**핵심 과제**: 분리 후 monkos.ai 레포에서 작업하는 에이전트가 "monk.kr이 존재하고 이런 구조다"를 알되, monk.kr 코드를 직접 읽거나 혼동하지 않는 구조.

**조사 항목**:
1. CLAUDE.md에 "상대 레포 개요" 섹션 배치 — 어떤 정보를 어디까지 기재할 것인가
2. 상대 레포 트리 구조 요약 (정적 스냅샷 vs 동적 참조)
3. 도메인 간 API 호출 관계 요약 (monk.kr → *.monkos.ai 등)
4. "이 레포의 범위는 여기까지" 경계 선언 — 에이전트 컨텍스트 오염 방지
5. `.claudeignore` 또는 유사 메커니즘으로 특정 디렉토리를 인덱싱 제외하는 방법 조사

### F. MEMORY.md 처리

MEMORY.md는 `~/.claude/projects/{프로젝트경로}/memory/`에 위치 (디바이스+프로젝트 종속).

**조사 항목**:
1. 레포 분리 시 프로젝트 경로가 바뀌면 MEMORY.md 경로도 바뀜 — 마이그레이션 방법
2. 현재 MEMORY.md 내용 중 monk.kr 전용 / monkos.ai 전용 / 공통 분류
3. 분리 후 각 레포의 MEMORY.md 초기 내용 설계
