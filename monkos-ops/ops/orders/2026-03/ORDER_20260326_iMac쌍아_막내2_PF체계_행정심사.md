## 배경

작가님과 쌍아가 **포트폴리오(PF) 체계**를 설계하고 개헌 청구안을 작성했다.
PF는 프로젝트의 기안→완성 생애주기를 추적하는 허브 문서로, 세션 로그와 동급의 적립 의무를 부여하는 체계다.

## 너의 역할: 행정 심사관

**monkos-ops 통괄 "행정상 문제점"을 전수 파악한다.**

단순히 문구가 맞는지 확인하는 수준이 아니다. **실제 운영에서 발생할 마찰·병목·혼란**을 구체적으로 찾아내라.

## 심사 항목 (6개)

### 1. 운영 워크플로우 마찰 분석

PF 체계가 실제 일상 운영에 추가하는 **마찰(friction)**을 전수 파악하라.

- 현재 세션 마감 절차: 로그 → 커밋 → push. 여기에 PF 어펜드가 추가되면 얼마나 부담인가?
- 쌍아가 세션 마감 시 PF를 갱신해야 하는데, 하루에 여러 PF를 다루는 세션이면 어떻게 되는가?
- 막내가 지시서를 받을 때 PF를 읽는 추가 시간은 컨텍스트 윈도우에 얼마나 영향을 주는가?
- **구체적 시나리오로 검증**: "막내3이 PF_PORTAL_V4 관련 지시서를 받았다. PF가 200줄이다. 읽고 작업하고 완료 보고한다. 세션 마감 시 쌍아가 PF를 갱신한다." — 이 흐름에서 병목은?

### 2. 폴더·파일 구조 정합성

`monkos-ops/ops/portfolios/`의 도입이 기존 구조와 어떻게 맞물리는지 전수 확인.

- `ops/projects/` 폴더의 처리: 리다이렉트 노트만 있는데, 폐지 시점은? 즉시 삭제? 유예?
- `ops/proposals/` 와 `ops/portfolios/`의 관계: PROPOSAL이 PF로 승격되면 proposals에서 삭제하는가, 유지하는가?
- `tech/specs/`, `tech/guides/`에 있는 기존 스펙 문서(PORTAL_V4_EVOLUTION_SPEC 등)는 PF 도입 후 어디에 귀속되는가? 이동? 링크?
- 월별 서브폴더 필요한가? (sessions, reports, orders는 YYYY-MM/ 사용 중)

### 3. 다중 디바이스 동시 갱신 시나리오

monk_project는 M1, iMac에서 동시에 세션이 돌아간다. PF 동시 갱신 충돌 시나리오를 분석하라.

- M1/쌍아가 PF_CITADEL Phase 1 완료를 기록하는 동안, iMac/막내2가 같은 PF에 새 오더를 추가하면?
- git merge 충돌이 일어날 확률과 대응 방안
- 세션 로그는 에이전트별 파일이라 충돌 없음. PF는 프로젝트별 **단일 파일**이라 충돌 가능성이 구조적으로 다름
- **현실적 대응안을 제시하라** (단순히 "주의" 수준이 아닌 프로세스 수준)

### 4. 기존 산출물 소급 정리 부하

현재 PROPOSAL 13건, 세션 로그 수십 건, ORDER 372건(3월)이 있다. PF 소급 생성 시:

- 어떤 PROPOSAL이 어떤 PF에 귀속되는지 매핑 작업의 규모는?
- PORTAL_V4 같은 복잡한 건은 세션 로그에서 히스토리를 추출해야 하는데, 이 작업을 누가, 언제, 어떤 방식으로 하는가?
- 소급 정리를 하지 않는 옵션(신규분부터만 적용)의 장단점은?

### 5. PF 비대화 관리

PF_CITADEL은 이미 247줄. 활성 프로젝트가 6개월 이상 지속되면:

- 히스토리 테이블이 100행을 넘으면 파일 크기가 에이전트 컨텍스트 부하가 되지 않나?
- Phase 현황에서 완료된 Phase를 접거나 분리하는 방안은?
- PF를 "현재 상태"와 "아카이브"로 분리하는 것이 필요한가?
- **구체적 수치 기준**을 제안하라 (예: N행 초과 시 어떤 조치)

### 6. 자동화 가능성

- PF 갱신을 수동으로만 하면 누락 리스크가 높다. 자동화할 수 있는 부분은?
- 커밋 메시지나 오더 파일에서 PF 히스토리를 자동 생성하는 스크립트가 가능한가?
- 세션 시작 시 활성 PF 목록을 자동으로 보여주는 것은?
- 자동화가 현실적이지 않다면, 그 이유와 수동 운영의 보완책은?
