## 분석 항목

### 1. 프로젝트 단위 식별

자기 담당 기간에서 **독립된 프로젝트 단위**를 식별하라. 프로젝트 단위 = "하나의 목표를 향해 여러 세션에 걸쳐 진행된 작업 묶음".

판별 기준:
- 동일 코드 영역(파일/모듈)을 반복 수정
- 동일 주제의 ORDER/REPORT가 연속 발행
- 세션 로그에서 같은 키워드가 반복
- PROPOSAL이 존재하면 그 자체가 프로젝트 단위

**단발성 작업**(긴급 패치, 인프라 점검, 거버넌스 정비 등)은 별도 분류하되, 반복 패턴이 있으면 프로젝트로 묶을 수 있는지 검토.

### 2. PF 그루핑 제안

식별된 프로젝트 단위를 **PF 코드네임**으로 그루핑하라. 제안 형식:

```markdown
| PF 코드네임 | 주제 | 포함 작업 | 시작일 | 현재 상태 | 관련 PROPOSAL |
|------------|------|----------|--------|----------|-------------|
```

그루핑 원칙:
- 너무 잘게 쪼개지 마라 — PF 1건 = "포트폴리오로 내보일 수 있는 완성 단위"
- 너무 크게 묶지도 마라 — "monk_project 전체"가 PF 1건이면 의미 없음
- 시간적으로 떨어져 있어도 같은 목표면 같은 PF (예: 결제 시스템 1차 구현 + 3주 후 리팩토링 = 같은 PF)

### 3. CITADEL 모델 적합성 검증

PF_CITADEL의 7섹션 구조:
```
1. 비전 (왜 하는가 + 성공 지표)
2. 히스토리 (append-only 이벤트 테이블)
3. Phase 현황 (에이전트 진입점)
4. 성과 (실측 데이터)
5. 복기 (교훈)
6. 관련 문서 인덱스
7. 리스크
```

각 PF 후보에 대해:
- 이 7섹션이 **전부 적용 가능한가?**
- **불필요한 섹션**이 있는가? (예: 성과 측정이 불가능한 인프라 프로젝트)
- **추가 필요한 섹션**이 있는가? (예: 외부 의존성, 예산, 일정 등)
- CITADEL은 SEO 프로젝트 — **코딩 프로젝트**(Portal v4), **사업 프로젝트**(특허), **콘텐츠 프로젝트**(SPREAD)에도 같은 구조가 맞는가?

### 4. 분류 체계 필요성 판단

PF가 10개 이상이면 분류가 필요할 수 있다:

- **대분류** (예: 서비스/인프라/콘텐츠/사업) 가 필요한가?
- **소분류** (예: 서비스>포털/서비스>스튜디오) 가 필요한가?
- 분류 없이 flat 목록으로 충분한가?
- 분류가 필요하다면 어떤 기준이 최적인가? (도메인별? 서비스별? 시간별?)

### 5. 단발성 작업 처리 방안

PF에 귀속되지 않는 단발성 작업의 패턴을 분석하라:
- 어떤 유형의 작업이 무귀속인가?
- 무귀속 작업의 비율은 전체의 몇 %인가?
- 이것들을 묶을 수 있는 "기타 PF"가 필요한가, 아니면 무귀속으로 두는 것이 맞는가?
