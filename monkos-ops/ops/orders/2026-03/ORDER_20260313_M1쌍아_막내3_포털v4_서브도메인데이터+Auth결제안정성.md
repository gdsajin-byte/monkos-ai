## 조사 범위

### 1. 서브도메인 간 데이터 공유 현황

현재 서비스 구조:
```
monkos.ai (portal) — Cloud Run
idphoto-kr.monkos.ai — Cloud Run
idphoto-jp.monkos.ai — Cloud Run
crop.monkos.ai — Cloud Run (또는 별도?)
```

각 서비스 간 **데이터 공유 지점**을 전수 파악:

| 항목 | 공유 방식 | 관련 코드 위치 |
|------|----------|---------------|
| Firebase Auth 세션 | 쿠키? 토큰? | 확인 필요 |
| 크레딧 잔고 | Firestore 직접? API 콜? | 확인 필요 |
| 사용자 프로필 | Firestore `users` 컬렉션 | 확인 필요 |
| CORS 허용 목록 | server.js `ALLOWED_ORIGINS` | 확인 필요 |

### 2. 크롭앱 통합 영향 분석 (§13)

v4에서 `crop.monkos.ai` → `monkos.ai/crop`으로 전환.

- 크롭앱 현재 코드 위치 확인 (별도 레포? 같은 모노레포?)
- 크롭앱이 사용하는 외부 의존성 (FaceMesh, MediaPipe 등)
- 크롭앱의 현재 배포 방식 (Cloud Run? CF Pages? Workers?)
- 포털 내부 라우트로 옮길 때:
  - iframe 임베딩인지 코드 통합인지
  - iframe이면 CORS/쿠키 이슈
  - 코드 통합이면 번들 사이즈/충돌 이슈
- `crop.monkos.ai` → `monkos.ai/crop` 리다이렉트 설정 방법
- 기존 crop 사용자 북마크/링크 유지 전략

### 3. Auth 시스템 안정성

현재 Auth 흐름을 **전수 추적**:

```
포털 로그인 → 어떤 SDK? → 세션 저장 방식? → 서브도메인 공유?
```

조사 대상:
- `lib/auth.js` — 카카오/LINE/구글 OAuth 핸들러
- index.html 내 Firebase Auth 초기화 코드
- 쿠키 도메인 설정 (`.monkos.ai` vs `monkos.ai`)
- 포털 로그인 후 idphoto-kr/jp에서 세션 유지되는지
- v4 레이아웃 전환이 Auth 흐름에 영향을 주는 지점:
  - 로그인 팝업 트리거 위치 변경
  - 크레딧 배지 위치 변경 (user-bar)
  - 언어 스위치 제거가 Auth에 영향?

### 4. 결제 시스템 안정성

현재 결제 흐름을 **전수 추적**:

```
크레딧 충전 → 토스(KR) / LemonSqueezy(JP) → 콜백 → 크레딧 적립
```

조사 대상:
- `lib/payments.js` — 토스/LS 핸들러
- charge.html (KR) / charge.html (JP) — 결제 페이지 위치
- 결제 완료 콜백 URL 하드코딩 여부
- v4에서 `/pricing` 라우트 신설 — 기존 charge 페이지와의 관계
  - charge.html은 idphoto-kr/jp에 있는지 portal에 있는지
  - `/pricing`은 새 페이지인지 charge 리다이렉트인지
- v4 레이아웃으로 charge.html 접근 경로가 바뀌면 토스 위젯에 영향?
- 결제 시스템이 index.html의 특정 DOM 요소에 의존하는지

### 5. Firestore 스키마 정합성

v4 문서 §4에서 Firestore 스키마를 정의:
```
blog_posts/{slug} — ko/ja/en 필드, author, tags, category 등
```

현재 CMS 구현(오늘 iMac 세션)의 실제 스키마와 v4 문서 스키마를 **필드 레벨로 비교**:
- 일치하는 필드
- 누락된 필드 (v4에 있는데 현재 구현에 없는 것)
- 추가된 필드 (현재 구현에 있는데 v4에 없는 것)
- `board_posts` 스키마도 동일하게 비교
