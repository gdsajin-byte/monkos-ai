# 지시서: 챗봇·이미지 데이터 보관 정책 기술 구현 설계

**[2026-03-08 13:52 KST] iMac/쌍아 → 막내2**

## 배경

데이터 보관 정책이 2단계(L1/L2)로 확정 방향이다.
이 정책이 **챗봇 대화 데이터 + 이미지 데이터** 양쪽에 적용될 때의 기술 구현 방안을 설계한다.

| 등급 | 보관 기간 | 동의 방식 | 대상 |
|------|-----------|-----------|------|
| **L1 (기본)** | 30일 자동삭제 | 이용약관 명시 | 생성 결과물, 대화 로그 |
| **L2 (활용)** | 90일 자동삭제 | 체크박스 옵트인 | 마케팅·품질 개선용 |

## Phase A: 현행 데이터 흐름 분석

### 1. 이미지 데이터 흐름 (현재)
- 현재: 클라이언트 촬영 → base64 전송 → 엔진(Gemini/Imagen) → base64 응답 → 클라이언트 직접 수신
- **서버 저장 단계 없음** — L1 적용 시 비동기 저장 단계 추가 필요
- 관련 코드 추적: `monkos_AI/portal/lib/` 내 이미지 처리 파이프라인

### 2. 챗봇 대화 데이터 (현재)
- **chat-engine.js** (`monkos_AI/portal/lib/chat-engine.js`) 분석 필수
- 현행 Firestore 컬렉션:
  - `chat_conversations` — 웹 챗봇 (무기한 저장)
  - `cs_conversations` — 텔레그램 CS (무기한 저장)
  - `kakao_conversations` — 카카오 챗봇 (무기한 저장)
  - `idphoto_kr_conversations` — idphoto-kr 챗봇 (무기한 저장)
  - `prep_conversations` — 촬영 안내 (무기한 저장)
  - `qc_results` — QC 결과 (무기한 저장)
- 인메모리 TTL은 있으나 (30분~1시간), **Firestore에는 삭제 정책이 없음**
- ⚠️ 이것이 L1 정책 위반 — 30일 자동삭제 구현 필요

## Phase B: L1 기본 보관 기술 설계

### 1. 이미지 비동기 저장 아키텍처

현재 엔진 → 클라이언트 직접 전송 속도를 **유지하면서** 비동기로 저장:

```
[요구 플로우]
클라이언트 → 서버 → 엔진 → 결과 생성
                              ├→ 클라이언트 즉시 응답 (속도 유지)
                              └→ 비동기: GCS/R2 임시 저장 (L1: 30일 TTL)
```

설계 항목:
- 저장소 선택: GCS (Object Lifecycle 네이티브 TTL) vs R2 (Workers 기반 TTL)
- 저장 형식: 원본 base64 → WebP 변환 후 저장? 또는 원본 유지?
- 키 구조: `{user_id}/{timestamp}_{type}.webp` 등
- 비동기 저장이 실패해도 클라이언트 응답에 영향 없는 구조 보장
- 저장 시점: 생성 완료 직후 (엔진 응답 수신 즉시)

### 2. Firestore 대화 로그 TTL 구현

현재 Firestore에 TTL 필드가 없음. 구현 방안 비교:

| 방안 | 장점 | 단점 |
|------|------|------|
| **Firestore TTL 정책** (네이티브) | 코드 수정 최소, 자동 삭제 | TTL 필드 추가 필요, 24시간 지연 가능 |
| **Cloud Scheduler + Cloud Functions** | 정밀 제어 가능 | 추가 인프라 |
| **서버 시작 시 배치 삭제** | 간단 | Cloud Run cold start에 의존 |

- Firestore 네이티브 TTL이 가장 적합할 것으로 예상되나, **장단점 비교 후 추천**
- 각 컬렉션별 TTL 적용 범위: L1=30일, L2=90일
- 기존 무기한 데이터 처리 방안 (일괄 TTL 부여? 일괄 삭제?)

### 3. 재다운로드 API 설계

L1 보관 데이터의 재다운로드 경로:
- `GET /api/download/{session_id}` — 30일 내 재다운로드
- 인증: OAuth 세션 기반 (본인 확인)
- 만료 시 응답: "보관 기간이 만료되었습니다"

## Phase C: L2 활용 동의 기술 설계

### 1. 동의 수집 및 저장

- 동의 체크박스 → Firestore `user_consents` 컬렉션에 기록
- 스키마:
  ```
  {
    userId: string,
    consentType: 'L2_marketing',
    consentedAt: timestamp,
    expiresAt: timestamp (90일),
    channel: 'web' | 'kakao' | 'idphoto-kr',
    version: '1.0'  // 약관 버전
  }
  ```
- 동의 철회 API: `DELETE /api/consent/{userId}` → 해당 L2 데이터 즉시 삭제

### 2. L2 데이터 격리

- L1 데이터와 L2 데이터 **물리적 분리** vs **논리적 분리** (태그) — 장단점 비교
- L2 데이터에 비식별 처리 적용 방안 (얼굴 블러? 메타데이터만 추출?)
- 마케팅 소재 추출 파이프라인 (승인된 데이터만 → 비식별 → 소재화)

### 3. 챗봇 대화 L2 코퍼스화

- 동의 있는 대화만 → 비식별 → RAG 코퍼스에 편입
- 현행 `monkos_AI/portal/lib/rag.js` 구조와 연동 방안
- 코퍼스 갱신 주기 및 자동화

## Phase D: 워터마크·해상도 차등 설계 (선택)

작가님이 언급한 비즈니스 모델 확장 가능성:

- 무료: 워터마크 저해상도 미리보기
- 유료(크레딧): 워터마크 없는 고해상도 다운로드
- 워터마크 적용 방식: 서버 사이드 (Sharp/Canvas) vs 클라이언트 사이드
- 현행 크레딧 시스템(생성 10 + 다운로드 70)과의 정합성

> 이 Phase는 **가능성 분석만** 수행. 구현 결정은 작가님이 별도 확정.

## Phase E: 프론트엔드 동의 UI 플로우

### 결과 화면 동의 UI
- 결과물 표시 시점에 L2 체크박스 노출
- 체크 없이 다운로드 → L1 (30일 보관, 이용약관 기반)
- 체크 후 다운로드 → L2 (90일 보관, 마케팅 활용)
- UI 와이어프레임 (텍스트 다이어그램)

### 챗봇 동의 연동
- 첫 대화 시작 시 "대화 내용은 서비스 개선에 활용될 수 있습니다" 안내 표시
- 동의 거부 시에도 L1 (30일 보관 후 삭제) 적용 — 이용약관 기반
