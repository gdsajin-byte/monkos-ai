## 심사 항목 (6개)

### 1. 목적 정합성

PF가 해결하려는 문제("에이전트마다 해석이 달라짐", "컴팩팅 후 맥락 유실")를 PF 체계가 **실제로** 해결하는가?

- 세션 로그만으로 해결 가능한 부분은 없는가?
- PF가 있어도 해결되지 않는 맹점은 무엇인가?
- "세션 로그를 더 잘 쓰면 되지 않나?"라는 반론에 어떻게 답할 것인가?

### 2. 의무 수준의 적절성

세션 로그와 **동급의 의무**(헌법 제3조 2항)를 부여하는 것이 과도한가, 적절한가?

- 세션 로그는 매 턴 어펜드. PF는 "세션 마감 시" 어펜드. 이 차이가 적절한가?
- PF 갱신을 법률(ch3) 수준의 의무로 두고, 헌법에는 원칙만 명시하는 대안은 어떤가?
- 의무 위반 시 제재 수준이 불명확한데, 이를 어떻게 규정해야 하는가?

### 3. 대안 검토

PF 외에 같은 문제를 해결할 수 있는 대안이 있는가? 있다면 PF 대비 장단점은?

- **대안 A**: 세션 로그에 "프로젝트 상태 섹션"을 추가하는 방식
- **대안 B**: CLAUDE.md에 활성 프로젝트 상태를 직접 기재하는 방식
- **대안 C**: .claude/rules/ 에 프로젝트별 룰 파일을 두는 방식
- **대안 D**: 외부 도구(Linear, Notion 등)로 관리하는 방식
- 기타 네가 생각하는 대안이 있다면 자유롭게 제시

### 4. 기존 법체계와의 정합

PF 체계가 기존 헌법·법률과 **충돌하는 지점**이 있는가?

- 헌법 제3조 4항(정본 단일 원칙)과 PF의 관계: PF 히스토리와 세션 로그가 같은 사건을 기록하면 이중화 아닌가?
- ch4 2조 3항(정본 이중화 금지)과의 관계
- PF의 "관련 문서 인덱스" 섹션과 기존 정본 테이블의 중복 가능성

### 5. 네이밍·분류 적절성

- "포트폴리오"라는 명칭이 문서 유형으로 적합한가? (이미 확정되었지만, 입법 심사로서 검토)
- `PF_` 접두사, `portfolios/` 경로의 적절성
- domain 필드의 허용값이 지금으로 충분한가?

### 6. 확장성·미래 리스크

- PF가 10개, 20개로 늘어나면 관리 부하가 세션 로그 이상이 되지 않는가?
- 위성 환경(M1, M2, M4)에서 PF를 동시에 갱신할 때 충돌 가능성은?
- PF 아카이빙 정책이 필요한가? (완료된 PF의 처리)
