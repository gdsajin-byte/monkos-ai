# 지시서: 프로젝트 분기 시 이미지 에셋 관리 방안

**[2026-03-08 11:45 KST] iMac/쌍아 → 막내3**

## 배경

현재 monk.kr(CF Pages)과 monkos.ai(Cloud Run)가 **단일 레포(monk_project)**에 공존한다.
향후 별도 레포로 분리될 가능성이 있으며, 그 때 이미지 에셋의 공유/독립 방식을 미리 설계해야 한다.

참고: 기존 분리 조사 지시서 `ORDER_20260304_M1쌍아_막내4_레포분리_배포라인분석.md` 결과를 반드시 참조할 것.

## Phase A: 현재 공유 구조 파악

### 조사 항목

1. **이미지 에셋 교차 참조 맵**
   - MONK_kr에서 monkos_AI의 이미지를 참조하는 경우 (있다면)
   - monkos_AI에서 MONK_kr의 이미지를 참조하는 경우 (있다면)
   - 양쪽이 동일한 GCS 경로(monk-ai-images/ads/)를 공유하는 부분
   - 공통 브랜딩 에셋 (favicon, icon, OG image 등) 중복 여부

2. **배포라인별 이미지 서빙 경로**
   - MONK_kr (CF Pages): 빌드 시 어떤 이미지가 포함되는가
   - monkos_AI (Cloud Run): Docker 빌드 시 어떤 이미지가 포함되는가
   - 공용 GCS: 양쪽 모두에서 참조하는 버킷 경로

3. **Git 추적 현황**
   - .gitignore에 이미지 관련 규칙이 있는지
   - 대용량 이미지가 git 히스토리에 포함되어 레포 비대화 위험이 있는지

## Phase B: 분리 시나리오 분석

### 시나리오 1: 완전 독립
- 각 레포가 자체 images/ 폴더만 보유
- 공통 에셋은 각각 복사
- 장점: 단순, 의존성 제로
- 단점: 브랜딩 일관성 관리 수동

### 시나리오 2: GCS 공용 버킷
- 공통 에셋은 GCS 버킷(monk-project/assets/shared/)에 배치
- 양쪽 모두 GCS URL로 참조
- 장점: 단일 소스, 변경 시 양쪽 자동 반영
- 단점: GCS 의존도 증가, 헌법 10조 프록시 금지와 충돌 가능성 검토

### 시나리오 3: npm/git 공유 패키지
- 공통 에셋을 별도 패키지(monkos-assets)로 분리
- 각 프로젝트가 의존성으로 설치
- 장점: 버전 관리 가능
- 단점: 이미지를 npm으로 관리하는 것이 적절한지 의문

### 시나리오 4: 혼합 (현재 패턴 진화)
- 브랜딩(favicon, icon, logo) → 각 프로젝트 자체 보유 (현행)
- 광고/갤러리 → GCS manifest 기반 (현행 유지)
- 모델/배경 → GCS assets/ (현행)
- 장점: 현행 구조 최소 변경
- 단점: 규칙이 명문화되지 않으면 다시 산발
