## 배경

현행 인증 체계가 3중 혼재 상태다:

| 수단 | 키 | 용도 | 문제 |
|------|-----|------|------|
| sessionStorage | monkos_user, monkos_token | 탭 단위 세션 | 크로스도메인 불가, 탭 간 격리 |
| localStorage | monkos_free_gen | 무료생성 방지 | 인증과 무관하나 혼재 |
| .monkos.ai 쿠키 | monkos_session (HttpOnly) | 크로스도메인 세션 | sessionStorage와 충돌 → 12cr 버그 |

2/27 iMac 세션에서 **쿠키를 유일한 인증 수단으로 통일**하는 방향이 진단되었다. 이 방향이 올바른지, 더 나은 대안은 없는지 리서치한다.

## 리서치 범위: 방향성

### 1. 현행 MONKOS 서비스 구조 파악

아래 파일을 읽고 현행 인증 흐름을 정리할 것:
- `monkos_AI/portal/lib/auth.js` — OAuth 3사 (카카오/LINE/구글) 콜백, 쿠키 설정
- `monkos_AI/portal/lib/shared/config.js` — 토큰 생성/검증 (generateAuthToken, verifyAuthToken)
- `monkos_AI/idphoto-kr/public/shared.js` — 클라이언트 인증 초기화 (initCredits 2-phase)
- `monkos_AI/idphoto-kr/public/modules/gate.js` — GateModule OAuth 팝업
- `monkos_AI/portal/public/credits.html` — ⚠️ 여전히 localStorage 사용 중

### 2. 리서치 질문

| # | 질문 |
|---|------|
| Q1 | MPA(Multi-Page App) + 크로스 서브도메인 환경에서 **HttpOnly 쿠키 단일 인증**은 업계 표준인가? 어떤 서비스들이 이 패턴을 쓰는가? |
| Q2 | 현행 토큰 형식(`base64url(userId:expires:hmac)`)을 쿠키에 그대로 태우는 게 맞는가, JWT로 전환해야 하는가? |
| Q3 | `SameSite=Lax` + `.monkos.ai` 도메인 쿠키로 idphoto-kr ↔ portal 세션 공유가 완전한가? 누락 시나리오는? |
| Q4 | 쿠키 단일화 시 **토스 결제 리다이렉트** (외부 도메인 → monkos.ai 복귀) 흐름에서 세션 유지가 보장되는가? |
| Q5 | sessionStorage/localStorage 완전 제거 vs 보조 캐시로 유지 — 어느 쪽이 더 깔끔한가? |
| Q6 | **로그아웃 엔드포인트** 신설 시 쿠키 삭제만으로 충분한가, 서버 세션 무효화도 필요한가? |

### 3. 대안 검토

아래 대안도 비교 분석할 것:

| 대안 | 설명 |
|------|------|
| A. 쿠키 단일화 (현 방향) | HttpOnly 쿠키만 사용, sessionStorage/localStorage 인증 제거 |
| B. 쿠키 + sessionStorage 이중화 | 쿠키 = 크로스도메인, sessionStorage = 탭 내 캐시 (현행 유사) |
| C. 서버 세션 (Redis/메모리) | 쿠키에 세션ID만, 서버에서 상태 관리 |

각 대안의 **장단점, 구현 복잡도, MONKOS에 적합한 이유** 비교.
