## 배경

쿠키 단일화(HttpOnly `.monkos.ai` 쿠키를 유일한 인증 수단으로 통일) 방향이 확정 단계다. 이 리서치는 **전환 과정과 전환 후에 발생할 수 있는 모든 리스크**를 사전 식별한다.

### 현행 쿠키 설정 (portal/lib/auth.js)
```
Cookie Name:    monkos_session
Domain:         .monkos.ai
Path:           /
Secure:         true
HttpOnly:       true
SameSite:       Lax
Max-Age:        2592000 (30일)
Token Format:   base64url(userId:expires:hmac-sha256)
```

### 서비스 도메인
```
monkos.ai           ← portal (Cloud Run)
idphoto-kr.monkos.ai ← 한국 증명사진 (Cloud Run)
idphoto-jp.monkos.ai ← 일본 증명사진 (Cloud Run)
```

## 리서치 범위: 리스크

### 1. 브라우저 호환성 리스크

| # | 리스크 | 조사 |
|---|--------|------|
| R1 | **3rd Party Cookie 차단**: Chrome/Safari/Firefox의 3rd party cookie 정책. `.monkos.ai` 상위 도메인 쿠키가 서브도메인 간에 "3rd party"로 취급되는 경우가 있는가? |
| R2 | **iOS Safari ITP**: Intelligent Tracking Prevention이 `.monkos.ai` 쿠키를 제한하는가? 서브도메인 간 쿠키 공유 시 ITP 영향은? |
| R3 | **인앱 브라우저**: 카카오톡/LINE/인스타그램 내장 브라우저에서 쿠키 동작. 특히 카카오톡에서 monkos.ai 링크 열 때 쿠키가 정상 설정/전송되는가? |
| R4 | **모바일 Chrome/Samsung Internet**: SameSite=Lax 쿠키의 크로스 서브도메인 동작 검증 |
| R5 | **시크릿 모드/프라이빗 브라우징**: 쿠키 유지 범위 차이 |

### 2. 토스 결제 흐름 리스크

| # | 리스크 | 조사 |
|---|--------|------|
| R6 | **토스 리다이렉트 세션 유지**: 사용자가 토스 결제 페이지로 이동 → 결제 완료 → monkos.ai로 복귀할 때 `.monkos.ai` 쿠키가 유지되는가? SameSite=Lax 환경에서 top-level navigation으로 돌아올 때 쿠키 전송 여부 |
| R7 | **현행 _mo_p 백업**: result.js가 토스 리다이렉트 전에 sessionStorage._mo_p에 풀 원본을 저장하고 복귀 후 복원한다. 쿠키 단일화와 무관하게 이 이미지 데이터 흐름은 유지해야 하는데, sessionStorage 제거 범위에서 이것을 잘못 건드릴 리스크 |

### 3. 보안 리스크

| # | 리스크 | 조사 |
|---|--------|------|
| R8 | **CSRF 공격**: HttpOnly + SameSite=Lax가 CSRF 방어에 충분한가? 쿠키가 유일한 인증이면 CSRF 토큰 추가가 필요한가? |
| R9 | **쿠키 탈취 (XSS)**: HttpOnly라 JS에서 읽을 수 없지만, 만약 XSS가 있다면 fetch(credentials: include)로 API 호출은 가능. 이 위험도는? |
| R10 | **토큰 형식 안전성**: 현행 `base64url(userId:expires:hmac)` vs JWT 표준. 현행 형식의 보안 취약점은? |
| R11 | **로그아웃 불완전**: 쿠키 삭제만으로 로그아웃이 완전한가? 서버 측 토큰 무효화(블랙리스트) 없이 탈취된 토큰으로 30일간 접근 가능한 리스크 |

### 4. 전환 과정 리스크

| # | 리스크 | 조사 |
|---|--------|------|
| R12 | **기존 로그인 유저 세션 끊김**: 전환 배포 시 sessionStorage에 세션이 있는 기존 유저가 갑자기 로그아웃되는가? 쿠키가 아직 없는 상태에서 sessionStorage 로직이 제거되면? |
| R13 | **점진 전환 vs 빅뱅 전환**: 한번에 전환 vs 단계적 전환의 리스크 비교. 병행 기간 중 충돌 가능성 |
| R14 | **롤백 계획**: 전환 후 문제 발생 시 이전 상태로 복원하는 방법. 쿠키+sessionStorage 병행으로 돌릴 수 있는가? |

### 5. 운영 리스크

| # | 리스크 | 조사 |
|---|--------|------|
| R15 | **쿠키 크기 제한**: 브라우저별 쿠키 크기 한도 (보통 4KB). 현행 토큰 크기가 한도 내인가? 향후 클레임 추가 시 넘칠 가능성은? |
| R16 | **CORS 설정**: `credentials: 'include'` 사용 시 서버 CORS 헤더에 `Access-Control-Allow-Credentials: true` + 구체적 Origin 명시 필요. 현행 CORS 설정 확인 |
| R17 | **idphoto-jp 영향**: 일본 서비스도 동일 쿠키 사용. 한국/일본 유저가 동일 쿠키로 양쪽 접근 시 충돌 가능성 |
| R18 | **CDN/캐시 간섭**: Cloud Run 앞단에 CDN이 있다면, Set-Cookie 헤더가 캐시되는 문제 |
