## 1. 배경

MONK OS는 Firestore 9개 컬렉션에 사용자/결제/텔레그램/챗봇 데이터를 저장하지만,
이 데이터를 **조회·분석·관리**할 운영 도구가 부재하다.

현 상태:
- "누가 가입했는지" 확인하려면 REST API를 직접 호출해야 함
- "누가 결제했는지" 파악할 구조 자체가 없음
- 팀원(한송이, 꾸)은 데이터 현황을 알 방법이 없음
- 법률에 운영 데이터 관련 규정 없음 (scripts/ 귀속조차 미확정)
- 테스트용 계정 리셋 시 연관 데이터(users, telegram_links 등) 일괄 처리 불가

## 3. 산출물 A: 상세 설계서 요구사항

### 3-1. 도구 형태

**CLI 스크립트** (Node.js, ESM)
- Firestore 접근: `@google-cloud/firestore` (portal과 동일 패키지) 또는 REST API + gcloud auth
- 두 방식의 **장단점 비교 후 하나를 선택**하고 근거 명시

**배치 위치 후보** (설계서에서 결정):
- `scripts/ops-db/` — 범용 스크립트 폴더 활용
- `monkos-ops/ops/tools/` — ops 부서 직속

### 3-2. 필수 기능 명세

아래 기능을 각각 **입력/출력/동작** 수준으로 설계:

#### (1) 회원 관리

| 명령 | 설명 |
|------|------|
| `users` | 전체 회원 명단 (이메일, 가입일, 크레딧, 프로바이더, 최근 로그인) |
| `user <docId 또는 email>` | 특정 회원 상세 — users + telegram_links + telegramGateCodes + 크레딧 이력 일괄 |
| `user-reset <docId 또는 email>` | 테스트용 계정 리셋 — 연관 문서 일괄 삭제 (users + telegram_links + gateCodes). **삭제 전 확인 프롬프트 필수** |

#### (2) 결제 관리

| 명령 | 설명 |
|------|------|
| `payments` | 결제 내역 전체 (payments 컬렉션 + users.lastPurchase 교차) |
| `credits <docId>` | 특정 사용자 크레딧 흐름 (충전/차감/환불 추적) |

#### (3) 통계

| 명령 | 설명 |
|------|------|
| `stats` | 종합 현황 — 총 회원 수, 프로바이더별 분포, 크레딧 총잔액, 오늘 가입자 |
| `stats daily [YYYY-MM-DD]` | 일별 가입자 수 + 결제 건수 |
| `stats monthly [YYYY-MM]` | 월별 집계 |

#### (4) 서비스 로그

| 명령 | 설명 |
|------|------|
| `logs [서비스명] [--tail N]` | Cloud Run 로그 조회 (gcloud logging read 활용) |
| `errors [서비스명] [--hours N]` | 에러 로그만 필터 |

### 3-3. 출력 포맷

**3가지 출력 모드** 지원 설계:

| 모드 | 플래그 | 용도 |
|------|--------|------|
| **터미널 테이블** | (기본) | 즉시 확인. CLI 표준 |
| **CSV** | `--csv` | 엑셀 호환, GDrive 업로드 가능 |
| **JSON** | `--json` | 프로그래밍 연동, 에이전트 파싱 |

CSV 출력 시:
- 파일 저장 경로: `monkos-ops/ops/reports/data/` (자동 생성)
- 파일명: `{명령}_{YYYYMMDD_HHMMSS}.csv`
- BOM 포함 (엑셀 한글 깨짐 방지)
- 예시: `users_20260228_115000.csv`

### 3-4. 팀원 접근성 설계

팀원별 접점:

| 팀원 | 접점 | CLI 가능 | 대안 |
|------|------|----------|------|
| 작가님 | 직접 | ✅ | — |
| 에이전트 | 직접 | ✅ | — |
| 꾸 (M2) | SSH (sshm2) | ✅ | — |
| 한송이 (M4) | 텔레그램 | ❌ | 텔레그램 봇 or GDrive |

**텔레그램 팀봇 연동 설계 포함**:
- 기존 팀봇(`telegram-team.js`)에 명령어 추가 가능한 구조
- 예: `/회원현황`, `/결제현황`, `/통계`
- 출력: 텔레그램 메시지 (간략) + CSV 파일 첨부 (상세)
- **본 지시서에서는 설계만** — 구현은 후속 지시서

**GDrive 정기 보고 구조 설계 포함**:
- 일별/주별 자동 보고서 생성 → GDrive 업로드
- 또는 수동 트리거 (CLI `--gdrive` 플래그)
- **본 지시서에서는 설계만** — 구현은 후속 지시서

### 3-5. 보안 설계

| 항목 | 요구사항 |
|------|----------|
| 인증 | CLI: gcloud ADC (기존 서비스 계정). 팀봇: 허용 chatId 화이트리스트 |
| 개인정보 | 이메일 마스킹 옵션 (`--mask`): `gds***@gmail.com` |
| 결제정보 | paymentKey 마스킹 필수 (항상) |
| 로그 | 조회 행위 자체를 기록할지 여부 검토 |
| 삭제 | user-reset 시 삭제 대상 문서 목록 출력 + y/n 확인 |

### 3-6. Firestore 컬렉션 참조

설계 시 아래 구조를 기반으로 한다:

| 컬렉션 | docId 패턴 | 핵심 필드 | 관계 |
|--------|-----------|----------|------|
| `users` | `{google_sub}` 또는 `kakao_{id}`, `line_{id}` | email, credits, provider, createdAt, lastLogin, events, telegramId | 중심 |
| `payments` | 자동생성 | type, orderId, amount, paymentKey, downloadToken, createdAt | 독립 (비로그인 전용) |
| `telegram_links` | `{chatId}` | userId, telegramId, username, type, linkedAt | users.docId 참조 |
| `telegramGateCodes` | 6byte hex | userId, type, used, usedAt | users.docId 참조 |
| `chat_conversations` | sessionId | messages[], channel, createdAt | 느슨한 연결 |
| `cs_conversations` | `tg_{chatId}` | messages[], username, status | chatId 기반 |
| `cs_knowledge` | 자동/수동 | title, content, keywords | 독립 |
| `team_reports` | 자동생성 | author, content, category, timestamp | 독립 |
| `transactions` | 별도 D1 API | userId, amount, type, provider, balanceAfter | users.docId 참조 |

**관계 다이어그램**: 설계서에 Mermaid ER 다이어그램 포함할 것.
