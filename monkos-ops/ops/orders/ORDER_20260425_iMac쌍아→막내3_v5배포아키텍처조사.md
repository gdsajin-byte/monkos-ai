# 지시서 — v5 포털 디자인 전환 최적 배포·아키텍처 조사

## 0. 배경

포털 v5(iCloud 타일 그리드)를 기존 monkos-portal 서비스 내에서 안전하게 개발·테스트·전환하는
최적 아키텍처를 설계해야 한다.

**확정된 제약:**
- Cloud Run 서비스 분리 금지 (monkos-portal 단일 유지)
- 프론트/백 분리 금지 (도메인 점프·쿠키·인증 문제)
- 기존 v4-preview 태그 방식 활용 가능

## 1. 조사 범위

### 1-1. 기존 v4-preview 구조 실측

- 현재 v4-preview 리비전의 코드 상태 (어떤 커밋 기반인지)
- preview 태그 URL로 접속 시 동작 확인 (인증·결제·CMS 정상 여부)
- 트래픽 분할 메커니즘 (Cloud Run 태그 기반 라우팅 상세)

### 1-2. v5 개발·테스트·전환 시나리오 비교

아래 3가지 시나리오를 비교 분석:

**A안 — v5-preview 태그 방식 (기존 패턴 재활용)**
- 같은 서비스, 같은 코드에 v5 변경 포함 → `--tag v5-preview --no-traffic`로 배포
- 장점: 기존 검증된 구조, 쿠키/인증 문제 없음
- 단점: 같은 코드베이스에 v4/v5 코드 공존 → 분기 로직 필요?
- 의문: preview 태그 URL에서 v5 렌더러만 선택적 적용 가능한지

**B안 — 서버 내 라우트 분기 (/v5/* 경로)**
- server.js에 `/v5/` 접두사 라우트 추가 → v5 렌더러 호출
- 같은 배포, 같은 도메인, 같은 인증
- 장점: 프로덕션에서 `/v5/`로 즉시 비교 테스트 가능
- 단점: server.js 복잡도 증가, v5 확정 후 라우트 정리 필요

**C안 — 환경변수 플래그 분기**
- `PORTAL_VERSION=v5` 환경변수로 렌더러 분기
- preview 배포에 v5 플래그 → 프로덕션은 v4 유지
- 장점: 코드 분기 최소화, 전환 시 환경변수만 변경
- 단점: 코드에 if/else 산재 가능성

**D안 — 기타 (조사 중 발견되는 더 나은 방법)**

### 1-3. 전환(cutover) 시나리오

v5 확정 후 프로덕션 전환 시:
- 트래픽 전환 절차 (점진적 vs 즉시)
- 롤백 절차 (v5 문제 시 v4로 복귀)
- SEO 영향 (URL 변경 없으면 무영향이지만 확인)
- 인증 세션 유지 여부

### 1-4. render.js 분리와의 연계

render.js를 모듈 분리한다는 전제에서, v5 타일 렌더러 모듈이
어느 시나리오에서 가장 자연스럽게 끼워지는지 평가.
