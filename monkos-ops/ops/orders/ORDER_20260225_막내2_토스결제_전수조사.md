# 지시서: 토스페이먼츠 결제 연동 E2E 전수 조사 + 보정

## 배경

프로덕션 배포 후 토스 결제 E2E 테스트 중 결제창 연동 타이밍·플로우에 대한 전수 조사가 필요하다.
쌍아 사전 조사에서 **엔드포인트 불일치** 등 치명적 이슈가 발견되었다.

## 조사 범위

idphoto-kr + portal 양쪽 전부. 아래 체크리스트를 코드 레벨에서 확인하고, 문제 발견 시 즉시 수정한다.

## 체크리스트

### 1. 엔드포인트 불일치 (Critical — 즉시 수정)

**쌍아 사전 발견**: idphoto-kr `shared.js`에서 결제 승인 API를 호출할 때:
- idphoto-kr 호출: `${API.PORTAL_URL}/api/payment/confirm`
- portal 서버 실제 구현: `/api/payments/toss/confirm`

**확인 사항**:
1. `monkos_AI/idphoto-kr/public/shared.js` — confirm 호출 엔드포인트
2. `monkos_AI/portal/server.js` — 실제 라우트 매칭
3. 불일치 시 **idphoto-kr 쪽을 portal 서버에 맞춰 수정**

### 2. 결제 플로우 8단계 검증

아래 E2E 플로우 각 단계가 실제 코드에서 연결되는지 확인:

```
[1] 사용자 트리거 → [2] SDK 초기화 → [3] requestPayment
→ [4] 토스 리다이렉트 → [5] 프론트 콜백 처리
→ [6] 서버 confirm → [7] Firestore 크레딧 적립 → [8] UI 갱신
```

**단계별 확인 포인트**:

| 단계 | 확인 | 파일 |
|------|------|------|
| [1] 트리거 | 어떤 버튼/이벤트에서 `buyCreditsKR()` 호출되는지 | shared.js, index.html |
| [2] SDK 초기화 | `TossPayments(TOSS_CLIENT_KEY)` 시점, 키 유효성 | config.js, shared.js |
| [3] requestPayment | successUrl/failUrl이 현재 도메인 기준 정확한지 | shared.js |
| [4] 리다이렉트 | 토스 결제창 → 성공/실패 URL로 복귀 가능한지 | 도메인 설정 |
| [5] 콜백 처리 | `?toss=success` 쿼리 파싱 + paymentKey/orderId/amount 추출 | shared.js |
| [6] 서버 confirm | POST 요청 → portal 서버 라우트 매칭 → 토스 API 호출 | server.js |
| [7] 크레딧 적립 | Firestore 트랜잭션 + TOSS_AMOUNT_CREDITS 매핑 정합 | server.js |
| [8] UI 갱신 | 프론트 store/localStorage 크레딧 업데이트 | shared.js |

### 3. 크레딧 패키지 매핑 정합성

idphoto-kr과 portal 서버의 금액 → 크레딧 매핑이 일치하는지 확인:

**portal 서버 TOSS_AMOUNT_CREDITS** (server.js):
```
1450 → 10, 13050 → 100, 34800 → 300, 50750 → 500
```

**portal HTML buyToss()**:
```
12900 → 10, 29900 → 30, 45900 → 50
```

**idphoto-kr**: 함수 파라미터로 전달

→ portal HTML과 서버의 매핑이 완전 불일치. **이 매핑이 어디서 최종 결정되는지 확인하고 정합 맞출 것**.

### 4. 클라이언트 키 상태

| 앱 | 위치 | 현재 상태 |
|-----|------|----------|
| idphoto-kr | config.js | 테스트키 설정됨 (`test_ck_...`) |
| portal | index.html | 비활성화 (`TOSS_ENABLED = false`) |

→ idphoto-kr 테스트키가 유효한 상태인지, 결제 테스트 가능한지 확인.

### 5. CORS / 크로스도메인

idphoto-kr (`idphoto-kr.monkos.ai`) → portal (`monkos.ai`) 로의 결제 confirm 요청이 CORS에 의해 차단되지 않는지 확인.
- 막내3이 이번에 추가한 CORS 설정이 `/api/payments/toss/confirm`에도 적용되는지

### 6. 실패 처리

- 결제 실패 시 사용자 피드백 (alert인지 toast인지)
- 서버 confirm 실패 시 이중 결제 방지 로직 유무
- 네트워크 에러 시 타임아웃/재시도 처리

### 7. 크레딧 게이트 타이밍 (Critical — 현장 이슈)

**현상**: 토스 직원 테스트 시 결제창 팝업이 아예 안 뜨고 E2E가 그냥 통과됨.

**조사 포인트**:

1. **비로그인 사용자 플로우**: 로그인 없이 촬영 → 생성 → 다운로드까지 도달 가능한가?
   - 각 단계(`/api/precheck`, `/api/idgen`, `/api/credit/use`)에서 인증 체크가 있는가
   - 프론트의 `downloadGate()`가 유일한 관문인가, 서버에서도 차단하는가

2. **크레딧 0 사용자 플로우**: 로그인은 했지만 크레딧 0일 때
   - 생성(`/api/idgen`) 시점에서 크레딧 차감하는가, 다운로드 시점에서 차감하는가
   - 차감 없이 생성이 되면 결제 없이 미리보기까지 도달 가능 → 결제 동기 약화

3. **게이트 위치 매핑**: 아래 사용자 여정에서 어디가 유료 벽인지 정확히 표시

```
촬영 준비 → AI 코칭 → 촬영 확인 → AI 생성 → 클로즈업 → 다운로드
                                      ↑              ↑
                               여기서 차감?     여기서 차감?
```

4. **서버 사이드 차단**: `/api/credit/use` 가 실패(크레딧 부족)하면 어떤 응답이 오고, 프론트가 그걸 어떻게 처리하는지

5. **테스트키 행동**: 토스 테스트키(`test_ck_...`)가 결제창을 실제로 띄우는지, 아니면 테스트 모드에서 자동 승인되어 팝업 없이 넘어가는지

→ 이 항목이 이번 조사의 **핵심**이다. 결제 SDK 내부가 완벽해도 게이트가 없으면 무의미.

### 8. orderId 형식 차이

- idphoto-kr: `MONKOS_${userId}_${time}_${random}`
- portal: `monkos_${userId}_${time}`

→ 통일 필요 여부 판단. 서버에서 orderId 파싱하는 곳이 있다면 형식 차이가 문제될 수 있음.
