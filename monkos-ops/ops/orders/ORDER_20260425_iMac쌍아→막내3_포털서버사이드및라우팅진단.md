# 지시서 — 포털 서버사이드·라우팅·CMS·배포 구조 전수 진단

## 0. 배경

철창이가 포털 메인 디자인 시안을 JSX로 만들고 있다.
이 시안을 실제 반영하려면 **서버가 어떻게 페이지를 렌더하고, 라우트가 어떻게 연결되고, CMS 데이터가 어떻게 흐르는지** 파악해야 한다.
막내3은 서버사이드·라우팅·CMS·배포 레이어를 진단한다.

## 1. 진단 범위

### 1-1. 서버 구조
- `monkos_AI/portal/server.js` 전문 읽기
- Express 미들웨어 체인 순서
- 정적 파일 서빙 설정
- 환경 변수 의존 목록 (비밀값 제외, 키 이름만)
- 에러 핸들링 패턴

### 1-2. 라우팅 맵
- 전체 라우트 목록 (GET/POST, 경로, 핸들러 위치)
- `/specs`, `/specs/:slug`, `/blog`, `/blog/:slug` 등 동적 라우트 구조
- 다국어 라우트 (`/ja/...`, `/en/...`) 처리 방식
- 404 처리 (현재 미해결 이슈: `/pricing` 404, `/guide` 404)
- 리다이렉트 규칙 (있다면)

### 1-3. CMS 렌더링 파이프라인
- `monkos_AI/portal/lib/cms/` 전체 파일 목록 + 각 파일 역할
- `render.js` 핵심 분석: SSR 렌더링 방식, fragment 구조, 템플릿 패턴
- `specs-data.json` 구조: 26국 데이터 스키마, 권역 분류, 다국어 필드
- `blog.js`, `faq.js`, `gallery.js` 등: 데이터 소스 (Firestore? 정적? D1?)
- 렌더 → HTML 변환 과정 (SSR인지 CSR인지, 하이브리드인지)

### 1-4. 배포·인프라
- `deploy.sh` 분석: 빌드 프로세스 유무, Docker 이미지 구성
- `Dockerfile` 또는 `cloudbuild.yaml` 존재 여부 + 내용
- Cloud Run 설정: 메모리, 인스턴스, 동시 요청 (describe 조회 — 비배포 명령이므로 허용)
- v3/v4 트래픽 분할 현황

### 1-5. 제약·위험 목록
- nav 항목 추가/제거 시 라우트 등록 필요 여부
- specs 페이지 앵커(`#korea` 등) 동작 여부 — `renderSpecsList`에 id 부여되어 있는지
- 새 섹션 추가 시 서버 수정 필요 여부 vs 순수 프론트 변경으로 충분한지
- CMS 렌더러와 정적 HTML의 경계 (어디까지가 SSR이고 어디부터 정적인지)
- 블로그 데이터 끊김 이슈 (`.claude/rules/portal_seo.md` #3)의 원인
