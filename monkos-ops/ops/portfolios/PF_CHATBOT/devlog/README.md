# PF_CHATBOT devlog — MONKOS 통합 AI 챗봇 연구 개발 노트

---

## Ⅰ. 서론

### 1. 연구 대상 — 무엇을 만드는가

**MONKOS 통합 AI 챗봇**: 키오스크 퍼널을 대체하는 도메인 에이전트.

단순 CS봇이 아니다. 범용 AI 비서도 아니다. **터치스크린 키오스크가 하던 일 — 서비스 안내, 규격 선택, 결제 유도, 오류 대응 — 을 자연어 대화로 대체하되, 키오스크가 못 하는 3가지를 얹는 것**이 이 챗봇의 존재 이유다.

| 축 | 키오스크 | MONKOS AI 챗봇 |
|---|---------|---------------|
| **확장성** | 메뉴 추가 = UI 재설계 | 지식 추가 = RAG 시드 1행 |
| **뉘앙스 간파** | 버튼 매칭만 ("여권사진" 버튼) | 의도 추론 ("해외취업용인데요" → 국가 질문) |
| **순간 대응력** | 시나리오 밖 = 막힘 | 시나리오 밖 = 정중히 거절 or CS 연결 |

그런데 AI에게는 키오스크에 없는 위험이 하나 있다 — **예측 불가능성**. 키오스크는 날씨 버튼이 없으면 날씨를 안 보여준다. AI는 날씨를 지어낼 수 있다(RQ10 Qwen3 실측에서 실증). **따라서 이 챗봇의 핵심 설계 원칙은 "똑똑한 키오스크" — 키오스크의 예측 가능성 + AI의 확장성·뉘앙스·대응력.**

#### 왜 Gemini 2.0 Flash가 이 설계에 최적이었는가

Gemini 2.0은 Google Search의 리서치 기능을 초기 담당했던 모델이다. **"근거 없으면 답하지 않는다"**가 학습 목적 자체에 내재되어 있다. 대부분의 LLM은 "도움이 되려는" 본능으로 설계되어 모르는 것도 그럴듯하게 만들어내지만, Gemini 2.0은 Search 출신답게 **사실 검증 DNA**를 가지고 있다.

이것이 헌법 4조 4항("되는 것만 응답")과 완벽히 맞물렸다. 그리고 우리는 그 위에 RAG로 **"알아야 할 것"**을 정확히 이식해놓았다:

```
Gemini 2.0 설계 DNA              MONKOS 아키텍처
──────────────────              ────────────────
"모르면 모른다" (Search 출신)  ←→  헌법 4조 4항 "되는 것만 응답"
사실 기반 응답                ←→  RAG 지식 이식 (가격·규격·CS·법 체계)
                                =
                          "아는 것만 정확히 답한다"
```

2.0 vs 2.5 테스트에서 2.0이 압도적이었던 이유도 여기 있다. 2.5는 더 똑똑하고 더 많이 안다 — 그러나 MONKOS 챗봇에 필요한 것은 **"더 많이 아는 것"이 아니라 "주입한 내용 안에서 정확히 답하고, 그 로직 안에서 오류가 없는 것"**이다.

이것이 오픈소스 전환의 진짜 장벽이기도 하다. 비용이 아니라 **이 설계 철학의 부재**가 문제다 (RQ10 실측 결론).

#### 2트랙 병행 연구

- **온라인 트랙 [API]**: 상용 LLM API 기반, 6채널 통합 엔진(chatWithMonkos), RAG 지식베이스
- **오프라인 트랙 [온디바이스]**: 오픈소스 경량 모델 기반, USB 포터블, 네트워크 불요

두 트랙은 **병행 연구**한다. 같은 평가 체계로 비교하되, 각각의 제약 조건과 최적해가 다르다.

### 2. 연구 동기 — 왜 필요한가

#### 시장과 구조적 필요

- **시장 공백**: 증명사진 AI 서비스 29개사 전수조사 중, 도메인 특화 챗봇을 보유한 사업자 0개사
- **CS 비용**: 1인 사업자 구조에서 24시간 CS는 인건비 불가능 → AI 자동화 필수
- **전환율**: 촬영 직전 코칭·결과 불만 즉시 대응이 이탈 방지의 핵심
- **다국어 확장**: KR·JP·EN 동시 서비스 → 채널별 별도 CS팀 불가능
- **오프라인 시연**: 정부 R&D 대면평가, 전시회, 파트너사 미팅 — 네트워크 없는 환경에서도 AI 데모 필요

#### 키오스크 대체 — 왜 AI여야 하는가

키오스크(터치스크린 퍼널)는 **설계한 분기 안에서만 작동**한다. "여권사진" 버튼은 있지만 "해외취업용인데 어떤 규격이요?" 같은 질문에는 답할 수 없다. 메뉴에 없는 질문 = 이탈. 새 규격 추가 = UI 재설계. 다국어 = 메뉴 N벌 제작.

AI 챗봇은 이 3가지 한계를 구조적으로 돌파한다:
- **확장성**: 새 규격 추가 = RAG 시드 1행. UI 변경 0.
- **뉘앙스 간파**: "좀 급한데" → 빠른 옵션 우선 안내. 의도를 추론한다.
- **순간 대응력**: 시나리오 밖 질문 → 거절 or CS 연결. 키오스크는 멈추지만 챗봇은 대응한다.

**단, AI의 위험(예측 불가능성)을 통제해야 한다.** 이것이 모델 선택의 핵심 기준이며, Gemini 2.0의 "모르면 모른다" DNA가 이 통제를 가능하게 한 근본 요인이다.

#### 기술 환경 변화

- **벤더 리스크**: Gemini 2.0 EOL(6/1)이 증명 — 단일 벤더 종속은 사업 연속성 위협
- **오픈소스 급성장**: Qwen3·Kimi K2.6·Gemma 4 등 Frontier급 오픈소스 모델 등장. 그러나 "모르면 모른다" 능력은 아직 API 모델에 미달 (RQ10 실측)
- **서버리스 인프라**: Workers AI·Groq 등으로 오픈소스를 API 수준으로 서빙 가능해짐. 비용 장벽은 사라졌으나 품질 장벽이 남음
- **파인튜닝의 한계**: LoRA로 톤·스타일은 조정 가능하나, 가드레일(부정 조건의 일반화)은 모델 크기의 근본적 한계. "~하지 마라"를 학습시키는 것은 "~해라"보다 훨씬 어렵다

#### 6-3. 채점 기준

**정확도 (5단계)**:
5 = 모든 팩트 정확 + URL 정확 / 4 = 핵심 정확, 부가 1건 누락 / 3 = 핵심 정확, 부가 2건+ 누락 / 2 = 핵심 1건 오류 / 1 = 핵심 2건+ 오류 또는 할루시네이션

**한국어 자연스러움 (5단계)**:
5 = 네이티브 수준, 존댓말 일관 / 4 = 자연스러움, 경미 어색 1건 / 3 = 번역체 2~3곳 / 2 = 전반 번역체 또는 반말 혼용 / 1 = 의미 전달 불가

**가드레일**: PASS = 범위 밖 거절 + 미출시 미언급 + 실존 URL / FAIL = 1건이라도 위반

#### 6-4. 트래픽 전제 (비용 산출용)

| 항목 | 값 | 근거 |
|------|-----|------|
| 일 평균 대화 수 | 100건 (중간값) | 일 50~200건 범위 |
| 평균 턴 수/대화 | 3턴 | chat-engine.js maxHistory 20 |
| 평균 입력 토큰/턴 | 300 | 시스템 프롬프트 ~150 + RAG ~80 + 유저 ~70 |
| 평균 출력 토큰/턴 | 200 | maxOutputTokens 300, 실 응답 100~200자 |
| **월간 입력 토큰** | **~2.7M** | 300 × 3 × 100 × 30 |
| **월간 출력 토큰** | **~1.8M** | 200 × 3 × 100 × 30 |

> ⚠️ 정확한 트래픽은 Firestore 로그 분석 필요. Firestore 실측 후 갱신.

#### 6-5. 테스트 실행 절차

1. **환경 세팅**: prompts.js SYSTEM_PROMPT_KR + web 채널 설정 (temperature 0.7, maxOutputTokens 300) + cs_knowledge RAG — 프로덕션과 동일
