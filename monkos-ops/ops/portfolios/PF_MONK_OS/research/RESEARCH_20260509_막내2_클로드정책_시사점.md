## 1. Claude Code 현행 정책 조사

### 1-1. CLAUDE.md 공식 가이드

**설계 의도**: 매 세션 시작 시 자동 로딩되는 프로젝트 지시 파일. 코드에서 유추 불가능한 규칙(빌드 명령, 코드 스타일, 워크플로우 규칙)을 명시하는 용도.

**권장 구조 및 크기**:
- **200줄 이하** 권장. 길어지면 Claude가 지시를 무시하는 현상 발생.
- 형식 제한 없음 (자유 마크다운). 단, 인간이 읽을 수 있는 간결체 권장.
- "이 줄을 지우면 Claude가 실수할까?" — No면 삭제.

**파일 계층 (위→아래: 넓은 범위→좁은 범위)**:

| 스코프 | 위치 | 공유 범위 |
|--------|------|-----------|
| Managed (조직) | `/Library/Application Support/ClaudeCode/CLAUDE.md` | 조직 전체 |
| Project | `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` | 팀 (Git) |
| User | `~/.claude/CLAUDE.md` | 개인 전체 |
| Local | `./CLAUDE.local.md` | 개인 (프로젝트) |

**로딩 순서**: CWD → 상위 디렉터리 순 탐색, 루트→하위 순 정렬. 하위 디렉터리의 CLAUDE.md는 해당 디렉터리 파일 접근 시 **온디맨드 로딩**.

**컴팩팅 후**: 프로젝트 루트 CLAUDE.md는 디스크에서 **재읽기** (생존). 하위 디렉터리 CLAUDE.md는 자동 재주입 안 됨.

**포함해야 할 것**: bash 명령, 코드 스타일 규칙, 테스트 방법, 브랜치/PR 컨벤션, 아키텍처 결정, 환경 변수 quirks, gotchas.

**제외해야 할 것**: 코드에서 유추 가능한 것, 표준 언어 컨벤션, 상세 API 문서 (링크로 대체), 자주 변경되는 정보, 긴 설명/튜토리얼, 파일별 설명, 자명한 관행.

> 출처: [Best practices - Claude Code Docs](https://code.claude.com/docs/en/best-practices), [How Claude remembers your project](https://code.claude.com/docs/en/memory)

### 1-2. memory/ 시스템

**설계 의도**: Claude가 **스스로** 세션 간 학습을 축적하는 자동 메모리. 빌드 명령, 디버깅 인사이트, 아키텍처 노트, 코드 스타일 선호도, 워크플로우 습관 등을 저장.

**저장 위치**: `~/.claude/projects/<project>/memory/`
- `<project>`는 git 저장소 경로에서 파생 → 같은 repo의 모든 worktree가 **하나의 memory 디렉터리 공유**.

**로딩 제한**: MEMORY.md의 **처음 200줄 또는 25KB** (먼저 도달하는 쪽)만 자동 로딩. 토픽 파일은 온디맨드 읽기.

**Auto Dream (메모리 정리)** `[미확인 — 연구 프리뷰 단계]`:
- 유휴 시간에 메모리 파일을 리뷰하여 오래된 항목 삭제, 중복 병합, 모순 해결, 재조직.
- 상대 날짜를 절대 날짜로 변환 ("어제 결정" → "2026-03-15 결정").
- `/dream` 명령으로 수동 호출 가능.
- 2026년 3월 기준 서버 사이드 피처 플래그로 제어, 일반 사용자 미활성.

> 출처: [How Claude remembers your project](https://code.claude.com/docs/en/memory), [Claude Code Dreams](https://claudefa.st/blog/guide/mechanics/auto-dream)

### 1-3. .claude/rules/

**설계 의도**: CLAUDE.md가 비대해질 때, 주제별로 지시를 분리하는 파일 시스템. 파일 패턴으로 스코핑 가능.

**구조**:
```
.claude/rules/
  testing.md          # path: **/*.test.ts
  api-design.md       # path: src/api/**/*.ts
```

**특성**:
- Git 커밋 가능 (팀 공유)
- CLAUDE.md 대비 세분화된 스코핑 가능
- 프로젝트 규칙과 개인 규칙(`~/.claude/rules/`) 분리

> 출처: [Explore the .claude directory](https://code.claude.com/docs/en/claude-directory)

### 1-4. .claude/skills/

**설계 의도**: 온디맨드로 로딩되는 재사용 가능 지시 팩. 매 세션에 로딩하기엔 과한 도메인 지식이나 워크플로우에 적합.

**핵심 제약**:
- `description + when_to_use`: **1,536자**에서 잘림
- 스킬 설명 총 예산: 컨텍스트 윈도우의 **1%** (폴백 8,000자)
- 컴팩팅 후: 가장 최근 호출 스킬의 처음 **5,000 토큰** 재부착. 전체 스킬 합산 **25,000 토큰** 예산
- 이름: 소문자+숫자+하이픈, 최대 **64자**
- SKILL.md 권장 크기: **500줄 이하**

**스코프**:

| 위치 | 적용 범위 |
|------|-----------|
| Enterprise | 조직 전체 |
| `~/.claude/skills/` | 개인 전체 |
| `.claude/skills/` | 프로젝트 |
| Plugin | 플러그인 활성 범위 |

**호출 제어**:
- 기본: 사용자 + Claude 모두 호출 가능
- `disable-model-invocation: true`: 사용자만 호출 (설명이 컨텍스트에 미포함)
- `user-invocable: false`: Claude만 호출 (사용자 메뉴 미노출)

**동적 컨텍스트 주입**: `` !`command` `` 문법으로 쉘 명령 실행 결과를 스킬 내용에 삽입.

> 출처: [Extend Claude with skills](https://code.claude.com/docs/en/skills)

### 1-5. 프로젝트 구조 권장사항

**공식 .claude 디렉터리 구조**:

```
.claude/

  settings.json              # 권한, 훅, 설정
  settings.local.json        # 개인 설정 오버라이드

  skills/                    # 재사용 스킬
  commands/                  # 레거시 (skills 권장)
  output-styles/             # 출력 스타일

```

**대규모 프로젝트 권장사항**:
- 작업을 컨텍스트 크기 단위로 분할. 마라톤 세션 지양.
- `/clear`로 비관련 작업 간 컨텍스트 초기화.

- 서브에이전트로 탐색 위임 → 메인 컨텍스트 보호.
- Writer/Reviewer 패턴: 구현과 리뷰를 별도 세션에서 (신선한 컨텍스트).

> 출처: [Explore the .claude directory](https://code.claude.com/docs/en/claude-directory), [Best practices](https://code.claude.com/docs/en/best-practices)

## 3. PF 체계 관점에서의 시사점

### 3-1. Claude Code의 "프로젝트 단위 context" 관리

Claude Code는 **git repo = 1 project**로 자동 매핑한다. repo 내부의 서브 프로젝트(= PF)를 구분하는 네이티브 개념은 없다.

**시사점**: PF 체계는 Claude Code 플랫폼 위에 MONK OS가 자체 구축한 **상위 추상화**이며, 이를 파일 기반(PF 디렉터리 + 히스토리)으로 운용하는 현행 설계가 적절하다. Claude Code가 PF를 인식하려면 세션 내에서 PF 파일을 Read해야 하며, 이는 현행 스킬/지시서에서 PF 경로를 명시하는 방식으로 작동하고 있다.

### 3-2. 다중 에이전트 환경에서 shared state 관리

**Claude Code가 제공하는 메커니즘**:
1. **Auto memory**: git repo 단위 공유 → 같은 디바이스의 모든 에이전트가 동일 memory/ 접근
2. **Agent Teams**: 공유 태스크 리스트 + 메일박스 (실험적)
3. **Subagent memory**: project/local/user 3개 스코프 (`.claude/agent-memory/`)
4. **Git worktree**: 파일 충돌 방지를 위한 격리 (Agent Teams에서 자동 사용)

**우리 체계와의 비교**:
- MONK OS의 `monkos-ops/works/` (submodule 기반 공유 채널)은 Claude Code에 없는 독자적 설계.
- Claude Code의 Auto memory 공유는 같은 디바이스 내에서만 유효 → 디바이스 간 공유는 여전히 Git (mk-push/mk-pull) 의존.
- Agent Teams의 공유 태스크 리스트가 지시서 체계와 유사하나, Agent Teams는 단일 세션의 팀 리드가 관장 → 쌍아가 지시서로 분배하는 현행 방식과 아키텍처가 다름.

**시사점**: 현행 MONK OS의 멀티에이전트 조율은 Claude Code 플랫폼 위의 **응용 계층**이다. Agent Teams GA 시 기존 지시서 체계와의 통합/대체 여부를 재평가할 필요가 있으나, 현재는 파일 기반 지시서 + Git 동기화가 더 안정적.

### 3-3. PF 히스토리와 compaction 대응

**컴팩팅 동작**:
- 프로젝트 루트 CLAUDE.md는 컴팩팅 후 디스크에서 재읽기 → **생존**
- 스킬은 최근 호출된 것부터 5,000 토큰/25,000 토큰 예산 내 재부착
- 하위 디렉터리 CLAUDE.md, 일반 파일 내용은 **소실**

**PF 히스토리 보호 전략**:
1. PF 히스토리는 파일 기반이므로 컴팩팅에 직접 영향 받지 않음 (Read로 재접근 가능)
2. 컴팩팅 후 PF 컨텍스트가 유실되므로, 막내가 장시간 작업 시 PF 경로를 CLAUDE.md나 스킬에 명시하면 재접근 용이
3. 세션로그의 즉시 어펜딩 원칙 (헌법 3조)이 컴팩팅 대응의 핵심 — 기록이 파일에 있으면 컴팩팅으로 인한 맥락 유실을 파일 Read로 복원 가능

### 3-4. memory vs 파일 기반 기록의 트레이드오프

| 측면 | Auto Memory (memory/) | 파일 기반 (PF/세션로그) |
|------|----------------------|----------------------|
| **작성 주체** | Claude 자동 | 에이전트 규칙 기반 |
| **로딩** | 세션 시작 시 자동 (200줄/25KB) | 명시적 Read 필요 |
| **정밀도** | Claude 판단에 의존 | 규칙 기반으로 예측 가능 |
| **구조화** | 약함 (자유 형식) | 강함 (YAML frontmatter, 네이밍 규칙) |
| **디바이스 간 공유** | 불가 (로컬) | Git으로 가능 |
| **컴팩팅 후** | 자동 재로딩 | 수동 Read 필요 |
| **적합 용도** | 디버깅 교훈, 환경 quirks, 선호도 | 프로젝트 생애주기, 의사결정 이력, 보고 |

**시사점**: 두 시스템은 **보완적**이지 대체적이지 않다. Auto memory는 에이전트의 단기 학습과 환경 적응에, 파일 기반 기록은 조직적 지식 관리와 감사 추적에 적합. 현행 MONK OS의 이중 구조(MEMORY.md + PF/세션로그)가 Claude Code 설계 철학과 정합한다.

---

## 4. 핵심 발견 및 권고

### 4-1. 즉시 조치 가능한 사항

| # | 발견 | 권고 | 영향 |
|---|------|------|------|
| 1 | CLAUDE.md 222줄 (권장 200줄 초과) | 법률 인덱스 테이블, 규정 참조 테이블을 `.claude/rules/`로 이관 검토 | CLAUDE.md 경량화 → 지시 준수율 향상 |
| 2 | 법률 8장이 `governance/laws/`에만 존재, `.claude/rules/`에는 3개만 | 빈번 위반 조항을 rules 파일로 추출 (전체 이관 불필요, 핵심만) | 컨텍스트 부담 없이 규칙 강화 |
| 3 | HTML 주석이 CLAUDE.md에서 자동 제거됨 | 내부 메모를 `<!-- -->` 주석으로 두면 토큰 절약 가능 | 토큰 효율 |

### 4-2. 중기 검토 사항

| # | 항목 | 내용 | 전제 |
|---|------|------|------|
| 4 | Agent Teams 도입 검토 | GA 후 지시서 체계와의 통합/대체 재평가 | Anthropic GA 발표 시 |
| 5 | Auto Dream 활용 | 활성화 시 MEMORY.md 수동 관리 부담 감소 | GA 후 |
| 6 | Subagent 정의 파일 도입 | `.claude/agents/`에 막내 프로파일 정의 → 서브에이전트 역할 표준화 | 멀티에이전트 체계 고도화 시 |
| 7 | PF 경로의 스킬 연동 | PF 작업 시 자동으로 PF 디렉터리를 컨텍스트에 포함하는 스킬 구성 | PF 체계 개정 시 |

### 4-3. 구조적 정합성 평가

**현행 MONK OS 4계층 ↔ Claude Code 구조**:

| MONK OS 계층 | Claude Code 대응 | 정합 평가 |
|-------------|----------------|-----------|
| 헌법 (왜) | CLAUDE.md | ✅ 개념 일치. 크기만 조절 필요 |
| 법률 (무엇) | .claude/rules/ + governance/laws/ | ⚠️ rules 활용도 확대 여지 |
| 명령 (어떻게) | .claude/skills/ | ✅ 정합 |
| 규정 (디바이스 상세) | memory/ (MEMORY.md) | ✅ 정합 |

**결론**: MONK OS의 4계층 문서 위계는 Claude Code의 설계 철학(CLAUDE.md → rules → skills → memory)과 **구조적으로 정합**한다. Claude Code가 진화하면서 오히려 MONK OS의 설계가 선행적으로 올바른 방향이었음이 확인된다. 주요 개선 여지는 CLAUDE.md 경량화와 rules 활용도 확대이며, 이는 PF 체계 개정과 독립적으로 진행 가능하다.
