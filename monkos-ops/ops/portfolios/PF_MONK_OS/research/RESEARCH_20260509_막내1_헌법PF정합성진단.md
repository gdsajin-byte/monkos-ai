## 2. 정합성 갭 진단 — 6대 질문

### Q1. 정본 위치 규칙: 법률에 "PF 정본은 어디"라고 명시되어 있는가?

**판정: 부분 명시 — 루트 md vs 폴더/README.md 분기 기준 미정의**

- ch4 4조 정본 테이블: `monkos-ops/ops/portfolios/` → 포트폴리오(PF) 정본으로 **명시됨**
- ch4 3조 #15: 파일명 패턴 `PF_{코드네임}.md` → `monkos-ops/ops/portfolios/`로 **명시됨**
- **갭**: 법률·템플릿 모두 `PF_{코드네임}.md`(루트 단일 파일)만 상정한다. 그러나 실운용에서는:
  - **6개 폴더형 PF** 존재: PF_CDP, PF_DOCS, PF_MONK_OS, PF_RND, PF_SECURITY, PF_SPREAD
  - 이 중 4개(PF_DOCS, PF_MONK_OS, PF_RND, PF_SECURITY)는 **루트 md 없이 폴더/README.md만 존재**
  - 2개(PF_CDP, PF_SPREAD)는 **루트 md + 폴더 양쪽 존재** → 정본 이중화 가능성
- 법률 어디에도 "폴더형 PF의 정본은 폴더/README.md이다" 또는 "루트 md와 폴더/README.md 중 어느 것이 정본인가"에 대한 규정이 **없다**

### Q2. 히스토리 갱신 의무: 누가, 언제, 어떤 조건에서?

**판정: 주체·시점은 명확 — 조건(어떤 작업이 PF 대상인지) 판단 기준이 느슨**

- **누가**: 쌍아가 수행 (ch3 3조, README 운용 원칙). 막내는 COMPLETION으로 납품
- **언제**: ① 세션 마감 시 (ch3 3조) ② PF 간 작업 전환(일단락) 시 (ch3 3조) ③ Phase 완료·지시서 발행·배포 시 (README)
- **조건**: 헌법 제3조 2항 — "활성 PF가 존재하는 작업의 경우". ch3 3조 — "PF 대상 작업이 없는 세션은 스킵"
- **갭**: "이 작업이 PF 대상인가?"의 판단 기준이 지시서의 `portfolio:` 필드 존재 여부에만 의존. 지시서 없는 직접 지시 경로에서는 PF 귀속 판단이 에이전트 자율에 맡겨져 있음. 실무상 쌍아의 판단 누락 시 히스토리 갱신이 빠짐

### Q3. 히스토리 테이블 스키마: 열 구성이 법률/템플릿에 정의되어 있는가?

**판정: 템플릿에만 정의 — 법률 미규정. 카테고리 분류 열 없음**

- **PF_TEMPLATE.md** 히스토리 열: `날짜 | 주체 | 내용 | 산출물 | 상태` (5열)
- **법률 ch4 9조**: 히스토리 테이블 스키마에 대한 언급 **없음**. "히스토리는 append-only"라는 원칙만 규정
- **카테고리 분류 열**: 템플릿에도 법률에도 **없음**
- **실태**: 대부분의 PF가 템플릿 5열을 따르지만, PF_RND와 PF_MONK_OS는 열 순서가 뒤바뀌거나 변형된 행이 혼재
- **갭**: 스키마가 법률이 아닌 템플릿(권고)에만 있어 구속력이 없음. 작업 유형(코딩/설계/배포/리서치 등)을 식별할 카테고리 열이 없어 히스토리가 커질수록 탐색 효율 저하

### Q4. 세션로그→PF 환류: 법률상 의무인가, 권고인가?

**판정: 의무 — 단, 이행 확인 메커니즘 없음**

- 헌법 제3조 2항: "세션 로그 작성 시점에 해당 PF의 히스토리를 갱신한다" → **의무형 서술**
- ch3 3조: 세션 마감 절차 ② → PF 히스토리 어펜드 → **절차 필수 단계로 편입**
- ch3 3조: "미갱신 발견 시: 다음 세션 시작 시 보정 의무" → **사후 보정 의무까지 명시**
- **갭**: 의무는 명확하나, 실제 이행 확인은 쌍아의 수동 확인에 의존. 자동 검증(데몬, 스크립트 등) 없음. 히스토리 최종 갱신일 기준으로 장기 미갱신 PF가 다수 존재 (후술 §3 참조)

### Q5. PF 인덱스 관리: 갱신 주체/주기가 정의되어 있는가?

**판정: 미정의 — 인덱스 갱신 규칙 부재**

- `portfolios/README.md`가 PF 인덱스 역할을 하지만:
  - 갱신 주체: **규정 없음** (README 운용 원칙에도 인덱스 갱신 주체 미언급)
  - 갱신 주기: **규정 없음**
  - 갱신 트리거: **규정 없음** (PF 신설/폐지 시 인덱스 갱신 의무 미언급)
- **실태**: 인덱스에 **7개**만 등록, 실제 PF는 **16개** (루트 md 12개 + 폴더 전용 4개) → **9개 미등록**
- 미등록 목록: PF_BRIEF, PF_EVENT, PF_PRESENTATION, PF_PROFILES, PF_VIDEO, PF_DOCS, PF_MONK_OS, PF_RND, PF_SECURITY
- ch4 6조 4항(폴더 편입)은 README.md 동시 생성을 의무화하나, 인덱스(상위 README) 갱신은 언급 없음

### Q6. 폴더형 vs 파일형 PF: 기준이 있는가?

**판정: 기준 없음**

- 법률·템플릿·README 어디에도 "어떤 PF가 폴더를 갖고 어떤 PF가 단일 md인지"에 대한 기준 **없음**
- ch4 3조 #15: 파일명 패턴만 규정 (`PF_{코드네임}.md`). 폴더 생성 조건 미규정
- ch4 9조 3항(비대화 관리): 히스토리 100행 초과 시 별도 파일 분리를 규정하나, 이것은 폴더 생성 기준이 아닌 히스토리 분리 기준
- **실태**:
  - 파일만: PF_BRIEF, PF_CITADEL, PF_CROP, PF_EVENT, PF_PHOTOPRO, PF_PORTAL, PF_PRESENTATION, PF_PROFILES, PF_STUDIO, PF_VIDEO (10개)
  - 루트 md + 폴더: PF_CDP, PF_SPREAD (2개)
  - 폴더만(루트 md 없음): PF_DOCS, PF_MONK_OS, PF_RND, PF_SECURITY (4개)
- 폴더형 PF 중 PF_CDP는 `research/`, `case_studies.md` 등 하위 문서가 풍부한 반면, PF_DOCS는 README.md 1개뿐 → 폴더 생성 기준이 불명

## 4. 갭 총괄 — 구조적 문제 6건

### 갭 ①: PF 정본 형태(파일형/폴더형) 분기 기준 미정의

- **현상**: 16개 PF 중 10개 파일형, 2개 혼합형(루트md+폴더), 4개 폴더전용
- **법률 상태**: ch4 3조 #15는 `PF_{코드네임}.md` 패턴만 규정. 폴더형 규격 부재
- **위험**: 에이전트가 PF를 찾을 때 파일을 먼저 볼지 폴더/README를 볼지 판단 불가. 컴팩팅 후 정본 오인식

### 갭 ②: PF 인덱스 갱신 규칙 부재 + 대규모 누락

- **현상**: 인덱스 7개 등록, 실제 16개. 9개(56%) 미등록
- **법률 상태**: 인덱스 갱신 주체/주기/트리거 규정 없음
- **위험**: 세션 시작 시 활성 PF 목록 보고(ch3 5조)가 인덱스 기반이면 9개 PF가 보고에서 누락. 신규 에이전트가 PF 존재를 인지 못함

### 갭 ③: 히스토리 스키마의 법적 구속력 부재

- **현상**: 5열 스키마가 PF_TEMPLATE에만 존재. 법률 ch4 9조는 스키마 미규정
- **법률 상태**: 템플릿은 가이드(권고), 법률이 아님
- **위험**: PF별 히스토리 열 구성이 점진적으로 분화. 자동 파싱·집계 불가. 카테고리 분류 부재로 히스토리 탐색 비효율

### 갭 ④: YAML 규격 위반 다수

- **현상**: 16개 중 4개(PF_EVENT, PF_STUDIO, PF_DOCS, PF_SECURITY) YAML 규격 위반
  - PF_EVENT: `id` 누락, `status` 비정규값
  - PF_STUDIO: `status` 불일치 (본문 active ↔ 인덱스 paused)
  - PF_DOCS: `type: portfolio` 아님, 필수 필드 다수 누락
  - PF_SECURITY: `status` 비정규값("대기"), 비표준 필드 사용
- **법률 상태**: ch4 7조가 portfolio 타입 필수 필드를 명시하나 검증 미이행
- **위험**: YAML 자동 파싱 실패. 데몬/스크립트 기반 관리 불가

### 갭 ⑤: 비대화 관리 이행 미흡

- **현상**: PF_SPREAD 508줄(500줄 트리거 초과), PF_CDP 455줄(임계 근접)
- **법률 상태**: ch4 9조 3항 — "500줄 초과 시 아카이브 트리거. 쌍아가 세션 마감 시 줄 수 확인"
- **위험**: 비대화 시 에이전트 컨텍스트 과부하. PF 읽기 시 토큰 낭비

### 갭 ⑥: 환류 이행 검증 메커니즘 부재

- **현상**: PF_PHOTOPRO 히스토리 ~04/11 이후 미갱신 (28일+). PF_PRESENTATION ~04/10 이후 미갱신 (29일+). 한편 실제 세션에서 해당 프로젝트 작업이 있었는지는 세션 로그 대조 필요
- **법률 상태**: ch3 3조 — "미갱신 발견 시 다음 세션 시작 시 보정 의무" → 발견 자체가 수동
- **위험**: 의무 규정은 있으나 이행 확인이 없어 사실상 사문화 가능
