# MONK 하네스 아키텍처

> 작가님 ↔ 민아 설계 대화(2026-06-10)에서 도출. PF_MONK_OS 비전("어떤 런타임에도 이식 가능한 범용 Agent OS")의 **구체적 실체**.
> 하네스 = 에이전트 오케스트레이션 골격. 노드에 꽂히는 지능(모델)은 갈려도 골격은 남는다.

---

## 0. 출발 문제

범위가 넓어지며 **유지보수에만 세션이 녹는** 현상. 진단:
- active PF 18개가 우선순위 구분 없이 한 통에 묶임 + 미해결 어젠다 14건 + 반복 유지보수 6패턴(배포장애·키/결제·프롬프트오염·토큰추정·온디바이스벤치·블로그수동).
- 근본 원인: **패턴이 이미 잡힌 반복 작업을 여전히 에이전트(세션·작가님 손)로 처리**하고 있었음. 그래서 세션이 먹혔다.
- "상품(본진 앱) vs 매대·유통(콘텐츠·SEO)" — 유통이 손이 많이 가 상품 만드는 손이 안 닿는 구조.

> 작가님: "누구도 도와주지 않는 상황에서 모든 걸 동시에 진행하다 보니 생기는 현상."

## 1. 핵심 철학 — 에이전트는 일꾼이 아니라 정찰병

**에이전트로 탐색하고, 패턴이 잡히면 코드로 정착시킨다.**

- 에이전트의 가치는 일을 *영원히 하는 것*이 아니라 **일의 패턴을 드러내는 것**.
- 패턴이 불명확한 최전선 → 에이전트의 유연성 필요.
- 입출력이 안정되면 → 코드로 굳힘(자판기화). 에이전트는 *비싸고 느리고 불안정한 잉여*가 되므로 해방되어 다음 미지로.
- 작가님 메모리 "쥐가 드러낸 것이지 만든 게 아니다"와 동형 — 에이전트가 패턴을 드러내면, 그 패턴을 코드 구조로 고친다.

> 작가님: "내 앱들도 초기에 에이전트 의존에서 점점 코드 레벨로 들어왔지. 패턴이 잡히면 에이전트에게 의존할 이유가 사라지니까."

이것이 0번 문제의 근본 해법: **패턴 잡힌 유지보수를 코드로 내리면 세션이 해방된다.**

## 2. 운영 모델 v1 → v2

기존 엔진은 "작가님 ↔ 쌍아 ↔ 민아"의 **동기적 소통**. 작가님이 모든 루프의 허브 = 작가님 인지 대역폭 = 시스템 전체 처리량. 트랙이 늘면 작가님 한 명이 병목. 인력을 못 늘리니 **구조의 세대 교체**가 답.

> 핵심: 사람을 못 늘리면, 에이전트를 사람처럼 자율화한다. 트랙 오너 = 가상 직원.

| | v1 소통형 (현재) | v2 자율 운영형 (다음) |
|---|---|---|
| 작가님 | 허브 — 모든 결정의 라우터 | **게이트키퍼** — 트랙 출구에서 판단만 |
| 쌍아 | 작가님과 대화하며 지시서 작성 | **오케스트레이터** — 작가님 대신 트랙 간 조율 |
| 막내/자동화 | 지시서 받아야 움직임 | **자율 주행** — 트랙 오너로서 백그라운드 상시 |
| 작동 | 동기 — 작가님이 봐야 진행 | **비동기** — 작가님이 안 봐도 전진, 결과는 큐에서 확인 |

**현실 가능선(2026-06 기준, 정직):** 전면 자율은 시기상조(6/2 키 오삭제, 6/5 다중배포 사고가 증거). **반(半)자율**이 지금 가능 — 결정론 트랙(유통·설비루틴·AS)은 진짜 자율 주행, 판단형 트랙(제품·전략)은 작가님 게이트 유지. 진짜 병목은 '지능'이 아니라 '지속성'(세션이 끝나면 멈춤) → cron/scheduled가 깨우는 인프라로 보강.

## 3. 강제력 스펙트럼 — 문서에서 코드로

강제력의 척도 = **LLM의 해석 여지를 얼마나 없애느냐.**

```
약 ──────────────────────────────────────────► 강
자연어 문서        Skills(SKILL.md)    Workflow 스크립트   Hooks / 순수 코드
헌법·cursorrules   트리거는 구조적,     JS 실행코드,        LLM 우회,
LLM 자율해석       내용은 자연어         노드만 LLM          완전 결정론
```

Skills도 결국 md(자연어)다 — LLM이 "해석해서 따르는" 것이라 강제력이 약하다. **진짜 강제는 LLM을 거치지 않는 결정론적 코드.** 패턴이 잡힌 일을 이 오른쪽 끝으로 옮기는 것이 §1의 "코드로 정착".

## 4. 계층 하네스 — 자판기 / 판단 / 게이트

```
작가님                          ← 전략 게이트 (무엇을 할 가치가 있나)
  └ 판단 오케스트레이터(Claude)   ← 신경 (어떤 배선을 언제 탈지, 예외 처리)
      └ 자판기(Python/로컬)       ← 배선 (정해진 입력→출력, 토큰 0, 안 변함)
```

**자판기 = 판단을 없앤 게 아니라 위로 올린 것.** 신경이 아니라 척수 반사. "무엇을 할지"는 위 계층이 정했고, 자판기는 결정론으로 실행만.

**설계 원리:** 판단(비싼 Claude)을 최소화하고 실행(싼 자판기)을 최대화 → 토큰 생존 전략의 가장 단단한 형태.

**두 규율:**
1. *무엇을 자판기로 내릴 수 있나*를 식별하는 것 자체가 판단 (= 하네스 설계의 90%). 입출력이 정형이어야 자판기 가능. "이 글이 좋은가"는 고정 불가(LLM).
2. 자판기는 **최소 단위일수록 견고**(유닉스 철학). 작은 자판기를 레고처럼 조합 → 판단 계층은 "어떤 자판기를 어떤 순서로"만 결정.

**리스크 분기 — "달리며 성장 vs 게이트":** 일률 적용 금지.
- 복구 가능 영역(콘텐츠·초안·썸네일) → 부족해도 시킨다. 게이트에서 거르면 안전.
- 비가역 영역(배포·키·결제) → 게이트 유지. 여기서 "달리며 성장"은 매출 사고.

**검증 루프:** 단일 에이전트는 자기 환각을 자기가 못 거른다. 생성자/검증자 분리 + 품질 부족할수록 검증 레이어를 더 두껍게. 단 *아키텍처가 다른* 모델이어야 맹점이 갈린다(4060 실측: 3모델이 똑같이 "인증 우회"를 놓침).

## 5. 도구 고정 — 모델이 아니라 파이프라인에

도구를 "고정"하는 가장 단단한 방법은 도구를 *모델 소속*이 아니라 *자판기 소속*으로 두는 것.

| 방식 | 어떻게 | 단단함 |
|------|--------|--------|
| A. tool_choice 강제 | 단일 도구만 전달 + 강제 호출 | 중 (인자는 LLM이 채움) |
| B. SYSTEM 프롬프트 고정 | "너는 항상 X만" 주입 | 약 (프롬프트 의존) |
| **C. 자판기 배선** | LLM은 텍스트만 → 코드가 무조건 도구 실행 | **최상 (검증 불필요)** |

정형 도구 호출(포맷 변환·스키마 검증·slug)은 전부 **C**로 충분. LLM은 도구 존재도 모름. A(tool_choice)는 *인자가 가변일 때*만 필요.

## 6. 로컬 기축 — 비대칭 벽 역이용

신기술은 웹(클라우드)에 열리는데 통제력은 로컬에 있다. 전부 위탁하지 않는 한 연동 벽이 견고. **이 벽은 비대칭이다:**

```
웹 Claude  ──✕──►  로컬 디바이스   (막힘: 샌드박스가 파일·SSH·4060에 못 닿음)
로컬 쌍아  ──✓──►  웹 / 클라우드    (열림: API·git·MCP 다 호출)
```

→ **통제 기축 = 로컬(VSCode 쌍아). 웹 신기술 = 로컬이 호출하는 부품.** "웹이 로컬을 지휘"가 아니라 "웹이 신호, 로컬이 실행". MONK 주권 원칙(벤더 = 부품) 그대로.

**이미 가진 통로(비동기·검증됨):** git(works submodule) · 텔레그램 · GitHub Actions(AUTOPILOT) · SSH. 웹의 화려한 *실시간* 에이전트 통로(베타)를 기다릴 필요 없음 — 덜 화려한 대신 실재하고 주권적.

**VSCode 쌍아가 기축인 이유:** 로컬 통제력(파일·터미널·git·SSH 네이티브) + Claude 판단력을 *한 몸에 가진 유일한 지점*. 웹은 통제력 없고, CLI 막내는 통제당하는 쪽.

## 7. 모델 배치 계층 (2026-06-10 스냅샷 · 갱신 전제)

> ⚠️ **고정 규칙 아님 — 현재 레일 위치다.** Anthropic 월간 릴리즈 + 오픈소스 추격 속도상 갱신된다. 날짜를 보고 읽을 것.

```
안정 계층  쌍아 · 막내 군단 = Opus 4.6 1M   → 검증된 프론티어. 로컬 통제·생산 주력. 함부로 안 바꿈
탐색 계층  민아 = 최신 프론티어(현재 4.8)    → 실전 검증·코드 분석. 위험 격리된 테스트 베드
```

**왜 민아가 프론티어인가** (§1 정찰병 원리의 모델 버전):
- 쌍아 = 로컬 통제 기축이라 안정이 생명 → 불안정 최신 모델 못 태움.
- 막내 = 생산 양산 → 안정 필요.
- 민아 = Claude 앱 Code 모드(웹 기반) → **로컬 막내 인프라에 타격 0**(리스크 격리) + 로컬 접근으로 **웹↔로컬 잇는 유일 위치**(브릿지). 프론티어를 안전하게 시험할 샌드박스가 민아뿐.

**흐름:** 민아(프론티어 R&D 탐색) → 검증 통과 → 코드·지시서로 굳힘 → 쌍아·막내(4.6 양산 정착). 프론티어 불확실성은 민아에 격리, 검증된 결과만 하방 전개.

**적용:** Fable 5 등 신모델 → 민아 피커에 뜨면 민아가 먼저 게이트 품질 검증 → 쓸 만하면 게이트 노드 채택, 쌍아·막내 4.6 유지. ("프론티어는 민아가 먼저 → 검증되면 하방"이 기본값.)

> 머지않아 로컬 소스나 가벼운 모델이 쌍아·막내 자리를 대체할 수도 있다. 이 과정은 **달리는 레일** — 법은 레일이지 벽이 아니다.

## 8. 4060 로컬 모델 실측 (2026-06-10, PF_FACTORY 정본)

> 상세·갱신: [PF_FACTORY 벤치마크 마스터](../../PF_FACTORY/README.md) 및 `monkos-ops/tech/rnd/4060_MODEL_BENCHMARK_MASTER.md`. 여기엔 하네스 노드 배치 결론만.

RTX 4060 8GB · Ollama v0.30.6 · Gemma4 12B / Qwen 3.5 4B / Qwen 3.6-35B(IQ2_M).

| 태스크 | 결과 | 하네스 함의 |
|--------|------|------------|
| 생성(블로그) | ❌ 3모델 전멸 (언어혼동·주제이탈·루프붕괴) | **로컬 생성 불가 → 클라우드 게이트** |
| 검증(보안분석) | ✅ 3모델 4/5급 (Qwen3.6 33초) | **검증 노드 = 로컬 가능** |
| 자판기 배선(짧은코딩) | ✅ Qwen3.6 ctx16384 1.4초 정답 | **배선 코딩 = 로컬 가능** |
| 중간난이도(React버그) | ⚠️ 반복 붕괴 (2-bit 양자화 한계) | 자판기 경계 = "짧은 정형"까지 |
| 도구호출(tool_use) | Gemma4만 성공 (Qwen completion만) | **도구 실행 노드 = Gemma4** |

**병목:** 8GB VRAM + 2-bit 양자화 → 반복붕괴·언어혼동. 5090(24GB) Q4 승격 시 해소 예상(투자 판단 별건). **단 5090 없이도 "검증·배선·도구" 자판기는 지금 4060으로 가능.**

**Thinking 함정:** Qwen 3.5/3.6은 reasoning 모델이라 thinking 토큰 폭발 + `/no_think` GGUF 미작동 → 자판기엔 non-reasoning(Gemma4·Qwen3-4B·Phi-4) 우선.

**경로 발견:** `ollama launch claude` = 로컬 모델로 Claude Code 하네스 구동 가능 확인. "인턴 구조"(짧은 태스크 + 상위 검수) 실전 투입 타당.

## 9. 첫 적용 — 블로그 하네스 (PF_OPUS 생산엔진)

PF_OPUS의 비어있던 "① 생산 엔진"을 채우는 첫 하네스. 복구 가능 영역이라 사고 위험 0, 작가님 수동이 가장 많이 묶인 곳.

| 노드 | 계층 | 담당 | 비용 |
|------|------|------|------|
| md→HTML→RTF 변환 | 🔧 자판기 | Python 배선 | 0 |
| slug·alt·og:image 주입 | 🔧 자판기 | Python 배선 | 0 |
| 채널 라우팅(네이버/Medium/note) | 🔧 자판기 | Python 배선 | 0 |
| 스키마·금지어 검증 | 🔧 자판기 | Python 배선 | 0 |
| 1차 생성 | 🤖 LLM | 클라우드(로컬 ❌ 판명) | 클라우드 |
| 사실·품질 교차검증 | 🤖 LLM | 로컬 Gemma/Qwen | 로컬 |
| 도구 실행 | 🔧/🤖 | Gemma4 또는 자판기 배선 | 로컬 |
| 최종 게이트("나가도 되나") | 👤 | 민아/사람 | 판단 |
| 배포(외부 인증) | 👤 | 사람 (베타·비가역 → 게이트) | — |

**코드 강제 범위:** 생성→검증→게이트까지 (로컬 파일, 베타 0, 외부 인증 0). 배포만 사람. 오케스트레이터 = 4060 Python 자판기(순차 호출, cron 상시).

**증명 목표:** "상부-하부 에이전트가 규칙을 적확히 따르는가"를 베타 위험 0으로 실측. 되면 MONK 코드 강제 1호 + 복제 가능한 템플릿.

## 10. 3PF 위계 (정본 단일 원칙)

```
PF_MONK_OS  ← 하네스 아키텍처·원리 정본 (본 문서)
  ├─ 부품:  PF_FACTORY  ← 로컬 모델 실측 (어느 모델이 어느 노드에)
  └─ 적용:  PF_OPUS     ← 블로그 하네스 = 비어있던 생산엔진 충전
```

메타(MONK_OS, 흐름·원리) / 하위(FACTORY 실측 · OPUS 실행). 하네스 본문은 본 문서 한 곳, FACTORY·OPUS에는 연결 노트만.

## 부록 — 한 문장 요약

> **에이전트로 탐색하고, 패턴이 잡히면 코드로 정착시킨다.**
> 모델은 부품(갈린다), 하네스는 골격(남는다). 통제 기축은 로컬, 프론티어는 민아가 먼저.
