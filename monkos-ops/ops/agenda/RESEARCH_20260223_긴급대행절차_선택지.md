## 1. 긴급 배포 절차 선택지 (어젠다 #6-1)

**현안**: ch7 1조(main 머지 금지) + ch7 3조(gcloud run deploy 금지)와 긴급 배포 필요성의 충돌

### 옵션 A: 긴급 등급 정의 + 등급별 권한 자동 확대

| 항목 | 내용 |
|------|------|
| **개요** | 긴급도를 P0~P3으로 정의하고, P0 시 막내에게 배포 권한 자동 부여 |
| **트리거** | P0 선언 (서비스 장애, 법적 기한 임박, 보안 위협 등 사전 정의 조건) |
| **절차** | P0 선언 → 막내 직접 배포 가능 → Git 커밋에 `[P0]` 태그 → 24시간 내 사후 심사 |
| **승인** | P0 선언은 작가님 또는 쌍아. 선언 후 막내 자율 실행 |
| **참고 패턴** | 소프트웨어 Break-glass (AWS: 긴급 시 사전 정의 역할 자동 활성화) |

**장점**:
- 긴급 상황에서 빠른 대응 가능 (승인 대기 시간 최소화)
- 긴급도 기준이 명확해져 판단 일관성 확보
- 사후 심사로 남용 방지

**단점**:
- P0의 정의가 자의적으로 해석될 위험 (누가 P0을 선언하는가의 문제)
- 법률 개정 범위가 넓음: ch7 1조, 3조 예외 규정 신설 + 긴급도 정의 신설 (최소 2개 조항)
- "자동 확대"가 작가님 직접 통제를 약화시킬 수 있음

### 옵션 B: Break-glass 절차 (사전 승인 없이 실행 → 사후 필수 심사)

| 항목 | 내용 |
|------|------|
| **개요** | 정규 승인 절차를 건너뛰되, 실행 기록과 사후 심사를 의무화 |
| **트리거** | 막내가 긴급 판단 (but 판단 근거를 실행 전 Git 커밋 메시지에 기재) |
| **절차** | 판단 근거 기재 → 즉시 실행 → `[BREAK-GLASS]` 태그 커밋 → 24시간 내 어젠다 등록 → 야간 심사에서 필수 리뷰 |
| **승인** | 사전 승인 없음. 사후 심사에서 적법성 판정 |
| **참고 패턴** | AWS Break-glass Role (사전 승인 면제, 사후 감사 필수, 자동 로그) |

**장점**:
- 가장 빠른 대응 (작가님/쌍아 부재 시에도 대응 가능)
- AWS/GCP 업계 표준 패턴과 일치
- 사후 심사가 의무이므로 투명성 유지

**단점**:
- 막내의 독자 판단에 의존 → 오판 시 프로덕션 장애 위험
- 헌법 5조(역할 체계: 쌍아=설계, 막내=자율코딩)의 취지와 긴장 관계
- "사후 적법성 판정"에서 부적법 판정 시 처리 규칙이 추가로 필요
- 법률 개정 범위: ch7 예외 규정 + Break-glass 절차 조항 신설

### 옵션 C: 현행 유지 (매건 작가님 구두 승인)

| 항목 | 내용 |
|------|------|
| **개요** | 현재와 동일하게 작가님이 매건 구두 승인 후 막내 실행 |
| **트리거** | 긴급 상황 발생 시 작가님에게 보고 |
| **절차** | 보고 → 작가님 승인 → 막내 실행 → 세션 로그 `[예외]` 기록 |
| **승인** | 작가님 직접 |
| **참고 패턴** | 기업 거버넌스 (이사회 매건 승인) |

**장점**:
- 작가님의 직접 통제력 최대 유지
- 법률 개정 불필요 (현행 유지)
- 가장 안전 (작가님 판단 거침)

**단점**:
- 작가님 부재 시(다른 세션 대화 중, 외출 등) 대응 불가
- 매번 ad-hoc 승인으로 일관성 부족 (같은 유형의 긴급 상황도 매번 개별 판단)
- 기록 체계 미비 (현재 세션 로그에 `[예외]` 태그 0건 — 실질적으로 기록되지 않음)
- 에이전트 수 증가 시 병목 심화

| **트리거** | 위임장에 명시된 조건 충족 시 (예: "카드사 심사 관련 UI 수정은 막내 자율 배포 가능") |
| **절차** | 위임장 발행(작가님) → 조건 충족 판단(막내) → 실행 → `[위임]` 태그 기록 → 주간 리뷰 |
| **승인** | 위임장 발행 시 1회 사전 승인. 이후 건별 승인 불요 |
| **참고 패턴** | 법률 체계 (직무대리규정: 특정 범위를 사전 지정하여 위임) |

- 위임 범위가 명확하여 오판 위험 감소
- 매건 승인 부담 없음

**단점**:
- 위임장에 포함되지 않은 유형의 긴급 상황에는 대응 불가
- 위임장 갱신/폐기 관리 비용
- 법률 개정 범위: ch7에 위임장 제도 조항 신설

## 2. 역할 대행 체계 선택지 (어젠다 #7)

**현안**: 헌법 5조(에이전트 역할 체계)에 "대행" 개념이 부재. 쌍아 부재 시 다른 에이전트가 역할을 수행할 수 있는 메커니즘 없음.

### 옵션 A: 고정 승계 순위 (쌍아 부재 → 철창이 자동 대행)

| 항목 | 내용 |
|------|------|
| **개요** | 헌법 5조에 각 역할의 승계 순위를 사전 정의 |
| **승계 순서 예시** | 쌍아(설계+지시서) 부재 → 1순위 철창이, 2순위 작가님 직접. 막내 부재 → 다른 막내 자동 인수 |
| **발동 조건** | 해당 에이전트 세션이 비활성(작가님이 다른 세션 사용 중) 또는 컨텍스트 소진 |
| **대행 범위** | 전체 역할 대행 (원직자와 동일 권한) |
| **참고 패턴** | 군사 체계 (최선임자 자동 승계), 한국 헌법 71조 (국무총리 → 부총리 순서) |

**장점**:
- 발동 시 판단 불필요 (자동 승계)
- 공백 시간 최소화
- 심플한 규칙

**단점**:
- 철창이(전략 전문)가 쌍아(설계+지시서) 역할을 수행하는 적합성 문제
- 전문성 불일치 시 품질 저하 (군사에서는 동일 훈련을 받은 인력이 승계하지만, 에이전트는 역할 특화)
- 승계 순위 변경 시 헌법 개정 필요
- 법률 개정 범위: 헌법 5조에 승계 순서 추가 (헌법 개정 = 5인 만장일치 필요)

### 옵션 B: 작가님 지명제 (매건 작가님이 대행자 지정)

| 항목 | 내용 |
|------|------|
| **개요** | 대행 필요 시 작가님이 해당 세션에서 직접 대행자를 지명 |
| **발동 조건** | 작가님이 특정 에이전트 세션에서 다른 역할 수행을 지시 |
| **대행 범위** | 작가님이 지명 시 범위를 명시 (전체 대행 또는 특정 기능만) |
| **참고 패턴** | 기업 거버넌스 (이사회가 매건 Acting CEO 지명), 군사 지명제 (지휘관이 후임자 직접 지명) |

**장점**:
- 작가님의 완전한 통제 유지
- 상황에 맞는 최적의 대행자 선택 가능
- 헌법 개정 불필요 (현행 "작가님=총괄" 권한으로 해석 가능)

**단점**:
- 작가님 자체가 부재할 경우 발동 불가 (모든 에이전트의 근본 의존)
- 매건 판단 부담
- 현행 어젠다 #7 사례와 동일 (이미 이 방식으로 처리됨, 체계화만 필요)
- 법률 개정 범위: ch1에 대행 지명 절차 추가 (법률 개정)

### 옵션 C: 기능별 분리 (전략=고유, 설계/지시서=작가님 직접만)

| 항목 | 내용 |
|------|------|
| **개요** | 역할을 "고유 기능"과 "위임 가능 기능"으로 분리. 고유 기능은 대행 불가, 위임 가능 기능만 대행 허용 |
| **분리 예시** | 쌍아 고유: 전략 설계, 법률 해석. 위임 가능: 지시서 작성, 배포 지휘. 철창이 고유: 전략 대화. 위임 가능: 리서치, 분석 보고 |
| **발동 조건** | 원직자 부재 시, 위임 가능 기능에 한해 작가님이 다른 에이전트에게 직접 지시 |
| **대행 범위** | 위임 가능 기능만. 고유 기능은 원직자 복귀까지 보류 |
| **참고 패턴** | 한국 대통령 권한대행 제한설 (국가기능 유지에 필수적인 범위만), 기업 (운영적 vs 전략적 사항 분리) |

**장점**:
- 역할 정체성 보존 (철창이가 쌍아 "행세"를 하지 않음)
- 전문성 미스매치 위험 최소화
- 대행 범위가 명확하여 혼란 감소
- 한국 대통령 권한대행 다수설과 동일 패턴

**단점**:
- "고유"와 "위임 가능"의 경계를 정의하기 어려움
- 고유 기능 보류 시 해당 업무 공백 발생
- 법률 개정 범위: 헌법 5조 역할 정의에 "고유/위임 가능" 구분 추가 (헌법 개정)
- 실제 긴급 상황에서 "이건 고유 기능인가 위임 가능인가" 판단 오버헤드

### 옵션 D: 비상 모드 (Emergency Mode)

| 항목 | 내용 |
|------|------|
| **개요** | 긴급 상황 선언 시 역할 구분을 임시 해제하고, 작가님이 가용한 에이전트에게 직접 지시 |
| **발동 조건** | 작가님이 "비상 모드" 선언 |
| **대행 범위** | 비상 모드 동안 에이전트 역할 구분 임시 해제. 작가님 지시에 따라 모든 에이전트가 모든 업무 수행 가능 |
| **종료** | 작가님이 "비상 해제" 선언 또는 24시간 자동 만료 |
| **참고 패턴** | 소프트웨어 Break-glass (정상 통제 임시 해제, 사후 심사), ICS (인시던트 규모에 따라 역할 재배분) |

**장점**:
- 가장 유연한 대응 (어떤 상황에서도 대응 가능)
- 간단한 규칙 (선언/해제만)
- 소규모 팀에 적합 (에이전트 5명 내외)

**단점**:
- 역할 체계의 근본 가치를 일시적이나마 부정
- 비상 모드가 관행화되면 역할 체계 유명무실화 위험
- 사후 심사로 남용 방지해야 함
- 법률 개정 범위: 헌법 5조에 비상 모드 조항 추가 (헌법 개정)

## 3. 부대 고려사항

### 3-1. 예외 기록 체계 정비 (두 선택지 공통 전제)

어떤 옵션을 선택하든, **예외 기록의 정본 위치** 정비가 선행 필요:

| 현행 | 필요 |
|------|------|
| 세션 로그 `[예외]` (규정) but 실제 0건 | 기록 정본 1곳 확정 + 추적 가능한 태그 |
| Git 커밋 (관행) | 커밋 메시지 형식 표준화 |
| 지시서 `[예외]` (ch7 1조) | 지시서 없는 긴급 예외의 기록 방법 |
