### 후보별 상세 분석

#### A. SwiftUI 네이티브 (IDPASS 확장) — ⭐ 추천

**개념:** 기존 MonkosCrop(크롭 앱)에 AI 증명사진 생성 기능을 추가.

**작업 범위:**
- [신규] 카메라 촬영 UI (AVFoundation + AVCaptureSession)
- [신규] Gemini Live WebSocket 코칭 (URLSessionWebSocketTask)
- [신규] AI 생성 API 호출 (URLSession → 백엔드 `/api/idgen`)
- [신규] StoreKit 2 IAP ($1.99/컷)
- [신규] OAuth 로그인 (ASWebAuthenticationSession + Sign in with Apple)
- [신규] 결과 화면 + 워터마크 프리뷰 + 다운로드
- [기존 활용] 규격 선택 (202개국), 얼굴 감지, 배경 제거, ICAO 크롭 — 전부 재사용

**왜 6-8주인가 (10-12주가 아닌 이유):**
1. MonkosCrop에 이미 핵심 이미지 처리 파이프라인 완성 (크롭·배경제거·얼굴감지)
2. 백엔드 서버 그대로 유지 — iOS는 API 클라이언트만 구현
3. StoreKit 2는 SwiftUI와 직접 통합 (`ProductView`, `.onPurchase`)으로 구현 단순
4. WebSocket은 Foundation 네이티브 (`URLSessionWebSocketTask`) — 라이브러리 불필요

**리스크:**
- ContentView 1,900줄 — AI 기능 추가 시 구조 분리 필요 (MVVM 전환 또는 탭 분리)
- 웹 프롬프트 로직(`buildPromptV5`)을 서버에 유지하면 iOS는 파라미터만 전송 → 서버 의존

#### B. WKWebView 하이브리드

**개념:** 웹앱을 WKWebView로 감싸고, IAP 브릿지만 네이티브로 구현.

**치명적 문제 — App Store 리젝 고위험:**
- **4.2 Minimum Functionality**: "Your app should include features, content, and UI that elevate it beyond a repackaged website." 웹뷰 래핑 앱은 Apple이 가장 엄격하게 심사하는 유형
- **3.1.1 IAP**: WKWebView 내에서 토스페이먼츠/Lemon Squeezy 결제 감지 시 즉시 리젝. IAP 브릿지만으로는 "네이티브 기능"으로 인정받기 어려움
- **카메라**: WKWebView에서 `getUserMedia`는 iOS 14.3+부터 지원하나, 권한 프롬프트가 이중으로 뜨고 인앱 브라우저 제약과 유사한 UX 문제 발생
- **OAuth 팝업**: WKWebView에서 `window.open` 팝업 기반 OAuth가 정상 작동하지 않음. 커스텀 WKUIDelegate 필요

**결론: 빠르지만 App Store 리젝 가능성이 너무 높아 권장하지 않음.**

#### C. React Native

**개념:** React Native로 새 앱 작성.

**근본적 비효율:**
- 현재 웹앱은 **바닐라 JS** (React 아님) → React 컴포넌트 재사용 불가
- MonkosCrop은 **SwiftUI** → RN에서 재사용 불가
- 사실상 0에서 새로 작성하는 것과 동일, 두 기존 자산 모두 버림
- RN 카메라 모듈(`react-native-vision-camera`) + WebSocket + IAP(`react-native-iap`) 조합의 안정성 이슈
- Vision 프레임워크 (배경제거, 얼굴감지) 접근에 네이티브 모듈 브릿지 필요

**결론: 기존 자산 재활용률 최하. SwiftUI가 이미 있는데 RN을 선택할 이유 없음.**

#### D. PWA + Safari

**개념:** 웹앱을 PWA로 만들어 홈 화면 추가.

**구조적 불가:**
- **App Store 배포 불가** → Apple IAP 사용 불가 → $1.99/컷 과금 구조 구현 불가
- 웹 결제(토스/Lemon Squeezy)만 가능하지만, 이 경우 "iOS 앱 전환"이라는 목표 자체가 무의미
- 푸시 알림 제한 (iOS PWA는 2023년부터 지원하나 제약 많음)
- 카메라 접근 제한 (Safari getUserMedia는 동작하나 네이티브 대비 품질·안정성 열위)

**결론: $1.99 IAP 요구사항을 충족할 수 없어 후보에서 제외.**

#### E. Capacitor/Ionic

**개념:** 기존 웹앱을 Capacitor로 래핑, 네이티브 플러그인으로 카메라·IAP 접근.

**장점:**
- 웹 코드 70-80% 재사용 (monk.js, config.js, shared.js, 각 페이지 JS)
- `@capacitor/camera` 플러그인 → 네이티브 카메라 접근
- `@capawesome-team/capacitor-purchases` (RevenueCat 기반) → IAP 구현 가능
- WKWebView 기반이지만 네이티브 플러그인이 있어 4.2 리젝 리스크 B보다 낮음

**리스크:**
- 여전히 WKWebView 기반 → Apple 심사에서 "래핑 앱"으로 분류될 수 있음
- `monk.js` 마이크로 프레임워크의 Capacitor 환경 호환성 미검증
- WebSocket (Gemini Live)은 동작하나, 카메라 프레임을 Capacitor 레이어를 통해 전송하는 부분에서 성능 이슈 가능
- MonkosCrop 자산 활용 불가 (웹 기반이므로)
- IAP 커뮤니티 플러그인 안정성 불확실

**결론: B보다 나은 현실적 타협안이지만, A 대비 UX·심사 안정성 열위.**

2. **App Store 심사 안전**: 네이티브 앱은 4.2 리젝 리스크 최소. WebView 래핑(B/E)은 Apple 정책상 고위험
3. **IAP 최적 경로**: StoreKit 2 + SwiftUI 직접 통합. `ProductView`, `Product.purchase()`, `Transaction.updates` — 서드파티 라이브러리 불필요
4. **카메라 품질**: AVFoundation은 WebRTC 대비 해상도·포커스·노출 제어 우위. 증명사진 앱에서 카메라 품질은 핵심
5. **이미 있는 기술 스택을 버릴 이유 없음**: React Native(C)는 기존 바닐라 JS·SwiftUI 모두 못 쓰고 처음부터 작성. 가장 비효율적
