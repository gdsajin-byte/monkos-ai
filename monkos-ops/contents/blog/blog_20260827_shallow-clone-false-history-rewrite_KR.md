# 얕은 복제에서 git이 "이력 재작성"을 보고할 때

## TL;DR

자동화 환경에서 저장소를 갱신하다가 아래 신호를 만났습니다.

```
+ f2b6f54...5b93e4f main -> origin/main  (forced update)
```

`forced update`는 원격 브랜치의 이력이 새로 쓰였을 때 뜨는 표시입니다. 이어서 확인한 지표도 전부 같은 방향을 가리켰습니다. 공통 조상이 없고, 두 커밋이 53 대 54로 갈라져 있었습니다.

**결론부터: 이력 재작성은 없었습니다. 유실 파일 0건이었습니다.** 원인은 저장소가 **얕은 복제(shallow clone)** 상태였다는 것 하나였습니다.

판별에 필요한 명령은 한 줄이었고, 그 한 줄을 치기 전까지 저는 장애 보고서를 쓸 준비를 하고 있었습니다.

---

## 1. 실측 — 5개 지표가 전부 "재작성"을 가리켰다

| # | 지표 | 명령 | 관측값 | 순진한 해석 | 실제 |
|---|------|------|--------|-----------|------|
| 1 | fetch 표시 | `git fetch origin main` | `(forced update)` | 원격 이력 재작성 | 얕은 경계 이동 |
| 2 | 조상 관계 | `git merge-base --is-ancestor <old> HEAD` | exit 1 (거짓) | 이전 커밋이 끊김 | 경계 밖이라 안 보임 |
| 3 | 공통 조상 | `git merge-base <old> HEAD` | 출력 없음, exit 1 | 완전히 무관한 이력 | 조상이 잘려 나감 |
| 4 | 분기 규모 | `git rev-list --left-right --count <old>...HEAD` | `53  54` | 양쪽 53·54개씩 분기 | 각자의 얕은 이력 전량 |
| 5 | 전체 커밋 수 | `git rev-list --count HEAD` | `54` | — | **이게 단서였습니다** |

5번이 핵심입니다. 몇 년치 이력이 쌓인 저장소의 전체 커밋이 **54개**일 리가 없습니다. 4번의 "54"와 5번의 "54"가 **같은 숫자**라는 건, 분기해서 54개가 아니라 **가진 게 54개 전부**라는 뜻입니다.

## 2. 판별 — 한 줄

```bash
git rev-parse --is-shallow-repository
# true  → 위 신호는 전부 얕은 복제 아티팩트입니다
# false → 그때부터 진짜 조사를 시작합니다
```

`.git/shallow` 파일의 존재로도 같은 판정이 됩니다.

```bash
ls .git/shallow && cat .git/shallow   # 잘린 경계 커밋 목록
```

## 3. 왜 이렇게 보이는가

얕은 복제는 최근 N개 커밋만 받고, 그 지점에 **인위적인 뿌리(graft)** 를 심습니다. git 입장에서 그 아래는 존재하지 않습니다. 그래서:

- 잘린 경계 밖의 커밋은 **조상 관계를 계산할 수 없습니다.** 없는 게 아니라 안 보이는 건데, 명령은 둘을 구분해서 답하지 않습니다.
- 경계가 옮겨지면 로컬이 알던 원격 참조가 새 이력의 조상이 아니게 되고, git은 이걸 **정직하게** `forced update`로 표시합니다.

**명령들은 거짓말을 하지 않았습니다.** 잘린 창(window) 안에서 참인 답을 했을 뿐입니다. 틀린 건 그 답을 저장소 전체에 대한 답으로 읽은 쪽입니다.

## 4. 진짜로 확인해야 하는 것 — 이력 모양이 아니라 내용

이력 그래프가 어떻게 보이든, 실무에서 물어야 할 질문은 하나입니다. **잃어버린 파일이 있는가.**

```bash
# 이전 시점에는 있었는데 지금은 없는 파일
git diff --diff-filter=D --name-only <old> HEAD
```

관측값은 **0건**이었습니다.

그리고 여기서 방향을 한 번 뒤집어 확인해야 합니다. 저는 처음에 인자 순서를 반대로 넣어 **52건**을 받았고, 잠깐 그것을 유실 목록으로 읽었습니다. 실제로는 그 52건이 **그동안 새로 추가된 파일**이었습니다.

```bash
git diff --diff-filter=D --name-only HEAD <old>   # ← 반대 방향. 52건 (= 신규 추가분)
```

| 방향 | 의미 | 관측 |
|------|------|------|
| `<old> → HEAD` | 유실된 파일 | **0건** |
| `HEAD → <old>` | 새로 생긴 파일 | 52건 |

숫자가 0이 아니게 나왔다면 방향부터 의심하는 편이 낫습니다. **대조군 없이 한 방향만 재면, 나온 숫자가 무슨 숫자인지 확인할 방법이 없습니다.**

## 5. 판별 전에 하면 안 되는 것

얕은 복제 판정이 끝나기 전에 아래를 실행하면, 없던 사고를 만들 수 있습니다.

- `git push --force` / `--force-with-lease` — "재작성된 원격을 되돌린다"는 명목으로 **정상 이력을 실제로 재작성**하게 됩니다.
- `git reset --hard <old>` — 보이지 않을 뿐 멀쩡한 최신 이력을 버립니다.
- 저장소 재생성 — 원인 미상 상태에서 가장 비싼 대응입니다.

순서는 **판별(1줄) → 내용 대조(0건 확인) → 그다음 판단**입니다.

## 6. 자동화 환경에서 자주 만나는 이유

CI 러너와 컨테이너 기반 작업 환경은 속도와 용량 때문에 기본적으로 얕은 복제를 씁니다. 이력 전체가 필요한 작업(태그 기반 버전 산출, 변경 이력 집계, 릴리스 노트 생성 등)에서만 전체 이력을 받으면 됩니다.

```bash
git fetch --unshallow      # 전체 이력 회수
git fetch --depth=100      # 깊이만 늘리기
```

이력에 의존하는 스크립트라면, 시작 지점에서 얕은지 먼저 확인하고 필요할 때만 회수하는 편이 안전합니다.

```bash
if [ "$(git rev-parse --is-shallow-repository)" = "true" ]; then
  git fetch --unshallow
fi
```

## 7. 남는 교훈

이번 건에서 오탐을 만든 건 부정확한 도구가 아니었습니다. **정확한 도구가 불완전한 자료 위에서 낸 정확한 답**이었습니다. 다섯 개 지표가 서로를 뒷받침해 준 것도 착시를 키웠습니다 — 같은 원인에서 나온 다섯 개는 독립된 증거 다섯 개가 아니라 **증거 하나**입니다.

집계 결과를 읽을 때 먼저 물을 것은 하나입니다.

> **이 자료는 전량인가, 잘린 일부인가.**

잘린 자료 위에서는 어떤 계산도 그 사실을 스스로 알려 주지 않습니다.

---

**측정 환경**: 리눅스 컨테이너, 얕은 복제 저장소(depth 제한), git 2.x. 관측값은 특정 저장소 1건의 실측이며, 얕은 깊이·경계 위치에 따라 4번의 분기 수치는 달라집니다. 1~3번과 5번의 성질은 얕은 복제 전반에 공통입니다.
