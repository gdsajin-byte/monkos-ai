> 클라이언트 완결형 증명사진 크롭 서비스가 탄생하기까지의 기술 여정

## 1. 왜 만들었는가

증명사진 시장에는 "사진을 규격에 맞춰 잘라주고 돈을 받는" 앱들이 넘쳐난다. 단순한 크롭인데도 결제를 요구한다. MONKOS는 이 문제를 다르게 접근했다.

**핵심 전략**: 크롭 기능을 완전 무료로 제공하되, 서버 비용을 제로로 만든다. 모든 연산을 사용자 디바이스에서 처리한다. 사진이 디바이스 밖으로 나가지 않으므로 프라이버시도 완벽히 보호된다.

이 앱은 MONKOS AI 증명사진 서비스의 **전초 기지**(유입)이자 **후방 서비스**(다운로드 후 활용)로 설계되었다. 사용자가 직접 크롭한 사진과 MONKOS AI 보정 결과를 비교하는 순간이 전환 트리거다.

| 구분 | 경쟁 크롭앱 | MONKOS Crop |
|------|-----------|-------------|
| 가격 | 유료 | **완전 무료** |
| 서버 | 있음 (사진 전송) | **없음** (디바이스 처리) |
| 프라이버시 | 사진 서버 전송 | **디바이스에서만 처리** |
| 규격 검증 | 기본 | **ICAO 기준 3단계 실시간 판정** |

## 3. 아키텍처 진화 — 3단계

### v0 — 서버 LLM 크롭 (03-10)

**접근**: Gemini 2.0 Flash에게 얼굴 좌표 4개(이마 상단, 턱, 좌눈, 우눈)를 물어보고, 역산으로 크롭 영역을 계산한다.

```
[서버] 이미지 → Gemini Flash → 좌표 4개 → cropToSpec → sharp 크롭
```

**문제**:
- LLM은 본질적으로 "대략적인 위치"를 알려줄 뿐, 픽셀 단위 정밀도를 보장하지 않는다
- 좌표에서 크롭 영역을 역산하는 구조적 결함: `cropH > srcH`이면 턱이 잘리고, 비율이 왜곡된다
- **사진관 워크플로우와 정반대**: 사진에서 프레임을 만들어내는 방식이었다

실제 사진관에서는 "고정된 규격 프레임에 사진을 맞추는" 방식이다. 가이드 프레임이 먼저이고, 사진의 스케일과 위치를 조정한다.

**성과**: 외교부 규격(얼굴 길이 3.2~3.6cm / 45mm = 71~80%) 적용, QC 모델 통일(Gemini 2.0 Flash 단일). 서버 크롭의 한계를 명확히 드러냄으로써 아키텍처 전환의 근거를 마련했다.

### v1 — crop-engine 재설계 (03-11)

**접근**: LLM 좌표를 버리고, TensorFlow.js FaceMesh(478 랜드마크)로 얼굴을 정밀 감지한다. Cloud Run 독립 마이크로서비스로 설계한다.

```
monkos_AI/crop-engine/
├── server.js          # Express API
├── lib/
│   ├── face-detect.js # tfjs FaceMesh 모듈
│   └── crop.js        # 가이드 프레임 기반 크롭
├── specs/formats.js   # 국가별 규격 정의
└── Dockerfile
```

**핵심 설계 결정**:

1. **눈 앵커 기반 배치**: 눈 위치를 프레임의 43% 지점에 앵커링. 얼굴 크기 33mm 타겟.
2. **해부학적 정수리 추산**: 눈~턱 거리를 1:1로 반전하여 정수리 위치를 추산. (눈~정수리 ≈ 눈~턱 — 해부학적 근사)
3. **조건부 보정 알고리즘**: 헤어탑 잘림 → 밀기 → 하단 부족 → 축소(32mm까지) 순서의 안전장치

**tfjs 백엔드 선정 과정**:

| 백엔드 | 결과 |
|--------|------|
| `tfjs-node` | Node.js 20+ `util.isNullOrUndefined` 제거 + Transform 커널 미등록 → **불가** |
| `tfjs-backend-wasm` | BatchMatMul non-float32 미지원 → **불가** |
| `tfjs CPU` (pure JS) | **동작 확인, 742ms/장** |

CPU 백엔드에서 478 랜드마크 감지가 742ms/장으로 동작했다. 규격 튜닝 결과 얼굴 크기 33.0mm를 정확히 히트했다.

**문제**: 서버 사이드 크롭은 콜드스타트, 비용, 프라이버시 세 가지 문제를 근본적으로 해결하지 못한다.

### v2 — 클라이언트 완결 (03-12)

**전환 계기**: v1의 서버 크롭 엔진이 동작하는 것을 확인한 후, "이 연산을 브라우저에서 할 수 있다"는 발상이 나왔다. MediaPipe FaceMesh는 브라우저 CDN에서 직접 로드 가능하고, Canvas 2D API로 크롭 출력이 가능하다. 서버가 아예 필요 없다.

```
[브라우저] 사진 업로드 → MediaPipe FaceMesh(CDN) → 478 랜드마크
         → 자동 배치(눈 앵커 43%) → SVG 가이드 오버레이
         → 사용자 미세 조정 → Canvas 2D 크롭 → JPEG 다운로드
```

**결과**:

| 항목 | v0 (서버 LLM) | v1 (서버 FaceMesh) | **v2 (클라이언트)** |
|------|-------------|------------------|------------------|
| 얼굴 감지 | Gemini Flash (좌표 4개) | tfjs FaceMesh (478) | **MediaPipe FaceMesh (478)** |
| 실행 환경 | Cloud Run | Cloud Run | **브라우저** |
| 서버 비용 | 있음 | 있음 | **제로** |
| 프라이버시 | 사진 서버 전송 | 사진 서버 전송 | **디바이스에서만 처리** |
| 레이턴시 | 서버 RTT + 추론 | 서버 RTT + 추론 | **브라우저 내 즉시** |
| 해상도 | sharp 서버 크롭 | sharp 서버 크롭 | **Canvas 2D (원본 해상도 유지)** |
| DPI | 미설정 | 300dpi | **300dpi** |

**개발 집중도**: 03-12 하루 약 8시간 40분(10:30~19:16) 집중 개발. 같은 날 JP(일본) 클론까지 완료.

## 4. 기술 상세

### 4-1. 얼굴 감지 — MediaPipe Face Mesh

브라우저에서 CDN으로 로드되는 MediaPipe Face Mesh를 사용한다. 478개 랜드마크 중 핵심 5개를 추출한다.

| 용도 | 랜드마크 인덱스 | 설명 |
|------|---------------|------|
| 좌눈 중심 | #159 | 눈 위치 앵커 (좌) |
| 우눈 중심 | #386 | 눈 위치 앵커 (우) |
| 턱 최하단 | #152 | 얼굴 하단 기준점 |
| 좌측 윤곽 | #234 | 좌우 폭 |
| 우측 윤곽 | #454 | 좌우 폭 |

정수리는 랜드마크로 직접 측정할 수 없으므로, **해부학적 근사**로 추산한다:

```
crownY = eyeCenterY - (chinY - eyeCenterY)
```

눈~턱 거리를 1:1로 반전하면 정수리 위치가 나온다. 이 방식은 대부분의 성인 정면 사진에서 충분한 정확도를 보인다.

### 4-2. 자동 배치 알고리즘 — autoPlace

FaceMesh로 감지된 랜드마크를 기반으로 사진의 스케일과 위치를 자동 결정한다.

```
1. 눈 위치 실측 (FaceMesh #159, #386 중점)
2. 정수리 추산: crownY = eyeY - (chinY - eyeY)
3. 스케일: 얼굴(정수리~턱)이 faceTarget(mm)에 맞도록 계산
4. 위치: 눈을 프레임 43% 지점에 앵커링
5. 좌우: 얼굴 중심이 프레임 수평 중앙에 오도록 보정
```

### 4-3. 규격 데이터

```javascript
const SPECS = {
  passport: {
    wMm: 35, hMm: 45,
    faceMin: 32, faceMax: 36, faceTarget: 34,
    pxW: 413, pxH: 531  // 300dpi 기준
  },
  id: {
    wMm: 30, hMm: 40,
    faceMin: 24, faceMax: 32, faceTarget: 28,
    pxW: 354, pxH: 472
  }
};
```

### 4-4. 3단계 색상 판정 — ICAO 기준

규격 적합도를 실시간으로 시각화하는 3단계 색상 체계를 설계했다.

**얼굴 크기 (정수리~턱)**:

| 구간 | 색상 | 의미 |
|------|------|------|
| 33~35mm | 녹색 | 최적 |
| 32~33mm, 35~36mm | 노랑 | 허용 (경계) |
| 32mm 미만, 36mm 초과 | 레드 | 범위 이탈 |

**눈 위치 (프레임 상단 기준)**:

| 구간 | 색상 | 의미 |
|------|------|------|
| 43~45% | 녹색 | 최적 |
| 40~43%, 45~48% | 노랑 | 허용 |
| 40% 미만, 48% 초과 | 레드 | 범위 이탈 |

### 4-5. 다운로드 차단 로직

규격 이탈 사진의 다운로드를 원천 차단하여 사용자 실수를 방지한다.

- **레드 구간 1개 이상** → 다운로드 버튼 비활성화 + 구체적 안내 메시지 표시
- **노랑 구간** → 경고 표시 + 다운로드 허용
- **전체 녹색** → 즉시 다운로드

```
"얼굴 크기 31.2mm — 허용범위(32~36mm) 미달. 사진을 확대하세요."
```

이처럼 수치와 조정 방법을 함께 제시하여, 사용자가 스스로 문제를 해결할 수 있도록 유도한다.

### 4-6. Canvas 크롭 다운로드

다운로드 시 Canvas 2D API로 CSS 트랜스폼(translate + scale)과 object-fit: cover를 정확히 재현하여 원본 해상도 크롭을 생성한다.

```javascript
// CSS transform 재현
ctx.translate(FW / 2 + imgPos.x, FH / 2 + imgPos.y);
ctx.scale(imgScale, imgScale);
ctx.translate(-FW / 2, -FH / 2);

// object-fit: cover 재현
const coverScale = Math.max(FW / natW, FH / natH);
ctx.drawImage(loadedImg, (FW - dw) / 2, (FH - dh) / 2, dw, dh);
```

출력 파일명: `MONKOS_crop_passport_413x531.jpg` (JPEG 95% 품질)

## 5. UX 설계 결정

### 5-1. React 프로토타입 → Vanilla JS 전환

초기 프로토타입은 React(JSX)로 467줄 작성되었다. 하지만 MONKOS의 기술 스택(vanilla HTML + JS)에 맞추고, 빌드 도구 의존성을 제거하기 위해 vanilla JS로 전환했다.

**전환 원칙**:
- `useState` → 변수 + `render()` 함수
- `useRef` → `document.getElementById()`
- JSX → HTML 정적 구조 + JS 동적 갱신
- SVG 오버레이 → HTML에 정적 SVG 선언, JS에서 `setAttribute`로 좌표 갱신

결과적으로 977줄의 crop.js + 380줄의 crop.css + 217줄의 index.html이 되었다. 외부 의존성은 MediaPipe FaceMesh CDN 하나뿐이다.

### 5-2. 3단계 색상 체계 도입 배경

기존 프로토타입은 "통과/불합격" 2단계였다. 하지만 여권 규격에는 "허용 범위" 개념이 있다.

- ICAO 기준 얼굴 길이: 32~36mm (최적 33~35mm)
- 눈 위치: 40~48% (최적 43~45%)

2단계에서는 "32.5mm인데 빨간색"이라는 혼란이 생긴다. 3단계 체계(녹색/노랑/레드)는 "규격 내이지만 경계에 있다"는 정보를 전달한다. 노랑은 "제출 가능하지만 미세 조정을 권장"한다는 의미다.

### 5-3. "사진관 방식" 가이드 프레임

사진관에서 증명사진을 자를 때의 워크플로우를 그대로 디지털화했다.

**사진관 실무**:
1. 고정된 규격 프레임(3.5x4.5cm)이 먼저
2. 프레임 위에 2개의 가이드선: 정수리 상한선 + 턱 허용 하한선
3. 사진의 스케일과 위치를 조정하여 프레임에 맞춤

**MONKOS Crop**:
1. SVG 오버레이로 규격 프레임 + 가이드선 표시
2. FaceMesh가 자동으로 최적 배치 (눈 43% 앵커)
3. 사용자가 정수리 핀 드래그, 사진 이동/스케일로 미세 조정
4. 실시간 수치 피드백 (상단/얼굴/하단/눈위치 mm 표시)

### 5-4. 화이트 모드 전환 이유

초기 크롭앱은 다크 테마였다. 포털(monk.kr) 통합 시 테마를 화이트로 전환했다.

**결정 근거**:
- 포털 전체가 화이트 테마 — 시각적 일관성
- 증명사진 배경이 대부분 밝은 색 — 다크 UI와의 대비가 오히려 방해
- **캔버스 영역만 다크 유지** — 사진 편집 영역은 다크가 표준 (Photoshop, Lightroom 패턴)

```css
:root {
  --bg: #f5f5f5;      /* 전체 배경: 라이트 */
  --surface: #ffffff;   /* 카드/패널: 화이트 */
}
.frame-container {
  background: #0a0e17;  /* 캔버스만 다크 유지 */
}
```

### 5-5. 모바일 edge-to-edge

모바일에서 카드형 레이아웃의 좌우 여백은 화면 활용도를 떨어뜨린다. 700px 이하에서는 앱 컨테이너가 전체 너비를 채우도록 했다.

```css
@media (max-width: 700px) {
  body { padding: 0; }
  .app-container {
    width: 100%;
    border-radius: 0;
    border: none;
    box-shadow: none;
  }
}
```

## 6. 개발 과정의 주요 발견

### 6-1. LLM은 픽셀 정밀 작업에 부적합하다

Gemini 2.0 Flash에게 "이 사진에서 정수리, 턱, 좌눈, 우눈의 좌표를 알려줘"라고 물으면 대략적인 위치를 알려준다. 하지만 증명사진 크롭에서는 1mm 차이가 규격 탈락을 의미한다. LLM의 "대략적" 좌표로는 부족했다.

478 랜드마크를 제공하는 FaceMesh는 완전히 다른 차원의 정밀도를 보여줬다.

### 6-2. 서버가 아예 없는 것이 최선이었다

v1(서버 FaceMesh)가 동작하는 것을 확인한 순간, "이걸 브라우저에서 할 수 없을까?"라는 질문이 나왔다. MediaPipe의 브라우저 CDN이 답이었다. 결과적으로:

- **콜드스타트 문제 소멸**: Cloud Run의 10~30초 콜드스타트가 사라짐
- **비용 제로**: 서버가 없으니 비용도 없음
- **프라이버시 완전 보호**: 사진이 네트워크를 타지 않음
- **레이턴시 최소**: 브라우저 내 즉시 처리

### 6-3. iOS Safari의 다운로드 제약

Canvas `toBlob` 비동기 콜백 내에서 `window.open(blobURL)`을 호출하면 iOS Safari가 팝업으로 차단한다. 사용자 제스처(click)에서 시작되더라도, 비동기 콜백 안에서는 "사용자 의도"로 인식하지 않는다.

**해결**: `<a download>` 방식으로 복귀. iOS에서는 파일 시트를 경유하지만, 다운로드 자체는 정상 동작한다.

### 6-4. 표정 프롬프트의 dead code 문제

MONKOS AI 서비스에서 표정 제어를 위해 `EXPRESSION_PROMPTS` 객체를 정의해두었으나, 실제 프롬프트 빌더(`buildPromptV5`)에서 사용하지 않고 있었다. 정의만 되고 실행되지 않는 dead code였다.

이 발견은 크롭앱 자체와 직접 관련은 없지만, 크롭앱 개발 과정에서 전체 서비스 플로우를 점검하면서 발견된 부산물이다.

### 6-5. 해부학 비율의 한계

"눈~정수리 ≈ 눈~턱 (1:1)" 근사는 대부분의 경우 충분하지만, 이마가 유난히 길거나 짧은 사람, 볼륨 헤어, 대머리 등에서는 편차가 발생한다. 이 때문에 정수리 핀을 사용자가 수동으로 드래그할 수 있도록 했다. 자동 배치는 출발점이고, 최종 조정은 사람의 판단에 맡기는 구조다.
