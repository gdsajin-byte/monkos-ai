# 같은 점수, 다른 병

> 모바일 성능 점수 55와 60. 원인은 서로 관계가 없었다.

---

## 서론

우리 서비스 페이지 네 개를 PageSpeed Insights로 측정했다. 모바일 성능 점수는 55에서 67 사이였고, 가장 큰 지표는 LCP(Largest Contentful Paint)였다. 최악은 31.4초였다.

점수만 보면 같은 병으로 보인다. 분해해 보니 아니었다. 두 페이지가 비슷하게 낮았는데 원인에 공통분모가 없었다. 한쪽은 스크립트 때문이었고 다른 한쪽은 스크립트가 전혀 문제가 아니었다.

결론부터 쓴다. **성능 점수는 증상 이름이지 진단명이 아니다.** 증상이 같다고 처방이 같지 않다.

---

## 1. 측정값

| 페이지 | 모바일 | 데스크톱 | 모바일 LCP |
|---|---|---|---|
| 서비스 홈 | 60 | 77 | 20.3s |
| 규격 안내 (여권·한국) | 55 | 78 | 24.3s |
| 사진관 홈 | 67 | 95 | 5.7s |
| 사진관 안내 페이지 | 55 | 43 | 31.4s |

측정 조건을 먼저 밝힌다. 위 점수는 2026-10-03 측정값이고 **각 1회 실행한 랩 데이터**다. 실사용자 필드 데이터가 아니고, 랩 1회 점수는 실행마다 흔들린다. 그래서 아래 원인 분해는 점수에 기대지 않고 **문서와 응답을 직접 열어 확인한 사실**로만 썼다. 원인 확인은 2026-10-04에 다시 했다.

눈에 걸린 것은 네 번째 줄이다. 데스크톱 43은 모바일 55보다 낮다. 보통은 반대로 나온다. 데스크톱이 더 느린 페이지는 회선이나 기기 탓이 아니라 **문서 구조 탓**일 가능성이 높다.

---

## 2. 첫 번째 원인 — 렌더 차단 스크립트

사진관 안내 페이지의 `<head>`를 열었다. 외부 스크립트 세 개가 `async`도 `defer`도 없이 들어 있다.

| `<head>` 리소스 | 비동기 속성 |
|---|---|
| 분석 태그 | async |
| Tailwind CDN (런타임 빌드) | **없음** |
| MapLibre GL JS | **없음** |
| Lucide 아이콘 | **없음** |

스타일시트도 두 개가 외부 CDN 두 곳에서 온다. 렌더 차단 리소스가 한 문서에 다섯 개다.

여기서 가장 비싼 항목은 용량이 아니라 **성격**이다. Tailwind CDN은 CSS 파일이 아니라 브라우저에서 CSS를 생성하는 스크립트다. 빌드 단계에서 한 번 해도 되는 일을 방문자의 기기가 매번 한다. 방문자가 1,000명이면 같은 계산을 1,000번 한다.

데스크톱이 모바일보다 낮게 나온 이유도 여기서 설명된다. 렌더 차단은 회선이 빨라져도 **순서가 바뀌지 않는다**. 기기가 빨라서 얻는 이득이 직렬 대기 앞에서 깎인다.

처방은 교과서적이다. 런타임 빌드를 빌드 타임으로 옮기고, 지도 라이브러리는 지도가 화면에 들어올 때 불러오고, 아이콘은 쓰는 것만 인라인으로 넣는다.

---

## 3. 두 번째 원인 — 교과서대로 해도 20초

같은 처방을 서비스 홈에 적용하려고 `<head>`를 열었다. 고칠 것이 없었다.

| 항목 | 값 |
|---|---|
| `<head>` 길이 | 2,797자 |
| 렌더 차단 스크립트 | **0개** |
| 외부 스크립트 | 분석 태그 1개 (async) |
| 스타일시트 | 자체 호스팅 1개 |
| preconnect | 2개 |

교과서에서 하라는 것은 다 돼 있다. 그런데 LCP는 20.3초다. "스크립트를 defer하라"는 조언은 이 페이지에서 **고칠 대상이 없다**.

이미지를 셌다. 문서가 참조하는 이미지 9개의 실제 전송 바이트다.

| 이미지 | 전송 바이트 | 형식 |
|---|---|---|
| 인물 샘플 A | **1,675 KB** | **PNG** |
| 인물 샘플 B | 1,580 KB | JPEG |
| 인물 샘플 C | 1,371 KB | JPEG |
| 빌보드 1 | 437 KB | JPEG |
| 빌보드 2 | 377 KB | JPEG |
| 빌보드 3 | 275 KB | JPEG |
| 비교 전 / 후 | 103 / 54 KB | JPEG |
| 로고 | 2 KB | SVG |
| **합계** | **약 5.9 MB** | |

첫 줄이 문제다. **사진을 PNG로 내보냈다.** PNG는 무손실이라 사진에서 JPEG·WebP보다 몇 배 커진다. 1.67MB짜리 인물 사진 한 장이 페이지 전체 예산을 혼자 쓴다. 그리고 이 세 장은 문서 순서상 네 번째에서 여섯 번째, 즉 **첫 화면 근처**에 있다. LCP 후보가 4.63MB짜리 세 장이다.

이미지 태그 13개를 전수로 셌다.

| 검사 항목 | 결과 |
|---|---|
| `loading="lazy"` 보유 | **0 / 13** |
| `width`·`height` 보유 | 1 / 13 |
| `srcset` 보유 | **0 / 13** |
| `<picture>` 사용 | **0건** |

치수가 없으면 브라우저가 자리를 미리 잡지 못해 레이아웃이 밀린다. `srcset`이 없으면 휴대폰이 데스크톱용 원본을 그대로 받는다. 세 가지가 동시에 비어 있다.

---

## 4. 가장 아픈 줄

처방을 쓰려고 "WebP를 도입하라"고 적다가 멈췄다. 저장소를 먼저 셌다.

**WebP 파일이 137개 있었다.** 이미 쓰고 있다.

| 위치 | WebP 파일 수 |
|---|---|
| 규격 안내용 삽화 폴더 | 137 |
| 그 외 전체 | **0** |

도구가 없던 것도, 방법을 몰랐던 것도 아니다. 한 폴더에서 제대로 하고 나머지에 적용하지 않았다. 가장 무거운 이미지 세 장이 정확히 그 "나머지"에 있다.

이쪽이 렌더 차단보다 고치기 어려운 종류다. 렌더 차단은 **모르면 생기는** 결함이고, 이건 **알면서도 한 군데만 하면** 생기는 결함이다. 전자는 배우면 끝나고 후자는 배워도 끝나지 않는다. 적용 범위를 누가 지키는지가 따로 정해져 있지 않으면, 잘한 한 번이 규칙이 되지 않고 예외로 남는다.

---

## 5. 정리

| | 사진관 안내 페이지 | 서비스 홈 |
|---|---|---|
| 모바일 점수 | 55 | 60 |
| 원인 | 렌더 차단 리소스 5개 | 이미지 5.9MB |
| `<head>` 상태 | 문제 있음 | 문제 없음 |
| 일반 처방 적용 시 | 개선됨 | **변화 없음** |
| 성격 | 몰라서 생긴 결함 | 적용 범위가 안 지켜져 생긴 결함 |

두 페이지의 점수 차이는 5점이다. 원인은 겹치지 않는다. 점수가 같다는 이유로 같은 작업 지시를 내리면 한쪽은 고쳐지고 한쪽은 숫자만 그대로 남는다.

측정에서 얻은 것은 점수가 아니라 **점수를 믿지 않을 근거**였다. 점수는 "여기를 열어 보라"는 표지판까지만 해 준다. 그 뒤는 `<head>`를 직접 열고 바이트를 직접 세는 수밖에 없다.

아직 고치지 않았다. 고친 뒤의 숫자는 따로 쓴다. 이 글은 진단까지다.
