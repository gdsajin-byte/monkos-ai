# MONKOS Crop — 서버 없이 ICAO 증명사진을 자르기까지, 8일간 3번의 아키텍처 전환

> 브라우저에서 완결되는 증명사진 크롭 도구. 사진은 디바이스 밖으로 나가지 않는다.

---

## 왜 만들었나

증명사진 크롭 앱 시장에는 이상한 관행이 있다. 기본적인 산술(35×45mm 프레임에 얼굴을 32~36mm로 맞추는 것)에 돈을 받고, 사진을 서버로 전송한다.

MONKOS Crop은 세 가지 원칙으로 출발했다. **완전 무료, 서버 비용 제로, 사진이 디바이스 밖으로 나가지 않는다.**

이 앱은 MONKOS AI 증명사진 서비스의 전초 기지이자 후방 서비스다. 사용자가 직접 크롭한 결과와 MONKOS AI 보정 결과를 비교하는 순간이 전환 트리거가 된다.

---

## 3번의 아키텍처 전환

최종 구조가 처음부터 나온 게 아니다. 근본적으로 다른 세 가지 접근을 거쳤다.

### v0 — LLM에게 물어보기 (3월 10일)

Gemini 2.0 Flash에게 사진을 보내고 얼굴 좌표 4개(이마, 턱, 좌눈, 우눈)를 받아서 크롭 영역을 역산했다.

**실패 원인**: LLM은 "대략적인 위치"를 알려줄 뿐이다. 증명사진에서 1mm 차이는 규격 탈락을 의미한다. 더 근본적인 문제는, 사진에서 프레임을 만들어내는 방식 자체가 뒤집혀 있었다.

실제 사진관에서는 **고정된 규격 프레임에 사진을 맞춘다**. 프레임이 먼저이고, 사진의 스케일과 위치를 조정한다. v0는 이걸 반대로 하고 있었다.

### v1 — 서버 FaceMesh 엔진 (3월 11일)

LLM 좌표를 버리고 TensorFlow.js FaceMesh(478 랜드마크)로 교체했다. Cloud Run 위에 독립 마이크로서비스로 설계.

눈 위치를 프레임의 43% 지점에 앵커링하고, 정수리는 해부학적 근사(`crownY = eyeY - (chinY - eyeY)`)로 추산했다. CPU 백엔드에서 742ms/장으로 동작 확인.

**tfjs 백엔드 삽질기**: `tfjs-node`는 Node.js 20+에서 `util.isNullOrUndefined` 제거로 깨지고, WASM 백엔드는 BatchMatMul non-float32 미지원. 결국 pure JS CPU 백엔드만 동작했다.

정밀도는 해결됐지만 근본 문제가 남았다. Cloud Run 콜드스타트 10~30초, 서버 비용, 그리고 사진이 디바이스를 떠난다는 것.

### v2 — 클라이언트 완결 (3월 12일)

v1이 동작하는 걸 확인한 순간, "이 연산을 브라우저에서 할 수 있지 않나?"라는 질문이 나왔다. MediaPipe FaceMesh는 CDN에서 브라우저로 직접 로드된다. Canvas 2D API로 크롭 출력이 가능하다. 서버가 아예 필요 없다.

```
[브라우저] 사진 업로드 → MediaPipe FaceMesh (CDN, 478 랜드마크)
         → 자동 배치 (눈 43% 앵커) → SVG 가이드 오버레이
         → 사용자 미세 조정 → Canvas 2D 크롭 → JPEG 300dpi 다운로드
```

03-12 하루, 8시간 40분(10:30~19:16) 집중 개발. 같은 날 일본어 클론까지 완료했다.

| 항목 | v0 (LLM) | v1 (서버) | v2 (클라이언트) |
|------|---------|---------|--------------|
| 감지 | Gemini 좌표 4개 | tfjs 478 랜드마크 | MediaPipe 478 랜드마크 |
| 실행 | Cloud Run | Cloud Run | **브라우저** |
| 서버 비용 | 있음 | 있음 | **제로** |
| 프라이버시 | 사진 전송 | 사진 전송 | **디바이스에서만** |
| DPI | 미설정 | 300dpi | **300dpi** |

## 기술 상세

### 얼굴 감지 — 478개 중 5개

MediaPipe FaceMesh가 감지하는 478개 랜드마크 중 핵심 5개만 사용한다.

| 용도 | 인덱스 | 설명 |
|------|--------|------|
| 좌눈 중심 | #159 | 눈 위치 앵커 |
| 우눈 중심 | #386 | 눈 위치 앵커 |
| 턱 최하단 | #152 | 얼굴 하단 기준 |
| 좌측 윤곽 | #234 | 좌우 폭 |
| 우측 윤곽 | #454 | 좌우 폭 |

정수리는 랜드마크로 직접 감지할 수 없다. `crownY = eyeY - (chinY - eyeY)` — 눈~턱 거리를 1:1로 반전하면 정수리 위치가 나온다. 이마가 유난히 길거나 볼륨 헤어인 경우를 위해 정수리 핀을 수동 드래그할 수 있도록 했다. 자동 배치는 출발점이고, 최종 조정은 사람에게 맡기는 구조.

### 핵심 연산

```javascript
getMM()  = FH / spec.hMm           // 프레임 높이 → mm 변환 계수
getFW()  = FH × spec.wMm / spec.hMm // 비례 프레임 폭
faceMm   = (chin.y - crown.y) / MM   // 정수리~턱 실측 mm
eyeRatio = eyeY / FH                 // 눈 위치 비율 (타겟: 0.43)
outScale = spec.pxH / FH             // 프레임 → 출력 픽셀 스케일
```

### 3단계 색상 판정

"통과/불합격" 2단계는 혼란을 준다. 32.5mm인데 빨간색이면 사용자는 "규격 내인데 왜 빨간색이지?"라고 느낀다. ICAO에는 "허용 범위"가 있기 때문이다.

**얼굴 크기**: 33~35mm(녹색, 최적) · 32~33mm/35~36mm(노랑, 허용) · 범위 밖(레드, 이탈)

**눈 위치**: 43~45%(녹색) · 40~43%/45~48%(노랑) · 범위 밖(레드)

레드가 하나라도 있으면 다운로드 버튼이 비활성화되고, 구체적인 조정 안내가 표시된다. "얼굴 크기 31.2mm — 허용범위(32~36mm) 미달. 사진을 확대하세요." 수치와 해결 방법을 함께 제시한다.

### Canvas 크롭 파이프라인

사용자가 보는 화면과 다운로드되는 결과물이 정확히 일치해야 한다. CSS의 `object-fit: cover` + translate/scale 트랜스폼을 Canvas 2D 컨텍스트에서 수학적으로 재현한다.

출력: `MONKOS_crop_passport_413x531.jpg` (JPEG 95%, 300dpi)

### iOS Safari 다운로드 문제

`canvas.toBlob()` 비동기 콜백 안에서 `window.open(blobURL)`을 호출하면 iOS Safari가 팝업으로 차단한다. 사용자 제스처(click)에서 시작했더라도, 비동기 콜백에서는 "사용자 의도"로 인식하지 않는다. `<a download>` 방식으로 해결.

## 개발 과정에서 배운 것

**LLM은 픽셀 정밀 작업에 부적합하다.** Gemini Flash가 알려주는 좌표와 FaceMesh의 478개 랜드마크는 완전히 다른 차원이다. 도구의 성격을 구분해야 한다.

**서버가 아예 없는 것이 최선이었다.** 콜드스타트, 비용, 프라이버시 — 서버를 제거하는 순간 세 문제가 동시에 사라졌다.

**사진관이 원래 옳았다.** 고정 프레임에 사진을 맞추는 방식. 20년 사진관 실무에서 당연했던 워크플로우가 소프트웨어 설계의 정답이었다.
