## 검토 1: 긴급 상황 대응 — 코드 수정 금지가 대응 속도를 치명적으로 저하시키는가?

### 결론: **예외 조항이 필요하다.**

### 분석

현행 체계의 긴급 대응 경로는 ch1 2조 2항(b)에 존재한다:

> 긴급 장애 대응(INCIDENT) 시 → 작가님 → 막내 직접 지시

이 경로는 **막내가 가동 가능하다는 전제**에 서 있다. 그러나 다음 상황이 가능하다:

- 새벽 시간대, 작가님이 모바일(iPhone)에서 장애를 인지
- M1의 iTerm이 닫혀 있거나 막내 세션이 전부 종료된 상태
- Desktop App(민아)만 백그라운드에서 가동 중
- 프로덕션 사이트가 500/404 오류 발생 중

이 시나리오에서 민아가 코드를 수정할 수 없다면:

1. 작가님이 M1으로 이동 → iTerm 실행 → 막내 세션 기동 → 지시 → 실행
2. 또는 민아가 아무것도 못 하고 대기

P0 프로덕션 장애에서 이 지연은 **분 단위로 사용자 경험에 영향**을 미친다.

### 기존 선례

본 개정안의 근간인 "역할 분리" 원칙에도, 체계 내에는 이미 예외 구조가 존재한다:

- **쌍아**: 원칙상 코딩 금지 → "쌍아 직접 실행" 트리거로 예외 (ch1 1조)
- **민아 커밋**: 원칙상 쌍아 경유 → 쌍아 부재 시 작가님 직접 승인으로 예외 (ch1 2조 5항)
- **문서 규격**: 긴급 장애(INCIDENT) 시 최소 필드만으로 허용, 24시간 내 보정 (헌법 3조 3항)

예외 없는 절대 금지는 체계의 다른 부분과 일관성이 떨어진다.

### 제안: 긴급 예외 조항

개정안 권한표에 다음 단서를 추가할 것을 권고한다:

> **긴급 예외**: P0 프로덕션 장애(INCIDENT)에서 코드 수정 권한을 가진 에이전트가 가동 불가할 때, 작가님의 명시적 승인 하에 민아가 최소 범위의 코드 수정을 할 수 있다.
>
> 조건:
> 1. 프로덕션 서비스 장애(사이트 다운, 500 오류 등)가 확인된 상태
> 2. 막내·소넷이 등 코드 수정 권한 에이전트가 가동 불가
> 3. 작가님의 명시적 구두/문자 승인
> 4. 세션 로그에 `[긴급예외]` 태그 기록
> 5. 장애 해소 후 24시간 내 쌍아 사후 리뷰 + INCIDENT 보고서 작성

이 예외는 "쌍아 직접 실행" 트리거와 동일한 설계 패턴(원칙 금지 + 명시적 트리거로 예외)을 따른다.

## 검토 2: 범위 해석 분쟁 — "코드 수정"과 "문서 쓰기"의 경계

### 결론: **경계 사례가 존재하며, 판정 원칙이 필요하다.**

### 모호 사례 분석

| 사례 | "코드 수정"인가? | 근거 |
|------|-----------------|------|
| markdown 보고서 내 코드 블록 | ❌ 아님 | 문서의 설명용 코드. 실행 경로에 영향 없음 |
| `sitemap.xml` 직접 편집 | ✅ 코드 수정 | 빌드 산출물 또는 라우팅에 직접 영향. 배포 체계와 연동 |
| 설정 JSON (`config/*.json`) | ✅ 코드 수정 | 런타임 동작을 변경함 (라우팅, API 엔드포인트 등) |
| CSS/스타일 파일 | ✅ 코드 수정 | 프로덕션 렌더링에 직접 영향 |
| `package.json` 의존성 수정 | ✅ 코드 수정 | 빌드·런타임 동작 변경 |
| SEO 메타데이터 JSON (정적 데이터) | ⚠️ 경계 | 런타임 로직은 아니나, 사이트 출력에 직접 영향 |
| `.env` 파일 | 별도 규정 | 헌법 4조 1항에서 이미 수정 전 승인 필수 |

### 제안: 원칙 기반 판정 기준

열거식(exhaustive list)은 새로운 파일 유형이 등장할 때마다 개정이 필요하므로 비효율적이다. 대신 **원칙 기반 판정 기준**을 제안한다:

> **"코드 수정"의 정의**: 애플리케이션의 런타임 동작, 빌드 결과물, 또는 프로덕션 출력에 영향을 미치는 파일의 변경.
>
> **"문서 쓰기"의 정의**: `monkos-ops/` 산하의 보고서·제안서·세션 로그 등 프로젝트 운영 목적의 문서 작성.
>
> **불확실 시 기본값**: 코드 수정으로 간주하여 지시서 경유.

이 원칙은 구체적 파일 확장자나 경로에 의존하지 않으므로, 새로운 기술 스택이 추가되어도 유효하다.

## 검토 3: 역차별 우려 — 민아에게만 코드 수정을 금지하는 것이 형평성에 문제가 있는가?

### 결론: **역차별에 해당하지 않는다. 다만 코웍이 권한 명확화를 동시에 진행할 것을 권고한다.**

### 분석

현행 체계에서 코드 수정이 금지되거나 제한된 에이전트는 민아만이 아니다:

| 에이전트 | 코드 수정 권한 | 근거 |
|----------|--------------|------|
| **쌍아** | ❌ (트리거 예외만) | ch1 1조 "쌍아 직접 코딩 규칙" |
| **민아** | ❌ (개정안) | 본 개정안 |
| **철창이** | ❌ (물리적 불가) | ch1 1조 "브라우저, 코드 접근 불가" |
| **데몬** | ❌ (전면 금지) | ch1 6조 권한표 |
| **막내** | ✅ 자유 | ch1 1조 "자율 코딩" |
| **소넷이** | ✅ (제한적) | ch1 1조 "모니터링, 경량 자동화" |
| **코웍이** | ⚠️ **미규정** | 역할은 "SPREAD 배포 실행, 전략 보고서"이나 명시적 금지 없음 |

코드 수정은 **역할에 따른 권한 배분**이지 차별이 아니다. 쌍아에게도 동일한 원칙이 적용되며, 작가님의 "각자 잘하는 것을 더 잘하라"(01-08) 철학에 정확히 부합한다.

### 코웍이 파급 효과

다만 **코웍이**의 코드 수정 권한이 현행 ch1에서 명시적으로 규정되어 있지 않다. 코웍이의 정의된 역할("SPREAD 배포 실행, 전략 보고서, 브라우저 기반 채널 운영")은 코드 수정을 내포하지 않으나, 민아와 마찬가지로 "읽기·쓰기" 해석의 여지가 남는다.

민아 권한만 명확화하고 코웍이를 방치하면, 동일한 해석 분쟁이 코웍이에서 재발할 수 있다.

### 제안

본 개정 시 **코웍이의 코드 수정 권한도 동일 원칙으로 명확화**할 것을 권고한다. 코웍이 권한표를 ch1 1조에 신설하거나, 민아 권한표 개정 시 "코웍이 준용" 조항을 추가하는 방식이 적합하다.

## 검토 4: 대안 — 경미한 수정(5줄 이하) 예외를 둘 근거가 있는가?

### 결론: **경미한 수정 예외를 두지 않을 것을 권고한다.**

### 반대 근거

**1. 이번 사건 자체가 반례이다.**

민아의 수정은 기술적으로 양호했다(P0·P1 합격). 문제는 코드 품질이 아니라 **P2의 설계사항 3건**(slug 역산, Firestore 인덱스, 캐싱)이 지시서 경유 시 사전 포착되었을 항목이라는 점이다. 이 3건은 "5줄 이하"의 경미한 변경 안에 숨어 있었다.

줄 수는 변경의 복잡도나 설계 영향을 예측하는 신뢰할 수 있는 지표가 아니다.

**2. 작가님 핵심 원칙과 충돌한다.**

> "지시서 체계는 능력의 제약이 아니라 맥락의 축적 장치다."

지시서 체계의 가치는 **코드 품질 게이트키핑이 아니라 의사결정 궤적의 문서화**에 있다. 1줄 수정이라도 "왜 이 수정이 필요했고, 누가 판단했고, 어떤 맥락에서 실행되었는가"가 기록되어야 한다. 경미한 수정 예외는 이 궤적에 구멍을 만든다.

**3. 미끄러운 경사면(slippery slope) 위험.**

"5줄 이하"라는 기준은:
- 측정이 자의적이다 (5줄? 10줄? 함수 하나?)
- 예외가 관례화되면 "이 정도는 경미하다"는 판단이 점진적으로 확대된다
- 쌍아의 "직접 실행" 트리거와 달리, 줄 수 기준은 **실행 전에 정확히 판정하기 어렵다** (수정을 시작해봐야 몇 줄인지 안다)

**4. 절차 부담이 실제로는 경미하다.**

민아 → 1문단 제안서 → 작가님 승인 → 막내 실행. 이 경로의 추가 비용은:
- 민아: 제안서 작성 (이미 진단 보고서를 쓰는 과정에서 자연스럽게 생성됨)
- 작가님: 승인 한 마디
- 막내: 지시 수신 후 실행

이미 이번 사건에서 민아가 제안서를 작성한 바 있으며, 그 과정이 과도한 부담이 아님이 실증되었다.

### 유일한 고려 가치가 있는 대안

경미한 수정 예외 대신, **검토 1에서 제안한 긴급 예외 조항**이 "빠른 대응"의 합리적 필요를 충분히 커버한다. 일상적 업무에서의 편의는 절차 간소화(제안서 양식 경량화 등)로 해결할 수 있으며, 예외 조항의 확대로 해결할 문제가 아니다.
