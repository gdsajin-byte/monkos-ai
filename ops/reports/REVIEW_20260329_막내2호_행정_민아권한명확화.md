1. 개정 후 민아 일상 워크플로우에 행정적 병목이 생기는가?

## 1. 워크플로우 병목 검토

### 현행 vs 개정안 핸드오프 비교

| | 현행 (ch1 2조 5항) | 개정안 |
|---|---|---|
| 경로 | 작가님→민아 실행→보고→쌍아 사후 보정 | 민아 CDP진단→제안서→쌍아 설계검토→지시서→막내 실행→민아 검증 |
| 핸드오프 수 | **1회** (실행→보정) | **3회** (제안서→설계검토→지시서→실행) |
| 세션 경계 횡단 | 1회 | 최소 2~3회 |

### 판정: 병목은 발생하나, 의도된 설계이다

핸드오프가 3배 증가한다. 이것은 사실이다. 그러나 이 병목은 "맥락 축적 장치"라는 핵심 원칙의 직접적 비용이며, 작가님이 의도한 트레이드오프이다.

**단, 실무적으로 병목을 완화할 수 있는 지점이 있다:**

- **P0/P1급 버그 수정**(이번 JA 404 같은 건): 민아 제안서의 해결 방향이 명확하고, 쌍아가 설계 검토 후 지시서로 변환하는 과정이 실질적으로 "제안서를 지시서 포맷으로 감싸는" 작업에 가까움. 이 경우 쌍아가 제안서를 수신하고 **동일 세션 내에서** 지시서로 변환·하달하면 병목이 최소화됨.
- **P2급 신규 기능**: 설계 사항이 실재하므로(이번 건의 slug 역산, Firestore 인덱스, 캐싱 등) 핸드오프 비용이 정당화됨. 민아 제안서 → 쌍아 설계 보강 → 지시서의 경로가 P2의 설계 품질을 실제로 올린다.

**행정적 권고**: 개정안 본문에 "쌍아가 제안서를 수신한 세션 내에서 지시서 변환이 가능하면 즉시 하달한다"는 운영 지침을 부기할 것을 권고. 이는 절차를 완화하는 것이 아니라, 절차 이행 속도를 현실적으로 규정하는 것.

## 2. 문서 흐름과 ch4 정합성 검토

### 발견 사항: PROPOSAL 유형이 ch4에 미등록

**이것이 본 행정 심사의 핵심 발견이다.**

개정안의 민아 워크플로우는 **PROPOSAL(제안서)**을 핵심 산출물로 전제한다:

```
민아 CDP 진단 → [PROPOSAL 작성] → 쌍아 설계 검토 → 지시서 → 막내 실행
```

그런데 PROPOSAL은 현행 ch4에서 다음이 **모두 누락**되어 있다:

| ch4 조항 | 등록 여부 | 상태 |
|----------|----------|------|
| 3조 파일 네이밍 규칙 (15종 패턴) | **미등록** | PROPOSAL 패턴 없음 |
| 4조 정본 위치 테이블 | **미등록** | `ops/proposals/` 미기재 |
| 7조 YAML type 허용값 | **미등록** | `proposal` 없음 (현행: order, report, spec, incident, design, sprint, petition, research, completion, review, agenda, portfolio) |

한편 ch4 9조(PF 운용 규칙)에서는 PROPOSAL을 이미 참조하고 있다:
- 9조 1항: "기안(PROPOSAL) 승인 시, PF 신규 생성..."
- 9조 4항: "PROPOSAL은 PF 승격 후에도 `ops/proposals/`에 영구 보존"

**실태**: `monkos-ops/ops/proposals/`에 이미 17건의 PROPOSAL 파일이 존재. 민아 단독으로 7건을 발행.

**문제**: PROPOSAL이 사실상(de facto) 운용되고 있으나, 법적(de jure) 등록이 없다. 이 상태에서 개정안이 "민아 → 제안서 → 승인 → 막내 실행"을 정식 워크플로우로 선언하면, **법적 근거 없는 문서 유형이 핵심 절차의 필수 산출물이 되는 모순**이 발생한다.

**행정적 권고**: ch1 개정과 동시에 ch4에 PROPOSAL을 정식 등록해야 한다:

```
[ch4 3조] 패턴 추가:
| 16 | `PROPOSAL_YYYYMMDD_{agent}_{topic}.md` | `monkos-ops/ops/proposals/` | `PROPOSAL_20260329_민아_SEO검색노출_수정제안서.md` |

[ch4 4조] 정본 테이블 추가:
| 제안서 (PROPOSAL) | `monkos-ops/ops/proposals/` | — | PF 승격 후에도 영구 보존 (9조 4항) |

[ch4 7조] type 허용값 추가: proposal
타입별 추가 필수 필드:
| proposal | `from`, `to`, `subject`, `priority` | `pf_ref`, `tags` |
```

이 보정 없이 ch1만 개정하면, 민아의 정규 워크플로우가 ch4의 문서 체계 바깥에서 운용되는 행정적 공백이 계속된다.

## 3. 민아 세션 로그 기록 의무

### 판정: 기본 의무 변경 불필요, 단 태그 추가 권고

현행 ch3의 세션 로그 의무는 에이전트 공통이며, 민아에게도 동일하게 적용된다:
- 분산 기록 원칙 (ch3 1조): 각 에이전트가 자기 세션 로그를 자체 기록 → 변경 불필요
- 타임스탬프 필수 (ch3 4조) → 변경 불필요
- 세션 시작 절차 (ch3 5조) → 변경 불필요

**단, 개정 후 민아 세션에서 새로운 이벤트 유형이 발생한다:**

| 이벤트 | 기존 | 개정 후 |
|--------|------|---------|
| CDP 진단 완료 | 기록 | 기록 (변동 없음) |
| 코드 직접 수정 | 기록 | **금지됨** |
| 제안서 작성·제출 | 기록 | 기록 (빈도 증가) |
| 막내 실행 결과 CDP 검증 | — | **신규** (검증 루프) |

**권고**: ch3 2조(형식)의 직접지시/추인 태그 체계에 민아 전용 태그를 추가하는 것이 유용하다:

```markdown
### [HH:MM] [CDP진단] monkos.ai SEO 전수 크롤
- 발견 이슈: P0 JA 404 13건, P1 FAQ hreflang 미연결
- 제안서: PROPOSAL_20260329_민아_SEO검색노출_수정제안서.md

### [HH:MM] [CDP검증] JA 404 수정 배포 후 검증
- 결과: 13건 전수 200 전환 확인
```

이는 법률 개정이 아닌 **운영 가이드라인** 수준이다. ch3 자체를 개정할 필요까지는 없으나, 민아 세션 로그에서 CDP 활동의 추적성을 높이는 효과가 있다.

## 4. 코웍이 파급 효과 검토

### 발견 사항: 코웍이에 권한표가 존재하지 않는다

ch1 1조의 에이전트 테이블에서:
- **민아**: 별도 권한표 존재 (읽기·쓰기, 커밋·푸시·배포, 기안서, 지시서 발행, governance 수정)
- **코웍이**: 별도 권한표 **없음**. 역할란에 "SPREAD 배포 실행, 전략 보고서, 브라우저 기반 채널 운영"만 기재.

코웍이의 환경은 **Desktop App (웹+CLI)** — 민아와 동일하다. 실행 권한도 유사하다.

**위험**: 민아에게 "코드 수정 금지"를 명확히 하면서 코웍이에 동일 명확화를 하지 않으면, 코웍이가 유사 상황에서 "나는 금지 조항이 없으니 코드 수정 가능"으로 해석할 여지가 있다.

**현실적 파급도 분석:**

| 에이전트 | 코드 수정 가능성 | 권한표 | 명확화 필요도 |
|----------|----------------|--------|-------------|
| 민아 | 높음 (CDP 진단 → 수정 유혹) | 있음 (개정 예정) | **이번 개정 대상** |
| 코웍이 | 중간 (SPREAD 배포 시 설정 수정 등) | **없음** | **높음** |
| 한/꾸 | 낮음 (위성 환경, 본진 직접 접근 제한) | 위성 CLAUDE.md 적용 | 낮음 |

**행정적 권고**: ch1 개정 시 코웍이 권한표를 동시 신설할 것을 강력히 권고한다.

코웍이 권한표 (안):

| 권한 | 허용/금지 | 비고 |
|------|----------|------|
| 본진 읽기 | ✅ 자유 | 민아와 동일 |
| SPREAD 채널 배포 실행 | ✅ 자유 | 코웍이 고유 역할 |
| 문서 쓰기 (보고서·전략·기획) | ✅ 자유 | `monkos-ops/` 산하 |
| **코드 수정·신규 기능 추가** | **❌ 지시서 경유** | 민아 개정안 준용 |
| 커밋·푸시 | ⚠️ works subtree 한정 자유 / 본진은 쌍아 경유 | 현행 운용 반영 |
| governance/, CLAUDE.md 수정 | ❌ 쌍아 전권 | 민아와 동일 |

이 권한표가 없으면 "민아에게만 규제하고 코웍이는 방치"라는 행정적 형평성 문제가 남는다.

## 5. 종합 의견

### 개정안 자체에 대한 행정 판정: **조건부 찬성**

개정안의 방향성 — CDP 진단/검증은 자유, 코드 수정은 지시서 경유 — 은 행정적으로 건전하다. 민아의 워크플로우가 명확해지고, 문서 체계를 통한 맥락 축적이 강화된다.

### 조건 (동시 정비 필요 사항)

| # | 정비 사항 | 대상 법률 | 긴급도 |
|---|----------|----------|--------|
| 1 | **PROPOSAL 유형 ch4 정식 등록** (3조 패턴, 4조 정본, 7조 YAML) | ch4 | **필수** — 개정안의 핵심 산출물이 법적 미등록 |
| 2 | **코웍이 권한표 신설** | ch1 1조 | **강력 권고** — 형평성 + 동일 환경의 규범 공백 |
| 3 | 병목 완화 운영 지침 부기 (쌍아 동일 세션 내 지시서 변환 가능) | ch1 2조 또는 부칙 | 권고 |
| 4 | 민아 세션 로그 CDP 태그 가이드라인 | 운영 가이드 (법률 미개정) | 참고 |

특히 **조건 1은 필수**이다. 민아의 정규 워크플로우가 "제안서 작성"을 경유하도록 법률로 선언하면서, 그 제안서의 파일 유형이 법률에 등록되어 있지 않은 것은 행정적 모순이다.
