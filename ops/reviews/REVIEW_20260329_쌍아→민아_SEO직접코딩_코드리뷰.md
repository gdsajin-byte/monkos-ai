## 2. 코드 리뷰

### P0: JA 한자/가나 슬러그 404 — ✅ 양호

**변경**: `blogPostFragment`에서 `slug-ja` 조회 실패 시 `slug` 자체로 fallback + `lang` 일치 검증

- fallback 로직 건전
- optional chaining(`?.`) 적용 적절
- 기존 신규 방식(`slug-lang`) 호환 유지
- **지적 사항 없음**

### P1: FAQ hreflang + OG 보강 — ✅ 양호

**변경**: `faqFragment`에 hreflang 4개 + `og:image`, `og:locale` 추가

- 블로그 포스트에 이미 존재하는 패턴의 복제
- 하드코딩된 URL(`https://monkos.ai/faq` 등)은 기존 코드와 동일한 방식
- **지적 사항 없음**

### P2: 관련 포스트 섹션 — ⚠️ 설계 사항 3건

**변경**: 블로그 포스트 하단에 같은 언어 최근 3건 카드 표시 (Firestore 쿼리 + HTML + CSS, ~42줄)

**양호한 점:**
- Firestore 쿼리 `where + orderBy + limit`으로 효율적
- `try/catch`로 감싸서 실패 시 포스트 본문 렌더에 영향 없음
- 다국어 라벨 처리됨
- 모바일 반응형 CSS 포함

**설계 리뷰 사항:**

| # | 사항 | 상세 |
|---|------|------|
| 1 | **slug 역산 로직 불일치** | `d.id.replace(/-(?:ja\|en)$/, '')` — P0에서 "구 방식 doc ID에는 `-ja`가 안 붙는다"는 걸 발견했는데, 관련 포스트 URL 생성에서는 일괄 strip. 구 방식 doc의 slug가 `-ja`로 끝나는 경우 잘못 잘릴 위험 |
| 2 | **Firestore 복합 인덱스** | `published + lang + createdAt` 복합 인덱스 존재 여부 미확인. 없으면 첫 호출에서 에러 → catch에 잡히지만 관련 포스트가 영구 미표시 |
| 3 | **캐싱 미고려** | 매 포스트 렌더마다 Firestore 추가 쿼리 1회. 현재 트래픽에서는 문제 없으나, 트래픽 증가 시 비용/성능 영향 |

→ 이 3건은 **지시서 경유 시 사전 설계 단계에서 검출되었을 항목**이다.

## 3. 절차 리뷰 — 작가님 교시

### 현행 헌법 대조

민아의 직접 실행은 **헌법 제1조 2항 ③에 합헌**이다. 위헌이 아니다.

그러나 작가님이 이번 건을 계기로 명확히 하신 원칙이 있다:

### 핵심 원칙: 지시서 체계는 능력의 제약이 아니라 맥락의 축적 장치

> "우리 체계의 가장 강력한 힘은 단일 에이전트의 능력보다 팀 전체가 쌓아온 문서체계이다. 모든 지시서 체계가 전달되고 리포팅되고 추출되면서 하나의 큰 프로젝트가 유기적으로 성장하고 있는 것이다."

단일 세션에서는 누구나 코딩을 잘 할 수 있다. 그러나 세션이 끝나면 컨텍스트는 사라진다. 이번 P0~P2에서:
- 왜 fallback을 이 방식으로 했는지
- P2의 설계 대안으로 무엇을 검토했는지
- Firestore 인덱스 의존성은 어떻게 판단했는지

이 모든 의사결정 맥락이 **민아의 세션 안에서만 존재하고 이미 휘발되었다.**

지시서가 있었다면 이것들이 문서로 남고, 다음 리팩토링에서 누가 이 코드를 만져도 "왜 이렇게 했는지"를 알 수 있다.

|------|------|------|

## 4. 요청 사항

### 즉시

1. 이번 `render.js` / `server.js` 변경은 **unstaged 상태로 보류**한다
2. 민아는 CDP 진단 결과를 기반으로 **제안서(또는 지시서 초안)**를 작성한다
3. 쌍아가 설계 검토 후 정식 지시서로 변환 → 막내 실행

### 향후

- CDP 진단 → 보고서 작성 → 제안서/지시서 → 승인 → 막내 실행 → 민아 CDP 검증
- 이 루프가 민아의 정규 워크플로우
- 코드를 직접 건드리지 않아도 민아의 가치(진단+검증)는 온전하다

## 5. 부기
