MONK.js — 프레임워크 설계서

00079 모놀리스에서 추출한 패턴 → 커스텀 마이크로 프레임워크 | 2026-02-17

1. 왜 프레임워크인가

"단순함은 초보의 단순함 - 중수의 복잡함 - 고수의 통합 - 초고수의 심플"
지금: 모놀리스 (2,187줄)

56개 함수가 전역 상태 + DOM을 직접 조작
capturePhoto() 하나에 상태/미디어/AI/UI가 혼재
수정 = 전체 이해 필요 → 유지보수 벽

목표: 프레임워크 + 앱 코드

프레임워크가 "어떻게"를 처리 (DOM, 카메라, WS)
앱 코드는 "무엇을"만 선언 (화면, 흐름, 규칙)
수정 = 해당 선언만 변경 → 격리된 변경

핵심 판단 기준: 파일을 10개로 나누는 게 아니라, "capturePhoto()의 12줄 DOM 조작을 앱 코드에서 제거할 수 있는가?" — 이것이 가능하면 프레임워크. 불가능하면 그냥 파일 분리.

2. 00079에서 추출한 4가지 축

2,187줄 × 56함수를 관통하는 패턴은 딱 4개:

01
Screen (화면 상태 머신)

02

값 변경 → DOM 자동 갱신 (지금은 수동)
→ 중앙 저장소 + 구독 패턴
03

→ 선언적 AI 통신 계층
04

→ 미디어 자원 독점/해제 관리

이 4개가 프레임워크 코어. 나머지(인증, 결제, 로그, i18n)는 앱 레벨 플러그인.

4. 코어 모듈 상세

4-1. Screen — 화면 상태 머신

현재 00079에서 화면 전환하는 코드 패턴:

// 00079 현재 — startShooting() 내부
document.getElementById('prep-screen').classList.add('hidden');
document.getElementById('camera-area').classList.add('active');
document.getElementById('controls').classList.add('active');
document.getElementById('step-label').textContent = t('step1');
currentStep = 1;
connectWS();  // AI 연결도 여기서...

프레임워크 적용 후:

// MONK.js Screen 사용
const screens = Monk.screens({
  prep:     { el: '#prep-screen' },
  camera:   { el: '#camera-area',  enter: onCameraEnter,  exit: onCameraExit },
  result:   { el: '#result-overlay' },
  thankyou: { el: '#thankyou-screen' },
});

// 전환은 이 한 줄. DOM 조작은 프레임워크가 처리.
screens.go('camera');

// 생명주기: enter 콜백에서 AI 연결
function onCameraEnter() {
  pipe.connect('coaching');
  media.startCapture();
}
function onCameraExit() {
  pipe.disconnect('coaching');
  media.stopCapture();
}
변화: 앱 코드에 getElementById가 사라진다. 화면 전환 로직이 선언으로 바뀐다. enter/exit 생명주기가 자원 관리(카메라, WS)를 보장한다.

4-2. Store — 반응형 상태

현재 00079의 상태 → DOM 갱신 패턴:

프레임워크 적용 후:

// MONK.js Store — 값 변경 시 바인딩된 DOM 자동 갱신
const store = Monk.store({
  user: { id: null, email: null, credits: 0 },
  style: null,
  gender: null,
  age: null,
  step: 0,
  captured: null,    // base64
  generated: null,   // base64

// HTML에서 바인딩:
//  <span data-bind="user.credits"></span>
//  <img data-bind-src="generated">
//  <div data-show="coaching.ready">촬영 OK</div>

// 앱 코드: 값만 바꾸면 UI가 따라온다

4-3. Pipe — AI 파이프라인

현재 00079의 AI 통신 패턴:

// 00079 현재 — confirmAndGenerate() 내부 (약 80줄)
// 사전분석 → 생성 → QC 가 try/catch 3중첩
try {
  const preCheck = await apiPost('/api/pre-check', { image });
  // DOM 조작 10줄...
  try {
    const genResult = await apiPost('/api/generate', { ... });
    // DOM 조작 8줄...
    try {
      const qcResult = await apiPost('/api/qc', { ... });
      // DOM 조작 + 결과 표시...
    } catch { /* QC 에러 */ }
  } catch { /* 생성 에러 + 크레딧 부족 */ }
} catch { /* 사전분석 에러 */ }

프레임워크 적용 후:

// MONK.js Pipe — AI 파이프라인 선언
const pipe = Monk.pipe({
  coaching: {
    type: 'ws',
    url: () => `${wsProtocol}//${location.host}`,
    onMessage: (msg) => {
      if (msg.type === 'ai-coaching') store.coaching.text = msg.text;
    },
  },
  precheck: { type: 'post', path: '/api/pre-check' },
  generate: { type: 'post', path: '/api/generate' },
  qc:       { type: 'post', path: '/api/qc' },
});

// 앱 코드: 체이닝으로 파이프라인 실행
async function generateFlow() {
  const image = store.captured;

  const pre = await pipe.run('precheck', { image });
  if (!pre.suitable) return screens.go('result', { mode: 'retake', reason: pre.suggestion });

  const gen = await pipe.run('generate', { image, ...store.profile });
  store.generated = gen.image;

  const qc = await pipe.run('qc', { original: image, generated: gen.image });
  store.qcResult = qc;
  screens.go('result', { mode: qc.passed ? 'done' : 'fail' });
}
변화: 80줄 try/catch 3중첩이 → 12줄 선형 흐름으로. DOM 조작이 store 바인딩 + screen 전환으로 자동 처리된다. 에러 핸들링은 pipe.run()이 통합 처리 (402 → 크레딧 모달 자동 트리거).

7. 프레임워크 코어 스케치

monk.js의 실제 구현 윤곽 (~300줄 예상):

/**
 * MONK.js — AI Creative App Micro-Framework
 * Screen + Store + Pipe + Media
 */

const Monk = (() => {

  // ─── Screen: 화면 상태 머신 ───
  function screens(defs) {
    let current = null;
    const map = {};

    for (const [name, cfg] of Object.entries(defs)) {
      map[name] = {
        el: document.querySelector(cfg.el),
        enter: cfg.enter || (() => {}),
        exit: cfg.exit || (() => {}),
      };
    }

    return {
      go(name, params = {}) {
        if (current) {
          map[current].exit(params);
          map[current].el.classList.remove('active');
        }
        current = name;
        map[name].el.classList.add('active');
        map[name].enter(params);
      },
      get current() { return current; },
    };
  }

  // ─── Store: 반응형 상태 + DOM 바인딩 ───
  function store(initial) {
    const subs = new Map(); // key → Set<callback>

    function bind() {
      // data-bind="key" → textContent
      // data-bind-src="key" → img.src
      // data-show="key" → display toggle
      // data-class="key:className" → classList toggle
      document.querySelectorAll('[data-bind]').forEach(el => {
        const key = el.dataset.bind;
        subscribe(key, (v) => { el.textContent = v ?? ''; });
      });
      // ... 기타 바인딩 타입
    }

    function subscribe(key, fn) {
      if (!subs.has(key)) subs.set(key, new Set());
      subs.get(key).add(fn);
    }

    // Proxy로 자동 구독 트리거
    const state = new Proxy(initial, {
      set(target, prop, value) {
        target[prop] = value;
        (subs.get(prop) || []).forEach(fn => fn(value));
        return true;
      }
    });

    bind(); // 초기 DOM 바인딩 스캔
    return state;
  }

  // ─── Pipe: AI 통신 계층 ───
  function pipe(defs, opts = {}) {
    const connections = {};

    async function run(name, data) {
      const def = defs[name];
      if (def.type === 'post') {
        const res = await fetch(def.path, {
          method: 'POST',
          headers: { 'Content-Type': 'application/json' },
          body: JSON.stringify(data),
        });
        if (!res.ok) {
          const err = await res.json().catch(() => ({}));
          err.status = res.status;
          if (res.status === 402 && opts.onCreditShort) opts.onCreditShort(err);
          throw err;
        }
        return res.json();
      }
    }

    function connect(name) {
      const def = defs[name];
      if (def.type !== 'ws') return;
      const ws = new WebSocket(def.url());
      ws.onopen = () => def.onOpen?.(ws);
      ws.onmessage = async (e) => {
        const raw = e.data instanceof Blob ? await e.data.text() : e.data;
        try { def.onMessage?.(JSON.parse(raw), ws); } catch {}
      };
      ws.onclose = () => def.onClose?.();
      connections[name] = ws;
    }

    function disconnect(name) {
      connections[name]?.close();
      delete connections[name];
    }

    function send(name, data) {
      const ws = connections[name];
      if (ws?.readyState === 1) ws.send(typeof data === 'string' ? data : JSON.stringify(data));
    }

    return { run, connect, disconnect, send };
  }

  // ─── Media: 카메라 + 캡처 + 얼굴검출 ───
  function media(cfg) {
    let stream = null, timer = null, detector = null;
    const video = document.querySelector(cfg.video);
    const canvas = document.querySelector(cfg.canvas);

    return {
      async start() { /* getUserMedia + video.srcObject */ },
      capture() { /* canvas drawImage → toDataURL */ },
      onFrame(cb) { /* setInterval frame capture */ },
      async crop(imageData, spec) { /* 얼굴검출 + 규격 크롭 */ },
      stop() { /* stream.getTracks().stop() + clearInterval */ },
    };
  }

  return { screens, store, pipe, media };
})();

8. app.js 전체 윤곽 (증명사진 앱)

/**
 * MONKOS ID Photo — MONK.js 기반 앱 코드
 * 프레임워크가 "어떻게"를 처리, 여기서는 "무엇을"만 선언

// ─── 4. 화면 정의 ───

9. 확장성: 다른 앱에도 적용 가능

monk.js는 증명사진 전용이 아닙니다. 4가지 축은 AI 크리에이티브 앱의 공통 패턴입니다:

룩북 (lookbook)

Screen: 의상 선택 → 생성 → 갤러리
Store: 선택한 의상, 모델, 생성 이미지
Pipe: Imagen T2I 생성
Media: 갤러리 뷰어

모델 에이전시 (model_agency)

Screen: 모델 선택 → 포즈 → 합성
Store: 모델 데이터, 포즈, 생성물
Pipe: Imagen I2I + T2I
Media: 포즈 가이드 + 결과물

각 앱은 자신의 app.js만 다르게 작성하고, monk.js는 동일하게 공유한다.

10. 기술 스택 선택지

"순수 JS"는 규칙이 아니라 현재 상태였다. 프레임워크에서 선택할 수 있는 옵션:

A. 순수 JS (Vanilla) — monk.js를 순수 JS로 구현
장점: 의존성 0, 번들링 불필요, Cloudflare Pages 즉시 배포
단점: Proxy 반응성 직접 구현, 깊은 객체 추적 한계

B. ES Module + 경량 반응성 라이브러리 — Preact Signals 등
장점: 검증된 반응성 엔진 위에 구축, Store 구현 신뢰도↑
단점: 번들러 필요 가능성 (또는 CDN import)

C. Lit Element (Web Components)
장점: 표준 기술, 컴포넌트 캡슐화, Shadow DOM
단점: 학습 비용, 기존 CSS와 Shadow DOM 충돌 가능

제안: A안 (순수 JS)으로 시작. Proxy 기반 반응성은 이 규모(상태 변수 ~15개)에서 충분하고, Cloudflare Pages 배포에 번들 과정이 추가되지 않는다. monk.js 자체가 ~300줄이면 외부 의존성이 필요 없다.

필요하면 B/C로 진화 가능 — monk.js의 인터페이스(screens/store/pipe/media)는 유지되므로 내부 구현만 교체하면 된다.

11. 구현 로드맵

Phase 1: monk.js 코어 구현 (Screen + Store)
— 화면 전환 + 반응형 바인딩만으로도 00079 코드의 60%가 정리된다

Phase 2: Pipe 모듈 (REST + WS 통합)
— AI 파이프라인 추상화. 기존 서버 API는 그대로 사용

Phase 3: Media 모듈 (카메라 + 얼굴검출 + 크롭)
— 미디어 자원 캡슐화. Screen 생명주기와 연동

Phase 4: app.js 작성 + index.html 리빌드
— 00079 비즈니스 로직을 monk.js API로 재작성

Phase 5: 인증 + 결제 플러그인
— 포탈 연동 (OAuth, 크레딧, 토스) = 앱 레벨 모듈
