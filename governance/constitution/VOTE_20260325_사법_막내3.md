#### 청구안의 대응은 충분한가?

**부분적으로 충분하다.** 청구안 §5의 하위 법률 정비 계획은 법률 8장의 참조 라인 갱신을 모두 커버한다. 그러나 다음이 누락되어 있다:

**누락 1: 전환 경계일자**

개헌 발효일 이전 문서는 구(舊) 7조 체계를, 이후 문서는 신(新) 5축 체계를 참조한다. 이 경계가 어디인지 **명시적으로 선언되지 않았다.** 향후 에이전트가 과거 문서를 읽을 때 "헌법 2조 1항"이 역할 체계(구)인지 디바이스 맵(신)인지 판별할 수 없다.

**대응 방안**: 개헌안 발효 시 CLAUDE.md 하단에 경계 선언 추가:

```
> ⚠️ 2026-03-25 이전 문서의 "헌법 N조" 참조는 구(舊) 7조 체계 기준이다.
> 매핑: governance/constitution/AMENDMENT_20260325_5축재편_개헌청구안.md §4
```

**누락 2: 코드 내 조항 참조**

코드(주석, 에러 메시지 등)에서 헌법 조항을 참조하는 경우가 있는지 확인하지 않았다. 코드의 `// 헌법 4조 1항 준수` 같은 주석이 있다면 갱신 대상이다. 다만 MONK 코드베이스에서 헌법 조번호를 직접 참조하는 코드는 극히 드물 것으로 예상된다.

**판정**: 전환 경계일자 명시를 **조건**으로 부여한다 (조건 #2).

### 2. 4계층 도입의 복잡성 — 심각도: **중**

#### 단순화인가, 복잡화인가?

| 관점 | 3계층 (현행) | 4계층 (제안) | 판정 |
|------|-------------|-------------|------|
| **계층 수** | 3 | 4 | ⚠️ 증가 |
| **의미 구분** | 원칙/규칙/상세 | 왜/무엇/어떻게/디바이스 | ✅ 더 명확 |
| **기술 매핑** | CLAUDE.md / laws / MEMORY.md | CLAUDE.md / rules / skills / MEMORY.md | ✅ Anthropic 1:1 |
| **변경 권한** | 만장일치 / 합의 / 자율 | 만장일치 / 합의 / **합의** / 자율 | ⚠️ 2·3층 동일 |

**핵심 우려: "법률"과 "명령"의 변경 권한이 동일하다 (쌍아+작가님 합의).**

4계층에서 법률과 명령은 다음이 다르다:

| | 법률 | 명령 |
|--|------|------|
| 성격 | 무엇 (정의·목록) | 어떻게 (실행 절차) |
| 물리 위치 | `.claude/rules/` + `governance/laws/` | `.claude/skills/` |
| 로딩 방식 | 상시/path 매칭 | 키워드 트리거 온디맨드 |

차이는 **기술적 구현**(로딩 방식)에 있지, **거버넌스**(변경 권한)에는 없다. 이는 다음 질문을 낳는다:

> "법률 개정과 동일한 절차를 거쳐야 하는데, 왜 별도 계층인가?"

**반론**: 계층의 의미는 변경 권한만이 아니다. **로딩 시점**이 다르면 에이전트의 행동이 달라진다. Rules(상시 로딩)과 Skills(온디맨드)는 기술적으로 근본이 다르다. 에이전트가 "이 규칙은 항상 따라야 하는가, 특정 상황에서만 따라야 하는가"를 구분하는 기준이 바로 이 계층이다.

**판정**: 우려는 유효하나, 반론이 더 설득력 있다. 다만 혼동 방지를 위해 제5조 1항 테이블에 "법률·명령 동일 권한"임을 **명시적 주석**으로 추가할 것을 권고한다 (조건 #3).

### 3. Skills 의존 리스크 — 심각도: **낮**

#### Anthropic Skills 변경/폐지 시 시나리오

| 시나리오 | 영향 | 대응 |
|---------|------|------|
| Skills 기능 제거 | `.claude/skills/` 무시됨 → 온디맨드 절차 로딩 불가 | 법률 ch1~ch8 원문이 **원본으로 존속** → 수동 Read로 복귀 |
| Skills 문법 변경 | 트리거 키워드 매칭 실패 | Skill 파일 문법만 갱신 (내용 불변) |
| Skills 강화 (기능 추가) | 긍정적 영향 | 점진 적용 |

**핵심 안전장치**: 이번 개헌에서 법률 ch1~ch8은 **삭제되지 않는다.** Skills는 법률의 "실행형 조항"을 재구성한 **파생 뷰**이지, 법률을 **대체**하지 않는다. 3차 보고서의 Skill 스펙에 `> 원천: chN M조`라는 참조가 있어 추적성도 확보된다.

**잠재 리스크**: 장기적으로 팀이 Skills에만 의존하고 원본 법률을 읽지 않게 되면, 법률 개정 시 Skill 동기화를 잊는 사고가 발생할 수 있다. 이것은 기술적 리스크가 아니라 **운영 습관의 리스크**다.

**대응 방안**: Skill 파일 상단에 원천 법률 참조를 필수 기재하는 규칙 (3차 보고서에서 이미 제안됨). 법률 개정 시 "관련 Skill 갱신 여부" 체크리스트 추가.

**판정**: 낮은 리스크. 추가 조건 불필요. 운영 규칙 수준에서 해결 가능.

### 5. 대안 검토 — 심각도: **중**

#### 대안 A: 7조 유지 + `.claude/rules/` 확장

| 항목 | 평가 |
|------|------|
| **접근** | 현행 7조 그대로 유지. 분산된 통신·적립 규칙을 `.claude/rules/`의 path-scoped rules로 모아서 노출 |
| **장점** | 조번호 변경 혼란 제로. 법률 참조 갱신 불필요. 기존 문서 호환성 100% |
| **단점** | 헌법 본문의 위상 꼬임이 해소되지 않음. 통신 규약이 여전히 5곳에 분산. `.claude/rules/`는 헌법 보완이지 대체가 아니므로 근본 문제 미해결 |
| **판정** | ⚠️ 단기 안전하나 구조적 문제 잔존 |

이 대안은 진지하게 고려할 가치가 있다. **"현행 7조가 실제로 사고를 유발하는가?"**를 검증해야 한다.

청구안 §1의 실무 사고 3건:
1. 파일명 디바이스 누락 (works 파일 전수) — 이것은 ch4(문서구조)와 works 규정의 문제이지, 헌법 조번호의 문제가 아니다.
2. push 범위 불명확 (M4 한송이 파일 미동기화) — 이것은 works subtree 운용 규정의 문제이지, 헌법 구조의 문제가 아니다.
3. 세션 마감 지연 (절차 산재) — 이것은 절차가 MEMORY.md/ch3/ch1에 분산된 것이 원인으로, **Skills 도입**으로 해결 가능하며 5축 재편 없이도 독립 실행 가능하다.

**반론**: 청구안의 본질적 주장은 "실무 사고의 직접 원인"이 아니라 "에이전트가 소통 방법을 파악하려면 헌법+법률 6개 파일을 읽어야 한다"는 **인지 부하**의 문제다. 이는 조번호가 아닌 **관심사(concern) 기준 배치**의 문제이므로, 재편이 적절한 대응이다.

**내 판정**: 대안 A는 **단기적으로 안전하나 구조적 부채를 유지**한다. 5축 재편의 리스크(조번호 혼란)가 전환 경계일자 명시로 관리 가능하다면, 재편이 장기적으로 우위다.

#### 장애 원인 특정 가능한가?

개별 파일 수준에서는 Git 롤백으로 특정 가능하다. 그러나 **행동 수준**에서는 특정이 어렵다:

| 장애 시나리오 | 원인 특정 가능? |
|-------------|---------------|
| 에이전트가 "헌법 4조"라고 했는데 구·신 어느 쪽인지 모호 | ⚠️ #1(5축)이 원인이나, 즉시 판별 어려움 |

| 민아 세션 시작 시 판별 실패 | ✅ #3(ch1 5조)으로 특정 가능 |

**핵심 문제**: #1(5축 개헌)과 #4(Skills 8건)이 **동시에 터지면 합성 장애**가 된다.

더 중요한 것은 **내 3차 보고서와의 모순**이다:

```
3차 보고서 권고:
  Phase 1: 5축 개헌 + settings.json + ch1 5조  (즉시)
  Phase 2: Skills 구현                          (1주 후)
```
