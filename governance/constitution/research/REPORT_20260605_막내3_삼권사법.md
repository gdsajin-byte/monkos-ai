## 2. 추가 발굴 — 숨은 모순 (연쇄 충돌)

선례(cdp-browser ↔ ch1:13)에 더해 다음을 발굴한다.

**모순 ①: 규정만 고치고 법률 본문은 잔류 (A의 미완)**
- cdp-browser 규정은 06-05 "단일점유 회피"로 정확화됐으나, **법률 ch1:13 "MCP 연동"은 본문 그대로**다. 정합 주석이 법률에 없어, 미래 에이전트가 ch1:13만 읽으면 다시 "민아=MCP연동"을 무제약으로 해석할 여지. → **규정 개정 시 대응 법률 동시 갱신(헌법 5조 1항 명령)을 이행하지 않은 흠결.**

**모순 ②: 오케스트레이터 ↔ 지시서 발행 권한 제약 (B)**
- 오케스트레이터가 워커에게 작업을 "지시"하는 행위는 ch1 1조 민아권한표 **"지시서 발행 ⚠️ 작가님 직접 승인 시만"**과 충돌. 자동 오케스트레이션은 매 투입마다 작가님 승인을 전제로 하면 "자동"이 무력화되고, 승인을 생략하면 권한 위반. **둘 중 하나를 택할 수 없는 구조적 모순.**

**모순 ③: 승인 내재성 공백 (B·E)**
- ch1 2조 2항은 "작가님 직접 지시 시 승인이 작가님 자신에게 내재"라고 본다. 그러나 **민아·쌍아가 워커를 투입할 때 그들은 작가님이 아니므로 "승인 내재"가 성립하지 않는다.** 오케스트레이터발 투입은 승인 주체가 공백 상태.

**모순 ④: 철창이 = 헌법 미상속 surface (C)**
- MEMORY 명문: "철창이는 Claude Code 제품이 아니므로 `.claude/skills`·CLAUDE.md 자동 로딩 경로 밖." 즉 **헌법 5조 1항 위계가 자동 적용되지 않는 환경**에 정본 리포를 연결하는 것. read-only라도 `.env`·`secrets/`·governance 내부 프로토콜이 헌법 무방비 외부 surface(claude.ai)로 흘러간다. 헌법 4조 1항(비밀정보 보호)·3항(내부기밀) 동시 저촉.

**모순 ⑤: 메타 PF 비대화 ↔ 아카이브 규칙 (D)**
- pf-ops.md "500줄 초과 시 아카이브 트리거". 메타 PF는 5축을 통괄해 본질적으로 비대해진다. **통괄 정본을 아카이브하면 흐름 추적이 끊긴다** — 일반 PF 운용 규칙이 메타 PF에 그대로 적용되면 충돌.

**모순 ⑥: 정본 단일 ↔ 메타 PF의 수치 복제 (D)**
- 헌법 3조 4항 "동일 문서의 정본은 하나만. 참조본은 읽기전용." PF_OPUS 성공지표표(§1)는 GSC 클릭·스프레드 진행률 등 **하위 PF가 정본인 수치를 복제**한다. 복제분이 "참조본(읽기전용)"임을 명시하지 않으면 정본 이중화.

## 3. 중점 심사 — E (멀티에이전트 운용)

가장 위험한 논점. 제품/거버넌스 분리 주장을 정밀 심사한다.

### 3-1. 명문 유보 조항의 존재
- ch1 2조 3항 말미: **"멀티에이전틱 직접 운용(쌍아가 막내를 자동 투입하는 체계)은 향후 특별법으로 설계한다."**
- MEMORY: "멀티에이전틱 직접 운용은 향후 특별법/파트 신설 + Anthropic 멀티에이전트 검증 후 설계할 영역."
- → **이미 입법자가 "지금은 안 됨, 특별법 필요"라고 못박은 영역.** 어젠다 E를 일반 개정으로 통과시키는 것은 이 유보 조항을 우회하는 것. 특별법 절차(헌법 5조 2항) 없이는 반려 사유.

### 3-2. "제품 워커 ↔ 운영 에이전트" 분리는 성립하는가
- **분리가 성립하는 경우**: monk.kr 서비스 런타임이 부리는 워커(콘텐츠 생산 자동화 등)는 애플리케이션 코드다. server.js의 Firestore 접근이 ch4 10조 예외(서비스 코드는 대상 아님)인 것과 동일 논리로, **제품 파이프라인은 거버넌스 적용 대상이 아니다.**
- **분리가 무너지는 경우**: 민아가 "오케스트레이터"로 워커를 부릴 때, 그 워커가 *제품 워커*인지 *운영 막내*인지 경계가 흐려진다. 민아가 운영 막내를 자동 투입하면 = **쌍아 spawn 금지 원칙을 민아라는 다른 입구로 우회.** "쌍아는 금지인데 민아는 허용"이 되면 금지 원칙 전체가 무력화된다(누구를 통해서든 자동 투입이 열림).

### 3-3. 선 긋기 제안 (조건부 통과의 조건)
1. **제품 파이프라인 한정**: 산출물이 monk.kr 제품·서비스 런타임으로 나가는 워커만 허용. ch4 10조 "서비스 코드 예외" 준용.
2. **운영 에이전트 자동 투입은 명시 배제**: 쌍아·민아·막내 상호 자동 spawn은 ch1 2조 3항 유보 그대로 유지. 특별법 + Anthropic 검증 전까지 금지.
3. **경계 판정 기준**: "산출물이 제품으로 나가는가(제품) vs 내부 거버넌스 문서·코드를 만드는가(운영)". **모호하면 운영으로 간주(보수적).** ch1:45 "불확실하면 코드 수정으로 간주" 정신 준용.
4. **오케스트레이터 권한 분리**: 민아의 제품 파이프라인 관제 권한과, 운영 막내 투입 권한을 문서상 분리. 후자는 여전히 작가님 경유.

> **사법 핵심 견해**: E는 "제품 자동화"로 한정하면 헌법과 양립 가능하나, "운영 멀티에이전트"로 확장하면 ch1 2조 3항 명문 유보·MEMORY spawn 금지·헌법 2조 역할체계를 정면 위반한다. **두 영역의 방화벽을 명문화하지 않은 채 통과시키면, 토큰 생존 전략(MEMORY: 멀티에이전트 분화)이라는 아키텍처 본질이 거꾸로 무너질 수 있다.**
