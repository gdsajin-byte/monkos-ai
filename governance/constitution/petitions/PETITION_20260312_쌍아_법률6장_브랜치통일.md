# 법률 제6장 1조·2조 개정 청구 — 브랜치 통일

> **[2026-03-12 10:48 KST] iMac/쌍아 → 작가님**

---

## 1. 청구 배경

작가님 직접 지적 (2026-03-12 10:45 KST):
- "브랜치 통일하자. 너는 맨날 develop에, M1은 main에. 굳이 그럴 이유가 있나"
- "이익포인트가 있나" → **없다**

### 현실 문제
- **M1은 main에 직접 커밋/push** — 이미 법률 6장 2조(main 보호) 위반 상태
- **iMac은 develop 고수** — 매 세션마다 main↔develop 머지 오버헤드 발생
- develop/main 분리의 전통적 이점(배포 보호)이 현재 구조에서 실익 없음:
  - CI/CD 자동 배포가 main 트리거가 아님
  - 실질 개발 주체 = 작가님 1인 + AI 에이전트
  - 코드 리뷰어 ≠ 별도 인원 (쌍아가 겸임)

## 2. 현행 조문

> **제6장 1조 (브랜치 전략)**
> - 기본 작업 브랜치: `develop`.
> - 지시서에 별도 브랜치 명시 시 해당 브랜치 사용.

> **제6장 2조 (main 보호)**
> - `main` 브랜치 직접 커밋/push 금지.
> - `main`으로 머지 금지 (쌍아 또는 작가님이 판단).

## 3. 개정안

> **제6장 1조 (브랜치 전략)**
> - 기본 작업 브랜치: `main`.
> - 기능 개발·실험 등 격리가 필요한 경우, 지시서에 별도 브랜치를 명시하여 사용할 수 있다.
> - 별도 브랜치 작업 완료 시 main에 머지 후 삭제한다.

> **제6장 2조 (main 운용)**
> - 모든 디바이스·에이전트는 main에서 직접 작업한다.
> - 커밋 전 `git pull`로 최신 상태 확인을 권장한다.
> - 충돌 발생 시 로컬에서 해소 후 push한다.

### 변경 요점
| 항목 | 현행 | 개정안 |
|------|------|--------|
| 기본 브랜치 | develop | main |
| main 보호 | 직접 커밋/push/머지 금지 | 직접 작업 허용 |
| 브랜치 분리 | 상시 (develop↔main) | 필요 시에만 (feature 브랜치) |
| 동기화 비용 | 매 세션 머지 필수 | 없음 (단일 브랜치) |
