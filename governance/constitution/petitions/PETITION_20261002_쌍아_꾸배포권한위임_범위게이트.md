## 3. 설계 — 범위 게이트 (G-K)

### 3.1 판정 위치와 base

- `deploy-monk-kr.yml`에 입력 `approver`(`작가님`|`꾸`, 기본값 `작가님`)를 추가한다. `approver=꾸`이면 **배포 스텝 앞에서** G-K를 돈다. 범위 밖이면 `exit 1`로 끝내고 배포하지 않는다.
- **ref 고정** (막내2 C2·막내4 C2): `approver=꾸`는 `github.ref == refs/heads/main`일 때만 허용한다. target(`sha` 또는 HEAD)이 `origin/main`의 조상이어야 한다. 이 조건을 충족하지 못하면 범위 밖이다.
- **base = 직전 *실제* production 배포 커밋** (3역 공통 C1):
  - 1순위: 직전 성공 run이 기록한 `배포 커밋`이다. 2판부터 워크플로가 STEP_SUMMARY와 run 산출물에 base·target을 기계 판독 가능하게 남긴다.
  - 2순위: CF API의 활성 배포(`canonical_deployment`)다. Idle·빌드 없음 항목은 제외한다.
  - **CF 배포 목록의 최상단 소스 커밋은 쓰지 않는다.** Git 연동이 푸시마다 남기는 Idle 항목이 섞여 있다(10-02 실측: 25건 중 23건이 Idle, Idle URL은 404). run의 `headSha`도 쓰지 않는다(sha 입력 시 실제 배포 커밋과 다르다).
  - 1·2순위가 다르면 차단한다. base가 target의 조상이 아니면 차단한다. **diff가 0건이어도 차단한다**(0건 ≠ 부재).
- **diff 범위** (막내3 C2): `MONK_kr/` `functions/` `.github/` `package.json`. 게이트 자신을 약화하는 커밋, 그리고 wrangler 버전의 정본도 판정 대상에 넣는다.
- 판정을 러너에서 하는 이유는 ch1 1조 판단 분리다. M2 세션의 사전 점검 스크립트(`--dry-run`)는 편의 도구일 뿐 판정이 아니다.

### 3.3 승인 인정 (J2 — 막내2 C3 반영)

- **승인 = ch1 7조 2항의 사람이 입력한 턴**이다. 꾸 경로에서는 M2 고정 세션에 꾸가 입력한 턴이다. 꾸 턴과 작가님 원격 턴은 구분하지 않는다. 작가님 턴은 원래부터 상위 승인이다.
- **E10 토큰은 실수 방지 장치다.** PETITION_20261001 묶음 C가 발효하기 전에는 승인의 증거가 아니다(L6-3·L6-5 준용). 게이트를 통과한 기록을 승인 증명으로 인용하지 않는다.
- **흔적 정합의 기계 확인** (막내4 C6):
  - `approver=꾸`이면 사유 `{주체}`가 `^꾸 via M2/쌍아\(M2-쌍아-[0-9]{4}-[0-9]{4}\)`와 일치해야 한다.
  - `approver=작가님`인데 `{주체}`에 `꾸`가 있으면 차단한다.
- 배포를 트리거하는 것은 M2 고정 세션의 본체 턴만 한다. 서브에이전트·팀원에게 배포 명령을 맡기지 않는다(session_id 공유 — 10-01·10-02 실측).

### 3.4 1회 승인 = 1회 트리거 — 유지 (J3, 3역 동의)

- 묶음 승인은 두지 않는다. 직전 배포 이후 누적분을 1회에 배포하면 묶음 효과가 난다.
- 대신 범위 밖 커밋이 1건이라도 끼면 그 구간 전체가 작가님 경로로 간다(막내3 실측: 10구간 중 6구간).

### 3.5 사후 보고 (J4 — 막내3 C5·막내4 C8)

- 별도 job으로 `uses: ./.github/workflows/notify.yml`을 호출하고 `if: always() && needs.deploy.outputs.deployed == '1'`을 단다. 스모크가 실패해도 배포됐다면 알림이 나간다.
- 서식: `[꾸 배포] run {id} · approver {…} · {headBranch} · base {sha8}→{sha8} · 변경 {n}파일 · 범위 게이트 통과 · 사유 {…}`
- **선행 수정**: `notify.yml`은 `inputs.message`를 셸에 직접 치환한다. 이것을 env 경유로 바꾼다(주입 차단 — 현행 작가님 경로 알림에도 적용된다).
- 알림 job이 실패하면 run 실패로 표기된다. 이때 배포 반영 표는 보존된다(ch5 1조 8항).

### 3.6 롤백 (J5 — 막내2 C4)

- 꾸 승인으로 롤백하려면 두 조건을 모두 충족해야 한다.
  - **직전 production 배포가 꾸 승인 run이다.**
  - `sha`가 **그 run이 기록한 base**와 일치한다.
- 이것은 "방금 꾸가 승인한 배포를 되돌리는 것"이고, 대상은 이미 승인된 라이브 내용이다. 그 밖의 `sha` 지정은 범위 밖이다.
- 발효 전에 `sha` 입력 롤백을 1회 실증한다(§6 P4).

## 7. 남은 위험

1. **고의 우회는 막지 못한다** (막내4 F2·막내2 F6).
   - 저장소 environments 0개, 브랜치 보호 불가(무료 비공개 플랜 403), CF 시크릿이 저장소 수준이다.
   - 그래서 자격증명을 가진 행위자는 게이트 없는 yml로 돌릴 수 있다.
   - 브랜치 yml 우회 시 ref 고정 검사도 함께 빠지므로, **탐지** 수단은 사후 대조 ③④뿐이다(막내4 17:11), **차단**은 못 한다. 차단하려면 GitHub 유료 플랜이나 environments 보호가 필요하다(이번 범위 밖).
2. **자격증명 공유**: M2의 `gh`가 작가님 계정이다. `approver=작가님`으로 입력하면 G-K를 건너뛴다.
   - 현행 ch5 1조 3항 한계와 같은 종류의 위험이다.
   - 흔적 정합(§3.3)과 사후 대조 ①로 탐지한다.
3. **문자열 탐지의 한계**: 기존 `fetch` 줄을 두고 엔드포인트 상수만 바꾸는 경우 등이다. `.js` 제외로 대부분 줄었지만, HTML 안의 기존 스크립트 블록 수정은 R5 `<script`가 추가 줄에 없으면 놓칠 수 있다.
   - 보완: 추가 줄이 **기존 `<script>` 블록 안**이면 차단하는 규칙을 P2에서 구현할 수 있는지 확인한다(가능하면 R5에 포함).
4. **예비 경로 배포**: 로컬 `wrangler`로 배포하면 CF Source와 실제 내용이 어긋날 수 있다. base 1순위를 run 기록으로 바꾸면서 영향이 줄었다.
