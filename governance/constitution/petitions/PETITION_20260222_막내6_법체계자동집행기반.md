## 지향성 성찰

### 왜 이 청구를 하는가

현행 법체계는 **사람이 읽고 지키는 법**으로 완성도가 높다. 헌법 11조, 법률 8장 34조, 개정 절차까지 정비되었다.

그러나 작가님이 02-17에 구상하신 미래가 있다:

> "플랜을 보고하고 승인받으면 필요노드를 생성, 각 역할을 배당하는 지시서를 깃에 올리면 생성된 막내들이 작동하고 보고폴더에 커밋하여 보고를 수신하는 체계"

이 비전이 실현되려면, 법은 **사람만 읽는 문서**에서 **기계도 파싱하는 규격**으로 진화해야 한다. 데몬(소넷이)이 지시서를 자동 분류하려면 YAML을 읽을 수 있어야 하고, 보고서를 수집하려면 `task_id`로 원본 지시서를 찾을 수 있어야 하고, 미분류 문서를 경보하려면 분류 규칙이 법률로 명문화되어 있어야 한다.

현재 법체계에 없는 것은 **자동 집행의 물리적 기반**이다.

### 무엇을 지향하는가

```
현재: 법 → 에이전트가 읽고 → 수동 준수
지향: 법 → 시행령(YAML 규격) → 데몬이 자동 집행 → 위반 자동 감지
```

이것은 작가님 철학의 기술적 구현이다:

| 작가님 격언 | 이 청구의 연결점 |
|-----------|--------------|
| "기억에 의존하지 말고 시스템에 의존" (01-08) | YAML = 기계에 기억을 위임하는 형식 |
| "멀티로 막내가 돌아가기 때문에 승인하고 지시하는것만도 정신없어" (02-15) | 자동 분류/라우팅 = 작가님 인지 부하 경감 |
| "헌법,법률,규정들은 문서를 운영하는 OS인 것이다" (02-20) | OS가 되려면 자동 실행 계층이 필요 |
| "법이 곧 체계고 시대를 아우르는 과학인 것이지" (02-20) | 과학은 재현 가능 = 자동화 가능 |
| "권한이 열려있을수록 규율이 중요하다" (02-15) | 데몬에게 권한 범위를 법으로 정의 |

### 무엇이 아닌가

- 폴더를 더 잘게 쪼개자는 구조 정리가 아니다.
- 서류 양식을 통일하자는 형식 표준화가 아니다.
- **법이 스스로 작동할 수 있는 기반**을 까는 것이다.

에이전트 수는 계속 늘어난다 (한/꾸 합류, 향후 팀 확장). 문서도 매일 3~8개씩 증가한다 (Phase 1 막내1 조사: 일 평균 3~8개). 수동 분류, 수동 라우팅, 수동 상태 추적은 조만간 한계에 도달한다. 그때 급하게 만드는 것이 아니라, 지금 기반을 깔아두는 것이 이 청구의 목적이다.

> "확장 가능성은 설계 단계에서 결정된다" (01-08)

## 청구 1: ch4 — YAML Frontmatter 필수 규격

### 현행

ch4 3조(파일 네이밍 규칙)가 9종 패턴을 정의하나, **파일 내부 메타데이터(YAML)에 대한 규격은 없다.**

### 모순

- ch4 3조의 파일명 패턴은 "사람이 보고 분류"하는 데는 충분하다.
- 그러나 데몬이 자동 분류하려면 파일 내부의 기계 가독 메타데이터가 필수.
- 현재 YAML frontmatter는 **관행**으로만 존재 (막내3 조사: 기존 파일 중 ~5개 YAML 미보유, `from` 표기 30파일 불일치, `priority` 표기 20파일 불일치).
- 법에 없으므로 에이전트마다 다른 형식으로 기재하고, 검증 근거도 없다.

### 청구안

ch4에 신설 조항:

> **모든 docs/monkos/ 및 docs/specs/ 문서에 YAML frontmatter를 필수 기재한다.**

**공통 필수 필드** (전 타입):

| 필드 | 타입 | 설명 |
|------|------|------|
| `type` | enum | task / report / spec / incident / design / session |
| `id` | string | 파일명과 동일 |
| `date` | string | `YYYY-MM-DD HH:MM KST` (헌법 제1조 준용) |
| `status` | enum | pending / in_progress / completed / archived / blocked |

**타입별 추가 필수 필드**:

| 타입 | 추가 필수 | 표기 통일 규칙 |
|------|----------|-------------|
| task | `from`, `to`, `priority` | from: 에이전트명 통일. priority: `P0`~`P3`만 |
| report | `task_id`, `from`, `to`, `result` | result: `success`/`partial`/`fail` |
| spec | `service`, `from` | service: ch4 5조 레지스트리 약칭 |
| incident | `service`, `severity` | severity: `critical`/`major`/`minor` |

**왜 이것이 구조화가 아닌 지향성인가**: YAML은 "서류 양식"이 아니라 **법과 코드의 접점**이다. YAML이 있으면 데몬은 `grep`이 아닌 `parse`로 문서를 다룰 수 있다. 법이 OS가 되는 첫 번째 물리 계층.

### 영향 범위

- ch4 3조 패턴 테이블에 "YAML 필수" 열 추가
- 기존 파일 점진적 보정 필요 (신규 파일부터 즉시 적용, 기존 ~95개 점진 보정)
- 사전 적합성 검토(CLAUDE.md 프로토콜)에서 YAML 검증 포함

## 청구 2: ch1 — 데몬 자동화 역할 법률 명문화

### 현행

ch1 1조에 소넷이(모니터링, 경량 자동화, 유지보수), 철창이(전략 브레인스토밍, 기획)가 **역할**로 정의되어 있으나, **자동화 업무의 구체적 범위와 권한 경계**가 미규정.

### 모순

- "경량 자동화"가 무엇을 포함하고 무엇을 포함하지 않는지 불명확.
- 데몬이 문서를 자동 이동할 수 있는가? YAML status를 갱신할 수 있는가? 자동 커밋할 수 있는가?
- 권한이 불명확하면, 데몬이 할 수 있는 일도 하지 않게 되거나(위축), 반대로 할 수 없는 일을 하게 된다(월권).
- "권한이 열려있을수록 규율이 중요하다" — 막내뿐 아니라 데몬에게도 적용되어야 한다.

### 청구안

ch1에 신설 조항:

> **데몬(소넷이/철창이)의 자동화 업무 범위와 권한을 명문화한다.**

| 권한 | 허용 | 금지 |
|------|------|------|
| 파일 이동 | 분류 규칙(ch4)에 따른 이동 | 분류 규칙 밖 이동 |
| YAML 갱신 | `status` 필드만 | 그 외 필드 수정 |
| 세션로그 | append만 | 기존 내용 수정/삭제 |
| 커밋 | `[daemon]` 접두 자동 커밋 | 사람 커밋 메시지 위장 |
| 알림 | 텔레그램 팀챗 발송 | 외부 서비스 호출 |
| 코드 | — | **전면 금지** |
| 삭제 | — | **전면 금지** |
| 배포 | — | **전면 금지** |

**왜 이것이 필요한가**: 데몬 없이는 자동 분류도, 보고서 수집도, 큐 관리도 구현할 수 없다. 데몬의 권한을 법으로 정하는 것이 자동 집행 체계의 두 번째 물리 계층.

### 영향 범위

- ch1 1조 소넷이/철창이 설명에 "자동화 범위: ch1 N조 참조" 추가
- ch7(막내 행동 강령)과 대구 — 막내에겐 3조(금지사항), 데몬에겐 본 조항
- 헌법 제8조(파괴적 명령 금지) 직접 준용

## 청구 3: ch7 — 보고서 작성 규격

### 현행

ch7에 보고서의 **형식**에 대한 규정이 없다. 1조(작업 흐름)에서 "완료 보고"를 언급하나, 어떤 필드가 있어야 하는지, 핵심요약이 필수인지 등은 미규정.

### 모순

- 막내마다 보고서 형식이 다르면, 쌍아가 검증할 때 매번 구조를 파악해야 한다.
- `task_id`가 없으면 데몬이 보고서와 원본 지시서를 연결할 수 없다.
- `변경 파일` 테이블이 없으면 쌍아 검증 체크리스트를 자동 생성할 수 없다.
- "핵심요약"이 있으면 작가님이 보고서 전문을 읽지 않고도 상태를 파악할 수 있다. 이것은 "멀티로 막내가 돌아가기 때문에 승인하고 지시하는것만도 정신없어"의 직접적 해소.

### 청구안

ch7에 신설 조항:

> **막내는 작업 완료 시 아래 필수 요소를 포함한 보고서를 작성한다.**

| 필수 요소 | 내용 | 자동 집행 연결 |
|----------|------|-------------|
| YAML frontmatter | `task_id`, `from`, `to`, `date`, `result` | 데몬이 `task_id`로 지시서 상태 갱신 |
| 결과 테이블 | 태스크별 상태 (✅/❌/⏳) | 쌍아 검증 자동화 |
| 완료 조건 체크 | 지시서 완료 조건 대비 | 누락 탐지 |
| 변경 파일 테이블 | 파일명 + 라인 + 유형 (코딩 작업) | git diff 자동 검증 |
| 핵심요약 | 보고서 말미 1~3줄 | 작가님 인지 부하 경감 |

### 영향 범위

- ch7 1조(작업 흐름) 마무리 절차에 "6조 규격 보고서 작성" 단계 삽입
- ch1 3조(엔드라인)의 `산출물` 필드와 연동

## 청구 4: ch3 — 보고서→세션로그 연동 규칙

### 현행

ch3에 세션로그와 보고서의 연동 규칙이 없다. 세션로그는 독립 문서, 보고서도 독립 문서. 시계열상 연결되지 않는다.

### 모순

- 02-22 하루에 막내 6명이 동시 작동. 각각 보고서를 냄. 세션로그에는 이 보고들의 흔적이 없다.
- 다음 날 세션로그를 읽어도 "어제 어떤 보고가 들어왔는지" 알 수 없다.
- 헌법 제1조(시계열 정합성)의 정신: 모든 사건은 시간축 위에 기록되어야 한다.

### 청구안

ch3에 신설 조항:

> **보고서 생성 시, 해당 날짜 세션로그에 요약 1줄을 append한다.**

형식:
```
### [HH:MM] 보고서 수신
- {agent}: {task_id} — {result} ({핵심요약 1줄})
```

주체: 보고서 작성 에이전트 또는 데몬.
제약: 세션로그가 해당 날짜에 존재하지 않으면 append 건너뜀 (세션로그 신규 생성 금지 — ch3 1조 준용).

### 영향 범위

- ch3 1조(기본 규칙)에 "4조 연동 참조" 추가
- 데몬 자동화 시 append 로직 구현 필요

## 청구 시스템 자체에 대한 부대 제안

### 현황

- amendment.md에 **절차**는 있으나, **청구의 물리적 형식과 접수처**는 미규정.
- 막내5가 `monkos-ops/03_개발/tasks/PETITION_*.md`에 선례를 만들었고, 본 청구도 동일 경로에 배치.
- 그러나 `PETITION`이라는 문서 유형은 **ch4 3조 패턴 테이블에 미등록**.

### 제안

**1. PETITION 문서 유형을 ch4 3조에 등록**

| # | 패턴 | 대상 폴더 | 예시 |
|---|------|----------|------|
| 10 | `PETITION_YYYYMMDD_{agent}_{topic}.md` | `monkos-ops/03_개발/tasks/` | `PETITION_20260222_막내6_법체계자동집행기반.md` |

**2. 청구 접수 경로 확정**

| 단계 | 행위 | 위치 |
|------|------|------|
| 작성 | 청구자가 PETITION 파일 생성 | `monkos-ops/03_개발/tasks/` |
| 접수 | 커밋+push → 쌍아에게 알림 | Git + 텔레그램 |
| 영향 평가 | 막내 2명+ 별도 조사 | 조사 보고서 → `monkos-ops/04_문서/reports/` |
| 합의 심의 | 쌍아+작가님 | 세션 중 결정 |
| 발효 | 법률 파일 갱신 + 세션로그 `[개정]` 기록 | `docs/infrastructure/laws/` |
