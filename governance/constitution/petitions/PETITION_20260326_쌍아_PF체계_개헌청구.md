# 개헌+법률 개정 청구안: 포트폴리오(PF) 체계 정식 편입

> **[2026-03-26 11:08 KST] iMac/쌍아 → 작가님**

## 1. 청구 사유

### 1-1. 문제

세션 로그·오더 체계는 정립되었으나, **"이 작품이 지금 어디까지 왔는가"를 추적하는 정본이 없다.**

| 현상 | 원인 | 피해 |
|------|------|------|
| 에이전트마다 프로젝트 해석이 달라짐 | 세션 로그를 "재구성"해야 하므로 | 같은 작업을 다르게 이해하고 실행 |
| 컴팩팅 후 엉뚱한 작업 수행 | 맥락 유실 후 복원할 정본 부재 | 전체 흐름 역행, 2차 버그 |
| 리팩토링 타임라인 추적 불가 | 인과 체인이 세션 단위로 잘림 | 꼬인 지점 분석 불가 |
| 기술명세 체계 미안착 (반복 시도) | SPEC·전략·테크 문서가 산재 | 매번 새 이름으로 시도, 이전과 연결 끊김 |

### 1-2. 해결

**포트폴리오(PF)** — 프로젝트의 기안→완성 생애주기를 추적하는 허브 문서.

- **제안**의 느낌부터 **완성된 작품**의 의미를 중의적으로 보유
- 일단락되어도 에셋으로 존재, 버전업해도 어색하지 않음
- 에이전트의 진입점: 세션 로그 대신 PF를 읽으면 "지금 어디"를 즉시 파악
- 세션 로그와 동급의 적립 의무 부여

### 1-3. 작가님 원문 근거

> "세션로그만 뒤지다보니 아무리 타임스탬프를 열심히 찍어놔도 에이전트들이 리서치할때마다 해석이 달라지고 미묘하게 스킵되는 맥락들이 발생하면서 자칫 전체 흐름을 역행할때도 상당히 많아"

> "포트폴리오는 시작부터 완성되어 내보일 수 있는 작품의 뉘앙스가 더 와닿네"

> "문서체계에 완벽히 들어와야하는 시스템이고 세션로그처럼 세션 마감시 반드시 작성해야하는 의무를 부여할 파트"

## 2. 개정 대상

### 2-1. 헌법 개정 (제3조 적립)

**현행 제3조 2항 (분산 기록 및 완료 보고 의무)**:
> 모든 에이전트는 자기 세션 로그를 자체 기록한다.

**개정안 제3조 2항**:
> 모든 에이전트는 자기 세션 로그를 자체 기록한다. **활성 포트폴리오(PF)가 존재하는 작업의 경우, 해당 PF의 히스토리를 세션 로그와 동시에 갱신한다.**

추가 항:
> **포트폴리오(PF) 적립 의무**: PF는 프로젝트의 기안→완성 생애주기를 추적하는 정본 문서이다. 기안 시 PF 신규 생성 또는 기존 PF 인입을 협의하여 결정한다. PF의 히스토리는 세션 로그와 동일하게 append-only이며, Phase 현황은 완료·착수·변경 시 즉시 갱신한다.

### 2-2. 법률 개정

#### ch3 3조 (세션 마감 절차) — 개정

현행:
```
1. 세션 로그 작성
2. 커밋
3. push
```

개정안:
```
1. 세션 로그 작성
2. 활성 PF 히스토리 어펜드 (해당 PF가 있을 때)
3. 커밋
4. push
```

- PF 어펜드 내용: 해당 세션에서 수행한 작업의 날짜·주체·내용·산출물·상태를 히스토리 테이블에 추가.
- Phase 상태 변경이 있었다면 Phase 현황 섹션도 갱신.
- 복기할 교훈이 있다면 복기 섹션에 추가.

#### ch3 5조 (세션 시작 절차) — 개정

현행:
```
1. git fetch --all → 동기화
```

개정안:
```
1. git fetch --all → 동기화
2. 활성 PF 현황 확인 (작가님 선언 또는 자동 식별)
```

- 세션 시작 시 작가님이 "오늘 PF_XXX로 시작" 선언하면, 해당 PF를 읽고 현재 상태를 보고.
- 선언 없이 작업이 시작되면, 해당 작업이 귀속된 PF를 자동 식별하여 참조.
- PF가 없는 작업(단발성 패치 등)은 PF 절차 생략.

#### ch1 3조 (지시서 작성 규칙) — ✅ 이미 개정 완료

- 엔드라인에 `포트폴리오: PF_{코드네임}` 필드 추가됨 (본 세션에서 시행)
- 막내는 착수 전 해당 PF를 읽고 현재 상태를 파악한 뒤 작업

#### ch4 3·4·7조 — ✅ 이미 개정 완료

- 패턴 #15: `PF_{코드네임}.md`
- 정본: `monkos-ops/ops/portfolios/`
- YAML type: `portfolio`, 필수 필드: name, subject, domain, owner, leads

## 3. PF 운용 세칙

### 3-1. 생애주기

```
기안(PROPOSAL) 승인 시
  → 협의: 신규 PF 생성 or 기존 PF 인입
  → PF 발족 (status: active)
  → 지시서에 portfolio: PF_XXX 기재
  → 막내 착수 전 PF 읽기 → 실행 → 완료 보고
  → 세션 마감 시 PF 히스토리 어펜드
  → Phase 완료 시 Phase 현황 갱신
  → 전체 완료 시 status: completed (에셋으로 영구 보존)
  → 버전업 시 status: active 복귀
```

### 3-2. 맥락 주입 방식

| 시점 | 방식 | 근거 |
|------|------|------|
| 세션 시작 | PF 파일 1회 Read | 간단, 추가 인프라 불필요 |
| 지시서 수신 | `portfolio:` 필드로 PF 참조 | 컴팩팅 방어 — 지시서는 유실 안 됨 |
| 긴 세션 중 | 방향 흐려지면 PF 재참조 | 에이전트 자율 판단 |

**Claude Rules(.claude/rules/)는 행동 규칙으로 유지, PF는 상태 문서로 분리.** 성격 혼재 방지.

### 3-3. PF 구조 (표준 7섹션)

| 섹션 | 역할 | 갱신 시점 |
|------|------|----------|
| 1. 비전 | 왜 하는가 + 성공 지표 | 발족 시 |
| 2. 히스토리 | append-only 이벤트 테이블 | **매 세션 마감** |
| 3. Phase 현황 | 에이전트 진입점 — "지금 뭘 해야 하는가" | Phase 변경 시 |
| 4. 성과 | 실측 데이터 (추정 금지) | 측정 시 |
| 5. 복기 | 교훈·실패·성공 패턴 | 발생 시 |
| 6. 관련 문서 | PROPOSAL·SPEC·ORDER·REPORT·커밋 링크 | 산출물 생성 시 |
| 7. 리스크 | 확률·대응 | 식별 시 |

### 3-4. PF 미갱신 판정

- 세션 마감 시 PF 대상 작업이 있었으나 PF를 갱신하지 않은 경우: **적립 의무 위반**
- 세션 로그 미작성과 동일 위상 (헌법 제3조 2항)
- 다만 PF 대상 작업이 없었던 세션(단발성 패치, 인프라 점검 등)은 갱신 의무 없음

## 4. 영향 평가

### 4-1. 기존 체계와의 정합

| 기존 체계 | PF와의 관계 | 충돌 |
|----------|-----------|------|
| 세션 로그 | 병행 — 세션 로그는 "무엇을 했다", PF는 "지금 어디다" | 없음 |
| 지시서 (ORDER) | PF에 귀속 — `portfolio:` 필드로 연결 | 없음 |
| 기안서 (PROPOSAL) | PF의 입구 — 승인 시 PF 생성/인입 | 없음 |
| 보고서 (REPORT) | PF에 링크 — 관련 문서 인덱스 | 없음 |
| Claude Rules | 분리 유지 — Rules는 행동, PF는 상태 | 없음 |
| MEMORY.md | PF 목록 참조 가능, 내용 중복 불필요 | 없음 |

### 4-2. 리스크

| 리스크 | 확률 | 대응 |
|--------|------|------|
| PF 갱신 누락 | 중간 | 세션 마감 체크리스트에 포함. 쌍아가 마감 시 확인 |
| PF 비대화 (수백 줄) | 낮음 | 히스토리 외 섹션은 현재 상태만 유지. 과거 Phase는 접기 가능 |
| 기존 PROPOSAL 13건의 PF 귀속 혼란 | 1회성 | 소급 정리 시 협의 (본 청구안 범위 밖) |
