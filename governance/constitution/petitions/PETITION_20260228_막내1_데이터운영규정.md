## 사안 1: scripts/ 귀속 확정

### 현행

ch4 1조 현재:

> *"scripts/는 귀속 미확정. 부서 결정 전까지 현 위치 유지."*

### 문제점

- scripts/ 폴더에 이미 5개 파일이 운용 중 (gcs_migrate.sh, md_to_pdf.py, 철창이_watcher.sh, img_clip.py, img_pick.py)
- 운영 데이터 조회 도구(`ops-db/`)도 scripts/ 배치 예정
- 그러나 법적 귀속이 없어 소관·변경 권한·정본 위치 모두 불명
- README.md에 `소관: 막내`로 기재되어 있으나 법률 근거 없음

### 후보 분석

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **A) ops/ 부서 직속** | 운영 도구 성격 명확, 정본 위치 통일 | 일부 스크립트(md_to_pdf, img_*)는 ops와 무관 |
| **B) 독립 유지 (역할 명시)** | 기존 구조 변경 없음, 범용 유틸 성격 보존 | 부서 없이 소관 불명 지속 |

### 개정안: B) 독립 유지, 역할 명시

**선정 근거**:
1. scripts/ 내 파일들의 성격이 다양함 — GCS 마이그레이션(인프라), PDF 변환(문서), 이미지 처리(도구), 운영 조회(ops) 등 특정 부서에 일괄 귀속 불합리
2. MEMORY.md에 이미 `scripts/ = 범용 유틸`로 정의되어 있음
3. 하위 폴더로 용도별 분리하여 관리 가능 (`scripts/ops-db/`, `scripts/tools/` 등)
4. 필요 시 하위 폴더 단위로 부서 소관 지정 가능 (예: `scripts/ops-db/` → ops 소관)

**ch4 1조 개정안** — 현행 문구 교체:

```

  예: scripts/ops-db/ → ops 소관
```

## 사안 2: 데이터 운영 규정 신설

### 현행

법률 ch1~ch8 전체에 운영 데이터 조회·관리·보호에 관한 규정이 **없다**.
운영 데이터 도구의 정본 위치, 조회 권한, 개인정보 보호 원칙, 삭제 절차 등이 미규정.

### 후보 분석

| 선택지 | 장점 | 단점 |
|--------|------|------|
| **A) ch4 확장** (8조 신설) | 문서/폴더 구조 장에 자연스럽게 편입, 정본 위치·파일명 규칙과 일체 운용 | 조항 수 증가 (7조→8조) |
| **B) ch9 신설** ("데이터 운영") | 독립 장으로 확장 용이, 향후 데이터 거버넌스 체계의 거점 | 현 규모에 비해 과도, 헌법 인덱스 갱신 필요 |

### 선정: A) ch4 확장 — 제8조 "운영 데이터 접근" 신설

**선정 근거**:
1. 운영 데이터 도구의 **정본 위치·출력물 경로**가 핵심 — ch4(문서/폴더 구조)의 본래 소관
2. 현재 규정 분량이 독립 장을 정당화할 수준이 아님 (5개 항 내외)
3. ch4 4조 정본 테이블, 5조 서비스 약칭과 직접 연동 — 동일 장에서 참조 효율적
4. 향후 데이터 거버넌스가 대폭 확장되면 그때 ch9 분리를 재청구

### ch4 제8조 신설안

```markdown
### 8조: 운영 데이터 접근

운영 데이터 조회·관리 도구의 위치, 권한, 보호 원칙을 규정한다.

**1항: 도구 정본 위치**

| 도구 | 정본 위치 | 비고 |
|------|----------|------|
| ops-db CLI | `scripts/ops-db/` | Firestore 조회·관리 |
| 보고서 출력물 | `monkos-ops/ops/reports/data/` | CSV/JSON 자동 생성 |

**2항: 조회 권한 체계**

| 등급 | 대상 | 권한 |
|------|------|------|
| L1 (전체) | 작가님, 에이전트 | 모든 명령, 마스킹 해제 가능 |
| L2 (운영) | 꾸 (SSH 접근) | 모든 조회 명령, 마스킹 해제 가능, 삭제 금지 |
| L3 (조회) | 한송이 (텔레그램 경유) | 통계·요약만, 개인정보 항상 마스킹 |

**3항: 개인정보 보호 원칙**

1. paymentKey는 **항상** 마스킹한다 (등급 불문).
2. 이메일은 L3 등급 조회 시 항상 마스킹한다.
3. `--mask` 옵션은 L1/L2에서 선택 적용 가능하다.
4. 출력물(CSV/JSON)에 마스킹 적용 여부를 파일명에 표시하지 않는다
   (파일 내부 첫 행에 `# masked: true/false` 주석으로 기재).

**4항: 데이터 삭제·리셋 절차**

1. 삭제 명령(`user-reset`)은 L1 등급만 실행 가능하다.
2. 삭제 전 대상 문서 목록을 반드시 출력하고 확인 프롬프트(y/N)를 거친다.
3. 크레딧이 잔존하는 계정은 추가 경고를 표시한다.
4. 삭제 대상: users, telegram_links, telegramGateCodes 문서.
   대화 로그(chat_conversations, cs_conversations)는 삭제하지 않는다.

**5항: 보고서 출력물 관리**

1. CSV/JSON 출력물의 정본 위치: `monkos-ops/ops/reports/data/`
2. 파일명 규칙: `{명령}_{YYYYMMDD_HHMMSS}.csv` (ch4 3조 적용 제외 — 자동 생성 데이터)
3. 보고서는 Git 추적 대상이 아니다 (`.gitignore`에 등록).
4. GDrive 업로드 시 공유 폴더에 복사한다.
```

### 연동 갱신

#### ch4 4조 정본 테이블 — 2행 추가

```
| 운영 데이터 도구 | `scripts/ops-db/` | — | 범용 유틸(scripts/) 소관 |
| 운영 보고서 | `monkos-ops/ops/reports/data/` | — | Git 미추적, 자동 생성 |
```

#### ch4 5조 서비스 약칭 — 갱신 불필요

현행 `ops` 약칭이 이미 등록됨: `ops | 운영 체계 (monkos-ops) | 비배포 (인프라)`
ops-db는 ops의 하위 도구이므로 별도 등록 불필요.
