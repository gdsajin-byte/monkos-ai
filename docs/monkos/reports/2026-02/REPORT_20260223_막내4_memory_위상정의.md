## 2. 4계층 위계와의 관계 분석

### 현행 4계층

| 계층 | 성격 | 물리 위치 | Git 추적 | 공유 범위 |
|------|------|----------|---------|----------|
| 1 헌법 | 커널, 불변 원칙 | CLAUDE.md | ✅ | 전 에이전트 |
| 2 거버넌스 | 법률+역사+철학 | governance/ | ✅ | 전 에이전트 |
| 3 세칙 | 부서별 운영 규정 | monkos-ops/ README | ✅ | 전 에이전트 |
| 4 데이터 | 실행 산출물 | 부서 하위 | ✅ | 전 에이전트 |
| ? **MEMORY** | **규정 (헌법 선언)** | **~/.claude/...** | **❌** | **디바이스 내** |

### 질문 1: MEMORY는 4계층 중 어디에 해당하는가?

**어디에도 해당하지 않는다.** 이유:

1. **"규정"은 "세칙"과 동일하지 않다.**
   - CLAUDE.md 문서 위계의 "규정"(3행)은 변경 권한이 "에이전트 자율"
   - ch4 1조의 "세칙"(3층)은 부서별 운영 규정으로 monkos-ops/ README에 위치
   - 두 용어가 같은 계층을 지칭하는지 명시적 매핑이 없다
   - 실질적 차이: 세칙은 **조직 단위**(부서), MEMORY는 **장치 단위**(디바이스)

2. **물리적 기반이 완전히 다르다.**
   - 4계층 1~4층: 전부 프로젝트 디렉토리 내, Git 추적, 전 에이전트 공유
   - MEMORY: 프로젝트 디렉토리 밖(`~/.claude/`), Git 비추적, 디바이스 격리
   - 이것은 단순한 위치 차이가 아닌 **존재론적 차이** — 4계층은 "프로젝트의 일부", MEMORY는 "에이전트의 일부"

3. **변경 통제가 4계층 어느 것과도 다르다.**
   - 헌법: 5인 만장일치. 거버넌스: 쌍아+작가님 합의. 세칙: 부서 자율(향후 규정). 데이터: 자유
   - MEMORY: "에이전트 자율 → 변경 보고" — 이것은 세칙보다 느슨하고 데이터보다 공식적

### 질문 2: Git 비추적이라는 물리적 특성이 위계 배치에 영향을 미치는가?

**결정적으로 영향을 미친다.**

Git 추적 여부가 결정하는 것:
- **버전 관리**: Git 추적 → 변경 이력 추적 가능. MEMORY → 이력 없음, 덮어쓰기만 가능
- **공유 범위**: Git 추적 → `git pull` 한 번으로 전 에이전트 동기화. MEMORY → 디바이스 격리, 동기화 메커니즘 없음
- **검증 가능성**: Git 추적 → 특정 시점 상태 복원 가능. MEMORY → 현재 상태만 존재
- **법적 효력**: Git에 있는 법률은 "확정된 규범"이다. Git 밖에 있는 MEMORY는 "각 에이전트가 알고 있는 것"이다

Git 비추적은 MEMORY를 4계층 **안에** 놓을 수 없는 물리적 장벽이다. 4계층은 Git 안의 세계이고, MEMORY는 Git 밖의 세계다.

### 질문 3: MEMORY는 법체계의 일부인가, 법체계 바깥의 보조 시스템인가?

**선언적 지위와 물리적 실체 사이에 괴리가 있다.**

| 관점 | 판정 | 근거 |
|------|------|------|
| 선언적 | 법체계 **내부** | CLAUDE.md 문서 위계에 명시 ("규정") |
| 물리적 | 법체계 **외부** | Git 비추적, 디바이스 격리, 버전 이력 없음 |
| 기능적 | **경계** | 법률이 MEMORY를 참조(ch5), 법률이 MEMORY 확인을 의무화(ch7 5조) — 법체계에 영향을 미치지만 법 자체는 아님 |

비유하자면:
- 법체계(4계층) = **헌법전** (인쇄된 법전, 공식 배포, 전 국민 열람 가능)
- MEMORY = **판사의 수첩** (법전을 참조하되, 개인의 경험·해석·메모를 포함. 공식 문서가 아니지만 판결에 영향을 미침)

### "각 부서의 세칙" vs "각 개인의 수첩"

40%의 "공식 사실"과 25%의 "운용 규칙"이 **디바이스 격리된 비추적 파일**에 있다는 것이 구조적 문제의 핵심이다.

| 항목 | laws/ | MEMORY |

| **성격** | 규범 ("어떻게 해야 하는가") | 사실+규범 혼재 ("무엇이 있고 어떻게 됐는가") |

### 선택지 A: "에이전트 OS의 RAM" — 법체계 외부 보조 시스템

```

└──────────────────┘         └─────────────────┘
```

**정의**: MEMORY는 4계층 바깥의 **보조 시스템**이다. 법체계에 선언된 "규정"이라는 이름을 **"에이전트 참조 메모리"**로 재정의한다.

**근거**:
- 물리적 실체(Git 비추적, 디바이스 격리)가 4계층과 다르다
- 변경 통제(에이전트 자율)가 법체계의 어떤 계층과도 일치하지 않는다
- 비유: 컴퓨터의 ROM(법률, 불변)과 RAM(MEMORY, 휘발+즉시 접근)의 관계

**장점**:
- 현실에 가장 부합 (현재 MEMORY가 실제로 작동하는 방식 그대로)
- 4계층 위계를 건드리지 않음 (개헌 불필요)
- MEMORY의 "에이전트 자율 갱신" 특성을 제도적으로 인정

**단점**:
- MEMORY에 담긴 "공식 사실"(API 명세, 인프라 IP)의 신뢰성 보장 메커니즘이 부재
- "법체계 외부"이면 ch7 5조(확인 의무)의 근거가 약해짐 — 법체계 외부 문서 확인을 법률로 강제하는 구조

**필요 조치**:
1. CLAUDE.md 문서 위계 3행 "규정" → "에이전트 참조 메모리"로 재정의 (용어 정비)
2. 4계층 위계 문서에 "MEMORY는 4계층 외부 보조 시스템" 명시
3. 공식 사실(API 명세, IP 등)은 Git 추적 문서(infrastructure/ 또는 ops/)에 정본을 두고, MEMORY는 그 "캐시"임을 명시

### 선택지 B: "5번째 계층" — 법체계 확장

```
5계층 (확장된 법체계)
┌──────────────────┐
│ 1. 헌법           │  CLAUDE.md (Git, 불변)
│ 2. 거버넌스       │  governance/ (Git, 합의)
│ 3. 세칙           │  ops README (Git, 부서 자율)
│ 4. 규정           │  MEMORY (비Git, 에이전트 자율) ← 신설
│ 5. 데이터         │  부서 하위 (Git, 자유)
└──────────────────┘
```

**정의**: MEMORY를 4계층과 데이터 사이에 **"규정"**이라는 독립 계층으로 공식 편입한다. 현행 4계층 → 5계층으로 확장.

**근거**:
- 헌법이 이미 "규정"이라 선언하고 있다 — 이를 공식 계층화
- MEMORY의 실질적 영향력(매 세션 자동 인젝션)은 세칙보다 높다
- 세칙(3층)과 데이터(4층) 사이에 "에이전트 자율 갱신"이라는 고유한 변경 통제를 갖는 층이 자연스럽다

**장점**:
- 선언적 지위와 물리적 실체의 괴리를 해소
- MEMORY에 대한 법적 근거가 명확해짐 (ch7 5조 등의 근거 강화)
- 향후 MEMORY 관리 규칙을 법률로 제정할 수 있는 틀 마련

**단점**:
- Git 비추적 엔티티를 법체계에 편입하는 것의 모순 — 검증/버전관리/복원이 불가능한 것을 "법"으로 볼 수 있는가
- 4계층 위계가 헌법 개정(2026-02-22 만장일치)으로 확정된 지 1일. 즉시 5계층으로 확장하면 안정성 훼손
- 에이전트마다 다른 MEMORY를 "동일 계층"으로 취급하는 것의 논리적 문제

**필요 조치**:
1. ch4 1조 4계층 → 5계층으로 개정 (법률 개정)
2. governance/README.md 위계 테이블 갱신
3. MEMORY 관리 법률 신설 (갱신 의무, 정본 구분, 동기화 규칙)

### 선택지 C: "이중 성격 분리" — 공식 사실은 Git으로, 경험 지식은 MEMORY 잔류

```
4계층 (법체계, Git 내부)        MEMORY (경험 계층, Git 외부)
┌──────────────────┐         ┌─────────────────┐
│ 1. 헌법           │         │  경험 지식 ~20%   │
│ 2. 거버넌스       │         │  디버깅 교훈      │
│ 3. 세칙           │         │  작가님 인사이트   │
│ 4. 데이터         │         │  + 인덱스 ~15%    │
│                  │         │  (Git 문서 참조)   │
│ + 인프라 사실 문서  │         └─────────────────┘
│   (API, IP, URL)  │
│   ~65% MEMORY에서  │
│   Git 정본으로 이관 │
└──────────────────┘
```

**정의**: MEMORY의 내용을 성격별로 분리한다. "공식 사실"(API 명세, 인프라 IP, 서비스 URL 등 ~65%)은 Git 추적 문서로 정본을 이관하고, "경험 지식"(디버깅 교훈, 작가님 인사이트 등 ~35%)만 MEMORY에 잔류시킨다. MEMORY는 "인덱스 + 경험"으로 경량화.

**근거**:
- 3절 분석에서 확인된 MEMORY 내용 4분류 중, "공식 사실"(40%)과 "운용 규칙"(25%)은 Git에 있어야 할 정보
- 이 정보가 Git 밖에 있어서 발생하는 문제(디바이스간 불일치, 검증 불가)가 반복
- MEMORY를 없애는 것이 아니라, **역할을 명확히 한정**하는 접근

**장점**:
- MEMORY의 200줄 포화 문제를 구조적으로 해결 (65% 이관 → ~70줄로 축소)
- 디바이스간 불일치 문제 해소 (공식 사실은 Git에서 동기화)
- 4계층 위계를 건드리지 않음
- MEMORY의 고유 가치(경험 지식, 즉시 접근)를 유지

**단점**:
- 이관 작업의 규모 (현행 MEMORY ~130줄 분량을 Git 문서로 옮겨야 함)
- "공식 사실"의 정본이 이관된 후에도, 에이전트가 MEMORY의 "캐시"를 참조하면 구버전 위험은 잔존
- "어디까지가 공식 사실이고 어디까지가 경험인가"의 분류 기준이 필요

**필요 조치**:
1. MEMORY 내용 4분류(공식 사실 / 운용 규칙 / 경험 지식 / 인덱스)의 정본 위치 확정
2. 공식 사실 → docs/infrastructure/ 또는 monkos-ops/tech/specs/로 이관
3. MEMORY를 "인덱스(Git 문서 참조 링크) + 경험 지식"으로 재구성
4. 갱신 규칙: Git 정본 변경 시 MEMORY 캐시도 갱신하는 트리거 정의 (막내6 리서치 영역과 교차)

## 핵심요약

> MEMORY.md는 헌법에서 "규정"으로 선언되었으나, 4계층 위계(헌법→거버넌스→세칙→데이터)의 **어디에도 배치되어 있지 않다**. Git 비추적·디바이스 격리·에이전트 자율 갱신이라는 물리적 특성은 Git 기반 4계층과 근본적으로 다르며, 내용의 65%는 Git에 있어야 할 공식 사실이다. 위상 배치안 3가지를 제시한다: (A) 법체계 외부 보조 시스템, (B) 5번째 계층으로 편입, (C) 공식 사실 분리 후 경험 계층으로 재정의.
