## 1. 파일명 → 폴더 자동 분류 규격

### 1.1 파일명 패턴 매핑 규칙 (7종)

| # | 파일명 패턴 | 대상 폴더 | 추출 메타데이터 |
|---|------------|----------|---------------|
| 1 | `TASK_YYYYMMDD_*.md` | `docs/monkos/tasks/YYYY-MM/` | date, agent, task_name |
| 2 | `REPORT_YYYYMMDD_*.md` | `docs/monkos/reports/YYYY-MM/` | date, topic |
| 3 | `SPEC_*.md` | `docs/monkos/specs/` | service_name |
| 4 | `INCIDENT_YYYYMMDD_*.md` | `docs/monkos/incidents/YYYY-MM/` | date, service |
| 5 | `DESIGN_YYYYMMDD_*.md` | `docs/monkos/designs/YYYY-MM/` | date, feature |
| 6 | `SPRINT_*.md` | `docs/monkos/sprints/` | sprint_range |
| 7 | `YYYYMMDD_*session*.md` | `docs/corpus/sessions/YYYY-MM/` | date |

### 1.2 파일명 정규식

```
^(TASK|REPORT|INCIDENT|DESIGN|SPRINT|SPEC)_(\d{8})?_?(.+)\.md$
```

그룹 추출:
- `$1` = type (TASK / REPORT / INCIDENT / DESIGN / SPRINT / SPEC)
- `$2` = date (YYYYMMDD, 없으면 null)
- `$3` = name (에이전트_작업명 또는 토픽)

### 1.3 파일명에서 추출하는 메타데이터

| 필드 | 추출 규칙 | 예시 |
|------|----------|------|
| `type` | 접두사 (TASK/REPORT/...) | `TASK` |
| `date` | `YYYYMMDD` 부분 → `YYYY-MM-DD` | `20260222` → `2026-02-22` |
| `agent` | TASK일 때 `_막내N_` 또는 `_에이전트명_` | `막내3` |
| `name` | 마지막 세그먼트 (한글/영문) | `포탈결제매핑v2` |

### 1.4 분류 불가능 파일 처리

- 위 7종 패턴 미매칭 → `docs/monkos/_unsorted/` 에 보관
- 데몬이 `_unsorted/` 경보 발생 → 쌍아가 수동 분류 또는 파일명 보정
- 7일 이상 미분류 → 세션로그에 경고 기록

### 1.5 현행 문서 대비 변경점

현재 `docs/monkos/`에 모든 파일이 플랫(flat) 배치. 위 구조 적용 시:
- 기존 50+ 파일 → `tasks/`, `reports/`, `specs/`, `incidents/`, `designs/`, `sprints/` 6개 서브폴더
- 월별 분류로 시계열 탐색 용이
- SPEC, SPRINT는 날짜 없는 경우가 많아 월별 분류 없이 서비스명/범위로 분류

## 2. YAML Frontmatter 표준 규격

### 2.1 공통 필수 필드 (모든 문서 타입)

```yaml
---
type: task | spec | report | incident | design | session
id: "{TYPE}_{YYYYMMDD}_{name}"    # 파일명과 동일
date: "YYYY-MM-DD HH:MM KST"
status: pending | in_progress | completed | archived | blocked
---
```

### 2.2 타입별 필수/선택 필드

#### 지시서 (task)

| 필드 | 필수 | 타입 | 설명 | 표기 규칙 |
|------|------|------|------|----------|
| `type` | ✅ | string | `task` 고정 | — |
| `id` | ✅ | string | 파일명과 동일 | `TASK_YYYYMMDD_에이전트_작업명` |
| `from` | ✅ | string | 발행자 | **`쌍아`** (통일. `M1/쌍아` 금지) |
| `to` | ✅ | string | 수신자 | `막내1` / `막내2` / `막내3` / `막내(any)` |
| `date` | ✅ | string | KST | `YYYY-MM-DD HH:MM KST` |
| `status` | ✅ | enum | 진행 상태 | `pending` → `in_progress` → `completed` |
| `priority` | ✅ | enum | 우선도 | **`P0` / `P1` / `P2` / `P3`** (HIGH/CRITICAL 금지) |
| `tags` | ⬜ | array | 키워드 | `[service, feature, keyword]` |
| `depends_on` | ⬜ | array | 선행 지시서 ID | `[]` 또는 `[TASK_20260222_xxx]` |
| `parent` | ⬜ | string | 보정 지시서의 원본 ID | 보정 지시서에만 사용 |

## 3. 지시서 표준 템플릿


```markdown
# 에이전트명: 작업명

## 배경
- 상황 (왜 이 작업이 필요한가)
- 문제 (현재 무엇이 잘못되었는가)
- 목표 (이 작업의 기대 결과)

## TASK

### T1: 제목
- **파일**: `path/to/file`
- **위치**: line N 부근
- **현재**: (코드 또는 설명)
- **변경**: (코드 또는 설명)

### T2: 제목
- **파일**: `path/to/file`
- **변경**: (설명)

## 대상 파일
- `path/to/file1` (T1)
- `path/to/file2` (T2)

## 건드리지 않는 파일
- `path/to/protected` (이유)

## 완료 조건
- [ ] 조건 1
- [ ] 조건 2
- [ ] 완료 보고 (✅❌💡⏳📁🔀 형식)

## 주의
- 헌법/법률 인용 (예: **헌법 제6조**)
- 배포 정책 (커밋 여부, main 머지 여부)

## 핵심요약
> TN개 작업, 파일 M개 수정, 핵심 변경 한줄 요약.
```

### 3.2 소형 보정 지시서 (핫픽스 / 누락 보정)

```yaml
---
type: task
id: TASK_YYYYMMDD_에이전트_보정명
from: 쌍아
to: 막내N
date: YYYY-MM-DD HH:MM KST
status: pending
priority: P0
tags: [hotfix]
parent: TASK_YYYYMMDD_원본지시서ID
---
```

```markdown
# 에이전트명: 보정명

## 배경
- 원본 지시서: `{parent}` 완료 후 누락 발견
- 누락 내용 1줄 요약

## TASK

### T1: 제목
- **파일**: `path/to/file`
- **현재**: `코드`
- **변경**: `코드`

## 완료 조건
- [ ] 변경 확인
- [ ] 커밋 정책 (커밋하지 말 것 / 커밋 후 push)

## 핵심요약
> N줄 변경. 과잉 수정 금지.
```

### 3.3 대형 vs 소형 구분 기준

| 기준 | 대형 | 소형 (보정) |
|------|------|-----------|
| 작업 수 | T2 이상 | T1만 |
| 배경 설명 | 상황+문제+목표 3단 | 원본 참조 + 1줄 |
| `parent` 필드 | 없음 | **필수** |
| `건드리지 않는 파일` | 필수 | 생략 가능 |
| `핵심요약` | 3줄 이내 | 1줄 |

### 4.3 쌍아 검증용 자동 체크리스트 생성 규격

보고서의 `변경 파일` 테이블 + 지시서의 `완료 조건`을 파싱하면 자동 생성 가능:

```markdown
## 쌍아 검증 체크리스트 (자동 생성)
- [ ] `path/to/file1` L78~83 — git diff 확인
- [ ] `path/to/file2` L815 — 값 `0 → 80` 확인
- [ ] 완료 조건 1: (지시서에서 복사)
- [ ] 완료 조건 2: (지시서에서 복사)
```

**생성 로직**: 보고서 `변경 파일` 테이블 파싱 → 파일+라인 추출 → `git diff` 명령 생성 → 지시서 `완료 조건` append

## 5. 데몬 자동 분류 시나리오 3건

### 5.1 시나리오 1: 쌍아 → TASK 생성 → 자동 분류 + 라우팅

```
트리거: PostToolUse (Write) 훅 — 파일명 TASK_*.md 감지
   ↓
파싱: YAML frontmatter에서 to, priority, depends_on 추출
   ↓
분류: docs/monkos/tasks/YYYY-MM/ 로 이동 (또는 심볼릭 링크)
   ↓
라우팅: to 필드 기준으로 해당 막내의 작업 큐에 등록
   ├── 파일: docs/monkos/_queue/{agent}_queue.json
   └── 항목: { id, priority, depends_on, created_at }
   ↓
알림: 텔레그램 팀챗에 "📋 새 지시서: {id} → {to}" 전송
   ↓
에러: YAML 파싱 실패 → _unsorted/ 이동 + 경고 로그
```

```json
      "status": "pending",
      "created_at": "2026-02-22 07:18 KST"
    }
  ]
}
```

### 5.2 시나리오 2: 막내 → REPORT 생성 → 자동 수집 + 지시서 상태 갱신

```
트리거: Stop 훅 — 막내 세션 종료 감지
   또는 PostToolUse (Write) — REPORT_*.md 감지
   ↓
파싱: YAML에서 task_id, result 추출
   ↓
분류: docs/monkos/reports/YYYY-MM/ 로 이동
   ↓
상태 갱신:
   ├── 원본 지시서의 YAML status → completed (result=success)
   ├── 또는 → blocked (result=partial/fail)
   └── 큐에서 해당 task 제거
   ↓
쌍아 통보:
   ├── 검증 체크리스트 자동 생성 (§4.3 규격)
   └── 텔레그램: "✅ 완료: {task_id} by {from}"
   ↓
세션로그 append: 해당 날짜 세션로그에 보고 요약 자동 추가
   ↓
에러: task_id 매칭 실패 → 수동 매핑 요청 경고
```

### 5.3 시나리오 3: 텔레그램 수신 → 디바이스 데몬 → 파일 배치

```
트리거: 텔레그램 봇이 .md 파일 수신 (팀 채널)
   ↓
수신: 디바이스 데몬(철창이/소넷이)이 파일 다운로드
   ├── M1(iMac): /Users/developer/monk_project/docs/monkos/_inbox/
   └── 기타 디바이스: Tailscale 경유 → 동일 경로
   ↓
파싱: 파일명 패턴 매칭 (§1.1 규칙)
   ├── 매칭 성공 → 해당 폴더로 이동
   └── 매칭 실패 → _unsorted/ + 경고
   ↓
YAML 검증:
   ├── 필수 필드 존재 확인 (§2.2 규격)
   ├── 누락 시 → 파일에 WARNING 주석 추가 + 경고
   └── 통과 시 → 정상 분류
   ↓
Git: git add + 자동 커밋 (메시지: "[daemon] 문서 분류: {filename}")
   ↓
에러:
   ├── 파일명/YAML 둘 다 실패 → _unsorted/ + 긴급 경고
   └── Git 충돌 → 분류만 하고 커밋 보류 + 수동 해결 요청
```

### 5.4 시나리오 공통 — 에러 처리 원칙

| 에러 유형 | 처리 | 알림 레벨 |
|----------|------|----------|
| YAML 파싱 실패 | `_unsorted/` 이동 | ⚠️ 경고 |
| 파일명 패턴 미매칭 | `_unsorted/` 이동 | ⚠️ 경고 |
| `to` 필드 미인식 에이전트 | 큐 등록 건너뜀 | ⚠️ 경고 |
| 원본 지시서 ID 미존재 | 보고서만 분류, 상태 갱신 건너뜀 | ⚠️ 경고 |
| Git 충돌 | 분류만 실행, 커밋 보류 | 🚨 긴급 |
| 7일 이상 `_unsorted/` 체류 | 세션로그 경고 | 🚨 긴급 |

```
│   ├── tasks/YYYY-MM/      ← 지시서 (월별)
│   ├── reports/YYYY-MM/     ← 보고서 (월별)
│   ├── specs/               ← 기술명세
│   ├── incidents/YYYY-MM/   ← 장애기록 (월별)
│   ├── designs/YYYY-MM/     ← 설계문서 (월별)
│   ├── sprints/             ← 스프린트
│   ├── _queue/              ← 에이전트별 작업 큐 (JSON)
│   ├── _inbox/              ← 텔레그램 수신 대기
│   └── _unsorted/           ← 미분류 문서
```

**신규 3조 제안: 파일명 표준 규격**

> 모든 `docs/monkos/` 문서는 `{TYPE}_{YYYYMMDD}_{name}.md` 형식을 따른다.
> TYPE: TASK / REPORT / SPEC / INCIDENT / DESIGN / SPRINT
> YAML frontmatter 필수. 필수 필드: type, id, date, status.

**신규 4조 제안: 자동 분류 규칙**

> 데몬(철창이/소넷이)은 파일명 패턴과 YAML type 필드를 기준으로 자동 분류한다.
> 분류 불가능 파일은 `_unsorted/`에 보관하며, 7일 이상 미분류 시 경고한다.

### 6.2 법률 제3장 (세션 로그) 개정 제안

- 세션로그 자동 append 규칙 추가: 보고서 생성 시 해당 날짜 세션로그에 요약 자동 추가
- 형식: `[HH:MM] {agent}: {task_id} — {result}` 1줄

### 6.3 법률 제7장 (막내 행동 강령) 개정 제안

- 보고서 작성 시 `task_id` 필드 **필수** (원본 지시서와 연결)
- `핵심요약` 섹션 **필수** (보고 말미)
- `변경 파일` 테이블 **필수** (코딩 작업의 경우)

### 6.4 헌법 영향 없음

본 규격은 헌법 조항과 충돌하지 않음. 제2조(완료 보고 의무)의 형식을 구체화하는 하위 법률/규정 수준.
