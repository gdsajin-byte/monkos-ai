## 2. 기존 유형과의 경계선 분석

### 2-1. ORDER_ vs TASK_ — 왜 같은 유형이 아닌가?

| 비교 축 | ORDER_ | TASK_ |
|---------|--------|-------|
| **파일명 구조** | `ORDER_YYYYMMDD_{topic}.md` | `TASK_YYYYMMDD_{agent}_{name}.md` |
| **에이전트 필드** | 없음 (topic 중심) | 있음 (수행자 특정) |
| **발행 단위** | 미션 단위 (1 ORDER → N TASK 가능) | 에이전트 단위 (1인 1 TASK) |
| **발행자** | 쌍아/철창이/작가님 (설계·전략 레벨) | 쌍아 (지시서), 작가님 (직접 지시) |
| **정본 위치** | `monkos-ops/ops/orders/` (운영체제) | `docs/monkos/tasks/` (참고문헌체제) |
| **수명주기** | 미션 종료까지 유효 | 에이전트 실행 완료 시 종료 |
| **산출물 링크** | ORDER → TASK → REPORT | TASK → REPORT (task_id 링크) |

**핵심 차이: 계층이 다르다.**

```
ORDER (미션 지시)
├── TASK_A (막내A 실행분)
│   └── REPORT_A (막내A 결과보고)
├── TASK_B (막내B 실행분)
│   └── REPORT_B (막내B 결과보고)
└── RESEARCH (조사 산출물)
```

**실례**: `ORDER_20260223_KOMOJU전수조사.md`는 막내A(계약/수수료)와 막내B(기술/결제수단)를 병렬 배치하는 미션 지시. 각 막내의 개별 실행은 TASK가 될 수 있다.

**통합 불가 근거**: ORDER에는 에이전트 필드가 없고, TASK에는 있다. 파일명 필드가 다르면 같은 패턴으로 등록할 수 없다. 또한 정본 위치가 ops/(운영체제) vs docs/(참고문헌체제)로 분리되어 있어 작가님의 "옵스는 운영체제, 독스는 참고문헌체제" 원칙에 부합한다.

### 2-2. RESEARCH_ vs REPORT_ — 왜 같은 유형이 아닌가?

| 비교 축 | RESEARCH_ | REPORT_ |
|---------|-----------|---------|
| **파일명 구조** | `RESEARCH_YYYYMMDD_{topic}_{detail}.md` | `REPORT_YYYYMMDD_{topic}.md` |
| **성격** | 의사결정 지원 (advisory) | 실행 결과 확인 (confirmatory) |
| **트리거** | ORDER 또는 어젠다 아이템 | TASK 완료 |
| **내용 패턴** | 선택지 제시, 패턴 분석, 현행 분석 | 결과 집계, 판정, 완료 조건 체크 |
| **YAML 링크** | `order_ref` (ORDER에 연결) | `task_id` (TASK에 연결) |
| **정본 위치** | `monkos-ops/ops/agenda/` (운영체제) | `docs/monkos/reports/` (참고문헌체제) |

**핵심 차이: 목적이 다르다.**

- REPORT = "이것을 했고, 결과는 이렇습니다" (과거형, 확인)
- RESEARCH = "이런 옵션들이 있고, 각각 이렇습니다" (현재형, 분석)

**실례**: `RESEARCH_긴급대행절차_선택지.md`는 4개 옵션을 중립적으로 제시하며 "본 보고서는 법률 초안이 아닌 선택지 제시입니다"라고 명시. 이는 REPORT의 `result: success/partial/fail` 필드와 양립할 수 없다.

**통합 불가 근거**: RESEARCH는 `result` 필드가 아닌 `order_ref` 필드를 사용한다. YAML 타입별 필수 필드가 다르므로 같은 유형으로 처리하면 ch4 7조 YAML 규격에서 모순이 발생한다.

### 2-3. 통합이 더 나은 경우는 없는가?

검토 결과: **없다.**

| 통합 시나리오 | 문제점 |
|-------------|--------|
| ORDER → TASK로 통합 | ORDER의 에이전트 필드 미보유 특성 소멸. 복수 에이전트 배분 문서를 표현 불가 |
| RESEARCH → REPORT로 통합 | `result: success/fail` 필드가 리서치에 적합하지 않음. 리서치는 "결과"가 아니라 "옵션" |
| ORDER+TASK 공동 패턴 | 에이전트 필드를 optional로 하면 자동 분류 정확도 저하 |
| RESEARCH+REPORT 공동 패턴 | YAML 필수 필드가 달라 타입별 검증 규칙 복잡화 |

## 5. 부대 고려사항

### 5-1. ORDER YAML frontmatter 미보유 문제

ORDER 6건은 YAML frontmatter 없이 마크다운 헤더로 메타데이터를 기재하고 있다:
```markdown
**발행**: 2026-02-23 18:21 KST
**발행자**: 쌍아 ← 철창이 협조공문
**수신**: 막내 (조사 담당)
**긴급도**: 높음
```

이관 시 YAML frontmatter를 추가하여 규격에 맞추되, 기존 마크다운 헤더는 **삭제하지 않는다** (가독성 유지). YAML은 기계 파싱용, 마크다운 헤더는 인간 가독용으로 공존.

### 5-2. RESEARCH 날짜 누락 패턴

현재 RESEARCH 3건의 파일명에 YYYYMMDD가 없다. 이는 ORDER에서 산출물 경로를 지정할 때 날짜 없이 지정했기 때문이다. 향후 ORDER에서 RESEARCH 산출물 경로 지정 시 `RESEARCH_YYYYMMDD_` 패턴을 준수하도록 ORDER 템플릿에 명시 필요.

### 5-3. `통로_연구_철창이.md` 특수 처리

이 파일은 `ORDER_` 지시서가 아닌 **막내2의 연구 산출물**이다. orders/ 폴더에 배치된 것 자체가 오류. RESEARCH_ 유형으로 재분류하여 `ops/agenda/`로 이관하는 것이 적절하다.

### 5-4. 막내A 전수조사와의 정합

막내A 보고서(REPORT_20260223_막내A_ch4_3조_파일유형_전수조사.md)에서 추가 미등록 유형은 발견되지 않았다. ORDER_(6건)과 RESEARCH_(3건)이 미등록 유형의 전부이며, 본 개정안은 이 2종만 다룬다.
