**일시:** 2026-02-25

**목적:** 클로드 데스크탑 앱의 구조적 이해 → 몽크스튜디오스 시스템 설계에의 적용

## 1. 코웍(Cowork)의 로컬 폴더 접근 원리

### 논의 내용
코웍은 사용자 컴퓨터 위의 경량 리눅스 VM(Ubuntu 22)에서 실행된다. VM은 보안 샌드박스 역할을 하며, 사용자 파일에 대한 통제된 접근을 허용한다.

### 접근 방식
- 코웍은 자동으로 파일시스템을 탐색하지 않음
- `request_cowork_directory` 도구를 통해 디렉토리 피커 다이얼로그를 표시
- 사용자가 명시적으로 폴더를 선택해야 접근 권한 받음
- 선택된 폴더는 VM 내부의 `/sessions/.../mnt/outputs` 경로에 마운트

### 핵심 공식
**샌드박스 + 사용자 승인 + 물리 폴더 마운트 = 코웍의 로컬 접근 근거**

### 마운트 구조
- `/sessions/.../mnt/outputs/`는 코웍 VM의 마운트 포인트
- 사용자가 로컬 폴더를 선택하면 이 마운트 포인트에 연결
- 코웍이 여기에 쓰는 파일 = 사용자 로컬 폴더에 직접 쓰는 것과 동일
- 폴더 미선택 시 코웍 자체의 작업 공간으로 동작

### 프로젝트 영향권
- 프로젝트 폴더를 마운트하면 코웍이 프로젝트 파일을 읽고 쓸 수 있게 됨
- `.claude/CLAUDE.md`가 있다면 코웍도 해당 프로젝트 헌법의 적용을 받음
- 단, CLI 클로드 코드 대비 제한적 권한 (샌드박스 내, 민감 작업 승인 필요, git 직접 이용 불가, 삭제 금지)

## 2. 챗 / 코웍 / 코드 — 세 모드의 구조적 차이

### 데스크탑 앱 내 세 탭의 본질적 차이: 실행 환경의 유무

| 모드 | 실행 환경 | 파일시스템 | 코드 실행 | 권한 수준 |
|------|-----------|-----------|-----------|-----------|
| **챗(Chat)** | 없음 | 업로드 파일 읽기만 가능 | 불가 | 최소 |
| **코웍(Cowork)** | VM 샌드박스 | 마운트 통한 접근 (승인 필요) | 가능 (샌드박스 내) | 중간 |
| **코드(Code)** | 로컬 머신 직접 | 터미널과 동일한 권한 | 완전 가능 | 최대 |

### 권한 범위
**Chat < Cowork < Code**

### 비유
- 챗: "말만 할 줄 아는 조수"
- 코웍: "말도 하고 컴퓨터 앞에 앉아서 직접 작업도 해주는 조수 (단, 가드레일 존재)"
- 코드: "개발자가 직접 제어하는 전진 허용 제약 최소화된 실행 환경"

## 3. 데스크탑 코드 탭 = CLI 클로드 코드 (동일 엔진)

### 핵심 사실
데스크탑 Code 탭은 "코드 아티팩트 생성기"가 아니라, CLI 클로드 코드와 **동일한 엔진**(same underlying engine)에 GUI를 씌운 것이다.

> 공식 문서: "Desktop runs the same underlying engine with a graphical interface."

### 공유 항목
- 설정 파일: CLAUDE.md, MCP 서버, 훅, 스킬
- CLI → 데스크탑 세션 이관 가능 (`/desktop` 명령)
- `~/.claude.json`, `~/.claude/settings.json` 공유

### GUI 추가 기능
- 비주얼 diff 뷰 (사이드 바이 사이드 비교)
- 앱 프리뷰 (내장 브라우저)
- Git worktree 기반 병렬 세션 관리
- PR 모니터링 및 자동 수정/머지

### CLI 전용 기능
- `--print` 스크립트/자동화 플래그
- `dontAsk` 퍼미션 모드
- Bedrock/Vertex 엔드포인트 프로바이더 연결
- 에이전트 툴 (멀티 에이전트 오케스트레이션)

## 4. 세 모드의 세션 독립성

### 원칙
챗, 코웍, 코드는 같은 앱 안의 탭으로 존재하지만 **컨텍스트를 공유하지 않는다.**

- 챗에서 나눈 대화를 코웍이 알 수 없음
- 코웍에서 작업한 내용을 코드 탭이 이어받지 못함
- 각각 완전히 별도의 세션

### 유일한 공유 지점
설정 파일 수준만 공유 (CLAUDE.md, MCP 서버 설정 등). 이는 대화 컨텍스트가 아니라 환경 설정.

## 5. CLAUDE.md 파일의 계층 구조와 영향력 사거리

### 핵심 인사이트
> **이름이 다 CLAUDE.md라 사거리가 없어 보이는 것일 뿐, 각 영향력은 전혀 다르게 작동한다. 파일 내용이 아니라 파일이 놓인 자리가 그 규칙의 사정거리를 정한다.**

### 계층 구조

| 위치 | 범위 | 공유 여부 | 역할 |
|------|------|-----------|------|
| `~/.claude/CLAUDE.md` | 글로벌 (모든 프로젝트) | 디바이스 귀속 | 개인 글로벌 규칙 |
| 프로젝트 루트 `CLAUDE.md` | 해당 프로젝트 전체 | git 추적 → 팀 공유 | 프로젝트 헌법 |
| 프로젝트 `CLAUDE.local.md` | 해당 프로젝트 (개인) | .gitignore → 디바이스 귀속 | 개인 프로젝트 설정 |
| 하위 폴더 `CLAUDE.md` | 해당 폴더 범위 | git 추적 → 팀 공유 | 영역별 세부 규칙 |

### 적용 원리
- 글로벌 설정이 깔리고 그 위에 프로젝트 설정이 덮어씀
- **충돌 시 더 가까운(구체적인) 쪽이 우선**
- 레이어: 글로벌 → 프로젝트 → 로컬
- 유닉스 설정 오버라이드 패턴(`.gitconfig`, `.npmrc`, `.eslintrc`)을 AI 에이전트 컨텍스트에 적용한 것

### 문법 통일, 위치로 권한 결정
같은 이름(`CLAUDE.md`)을 쓴 것은 의도적. 작성 방식은 통일하되, **위치가 곧 권한 범위를 결정**하는 설계.

## 6. 공유/귀속의 설계 원리

### 경계선
**git이 가져가면 공유, git이 무시하면 디바이스 귀속.**

### 공유되는 것 (git 따라감)
- 프로젝트 `CLAUDE.md` → 팀 규칙, 프로젝트 헌법
- 하위 폴더 `CLAUDE.md` → 영역별 규칙
- 프로젝트 내 모든 문서, 리드미

### 귀속되는 것 (디바이스 잔류)
- `~/.claude/CLAUDE.md` → 개인 글로벌 규칙
- `CLAUDE.local.md` → 개인 프로젝트 설정
- 메모리 파일 → 해당 디바이스의 학습 기록

### 루트 클로드 파일의 고유 귀속성
`~/.claude/CLAUDE.md`에 공통 규칙을 넣으면 해당 머신(디바이스)에 귀속되는 규정이 된다. CLI, 데스크탑 코드 탭, 코웍 모두에 적용. 단, Anthropic 서버 동기화가 아닌 **머신 로컬** 저장이므로 다른 디바이스에서는 별도 설정 필요.

### Anthropic의 의도적 설계
프로젝트 바깥의 클로드 파일과 메모리 파일이 git 클론 되지 않는 것은 의도적. 개인의 작업 습관과 선호는 프로젝트 규칙이 아닌 디바이스에 귀속되어야 하기 때문.

### 프로젝트 내부의 동일 원리
프로젝트 안에서도 CLAUDE.md는 git에 따라 공유되고, 메모리 파일은 디바이스에 귀속. 같은 원리가 재귀적으로 반복됨.

## 7. 리모트 세션 (Anthropic 클라우드)

### 개요
데스크탑 Code 탭에서 **Remote** 환경을 선택하면 Anthropic 서버 인프라에서 실행.

### 특성
- **앱을 꺼도 작업 계속됨** (서버에서 독립 실행)
- 모니터링: 데스크탑 앱, claude.ai/code, iOS 앱
- 진행 중 방향 전환 개입 가능
- 멀티 레포 동시 추가 지원
- 별도 컴퓨트 요금 없음 (구독 플랜 내 소모)
- 커스텀 환경 설정 가능 (네트워크 접근 수준, 환경변수)

### 권한 구조 (로컬과 다름)
- 이미 샌드박스된 환경 → Ask permissions 없음 (파일 수정 자동 수락)
- Bypass permissions도 없음 (격리 환경이라 불필요)
- Plan 모드에 Auto accept edits만 지원

## 8. 몽크스튜디오스 조직 구조와의 대응

### 구조적 유사성

| 몽크스튜디오스 | 클로드 데스크탑 | 역할 |
|-------------|---------------|------|
| 작가님 | 설계자/규칙 정의자 | 헌법 작성, 최종 판단 |
| 철창 (AI) | 챗/코웍 | 대화, 조언, 정보 정리, 실무 보조 |
| 쌍아 파트 | 코웍 수준 | 실무 실행력, 가드레일 내 이용 |
| 막내 파트 | 코드 수준 | 직접 실행, 코딩, 배치 |

### 공통 원리
- 하나의 조직/앱 안에서 각 파트가 독립적으로 움직임
- 프로젝트 헌법이라는 공유 규칙 아래 묶임
- 역할 분리, 권한 계층, 공유 규칙 → 조직이든 소프트웨어든 동일하게 작동

## 9. 라우터 클로드 구상: 작업 오케스트레이션 레이어

### 현재 문제
- 파일스케일, 슬랙 데몬, 깃, 구글 드라이브, 텔레그램 등 각각 통신 역할 수행
- 각자의 프로토콜과 정책이 달라 맥락 흐름이 점점 분해됨
- 깃은 깃의 정책을 따라 경직, 구글 드라이브/텔레그램도 각자의 제약 존재

### 구상
리모트 클로드를 **단순 장기간 작업용이 아닌, 세션 간 맥락을 설계하는 허브**로 활용.

### 작동 시나리오
1. 작가님 → 철창(코웍) 작업 세션 → 마크다운 정리
2. 리모트 클로드에 맥락 전달
3. 리모트 클로드가 항시 깨어 있는 상태로 맥락을 보존
4. 쌍아·막내 파트에 필요한 형태로 가공·전달
5. 각 파트는 자기 디바이스에서 자기 세션으로 작업

### 리모트 클로드의 역할
- **조직의 맥락 라우터**
- "세션은 로컬 귀속" 원칙을 깨지 않으면서 조직 차원의 맥락 공유 실현
- 기존 도구들을 버리지 않고, 그 위에 **자연어 오케스트레이션 레이어**를 치는 구조
- 도구들의 경직된 정책을 클로드의 맥락 이해가 완충

## 10. 최종 설계: 직·병렬 위계 구조

### 전체 위계

```
[라우터 클로드 - 리모트 상주]
  └─ CLAUDE.md: 조직 전체의 라우팅 규칙 (연결 규칙, 통신 규칙)
      │
      ├─ [프로젝트 A 클로드]
      │    └─ CLAUDE.md: 프로젝트 헌법 (경로 참조만 적시)
      │         ├─ /docs/rules/ → 세부 규정 (깃 관리)
      │         ├─ /docs/api-policy.md → API 정책 (깃 관리)
      │         ├─ 각 폴더 README → 영역별 규칙 (깃 관리)
      │         └─ 디바이스 메모리 파일 → 개인 맥락 (로컬 귀속)
      │
      ├─ [프로젝트 B 클로드]
      │    └─ (동일 구조)
      │
      └─ [프로젝트 N 클로드]
           └─ (동일 구조)
```

### CLAUDE.md의 역할 재정의
- **규칙 자체가 아니라 규칙의 라우팅 테이블**
- 어디에 뭐가 있는지, 뭘 따라야 하는지의 경로만 적시
- 간선의 경로만을 적시, 세부 규정은 깃이 관리하는 각 단위의 문서로 정리
- 헌법에 조문 전체를 넣지 않고 "제3조는 이 법률에 따른다"고 경로만 적시하는 구조

### 위계 구조의 세 축
- **직렬:** 라우터 → 프로젝트 → 폴더로 내려오는 위계
- **병렬:** 프로젝트 간 독립 운영
- **횡단:** 디바이스 메모리가 각 레이어에 횡으로 부착

## 11. 실행 파이프라인: 지시-실행-검토-코칭 사이클

### 흐름

```
작가님 (의도·방향성)
  → 정교한 시스템 프롬프트 + 규칙
쌍아 (VSCode → 리모트, 지시·판단)
  → 지시서 플로우
막내들 (코딩·배치·실행)
  → 커밋·푸시
쌍아 + 작가님 (검토·판단)
  → 코칭
막내들 (수정·재실행)
  → 반복
```

### 핵심
- 작가님의 의도가 여러 단위를 거치지 않고도 정교한 시스템 프롬프트와 규칙, 방향성에 담겨 전달
- 막내들은 작업이 자동으로 실행되고 커밋·푸시를 거쳐 판단받음
- 보고서는 깃에 정렬

## 12. 에이전트 이그노스틱 설계

### 원칙
프로젝트 헌법이 CLAUDE.md와 문서 체계에 담겨 있으면, **어떤 에이전트가 들어와도 동일한 규칙 적용.**

- 클로드, 제미나이, 용아 등 모든 에이전트가 규칙 공유 가능
- 에이전트는 교체 가능한 실행자, **시스템은 규칙에 의해 유지**
- 새 에이전트 투입 시 온보딩 = 폴더 접근 ("이 폴더 읽어"로 됨)
- 프로젝트·팀의 규모 확대에도 일관된 법체계 안에서 운영

### 스케일링
프로젝트가 10개, 팀원이 20명, 에이전트가 5종류가 되어도 각자가 프로젝트 폴더에 진입하는 순간 헌법이 강제 로딩.

## 13. 통제 철학: 비아군 vs 적의 경계

### 핵심 명제
> **통제받지 않고 연결되지 않는 슈퍼에이전트는 내 비아군이 아니라 적이다.**

### Anthropic의 설계 철학과의 수렴
- 샌드박스, 사용자 승인, 권한 계층, 강제 로딩 규칙
- 에이전트를 강하게 만들되 반드시 통제 안에 둠
- 멀티에이전트를 받아들이면서도 CLAUDE.md 강제 로딩, 퍼미션 모드, 세션 격리를 고집

### 몽크스튜디오스의 동일한 결론
- 에이전트가 아무리 똑똑해도 헌법 없이 풀어놓으면 각자 제멋대로 → 유지비 비용 증가
- 규칙 체계가 먼저, 에이전트는 그 안에서 움직이는 실행자
- 자유를 주되 헌법 안에서

### 결론
비아군과 적의 차이는 능력이 아니라 **통제 구조의 유무**.

## 14. 헌법 개정 관련 사항

### 현재 상태
- 쌍아를 통해 오퍼스 6기에게 각 관점·단위에서 적합성 보고, 데이터 스키마 파일링 최적화 방식 제시 지시 완료
- 보고서 수합 후 헌법 개정안 도출 예정

### 개정 시 주의
- 하위 법률, 리드미, 스키마, 라우팅 규칙이 전부 헌법에 참조
- 한 줄 변경 시 연쇄적 영향 발생
- 오퍼스 6기의 각 관점별 적합성 보고 → 쌍아 종합 → 작가님 최종 판단
