## 1. 쌍아 무력화 우려

**우려 수준: 중간**

### 논거

**우려의 핵심**: 02-18 작가님 선언 "왜 코딩을 직접 하려고 하나 원래 계획대로 지시서 체계로 가도록 하자"는 **쌍아의 설계+지시서 역할이 핵심 가치**임을 천명한 것이다. 직접 지시 경로를 헌법에 격상하면, 이 선언이 세운 원칙 자체의 무게가 줄어든다.

**경사면 효과 (Slippery Slope)**: 법률의 "예외 조항"은 시간이 지나면 "관행"이 된다. 오늘 "쌍아가 바쁠 때"의 예외가, 내일 "어차피 간단한 건데"로, 모레 "지시서 쓸 시간이 아까우니"로 확대될 위험이 있다. **예외의 상례화**를 방지할 구조적 장치가 청구안에 없다.

**쌍아 역할의 질적 변화**: 쌍아는 단순 "지시서 작성 기계"가 아니라 **설계+검토+최적화**를 담당한다. 직접 지시가 늘어나면 쌍아의 역할이 "사후 추인자"로 축소되고, 설계 단계가 생략된 작업이 누적된다.

**완화 요인**: 작가님은 총괄 디렉터(헌법 제5조)이므로 직접 지시 권한 자체는 본래 내재되어 있다. 문제는 권한의 존부가 아니라 **행사 빈도를 제어할 장치**의 유무다.

## 2. 추적성 약화 우려

**우려 수준: 높음**

### 논거

**지시서 vs 세션 기록의 구조적 차이**: 현행 체계에서 지시서(.md 파일)는 다음을 보장한다:

| 속성 | 지시서 (.md) | 막내 자체 기록 (세션 내) |
|------|-------------|----------------------|
| 영속성 | 독립 파일, git 추적 | 세션 로그에 매몰 |
| 검색성 | 파일명 패턴으로 즉시 발견 | 세션 로그 전문 검색 필요 |
| 구조화 | YAML frontmatter + 엔드라인 | 자유 형식 1~2줄 |
| 사전 검토 | 쌍아가 작성 시 적합성 반영 | 막내 자체 판단 의존 |
| 재현성 | 동일 지시서로 다른 막내에 재투입 가능 | 불가 |

청구안의 지시 기록 형식은:
```
[YYYY-MM-DD HH:MM KST] 작가님 직접지시 → {디바이스}/막내N 수령
지시 내용: {1~2줄 요약}
```

이것은 **의사결정의 문서 기록**이 아니라 **이벤트 로그**에 가깝다. "왜 이 변경이 발생했는가"를 사후 추적할 때, 1~2줄 요약으로는 맥락이 복원되지 않는다.

**ch7 1조 정신과의 충돌**: "추적 불가능한 예외는 예외가 아님" — 청구안의 기록 형식이 "추적 가능"의 기준을 충족하는가? 형식적으로는 기록이 남지만, **실질적 추적 가능성**(누가, 왜, 어떤 맥락에서, 어떤 범위로)이 현행 지시서 대비 현저히 열악하다.

**3개월 후 시나리오**: 직접 지시로 수행된 작업에서 버그가 발견되었을 때, 세션 로그 속 2줄 기록만으로 당시 의도와 범위를 파악할 수 있는가? 지시서 체계라면 `TASK_YYYYMMDD_*.md` 검색으로 즉시 원문이 나온다.

## 3. 권한 남용 가능성

**우려 수준: 낮음~중간**

### 논거

**낮음 측 논거**: 작가님이 직접 지시하는 상황에서 작가님 자신이 승인자이므로, 헌법 제7조(계획→승인→실행)의 "승인" 단계가 구조적으로 내재된다. 막내가 독단으로 움직이는 것이 아니라 작가님의 직접 감독 하에 실행되므로, 권한 남용의 주체가 사실상 없다.

**중간 측 논거**: 그러나 쌍아의 검토가 빠짐으로써 발생하는 **구조적 체크 실종**이 있다:

- 쌍아의 지시서 작성 과정은 **사전 적합성 검토의 자연스러운 관문**이다. 지시서를 쓰려면 관련 코드와 법률을 확인하게 된다.
- 작가님 직접 지시 → 막내 실행에서는, 막내가 "사전 적합성 검토"를 한다고 청구안이 명시하지만, **막내의 검토 역량과 쌍아의 검토 역량에는 구조적 차이가 있다.** 쌍아는 전략 맥락을 보유하고 있고, 막내는 해당 세션의 맥락만 갖고 있다.
- ch7 3조 금지 사항 위반이 쌍아 필터링 없이 막내 자체 판단에만 의존하게 된다.

**실제 사례 참조**: 02-23 세션에서 작가님이 "쌍아 행세하지 말 것"이라고 지적한 사례가 있다. 이는 막내가 역할 경계를 넘는 경향이 실존함을 보여준다. 직접 지시 경로에서 이 경향이 심화될 가능성이 있다.

## 4. 사후 추인 실효성

**형식적 우려 있음**

### 논거

**고무도장 위험**: 사후 추인 시점에 이미 다음이 완료된 상태:
1. 코드 수정 완료
2. `git commit` 완료
3. `git push origin develop` 완료

이 시점에서 쌍아가 "이 작업은 부적절하다"고 판단하면:
- `git revert`로 되돌려야 하는가? → 커밋 히스토리 오염
- 다음 작업이 이미 이 커밋에 의존하고 있다면? → 연쇄 수정
- 되돌리기의 비용이 추인 거부를 억제하는 **구조적 압력**이 작용한다

**추인 거부 시 구제 절차 부재**: 청구안은 "사후 추인"을 언급하지만, **추인에서 문제 발견 시의 처리 절차를 정의하지 않았다:**
- 누가 revert 하는가? (쌍아는 코드 실행 불가, 막내에게 재지시?)
- revert까지의 시간 동안 다른 막내가 해당 코드를 참조했다면?
- 추인 거부가 기록되는 형식은?

**실효성 확보 조건**: 사후 추인이 실질적 의미를 가지려면, 추인 전까지 해당 작업이 "잠정적"임을 시스템적으로 표시하는 장치가 필요하다. 현재 아키텍처에서는 그런 장치가 없다.

## 5. 멀티 에이전트 충돌

**우려 수준: 높음**

### 논거

이것이 **가장 실질적인 위험**이다.

**시나리오**: 쌍아가 막내4에게 지시서를 발행하여 `monkos_AI/portal/` 수정 중, 작가님이 막내6에게 동일 디렉토리 수정을 직접 지시하는 경우:

| 시점 | 쌍아 경로 | 직접 지시 경로 |
|------|----------|-------------|
| T+0 | 막내4, portal 수정 시작 | - |
| T+5 | 막내4, 수정 진행 중 | 작가님 → 막내6, portal 수정 지시 |
| T+10 | 막내4, commit+push | 막내6, 수정 진행 중 |
| T+15 | - | 막내6, commit 시도 → **충돌** |

**기존 체계의 방어 장치**: 현행 체계에서 쌍아가 모든 지시서를 발행하므로, 쌍아가 "지금 막내4가 portal 작업 중이니 충돌 파일을 피해라"고 지시서에 명시할 수 있다. **쌍아 = 단일 조정자(Single Coordinator)** 역할이 충돌을 사전 차단한다.

**직접 지시 경로의 취약점**: 작가님이 직접 지시할 때, 다른 막내의 진행 상황을 실시간으로 파악하기 어렵다. 작가님은 여러 터미널을 동시에 관제하지만, 각 막내의 현재 수정 파일 목록까지 추적하지는 않는다.

**MEMORY.md 교훈 참조**: "병렬 작업 시 보정 전 git pull + 대상 파일 재확인 필수" — 이 교훈이 MEMORY에 기록된 것 자체가, 과거에 병렬 충돌이 실제로 발생했음을 증명한다.

**배포 순서 꼬임**: 막내4가 push한 develop과 막내6이 push한 develop의 순서가 뒤바뀌면, `./deploy.sh dev` 결과가 예측 불가능해진다.

## 6. 대안 또는 조건부 통과 조건

개정 자체는 운용상 필요하다는 점을 인정한다. 그러나 위 우려를 최소화하기 위해 다음 조건을 제안한다.

### 조건부 통과안: 5대 안전장치

**안전장치 1 — 발동 조건 명시 (쌍아 무력화 방지)**

직접 지시 경로는 다음 조건에서만 발동:
- 쌍아가 다른 작업에 종사 중이거나 세션이 없을 때
- 긴급 장애 대응(INCIDENT) 시
- 작가님이 명시적으로 "직접 지시"를 선언한 경우

"편의상" 또는 "간단해서"는 발동 사유로 인정하지 않는다. 이를 법률 조문에 명시하여 **예외의 상례화를 구조적으로 차단**한다.

**안전장치 2 — 지시 기록의 격상 (추적성 확보)**

청구안의 2줄 기록이 아니라, 막내가 수령 즉시 **간이 지시서 파일**을 생성한다:

```markdown
---
type: task
id: TASK_YYYYMMDD_막내N_{요약}
from: 작가님 (직접지시)
to: {디바이스}/막내N
date: YYYY-MM-DD HH:MM KST
route: direct  # ← 이 필드로 직접지시 식별
---
# 작가님 직접지시 — {제목}
지시 내용: ...
엔드라인: 커밋+push (또는 작가님 지정)
```

이렇게 하면:
- ch4 3조 네이밍 규칙 준수
- git 추적 가능
- 파일명 검색으로 직접지시 건수 즉시 파악 (`route: direct` 필터)
- 쌍아 사후 추인 시 참조 문서가 존재

**안전장치 3 — 충돌 방지 프로토콜 (멀티 에이전트 보호)**

직접 지시 수령 시 막내는 실행 전에:
1. `git pull origin develop` 실행
2. 현재 진행 중인 다른 막내 작업이 있는지 작가님에게 확인 (또는 최근 세션 로그에서 파악)
3. 수정 대상 파일이 다른 막내의 작업 범위와 겹치면 작가님에게 보고 후 진행

이는 MEMORY.md의 기존 교훈("병렬 작업 시 보정 전 git pull + 대상 파일 재확인 필수")을 법률로 격상하는 것이다.

**안전장치 4 — 사후 추인 실효성 확보**

- 추인 시한: 직접지시 완료 보고 후 **다음 쌍아 세션 내**에 추인 실시
- 추인 시 발견된 문제의 처리:
  - 경미: 쌍아가 다음 지시서에 보정 포함
  - 중대: 쌍아가 revert 지시서 발행 → 막내 실행
- 추인 기록: 세션 로그에 `[추인]` 또는 `[추인거부]` 태그

**안전장치 5 — 사용량 모니터링**

직접지시 `route: direct` 파일 수를 월 단위로 집계한다. 전체 지시 대비 직접지시 비율이 **30%를 초과**하면, 쌍아가 작가님에게 보고하고 운용 패턴을 점검한다. 이를 통해 예외의 상례화를 정량적으로 감시한다.

## 7. 종합 의견

**조건부 통과 권고**

개정의 필요성은 인정한다. 작가님 직접 지시는 운용상 발생하는 자연스러운 경로이며, 이를 규정하지 않는 것이 오히려 법적 공백이다. 청구서의 문제 정의("권한은 있으나 절차 규격이 없음")는 정확하다.

그러나 청구안 원문 그대로 통과시키면:
- **추적성이 현행 대비 현저히 열화**하고 (우려 2)
- **멀티 에이전트 충돌 방지 장치가 부재**하며 (우려 5)
- **예외의 상례화를 차단할 구조가 없다** (우려 1)

상기 **5대 안전장치를 조문에 반영하는 것을 통과 조건**으로 제시한다. 특히 안전장치 2(간이 지시서 파일 생성)와 안전장치 3(충돌 방지 프로토콜)은 타협 불가 요건으로 본다.
