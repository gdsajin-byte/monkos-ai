## 1. 자동 로드 파일 구조

Claude Code는 세션 시작 시 아래 파일을 시스템 프롬프트에 자동 주입한다. Anthropic 하드코딩이며 끄거나 변경할 수 없다.

| 파일 | 위치 | 성격 | 제한 |
|------|------|------|------|
| **CLAUDE.md** | 프로젝트 루트 (Git) | 프로젝트 정책. 팀 공유. 공식. | 명시적 줄 수 제한 없음 |
| **MEMORY.md** | `~/.claude/projects/{프로젝트}/memory/` (로컬, Git 밖) | 에이전트 자율 메모장. 개인. 비공식. | **200줄 하드캡** (초과 시 절삭) |

### 계층 구조 (CLAUDE.md)

```
~/.claude/CLAUDE.md           ← 유저 전역 (모든 프로젝트 공통)
~/CLAUDE.md                   ← 홈 디렉토리
/project/CLAUDE.md            ← 프로젝트 루트 ★
/project/subdir/CLAUDE.md     ← 서브디렉토리 (해당 폴더 작업 시)
```

위에서 아래로 전부 읽고 병합한다. 팀 플레이 시 개인별/파트별 분리 가능.

### MEMORY.md

- 프로젝트당 1개 고정. 계층 분리 불가.
- 200줄 초과 시 시스템이 자동 경고 + 200줄 이후 절삭.
- 에이전트가 자율적으로 Write/Edit하는 구조.

## 2. CLAUDE.md와 MEMORY.md의 본질적 차이

기술적으로는 **동일한 것** — "세션 시작 시 시스템 프롬프트에 주입되는 텍스트 파일".

| 구분 | CLAUDE.md | MEMORY.md |
|------|-----------|-----------|
| 저장소 | Git (공유) | 로컬 (개인) |
| 작성자 | 작가님 (+쌍아 합의) | 에이전트 자율 |
| 변경 권한 | 헌법/법률 개정 절차 | 에이전트 자율 갱신 |
| 성격 | **선언된 법** | **학습된 경험** |

Git을 제거하면 경계가 사라진다. 권위의 위계는 **MONK 거버넌스가 부여한 것**이지 시스템 강제가 아니다.

## 3. 토큰 경제학

### 바이트 vs 토큰

| | 바이트 (Byte) | 토큰 (Token) |
|---|---|---|
| 단위 | 저장/전송 최소 단위 | LLM 처리 최소 단위 |
| 정의 | 고정 (8bit = 1byte) | 모델마다 다름 (토크나이저 의존) |
| 한글 | 1글자 = 3byte (UTF-8) | 1글자 ≈ 1~2토큰 |
| 영어 | 1글자 = 1byte | 1단어 ≈ 1토큰 |

### 한글 토큰 패널티

한글은 영어 대비 **동일 의미에 2~3배 토큰 소비**. CLAUDE.md + MEMORY.md가 한국어이므로 영어 프로젝트 대비 시스템 프롬프트 고정 비용이 2~3배.

### 컨텍스트 윈도우

| 모델 | 컨텍스트 |
|------|---------|
| Opus 4.5 | 200K 토큰 |
| Opus 4.6 | 1M 토큰 |
| Sonnet 4.6 | 1M 토큰 |

한국어 실질 가용량은 영어 대비 ~50%. 1M이라도 체감은 영어 사용자의 ~500K 수준.

### 200줄 제한의 성격

줄 수 제한은 토큰 제한의 **근사치**. 한 줄이 2토큰일 수도, 30토큰일 수도 있다. Anthropic이 사용자 직관을 위해 택한 대략적 가드레일.

## 4. MEMORY.md 유입 규칙

### 핵심 기준

**"세션 시작 시, 파일을 열기 전에, 에이전트가 알아야 하는 OS만 남긴다."**

| 유형 | MEMORY.md에 | 이유 |
|------|------------|------|
| 행동 규칙 (OS) | **O** | 파일 열기 전에 알아야 함 |
| 도메인 지식 | **X** | 코드 파일에 있음. Read하면 됨 |
| 세션 결정사항 | **X** | 세션 로그/docs에 기록 |
| 헌법 중복 | **X** | CLAUDE.md에 이미 있음 |
| 인프라 레퍼런스 | **X** | 필요 시 외장 파일 Read |

### 설계 의도

MEMORY.md는 **에이전트의 자율 메모장**이다. 작가님의 지식을 에이전트 캐시에 넣는 것은 구조적 비효율 — 작가님 지식은 CLAUDE.md(법)와 코드(도메인)에 이미 존재한다.

> 근거: 작가님 2026-02-24 — "설계상 메모리는 너의 자율 메모장이라 내가 명시를 많이 남기는 자체가 구조적 비효율"

### 유입 통제 없이 정리만 하면

- 거버넌스 집중 세션: 하루 50~100줄 유입
- 200줄 중 100줄 비워야 2~3일 버팀
- OS만 남기면 ~35줄 → 165줄 여유 → 약 1주일치

```

```

| | MEMORY.md (자동) | 외장 파일 (수동 Read) |
|---|---|---|
| 로드 | 시스템 프롬프트 직접 주입 | 도구 호출 1회 소비 |
| 비용 | 컨텍스트에 상주 | 읽는 순간만 점유 |

항상 필요하지 않은 도메인 지식은 외장이 더 효율적 — 필요할 때만 읽으니까.

## 6. 구조적 인과 — 왜 이 거버넌스가 태어났는가

```
한글 토큰 비효율 → 컨텍스트 압박 → 구조화 욕구 → 법체계
→ 세션 분리 필요 → 멀티에이전트 → 통신 규약 → 거버넌스
```

영어 사용자는 컨텍스트가 넉넉하여 비구조적 운용이 가능하다. 한국어 사용자는 같은 윈도우에서 1/3밖에 못 담으므로 — 정리하지 않으면 세션이 죽는다. 법률, 압축, 역할 분리, 지시서 체계가 **생존 전략**이 된 것이다.

> 근거: 작가님 2026-02-24 — "구조적으로는 손실이 많으나 또다른 가능성을 낳게 되는 법"

제약이 사라져도 제약이 낳은 구조는 남는다. 토큰이 넉넉해져도 법체계가 불필요해지는 것이 아니라, 에이전트 수와 복잡도가 올라가면 더 필요해진다.

> 근거: 작가님 2026-02-24 — "수요가 진화를 낳는 것이니. 세션관리와 맥락유지에 대한 내 욕구가 강하다 보니 이렇게 가는것이고 멀티에이전트체제에 대한 이해도가 높은 이유도 그러한 제한이 있기 때문이다"

## 7. 멀티에이전트 분화의 필연성 — 아키텍처의 본질

### 세션 토큰 소비 분포

| 주체 | 비중 | 성격 |
|------|------|------|
| 도구 결과 (Read, Bash) | ~50% | 파일 내용 덤프 |
| 에이전트 출력 | ~40% | 코드, 설명, 분석 |
| 작가님 발화 | ~5~10% | 짧고 정확한 지시 |

세션을 죽이는 것은 작가님의 지시가 아니라 **에이전트의 코드 생성과 도구 호출**이다.

### 역할 분리 = 토큰 생존 전략

```
쌍아 세션: 설계 + 지시서 → 텍스트 위주 → 토큰 효율 높음
막내 세션: 코딩 + 실행 → 도구 호출 폭발 → 토큰 소모 큼
```

한 세션에서 설계와 코딩을 동시에 하면 — 설계 맥락이 코딩 덤프에 밀려 compaction으로 소멸한다. 분리하면 각 세션이 자기 역할의 컨텍스트를 보전한다.

**멀티에이전트 막내 분화 시스템은 필연적 귀결이다. 같은 토큰으로 작업의 효율을 극대화하는 최적의 방안이며, 이것이 MONK 아키텍처의 본질이다.**

> 근거: 작가님 2026-02-24 — "멀티 에이전트 막내 분화 시스템은 필연적 귀결이다. 같은 토큰으로 작업의 효율이 극대화할 최적의 방안인것이지. 핵심 인사이트이며 우리 아키텍쳐의 본질이다"

### Compaction이 보여주는 원칙

세션 컨텍스트가 한계에 도달하면 시스템은 자동 압축(compaction)한다:
- **보존**: 사실 (작가님 발화 원문, 파일 경로, 결정사항)
- **압축**: 해석 (에이전트 설명, 분석, 장문 답변)

이 원칙은 MEMORY.md 운용에도 동일하게 적용된다 — 사실과 규칙만 남기고, 해석은 빼라.

## 8. Claude Code 로컬 데이터 구조

`~/.claude/` — Claude Code의 전체 로컬 상태. 프로젝트 repo 밖에 위치.

```
~/.claude/
├── settings.json              ← 권한 설정 (도구 자동 허용 등)
├── history.jsonl              ← 전체 대화 이력
├── stats-cache.json           ← 사용 통계
├── backups/                   ← 설정 백업
├── cache/                     ← 캐시
├── debug/                     ← 디버그 로그
├── file-history/              ← 파일 수정 이력 (세션ID별)
├── ide/                       ← VSCode 연동 데이터
├── paste-cache/               ← 붙여넣기 캐시
├── plans/                     ← 플랜 모드 데이터
├── plugins/                   ← 플러그인
├── session-env/               ← 세션 환경 스냅샷
├── shell-snapshots/           ← 쉘 상태
├── tasks/                     ← 태스크 데이터
├── telemetry/                 ← 원격 측정
├── todos/                     ← 투두 리스트
└── projects/
    └── {프로젝트 경로 해시}/
        ├── memory/
        │   └── MEMORY.md       ← ★ 세션 시작 시 자동 로드 (200줄 캡)
        ├── sessions-index.json ← 세션 인덱스
        └── {세션UUID}/         ← 세션별 폴더
            ├── {UUID}.jsonl    ← 대화 전문 (전체 transcript)
            ├── subagents/      ← 서브에이전트 실행 데이터
            └── tool-results/   ← 도구 호출 결과 캐시
```

### MONK 체계와의 구조적 유사점

| Claude Code | MONK |
|-------------|------|
| `CLAUDE.md` (프로젝트 정책) | 헌법 + 법률 |
| `MEMORY.md` (에이전트 학습) | 규정 (에이전트 자율) |
| `{세션UUID}.jsonl` (대화 전문) | 세션 로그 (ch3) |
| `subagents/` (서브에이전트) | 막내 분화 체계 |
| `tool-results/` (도구 결과) | 보고서 (REPORT_) |
| `settings.json` (권한) | 헌법 제5조 (역할 체계) |

> MONK 거버넌스가 Claude Code의 내부 구조와 독립적으로 진화했으나, 결과적으로 유사한 패턴에 수렴했다. 문제의 구조가 같으면 해법도 수렴한다.
